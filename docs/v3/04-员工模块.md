# V3 员工模块

> 模块代码：`employee`  
> 文档版本：V3.1  
> 编写日期：2026-10-29  
> 状态：V3 员工模块评审稿；评审通过前不进入页面实现

本文是 V3 员工模块的唯一需求与设计依据。员工模块只维护员工档案、固定岗位、在职与离职记录和员工快照；工资标准、小组、排班、每日产出和生产事实均不属于本模块。

## 摘要

- 员工模块是一份员工花名册：编号、姓名、电话、备注、固定岗位和在职状态。
- 每名员工只有一个固定岗位；岗位同时决定他能排什么活，不再单独维护多选工种资格。
- 员工编号自动生成，格式 `E-000001`；创建后不可修改、不可复用，员工不硬删除。
- 员工姓名允许重复，电话可以留空且不要求唯一，以员工编号区分身份。
- 每次入职、离职、返聘和岗位调整都保留记录；返聘沿用原编号，不新建员工。
- 岗位是全局固定枚举，全局模块只能改显示名称；员工只保存岗位代码。
- 同岗位同单价；岗位时薪由全局模块按岗位维护，计件单价、计薪方式和调价历史由工资模块维护；员工模块不保存工资标准。
- 员工模块自己保存员工快照；排班、生产、工资只保存快照引用，按版本查询。
- 员工模块不管理小组、排班、每日产出、工资和考勤；离职或岗位调整不检查未来排班。
- 本期员工不登录；平台账号模型预留 `EMPLOYEE` 主体，员工模块不创建账号、不保存密码、不保存角色。
- 本模块没有业务计算，不依赖计算模块。

## 1. 模块说明

员工模块管理“谁可以来上班、固定做什么岗位，以及他什么时候在职”。

每名员工只有一个固定岗位，岗位既是排班依据，也是工资模块选择计薪规则的依据。排班模块只从在职且岗位匹配的员工中选择人员；生产计划、生产记录和工资记录保存员工快照引用，之后员工改姓名、离职或调整岗位，不会改变已经发生的历史。

员工模块回答“这个员工是谁、现在是否在职、固定什么岗位、历史什么时候入离职和调岗”；工资模块回答“这个岗位按计时还是计件、单价多少”；排班模块回答“哪天谁来、做什么”；每日产出模块回答“实际做了多少”。

## 2. 用户与使用场景

### 2.1 用户

| 用户 | 关心什么 | 在员工模块做什么 |
|---|---|---|
| 管理员 | 现在有哪些人能上班、各自固定做什么岗位 | 新建员工，维护电话和备注，调整岗位，办理离职和返聘 |
| 老板 | 员工人数、在职情况和岗位分布 | 查看员工列表、详情和历史 |
| 排班 | 某天有哪些在职且岗位匹配的员工 | 通过员工查询和岗位校验取得候选员工及员工快照引用 |
| 每日产出 | 产出登记对应哪个员工 | 保存员工快照引用，按版本解析员工姓名、编号和岗位 |
| 工资 | 员工在岗期间是什么岗位、按什么规则计薪 | 保存员工快照引用，通过岗位代码读取全局岗位时薪和工资模块的计薪规则 |
| 报表 | 员工维度和岗位维度汇总 | 通过员工公开查询或后续报表投影读取，不直接读员工表 |

### 2.2 现状与目标

管理员现在用 Excel 记录兼职员工和每日产出，员工姓名和岗位通常直接写在排班表或产出表里。

V3 把员工独立成一份可复用档案：

- 员工只录入一次，排班、产出和工资都引用同一个员工身份；
- 员工固定一个岗位，岗位决定能排什么活，也决定工资模块用哪条计薪规则；
- 员工离职再回来，沿用原编号和历史，不重复建档；
- 员工调岗或离职后，历史排班、产出和工资仍能还原当时的人和岗位；
- 工资单价不塞进员工档案，避免同一个岗位的单价在多个员工上重复维护。

## 3. 本期范围

### 3.1 本期提供

- 员工创建、编辑、查看；
- 员工编号自动生成；
- 员工姓名、电话、备注；
- 员工固定岗位；
- 员工在职、离职和返聘；
- 每次入职、离职和返聘记录；
- 每次岗位设置和岗位调整记录；
- 员工快照创建、复用和按版本查询；
- 按岗位和在职状态筛选员工，供排班选择；
- 员工岗位匹配校验；
- 员工列表搜索和分页。

### 3.2 本期不提供

- 一个员工多个岗位、多选工种资格和跨岗位支援；
- 小组、成员、组长、组内岗位和组内步骤；
- 小组效率因子、每日有效工作时间和活动占用；
- 排班、每日产出和生产计划；
- 时薪、计件单价、计薪方式、工资标准和调薪历史；
- 工资结算、考勤、请假和加班；
- 员工登录入口、员工账号管理和员工账号绑定操作（平台账号模型已预留 `EMPLOYEE` 主体）；
- 组织架构、部门、岗位职级；
- 员工级工资单价或个性化提成；
- 身份证号、住址、紧急联系人、银行卡、合同和附件；
- 员工头像和员工颜色字段；
- 员工删除、合并和批量导入导出；
- 未来生效的预约离职、预约返聘和预约调岗；
- 员工字段级变更历史表和历史页；
- 通用“基础资料模块”。

## 4. 业务概念

| 术语 | 定义 |
|---|---|
| 员工 | 一个可复用的生产执行者身份，以员工编号区分 |
| 岗位 | 员工固定承担的工作类别，例如制作、捏毛装袋、缝边剪袋、其他任务；由全局模块静态数据维护 |
| 在职状态 | 员工当前是否可被安排新工作，只有在职和离职两种 |
| 就业记录 | 一次入职、离职或返聘事实，按生效日期保留 |
| 岗位记录 | 一次岗位设置或岗位调整事实，按生效日期保留 |
| 员工快照 | 员工被排班、生产或工资引用时冻结的员工身份和岗位 |
| 内容版本 | 员工姓名、岗位或在职状态发生变化时递增的版本号 |
| 岗位校验 | 判断某员工在某一天是否可以承担某个岗位 |

员工、就业记录、岗位记录和员工快照的关系：

```text
员工 1 ── N 就业记录
员工 1 ── N 岗位记录
员工 1 ── N 员工快照
```

## 5. 字段定义

### 5.1 员工基本信息

| 字段 | 必填 | 类型/精度 | 规则 |
|---|---|---|---|
| 员工编号 | 系统生成 | `VARCHAR(32)` | 格式 `E-000001`；创建后不可修改、不可复用 |
| 员工姓名 | 是 | `VARCHAR(40)` | 去首尾空格；不允许只输入空格、换行或控制字符；允许重名 |
| 联系电话 | 否 | `VARCHAR(30)` | 可空；填写时允许数字、`+`、括号、空格和短横线；6 至 30 字符且至少 6 位数字；不要求唯一 |
| 员工备注 | 否 | `VARCHAR(500)` | 可空；用于兼职时间、联系习惯或内部提醒；不参与排班和工资计算 |

本期员工不登录。平台账号模型预留员工主体，员工档案不自动创建账号、不保存密码和角色；启用员工登录后由管理员在平台侧绑定账号。

### 5.2 岗位信息

| 字段 | 必填 | 类型/精度 | 规则 |
|---|---|---|---|
| 当前岗位 | 是 | `VARCHAR(64)` | 必须是全局固定岗位枚举之一；新建时必须选择 |
| 岗位名称 | 显示字段 | `VARCHAR(80)` | 当前页面显示全局模块中的当前名称；员工快照保存快照时的名称 |

全局固定岗位枚举：

| 岗位代码 | 默认显示名 | 用途 |
|---|---|---|
| `MAKING` | 制品（制作） | 制作工序岗位 |
| `BAGGING` | 捏毛（捏毛装袋） | 捏毛装袋工序岗位 |
| `SEAM_CUTTING` | 缝边（缝边剪袋） | 缝边剪袋工序岗位 |
| `OTHER` | 其他 | 打包、发货、清洁等非工序工作 |

岗位代码写死，不能新增、删除、停用或修改；全局模块只允许修改显示名称。每名员工同一时间只有一个当前岗位。员工模块不再单独保存多选工种资格；调岗见 R4。

当前岗位的生效日期取该员工最后一条岗位记录的生效日期，只用于详情展示，不在员工根表重复保存。

### 5.3 在职与就业信息

| 字段 | 必填 | 类型/精度 | 规则 |
|---|---|---|---|
| 在职状态 | 系统 | `EMPLOYED / LEFT` | 新建默认 `EMPLOYED`；只能通过离职和返聘改变 |
| 当前入职日期 | 是 | `DATE` | 首次入职日期；返聘后更新为最近一次入职日期；不得晚于当天 |
| 当前离职日期 | 否 | `DATE` | 在职时为空；离职后为最近一次离职生效日期；不得早于当前入职日期 |
| 离职原因 | 否 | `VARCHAR(300)` | 离职时必填；只写入就业记录，不放在员工根表 |

员工根表只保留当前在职状态和最近一次入离职日期；每次入职、离职、返聘过程保存在就业记录中。

### 5.4 岗位记录字段

| 字段 | 说明 |
|---|---|
| 记录类型 | `SET` 新建时设置岗位；`CHANGE` 员工调岗 |
| 调整前岗位 | `SET` 时为空；`CHANGE` 时为调整前岗位代码 |
| 调整后岗位 | 本次设置或调整后的岗位代码 |
| 生效日期 | 岗位设置或调整的生效日期；不得晚于当天 |
| 调整原因 | 可空；用于说明调岗原因 |
| 操作人 | 本次操作人 |

岗位记录只追加，不更新、不删除。员工当前岗位以员工根表为准，历史岗位通过岗位记录追溯。

### 5.5 系统字段

| 字段 | 说明 |
|---|---|
| `employee_business_id` | 稳定业务标识，不对外显示 |
| `content_version` | 员工姓名、当前岗位或在职状态发生变化时递增；用于员工快照版本 |
| `row_version` | 并发编辑控制；任何员工根更新都递增 |
| `created_at/created_by` | 创建时间和操作人 |
| `updated_at/updated_by` | 最近修改时间和操作人 |

电话和备注修改只递增 `row_version`，不递增 `content_version`，因为电话和备注不进入员工快照。姓名、岗位和在职状态变化会递增 `content_version`。

### 5.6 员工快照字段

| 字段 | 说明 |
|---|---|
| 员工快照引用 | 其他模块保存的稳定引用 |
| 员工编号 | 快照时的员工编号 |
| 员工姓名 | 快照时的员工姓名 |
| 岗位代码 | 快照时的岗位代码 |
| 岗位名称 | 快照时的岗位名称 |
| 在职状态 | 快照时的 `EMPLOYED / LEFT` |
| 当前入职日期 | 快照时的最近入职日期 |
| 当前离职日期 | 快照时的最近离职日期，可空 |
| 内容版本 | 快照对应的员工内容版本 |
| 内容指纹 | 校验快照载荷一致性 |

员工快照不保存电话、备注和工资单价，避免把不必要的联系方式或工资数据复制到排班、生产和工资记录中。

## 6. 业务规则

### R1 员工编号

- 由平台编号能力生成，格式 `E-000001`；
- 员工编号全局唯一，创建后不可修改、不可复用；
- 事务回滚可能产生空号，但不会重复或复用编号。

### R2 创建员工

- 员工姓名和岗位必填；电话和备注可空；
- 岗位必须是全局固定枚举 `MAKING / BAGGING / SEAM_CUTTING / OTHER` 之一；
- 当前入职日期默认当天，不得晚于当天；
- 新建员工状态为 `EMPLOYED`，`content_version = 1`；
- 创建时写入一条入职记录，生效日期等于当前入职日期；
- 创建时写入一条岗位记录，记录类型 `SET`，调整前岗位为空；
- 任一步失败整体回滚，不保存员工。

### R3 编辑员工

- 只能修改姓名、电话和备注；
- 员工编号、当前岗位、在职状态、当前入职日期和当前离职日期不能通过编辑表单直接覆盖；
- 修改携带 `rowVersion`，冲突返回 `EMPLOYEE_VERSION_CONFLICT`；
- 姓名允许重复，电话允许重复；
- 姓名修改递增 `content_version`；电话和备注修改不递增 `content_version`；
- 每次修改写平台审计。

### R4 调整岗位

- 只有 `EMPLOYED` 员工可以调整岗位；
- 调整后岗位必须与当前岗位不同，且必须是全局固定岗位枚举之一；
- 调整生效日期不得晚于当天，且不得早于当前入职日期；
- `CHANGE` 生效日期必须晚于最后一条岗位记录的生效日期，避免岗位期间倒挂；
- 调整原因可空；
- 调整后员工根表的当前岗位更新为新岗位，`content_version` 和 `row_version` 递增；
- 追加一条岗位记录，记录类型 `CHANGE`，保存调整前后岗位；
- 调整岗位不修改历史就业记录和岗位记录；
- 调整岗位不检查未来排班或生产计划；已有计划和记录继续使用员工快照，由排班模块负责提示或调整；
- 调整岗位从生效日期起影响后续排班和工资模块选择计薪规则。

### R5 离职

- 只有 `EMPLOYED` 员工可以办理离职；
- 离职生效日期不得晚于当天，且不得早于当前入职日期；
- 离职原因必填；
- 离职后状态变为 `LEFT`，当前离职日期写入员工根表，并追加一条离职记录；
- 离职递增 `content_version`；
- 离职不删除员工，不改变历史就业记录、岗位记录和员工快照；
- 离职不检查未来排班或生产计划；已有计划和记录继续使用员工快照，由排班模块负责提示或调整。

### R6 返聘

- 只有 `LEFT` 员工可以办理返聘；
- 返聘生效日期不得晚于当天，且必须晚于最近一次离职日期；
- 返聘后状态变为 `EMPLOYED`，当前入职日期更新为返聘日期，当前离职日期清空，并追加一条返聘记录；
- 返聘沿用原员工编号和原岗位，不新建员工；
- 返聘递增 `content_version`；
- 返聘后如需换岗位，另做岗位调整并写入岗位记录。

### R7 岗位固定枚举

- 岗位是全局固定枚举，代码固定为 `MAKING / BAGGING / SEAM_CUTTING / OTHER`；
- 岗位代码不能新增、删除、停用或修改；
- 全局模块只允许修改岗位显示名称；
- 员工模块只保存岗位代码，不建岗位配置表；
- 员工当前页面显示岗位当前名称；员工快照保存取得快照时的岗位名称，之后岗位改名不改变历史快照；
- 岗位改名不递增员工内容版本，也不改变快照指纹；已有快照继续复用；
- 已离职员工保留原岗位代码，返聘后继续使用；
- 员工模块不判断岗位是否可排班，排班模块按岗位代码判断。

### R8 岗位与排班

员工可以被安排新工作的条件是：

- 员工当前为 `EMPLOYED`；
- 员工当前岗位与排班需要的岗位一致。

岗位校验结果只回答员工状态和岗位是否匹配；岗位是固定枚举，不存在停用判断。员工模块不保存排班、日期负载、生产计划和每日产出。

### R9 与小组和排班解耦

- 员工模块不保存小组、成员关系、组长和小组效率；
- 员工模块不建立活动占用、预留或活动引用守卫；
- 离职、调岗和修改资料不会被未来排班阻断；
- 排班模块需要员工时，调用员工查询和快照接口，不直接读员工表。

### R10 员工快照

- 排班、生产、工资等模块引用员工时，由员工模块创建或复用员工快照；
- 快照按员工内容版本唯一；
- 同一员工、同一内容版本只保存一条快照；
- 同一版本并发创建时先按唯一键复用已有快照；只有员工编号、姓名、岗位代码、在职状态、入职日期或离职日期不同才返回 `EMPLOYEE_SNAPSHOT_CONFLICT`；
- 岗位显示名称不参与快照指纹；全局改岗位显示名不递增员工内容版本，不使已有快照冲突；
- 快照只插入，不更新、不删除；
- 当前页面读取员工当前资料，不读快照；历史记录通过快照引用解析。

### R11 历史与不回溯

- 就业记录和岗位记录是不可变事实，不覆盖、不删除；
- 员工改名、换电话、调岗、离职或返聘，不改变已有就业记录和岗位记录；
- 员工快照保留当时的姓名、岗位和在职状态；
- 历史排班、生产、产出和工资继续使用原快照，不因员工当前资料变化而重新解释；
- 员工返聘沿用原编号和原岗位，历史不断开。

### R12 审计

- 员工创建、编辑、调岗、离职和返聘写平台审计；
- 员工快照创建和复用写审计；
- 电话属于联系资料，读取按平台敏感数据访问审计记录；
- 员工模块不建字段级变更历史表，也不提供字段级变更历史页；就业记录和岗位记录是业务事实，不是审计替代品。

### R13 员工账号边界

- 本期员工不登录，员工模块不创建账号、不保存密码、不保存角色；
- 平台账号模型预留 `EMPLOYEE` 主体，账号由管理员在平台侧创建并绑定员工；
- 员工模块不提供账号绑定表、绑定命令或密码字段；
- 员工姓名和电话不作为登录凭据；
- 启用员工登录后，员工离职/返聘由员工模块调用平台账号服务禁用/启用绑定账号，平台不反向读取员工表；
- 权限由平台角色控制，不随员工档案自动授予。

### R14 重名与重复电话

- 员工姓名允许重复，以员工编号区分；
- 员工电话可以留空，也允许重复；
- 员工模块不自动合并重名或同电话员工；
- 列表和详情始终显示员工编号，避免只凭姓名选错人。

### R15 与工资标准的边界

- 同岗位同单价；同一岗位的所有员工使用同一岗位时薪和同一套计薪规则；
- 岗位时薪由全局模块按岗位维护；计件单价、计薪方式、调价生效日期和调价历史由工资模块按岗位维护；
- 员工模块不保存岗位时薪、计件单价、工资标准和调薪历史；
- 工资模块按岗位代码读取全局岗位时薪和自己的计薪规则，并结合员工快照和岗位记录还原历史；
- 员工调岗后，工资模块从岗位调整生效日期起使用新岗位的计薪规则；
- 员工模块不计算工资、不比较金额、不选择计薪公式。

## 7. 状态设计

### 7.1 在职状态

| 当前状态 | 操作 | 目标状态 | 说明 |
|---|---|---|---|
| `EMPLOYED` | 离职 | `LEFT` | 写入离职日期和离职记录 |
| `LEFT` | 返聘 | `EMPLOYED` | 更新入职日期，写入返聘记录 |
| `LEFT` | 离职 | 不允许 | 已离职员工不能再次离职 |
| `EMPLOYED` | 返聘 | 不允许 | 在职员工不能重复返聘 |

员工没有启用/停用开关，也没有删除状态。离职是唯一让员工退出排班候选的方式。

### 7.2 岗位

岗位不是员工状态，而是员工固定承担的工作类别：

- 固定岗位指同一时间只有一个当前岗位，不代表永远不能调岗；
- 每名员工只有一个当前岗位；
- 岗位可以在在职期间调整，调整必须写岗位记录；
- 离职期间不能调岗；返聘后可以再调岗；
- 岗位是固定枚举，没有新增、删除或停用；全局模块只允许修改显示名称；
- 岗位调整不改变在职状态，离职和返聘也不自动改变岗位。

## 8. 数据模型与表设计

### 8.1 关系

```text
employee_masters
├─ employee_employment_records      就业记录
├─ employee_position_records        岗位设置和调整记录
└─ employee_snapshots               员工快照
```

员工模块不建小组、成员、效率标准、每日工时、排班和生产计划表，也不建工资标准或调薪表。

### 8.2 表清单

| 表 | 类别 | 用途 |
|---|---|---|
| `employee_masters` | 当前根 | 员工当前资料、岗位和在职状态 |
| `employee_employment_records` | 不可变事实 | 每次入职、离职和返聘 |
| `employee_position_records` | 不可变事实 | 每次岗位设置和岗位调整 |
| `employee_snapshots` | 不可变快照 | 按员工内容版本冻结的员工身份和岗位 |

### 8.3 员工当前表

```sql
CREATE TABLE employee_masters (
    id BIGINT NOT NULL AUTO_INCREMENT,
    employee_business_id VARCHAR(64) NOT NULL,
    employee_no VARCHAR(32) NOT NULL,
    name VARCHAR(40) NOT NULL,
    phone VARCHAR(30) NULL,
    position_code VARCHAR(64) NOT NULL,
    employment_status VARCHAR(16) NOT NULL,
    hired_on DATE NOT NULL,
    left_on DATE NULL,
    employee_note VARCHAR(500) NULL,
    content_version BIGINT NOT NULL,
    row_version BIGINT NOT NULL,
    created_at DATETIME(6) NOT NULL,
    created_by VARCHAR(64) NOT NULL,
    updated_at DATETIME(6) NOT NULL,
    updated_by VARCHAR(64) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_employee_business_id (employee_business_id),
    UNIQUE KEY uk_employee_no (employee_no),
    KEY ix_employee_name (name),
    KEY ix_employee_phone (phone),
    KEY ix_employee_position (position_code, employment_status),
    KEY ix_employee_status (employment_status, employee_no),
    CONSTRAINT ck_employee_name CHECK (name <> ''),
    CONSTRAINT ck_employee_position CHECK (
        position_code IN ('MAKING', 'BAGGING', 'SEAM_CUTTING', 'OTHER')
    ),
    CONSTRAINT ck_employee_status CHECK (
        employment_status IN ('EMPLOYED', 'LEFT')
    ),
    CONSTRAINT ck_employee_phone CHECK (phone IS NULL OR phone <> ''),
    CONSTRAINT ck_employee_employment_dates CHECK (
        (employment_status = 'EMPLOYED' AND left_on IS NULL)
        OR (
            employment_status = 'LEFT'
            AND left_on IS NOT NULL
            AND left_on >= hired_on
        )
    )
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

说明：

- 员工姓名和电话不建唯一约束；
- 员工只有一个当前岗位，岗位代码不建唯一约束，同一岗位可以有多名员工；
- 员工没有启用/停用列，也不硬删除；
- 当前入职日期和离职日期只表示最近一次就业，完整历史在就业记录表。

### 8.4 就业记录表

```sql
CREATE TABLE employee_employment_records (
    record_business_id VARCHAR(64) NOT NULL,
    employee_business_id VARCHAR(64) NOT NULL,
    record_type VARCHAR(16) NOT NULL,
    effective_date DATE NOT NULL,
    reason VARCHAR(300) NULL,
    operator_id VARCHAR(64) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (record_business_id),
    KEY ix_employment_record_employee (
        employee_business_id, effective_date, created_at
    ),
    CONSTRAINT ck_employment_record_type CHECK (
        record_type IN ('HIRE', 'LEAVE', 'REHIRE')
    )
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

说明：

- 创建员工时写一条 `HIRE`；
- 离职写 `LEAVE`，必须带原因；
- 返聘写 `REHIRE`，原因可空；
- 记录只插入，不更新、不删除。

### 8.5 岗位记录表

```sql
CREATE TABLE employee_position_records (
    record_business_id VARCHAR(64) NOT NULL,
    employee_business_id VARCHAR(64) NOT NULL,
    record_type VARCHAR(16) NOT NULL,
    from_position_code VARCHAR(64) NULL,
    to_position_code VARCHAR(64) NOT NULL,
    effective_date DATE NOT NULL,
    reason VARCHAR(300) NULL,
    operator_id VARCHAR(64) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    PRIMARY KEY (record_business_id),
    KEY ix_position_record_employee (
        employee_business_id, effective_date, created_at
    ),
    CONSTRAINT ck_position_record_type CHECK (
        record_type IN ('SET', 'CHANGE')
    ),
    CONSTRAINT ck_position_record_to CHECK (to_position_code <> ''),
    CONSTRAINT ck_position_record_from CHECK (
        (record_type = 'SET' AND from_position_code IS NULL)
        OR (
            record_type = 'CHANGE'
            AND from_position_code IS NOT NULL
            AND from_position_code <> ''
            AND from_position_code <> to_position_code
        )
    )
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

说明：

- 创建员工时写一条 `SET`；
- 调岗写一条 `CHANGE`，保存调整前后岗位；
- 记录只插入，不更新、不删除；
- 当前岗位以员工根表为准，岗位记录用于历史和工资追溯。

### 8.6 员工快照表

```sql
CREATE TABLE employee_snapshots (
    snapshot_business_id VARCHAR(64) NOT NULL,
    employee_business_id VARCHAR(64) NOT NULL,
    employee_content_version BIGINT NOT NULL,
    employee_no VARCHAR(32) NOT NULL,
    name VARCHAR(40) NOT NULL,
    position_code VARCHAR(64) NOT NULL,
    position_name VARCHAR(80) NOT NULL,
    employment_status VARCHAR(16) NOT NULL,
    hired_on DATE NOT NULL,
    left_on DATE NULL,
    content_fingerprint CHAR(64) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    created_by_command_execution_id VARCHAR(64) NULL,
    PRIMARY KEY (snapshot_business_id),
    UNIQUE KEY uk_employee_snapshot_version (
        employee_business_id, employee_content_version
    )
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

快照载荷至少包含：

- 员工编号、姓名、在职状态；
- 岗位代码和岗位名称；
- 当前入职日期、当前离职日期。

- `content_fingerprint` 由员工编号、姓名、岗位代码、在职状态、当前入职日期、当前离职日期和 `employee_content_version` 生成；
- 岗位显示名称只用于展示，不参与指纹；

快照不包含：

- 联系电话、员工备注；
- 时薪、计件单价、工资标准和调薪记录；
- 当前页面上的临时筛选或展示状态。

同一员工、同一内容版本只创建一个快照；快照只插入，不更新、不删除。

## 9. 公开接口设计

### 9.1 命令

```java
interface EmployeeApplicationService {
    EmployeeRef create(CreateEmployeeCommand command);
    EmployeeRef update(UpdateEmployeeCommand command);
    EmployeeRef changePosition(ChangeEmployeePositionCommand command);
    EmployeeRef leave(LeaveEmployeeCommand command);
    EmployeeRef rehire(RehireEmployeeCommand command);
}
```

`CreateEmployeeCommand` 必须包含：

```text
name, phone, positionCode, hiredOn, employeeNote
```

`UpdateEmployeeCommand` 必须包含：

```text
employeeRef, name, phone, employeeNote, expectedRowVersion
```

`ChangeEmployeePositionCommand` 必须包含：

```text
employeeRef, positionCode, effectiveDate, reason, expectedRowVersion
```

`LeaveEmployeeCommand` 必须包含：

```text
employeeRef, effectiveDate, reason, expectedRowVersion
```

`RehireEmployeeCommand` 必须包含：

```text
employeeRef, effectiveDate, reason, expectedRowVersion
```

规则：

- 客户端不能提交员工编号、在职状态、内容版本和最近离职日期；即使提交也不接受；
- 员工编号由平台编号能力在创建事务内生成；
- 所有修改命令携带 `expectedRowVersion`，服务端以员工根行版本为准；
- 命令必须幂等，重复提交返回同一结果，不重复写就业记录或岗位记录。

### 9.2 查询

```java
interface EmployeeQuery {
    EmployeePage search(EmployeeSearchQuery query);
    EmployeeDetailView detail(EmployeeRef employeeRef);
    EmployeeHistoryView history(EmployeeRef employeeRef);
    List<EmployeeOptionView> options(EmployeeOptionQuery query);
    EmployeeEligibilityView checkEligibility(
        EmployeeRef employeeRef, String positionCode, LocalDate workDate
    );
    List<EmployeePositionPeriodView> listPositionPeriods(
        EmployeeRef employeeRef, LocalDate from, LocalDate to
    );
}
```

`EmployeeSearchQuery`：

```text
keyword（姓名、员工编号或电话模糊匹配）,
employmentStatus（EMPLOYED / LEFT / ALL）,
positionCode（可选）,
page, size
```

`EmployeeSearchQuery` 在页面默认使用 `EMPLOYED`；查看历史时可以选择 `LEFT` 或 `ALL`。

`EmployeeOptionQuery`：

```text
employmentStatus（默认 EMPLOYED）,
positionCode（可选）,
keyword（可选）
```

`EmployeeOptionView` 供排班选择使用：

```text
employeeBusinessId, employeeNo, name,
employmentStatus, positionCode, positionName
```

`EmployeeEligibilityView`：

```text
employeeBusinessId, positionCode, workDate,
eligible, reasonCode
```

`EmployeePositionPeriodView`：

```text
employeeBusinessId, positionCode, positionName,
effectiveFrom, effectiveTo（当前岗位为 null）, changeType（SET / CHANGE）
```

`effectiveTo` 由下一条岗位记录的 `effective_date - 1` 计算，不单独存储；工资模块通过 `listPositionPeriods` 读取，不直接读岗位记录表。

`reasonCode` 只使用：

- `OK`：在职且岗位匹配；
- `NOT_EMPLOYED`：员工已离职；
- `POSITION_MISMATCH`：员工当前岗位与请求岗位不一致。

员工不存在时直接返回 `EMPLOYEE_NOT_FOUND`，不作为岗位校验结果。岗位是固定枚举，不存在“岗位已停用”的校验原因。

### 9.3 快照服务

```java
interface EmployeeSnapshotService {
    EmployeeSnapshotRef acquireCurrent(EmployeeRef employeeRef);
    EmployeeSnapshotRef acquireEligibleForWork(
        EmployeeRef employeeRef, String positionCode, LocalDate workDate
    );
    EmployeeSnapshotView resolve(EmployeeSnapshotRef snapshotRef);
}
```

- `acquireCurrent` 冻结员工当前身份和岗位，不校验具体岗位；
- `acquireEligibleForWork` 先校验员工在职且岗位匹配，再返回快照引用；
- 员工已离职时返回 `EMPLOYEE_NOT_EMPLOYED`；岗位不匹配时返回 `EMPLOYEE_POSITION_MISMATCH`；
- `resolve` 按快照引用和版本返回快照内容；
- 快照引用是其他模块唯一需要保存的员工历史依据。

### 9.4 读模型

`EmployeeListItem`：

```text
employeeBusinessId, employeeNo, name, phone,
employmentStatus, positionCode, positionName,
hiredOn, updatedAt
```

`EmployeeDetailView`：

```text
employeeBusinessId, employeeNo, name, phone, employeeNote,
employmentStatus, positionCode, positionName, positionEffectiveFrom,
hiredOn, leftOn,
contentVersion, rowVersion, updatedAt
```

`EmployeeHistoryView`：

```text
employeeBusinessId,
employmentRecords（类型、生效日期、原因、操作人、记录时间）,
positionRecords（类型、调整前岗位、调整后岗位、生效日期、原因、操作人、记录时间）
```

`EmployeeSnapshotView`：

```text
snapshotRef, employeeBusinessId, employeeContentVersion,
employeeNo, name, positionCode, positionName,
employmentStatus, hiredOn, leftOn
```

列表、详情和历史中的岗位名称取全局模块当前名称；快照视图使用快照中冻结的名称。

### 9.5 快照所有权

- 员工快照只保存在员工模块；
- 排班、生产、工资、报表只保存 `EmployeeSnapshotRef`；
- 需要员工历史资料时调用 `EmployeeSnapshotService.resolve`，按版本解析；
- resolve 结果只用于当前读取或展示，不持久化为快照副本；
- 员工当前状态、电话和备注不写入员工快照。

## 10. 事务与并发

### 10.1 创建员工

```text
校验字段和岗位静态项
→ 生成员工编号
→ 写员工根
→ 写入职记录
→ 写岗位设置记录
→ 写审计
→ 一次提交
```

任一步失败整体回滚。员工编号可能因回滚产生空号，但不会重复或复用。

### 10.2 编辑员工

```text
按 row_version 锁定员工根
→ 校验版本
→ 更新姓名、电话或备注
→ 姓名变化时递增 content_version
→ 更新 row_version
→ 写审计
→ 一次提交
```

### 10.3 调整岗位

```text
按 row_version 锁定员工根
→ 校验当前状态为 EMPLOYED
→ 校验新岗位与当前岗位不同
→ 校验新岗位属于固定枚举
→ 校验生效日期
→ 更新当前岗位、content_version 和 row_version
→ 写岗位调整记录
→ 写审计
→ 一次提交
```

### 10.4 离职

```text
按 row_version 锁定员工根
→ 校验当前状态为 EMPLOYED
→ 校验离职日期和原因
→ 更新状态、离职日期、content_version 和 row_version
→ 写离职记录
→ 写审计
→ 一次提交
```

### 10.5 返聘

```text
按 row_version 锁定员工根
→ 校验当前状态为 LEFT
→ 校验返聘日期
→ 更新状态、入职日期、清空离职日期、content_version 和 row_version
→ 写返聘记录
→ 写审计
→ 一次提交
```

### 10.6 获取员工快照

```text
锁定员工根
→ 读取当前岗位和在职状态
→ 按 employee_business_id + content_version 查找快照
→ 已存在则校验载荷指纹并复用
→ 不存在则插入快照
→ 返回快照引用
```

- 员工查询和快照取得必须在同一事务内完成；
- 同一员工同一内容版本并发获取只能保留一条快照；
- 发现同版本载荷指纹不同返回 `EMPLOYEE_SNAPSHOT_CONFLICT`，不能覆盖旧快照；
- 快照取得失败时，引用方业务整体回滚。

### 10.7 并发与幂等

- 员工根使用 `row_version` 拒绝并发覆盖；
- 同一员工的编辑、调岗、离职和返聘先锁员工根，保证状态和岗位变更串行；
- 就业记录和岗位记录只追加，不更新；
- 所有命令使用平台幂等键，重复提交不重复写记录；
- 死锁只允许重试整个幂等命令。

## 11. 历史与追溯

### 11.1 当前记录与历史事实

- 员工根是当前记录，可以修改；
- 就业记录、岗位记录是不可变事实，只追加；
- 员工快照是不可变历史，按内容版本保存；
- 排班、生产、工资、报表保存员工快照引用，不复制员工快照载荷。

### 11.2 快照取得时机

- 排班安排员工时，取得并保存员工快照引用；
- 生产计划、生产记录和个人产出需要员工身份时，保存员工快照引用；
- 工资结算需要员工历史身份时，保存员工快照引用；
- 页面预览和员工列表不创建快照。

### 11.3 追溯内容

平台审计至少记录：

- 操作者、时间、动作；
- 员工业务标识和员工编号；
- 修改前后内容版本；
- 修改字段摘要；
- 离职、返聘和调岗的生效日期与原因；
- 快照创建或复用。

### 11.4 不回溯

- 员工改名不影响历史就业记录和岗位记录；
- 员工调岗、离职或返聘不影响历史排班和产出；
- 调岗不影响已经使用旧快照的生产和工资记录；
- 岗位改名不影响历史快照中的岗位名称；
- 员工当前资料变化不重新解释历史记录。

## 12. 权限、审计与错误

### 12.1 权限

| 权限 | 能力 |
|---|---|
| `employee.read` | 查看员工列表、详情、就业记录和岗位记录 |
| `employee.create` | 新建员工 |
| `employee.update` | 编辑员工姓名、电话和备注 |
| `employee.position.manage` | 调整员工岗位 |
| `employee.employment.manage` | 办理离职和返聘 |
| `employee.snapshot.read` | 直接读取员工快照；排班、生产、工资内部调用按调用方权限鉴权 |

角色建议：

- 管理员：全部员工权限；
- 老板：`employee.read`；
- 排班：`employee.read`，内部调用员工选项和快照接口；
- 工资：通过内部快照和岗位记录查询读取员工历史身份，不授予员工编辑权限。

员工模块不直接读其他模块表。

### 12.2 审计

必须审计：

- 员工创建、编辑；
- 调岗、离职、返聘；
- 员工快照创建、复用；
- 敏感员工资料读取（电话）按平台敏感数据访问审计记录。

员工模块不建字段级变更历史表，也不提供字段级变更历史页；就业记录和岗位记录用于业务追溯，平台审计记录操作和访问。

### 12.3 错误码

以下错误码在平台错误码目录登记 `category` 和 HTTP 映射，规则见平台模块 10.3。

| 错误码 | 含义 |
|---|---|
| `EMPLOYEE_NOT_FOUND` | 员工不存在 |
| `EMPLOYEE_FIELD_INVALID` | 员工字段不合法 |
| `EMPLOYEE_NO_CONFLICT` | 员工编号生成冲突 |
| `EMPLOYEE_VERSION_CONFLICT` | 员工资料版本冲突 |
| `EMPLOYEE_NOT_EMPLOYED` | 员工当前不在职 |
| `EMPLOYEE_ALREADY_EMPLOYED` | 员工当前已在职 |
| `EMPLOYEE_EMPLOYMENT_DATE_INVALID` | 入职、离职或返聘日期不合法 |
| `EMPLOYEE_LEAVE_REASON_REQUIRED` | 离职原因为空 |
| `EMPLOYEE_POSITION_INVALID` | 岗位不是固定枚举值 |
| `EMPLOYEE_POSITION_UNCHANGED` | 新岗位与当前岗位相同 |
| `EMPLOYEE_POSITION_DATE_INVALID` | 岗位生效日期不合法 |
| `EMPLOYEE_POSITION_MISMATCH` | 员工岗位与请求岗位不一致 |
| `EMPLOYEE_SNAPSHOT_CONFLICT` | 员工快照并发冲突且无法复用 |
| `EMPLOYEE_SNAPSHOT_NOT_FOUND` | 员工快照不存在 |
| `EMPLOYEE_SNAPSHOT_INVALID` | 员工快照类型、版本或指纹不匹配 |

前端提示：

- 字段错误在输入框内联显示；
- 员工不存在提示返回列表；
- 版本冲突提示刷新后重试，不覆盖服务端资料；
- 已离职员工再次离职、在职员工重复返聘时提示当前状态，不显示英文错误原文；
- 调岗选择当前岗位时提示“新岗位与当前岗位相同”；
- 快照版本不存在或不匹配提示“数据已失效，请刷新后重试”；
- 不显示内部 ID、指纹和版本号。

## 13. 页面与交互要求

### 13.1 页面清单

| 页面 | 建议路由 | 目的 |
|---|---|---|
| 员工列表 | `/employees` | 搜索、筛选、查看和新建员工 |
| 员工详情 | `/employees/:id` | 查看基本资料、当前岗位、就业记录和岗位记录 |
| 新建员工 | `/employees/new` | 录入员工基本资料和固定岗位 |
| 编辑员工 | `/employees/:id/edit` | 修改姓名、电话和备注 |

调岗、离职和返聘使用详情页内的短对话框，不单独占用页面。

### 13.2 员工列表

- 页头使用紧凑页栏，不使用大标题；
- 列：员工姓名、员工编号、当前岗位、联系电话、在职状态、入职日期、更新时间；
- 岗位以标签展示；
- 搜索：员工姓名、编号或电话；
- 筛选：在职状态（默认在职）、岗位；
- 默认按员工编号升序，支持分页；
- 行点击进入员工详情；
- 新建按钮进入新建员工页；
- 空状态提示“暂无员工”，提供新建入口；
- 离职员工默认不显示，切换到“离职”或“全部”后可见。

### 13.3 员工详情

按“先结论、后明细”组织：

1. 页头：员工姓名、员工编号、当前岗位、在职状态；操作：编辑、调整岗位、办理离职或返聘；
2. 基本信息：联系电话、当前入职日期、当前离职日期、员工备注、更新时间；
3. 当前岗位：岗位名称、进入该岗位的生效日期；操作：调整岗位；
4. 就业记录：入职、离职、返聘的生效日期、原因、操作人和记录时间；
5. 岗位记录：设置或调岗、调整前后岗位、生效日期、原因、操作人和记录时间。

详情页默认只读，操作通过明确的按钮进入；不在详情页直接编辑字段。

### 13.4 新建员工

- 页面为独立全页表单，不使用抽屉；
- 字段：姓名、联系电话、固定岗位、入职日期、员工备注；
- 岗位为必选，只能从四个固定岗位枚举中选择；
- 入职日期默认当天，最大为当天；
- 员工编号显示“保存后自动生成”，不允许手工填写；
- 保存前校验姓名、电话、岗位和日期；
- 保存成功后进入员工详情，显示自动生成的员工编号；
- 取消返回员工列表，不保留草稿。

### 13.5 编辑员工

- 只能修改姓名、联系电话和员工备注；
- 员工编号、在职状态、当前岗位、入职日期和离职日期只读展示；
- 岗位调整通过详情页的“调整岗位”进入，不在编辑表单中直接改；
- 保存携带当前 `rowVersion`；
- 版本冲突提示刷新后重试，不覆盖服务端修改；
- 取消返回详情，不保存修改。

### 13.6 调整岗位

- 入口在员工详情页，只对在职员工显示；
- 新岗位从四个固定岗位枚举中选择，不能选择当前岗位；
- 生效日期默认当天，最大当天，不得早于当前入职日期；
- 调整原因可空，最多 300 字；
- 确认前提示“调岗后从生效日期起影响后续排班和工资规则，历史记录保留”；
- 存在未来排班时不阻断，由排班模块提示调整；
- 确认后员工当前岗位立即更新，并追加岗位记录。

### 13.7 离职与返聘

离职对话框：

- 生效日期默认当天，最大当天，不得早于当前入职日期；
- 离职原因必填，最多 300 字；
- 确认前提示“离职后该员工不再出现在排班候选中，历史记录保留”；
- 存在未来排班时不阻断，由排班模块提示调整。

返聘对话框：

- 生效日期默认当天，最大当天，必须晚于最近离职日期；
- 原因可空；
- 确认后员工恢复在职，沿用原编号和原岗位；
- 返聘后如需换岗位，再单独调整岗位。

### 13.8 全局交互原则

- 页面使用 V3 全站设计语言和现有组件，不新造一套员工专用控件；
- 字段校验内联显示，提交失败不丢失已填内容；
- 所有时间显示为本地日期，不显示微秒时间戳；
- 不显示内部业务标识、内容版本和指纹；
- 员工颜色不是员工字段；排班需要颜色时，由排班模块按员工编号稳定生成；
- 列表和详情不出现英文枚举原文，统一使用中文状态名称和岗位名称。

## 14. 验收标准

### 14.1 员工主数据

- [ ] 新建员工后自动生成 `E-000001` 格式编号，且不可修改；
- [ ] 员工编号唯一，回滚可产生空号但不重复；
- [ ] 员工姓名必填，姓名可以重复；
- [ ] 员工电话可以为空，填写时格式校验生效，且不要求唯一；
- [ ] 新建员工必须选择固定岗位；
- [ ] 员工只能有一个当前岗位，不能多选岗位或工种；
- [ ] 编辑员工只能修改姓名、电话和备注，不能绕过表单修改岗位和在职状态；
- [ ] 员工不能硬删除。

### 14.2 在职与就业记录

- [ ] 新建员工写入一条入职记录；
- [ ] 离职必须填写原因，离职日期不晚于当天且不早于当前入职日期；
- [ ] 离职后员工状态为 `LEFT`，当前离职日期正确；
- [ ] 已离职员工不能再次离职；
- [ ] 返聘沿用原员工编号和原岗位，写入返聘记录并恢复 `EMPLOYED`；
- [ ] 返聘日期必须晚于最近离职日期；
- [ ] 离职和返聘不修改历史就业记录和岗位记录；
- [ ] 离职不检查未来排班，员工模块不依赖排班模块。

### 14.3 岗位

- [ ] 新建员工时岗位必须是 `MAKING / BAGGING / SEAM_CUTTING / OTHER` 之一；
- [ ] 在职员工可以调整岗位，调整后岗位不能与当前岗位相同；
- [ ] 调岗生效日期不得晚于当天，且必须晚于上一条岗位记录生效日期；
- [ ] 调岗写入岗位记录，保存调整前后岗位、生效日期和原因；
- [ ] 离职员工不能调岗，返聘后可以调岗；
- [ ] 岗位代码不能新增、删除或修改，只能修改显示名称；
- [ ] 员工模块不建岗位配置表，不直接维护岗位静态数据；
- [ ] 岗位校验只依据在职状态和岗位是否匹配；岗位固定，不存在启停判断。

### 14.4 员工快照

- [ ] 排班、生产或工资取得员工快照后只保存快照引用；
- [ ] 同一员工同一内容版本只创建一条快照；
- [ ] 同一版本并发获取复用已有快照，不覆盖；
- [ ] 同版本载荷指纹不同返回 `EMPLOYEE_SNAPSHOT_CONFLICT`；岗位显示名称不参与指纹；
- [ ] 全局修改岗位显示名称不递增员工内容版本，已有员工快照不冲突；
- [ ] 员工改名、调岗或离职后，旧快照内容不变；
- [ ] 快照不保存电话、备注和工资单价；
- [ ] 快照中的岗位名称冻结，之后岗位改名不影响历史快照；
- [ ] 员工当前页面不读快照，历史记录通过快照解析。

### 14.5 工资边界

- [ ] 员工模块不保存岗位时薪、计件单价、工资标准和调薪历史；
- [ ] 同岗位同单价；岗位时薪由全局模块按岗位维护，计件/计薪规则由工资模块维护；
- [ ] 工资模块按岗位代码读取全局岗位时薪和计薪规则，不要求员工模块计算工资；
- [ ] 调岗后工资模块能从岗位记录取得调整前后岗位和生效日期；
- [ ] 员工模块不调用计算模块，不含任何工资或成本公式。

### 14.6 数据与边界

- [ ] 员工模块不建小组、成员、效率标准、每日工时、排班和生产计划表；
- [ ] 员工模块不直接读写全局、平台及其他业务表，跨模块只走公开查询、命令或事件；
- [ ] 本期员工不登录，员工模块不创建账号、不保存密码和角色；平台账号模型预留员工主体；
- [ ] 员工模块不保存身份证号、住址、银行卡、合同和附件；
- [ ] 员工模块不提供批量导入导出和员工合并；
- [ ] 员工列表、详情和历史均支持权限校验；
- [ ] 创建、编辑、调岗、离职和返聘均写平台审计；
- [ ] 电话读取按平台敏感数据访问审计记录；
- [ ] 字段错误内联显示，不出现英文错误原文和内部标识。

## 15. 明确不采用

- 不把员工做成多岗位或多选工种资格；
- 不把小组、成员、组长、小组效率和每日有效工作时间放进员工模块；
- 不把排班、日期负载、生产计划和每日产出放进员工模块；
- 不把时薪、计件单价、工资标准、调薪历史、工资结算、考勤、请假和加班放进员工模块；
- 不做员工登录入口、员工账号管理和账号绑定操作（平台账号模型预留）；
- 不做组织架构、部门、岗位职级；
- 不做员工级工资单价和个性化提成；
- 不做身份证号、住址、紧急联系人、银行卡、合同和附件；
- 不做员工头像和员工颜色字段；
- 不做员工删除、合并和批量导入导出；
- 不做未来生效的预约离职、预约返聘和预约调岗；
- 不做活动占用、活动引用守卫和预留记录；
- 不做员工字段级变更历史表和历史页；
- 不做通用“基础资料模块”。

## 16. 与 V2 的主要差异

| V2 人员与小组 | V3 员工模块 |
|---|---|
| 员工和小组在同一个模块 | 员工单独成模块，小组和排班拆出 |
| 员工可以多选工种资格 | 员工只有一个固定岗位，岗位即排班依据 |
| 工种由 `workforce_work_types` 表维护 | 岗位是全局固定枚举，只有四个代码，显示名可改 |
| 资格通过 `workforce_qualification_facts` 记录 | 岗位设置和调整通过岗位记录追溯 |
| 小组有成员关系和效率标准 | 不包含小组和效率 |
| 人员变更受活动占用守卫阻止 | 员工模块不检查排班和活动占用，由排班模块负责 |
| 员工快照包含资格 | 员工快照包含当前岗位和岗位名称 |
| 一期不支持员工登录账号 | 本期员工不登录；平台账号模型预留员工主体和绑定 |
| 工资规则未放进员工模块 | V3 明确岗位时薪归全局模块、计件/计薪规则归工资模块，按岗位维护 |

## 17. 外部依赖

### 17.1 平台能力

- 员工编号：`PlatformNumberService.nextNumber("EMPLOYEE", "E-", 6)` 生成 `E-000001`；唯一、不可修改、不可复用；
- 权限：`employee.read`、`employee.create`、`employee.update`、`employee.position.manage`、`employee.employment.manage`、`employee.snapshot.read`；
- 审计：员工创建、编辑、调岗、离职、返聘和快照操作；
- 敏感数据访问审计：电话读取；
- 员工账号：本期不调用；启用员工登录后，离职/返聘调用 `PlatformAccountSubjectService.disableBySubject/enableBySubject` 同步绑定账号，平台不读取员工表；
- 幂等：所有命令使用平台幂等键；
- 平台不替员工模块管理在职状态和岗位。

### 17.2 全局模块

员工模块依赖通用静态数据查询：

```java
interface StaticDataQuery {
    List<StaticDataItemView> list(String typeCode, boolean includeInactive);
    StaticDataItemView get(String typeCode, String itemCode);
}
```

- 岗位类型代码为 `POSITION`，固定只有四个：`MAKING / BAGGING / SEAM_CUTTING / OTHER`；
- 岗位代码不能新增、删除、停用或修改；全局模块只允许修改显示名称；
- 岗位时薪参数由全局模块按岗位维护，员工模块不读取、不缓存；
- 新建员工和调岗时校验岗位代码属于固定枚举；
- 当前页面显示岗位当前名称；
- 快照取得时把岗位名称冻结到快照；
- 员工模块不维护、不新增、不删除岗位静态项。

### 17.3 工资模块

- 同岗位同单价；工资模块按岗位代码维护计薪方式、计件单价和调价历史；岗位时薪由全局模块按岗位维护，工资模块读取；
- 员工模块只提供岗位代码、岗位记录和员工快照，不提供工资标准；
- 工资模块按岗位记录取得员工在指定期间的实际岗位：调用 `EmployeeQuery.listPositionPeriods`；
- 工资模块按员工快照取得任务发生时的员工身份和岗位：调用 `EmployeeSnapshotService.resolve`；
- 工资模块不直接读员工表、岗位记录表或员工快照表；
- 员工模块不计算工资、不比较金额、不选择计薪公式。

### 17.4 排班与生产模块

排班和生产模块通过员工公开接口获取候选员工和员工快照：

```java
EmployeeQuery.options(EmployeeOptionQuery query);
EmployeeQuery.checkEligibility(
    EmployeeRef employeeRef, String positionCode, LocalDate workDate
);
EmployeeSnapshotService.acquireEligibleForWork(
    EmployeeRef employeeRef, String positionCode, LocalDate workDate
);
EmployeeSnapshotService.resolve(EmployeeSnapshotRef snapshotRef);
```

要求：

- 排班只选择在职且岗位匹配的员工；
- 排班和生产只保存员工快照引用，不复制员工姓名和岗位；
- 员工调岗或离职后，已有排班和生产继续使用原快照；
- 排班模块负责在调整排班时提示员工已离职或岗位已变化；
- 员工模块不建立排班、生产计划和活动占用。

### 17.5 报表模块

- 报表通过员工公开查询或后续报表投影读取员工维度和岗位维度；
- 报表不直接读员工表；
- 员工模块不提供报表专用汇总表。

## 18. 已确认口径

1. 员工模块只负责员工档案、固定岗位、在职离职和岗位历史；小组、排班、每日产出和工资独立。
2. 员工字段只保留姓名、电话、固定岗位、入职日期、在职状态和备注；身份证号、住址、紧急联系人、时薪和工资标准不保存。
3. 每名员工只有一个固定岗位，岗位就是排班依据，不再多选工种资格。
4. 岗位是全局固定枚举 `MAKING / BAGGING / SEAM_CUTTING / OTHER`，代码不能改；全局模块只允许修改显示名称。
5. 同岗位同单价；岗位时薪归全局模块按岗位维护；计件单价、计薪方式和调价历史归工资模块；都不放进员工档案。
6. 保留每次入职、离职和返聘记录，返聘沿用原员工编号。
7. 保留每次岗位设置和调整记录；调岗不在编辑表单中直接覆盖。
8. 员工离职或调岗不检查未来排班，由排班模块负责提示或调整。
9. 本期员工不登录，员工模块不创建账号、不保存密码和角色；平台账号模型预留 `EMPLOYEE` 主体，启用后由管理员绑定账号。
10. 员工编号格式为 `E-000001`，自动生成、不可修改、不可复用。
11. 员工模块不建小组、效率标准、每日工时和活动占用。
12. 员工模块没有业务计算，不依赖计算模块。
13. 员工快照归员工模块所有，其他模块只保存 `EmployeeSnapshotRef`。
