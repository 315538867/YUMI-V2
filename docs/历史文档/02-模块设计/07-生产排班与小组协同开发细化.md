## 3. 已冻结业务结论

### 3.1 排班与生产

- `scheduling` 只拥有排班计划、执行主体、工作量评估结果快照、取消和核验提交事实。
- `production` 只拥有生产需求、任务来源占用、实际生产事实、生产来源、物理阶段、质量和数量投影。
- 排班不得计算标准工时、有效工作时间和小组效率，也不得访问主数据、生产或成本台账的底层表与 Repository。
- 排班创建、取消和核验通过提供方公开接口使用 `master-data`、`production` 和 `cost-ledger` 的能力。
- 任务状态为 `ARRANGED`、`CANCELLED`、`VERIFIED`；首期不支持任务部分取消或部分核验。

### 3.2 小组

- 小组不设置组长、不设置可承接范围、不拆分倒胶、填色、画画等内部步骤。
- 小组任务按共同产出核验，不记录成员个人完成数量和贡献比例。
- 小组工作量标准与个人标准分开；首期使用按人数配置的全局协作效率因子。
- 小组可用标准分钟为：

```text
工作日小时数 × 60 × 制作有效工时率 × 小组人数 × 协作效率因子(小组人数)
```

- `ARRANGED` 任务活动引用小组时，名称、成员和状态不能修改；任务取消或核验后可以修改。
- 小组创建时和每次成功修改后，由 `master-data` 物化不可变快照；其他模块只保存强类型 `WorkTeamSnapshotRef`。
- 已核验小组任务的历史成员由工资模块通过快照查询解析；结算到人不是排班或生产职责。

### 3.3 协调器

- `workforce-coordination` 只编排 `scheduling → master-data` 的小组配置变更事务，不拥有表和业务事实。
- `fulfillment-coordination` 只编排同时改变 `scheduling` 与 `production` 的已登记履约用例，不拥有表和业务事实。
- 协调器不能读取参与模块的表、Repository、行对象或内部服务。
- 同一命令的参与端口必须加入同一个 MySQL 事务，任何一步失败均整体回滚。

## 4. 代码基线与模块可见性

### 4.1 目标工程

后端目标根目录固定为：

```text
backend/
├─ pom.xml
├─ src/main/java/com/yumi/
├─ src/main/resources/db/migration/
└─ src/test/java/com/yumi/
```

技术基线：Java 21、Spring Boot 3.5.x、Spring Modulith、Spring JDBC `JdbcClient`、MySQL、Flyway。核心业务持久化不使用 JPA。

当前设计分支没有后端工程，本方案只冻结未来创建路径，不把 `main` 分支旧实现当作新架构代码模板。

### 4.2 顶级包名

模块显示名与 Java 包名映射固定如下：

| 模块显示名 | Java 顶级包 |
|---|---|
| `production` | `com.yumi.production` |
| `scheduling` | `com.yumi.scheduling` |
| `workforce-coordination` | `com.yumi.workforcecoordination` |
| `fulfillment-coordination` | `com.yumi.fulfillmentcoordination` |
| `master-data` | `com.yumi.masterdata` |
| `cost-ledger` | `com.yumi.costledger` |
| `platform` | `com.yumi.platform` |

每个顶级包的 `package-info.java` 使用 Spring Modulith `@ApplicationModule` 声明模块。跨模块只允许依赖提供方 `api` 下显式声明的 named interface；`application`、`domain`、`infrastructure` 均为模块内部包。

### 4.3 公开包规则

每个业务模块采用：

```text
com.yumi.<module>
├─ api
│  ├─ application     对其他模块开放的完整应用用例
│  ├─ participant     对协调器或命令所有者开放的事务参与端口
│  ├─ query           对其他模块开放的只读查询
│  ├─ model           公开命令、结果、ID、SnapshotRef 和错误参数
│  └─ http            HTTP 适配层；不作为其他模块 Java 依赖入口
├─ application
│  ├─ command         用例实现与事务边界
│  ├─ query           查询实现
│  └─ port            本模块内部持久化与平台端口
├─ domain
│  ├─ model
│  ├─ policy
│  └─ service
└─ infrastructure
   ├─ persistence
   └─ integration
```

约束：

- 跨模块接口、入参和返回值必须全部位于提供方 `api` 包；
- 其他模块不得引用提供方 `application`、`domain`、`infrastructure`；
- `api` DTO 不包含数据库内部 `id`、JdbcClient 行对象、Entity、Repository、连接或可变集合；
- Java 集合入参在构造时执行 `List.copyOf` / `Set.copyOf`，返回结果保持不可变；
- 稳定业务 ID 使用提供方拥有的强类型 record，不在 `platform` 建立通用 `StringId`；
- 提供方公开契约不得导入调用方业务类型；调用方拥有的资源只能以稳定业务 ID、`BusinessPointer`、`SnapshotPointer` 或 `PreparedScopePointer` 传入；
- 调用方负责把本模块强类型引用解包为结构指针，提供方在边界重新校验 owner/type、准备者、协调类型和作用域；
- `platform` 只提供请求上下文、幂等、审计、通用错误和无行为结构值，不拥有生产、排班或小组业务类型。

### 6.2 跨模块结构引用

跨模块契约遵守“提供方拥有 API”原则：提供方 API 不导入调用方的 ID、枚举或 Ref 类型。调用方资源通过无行为结构值传入，提供方必须在应用边界校验固定语义。

目标文件：

```text
backend/src/main/java/com/yumi/platform/api/reference/BusinessPointer.java
backend/src/main/java/com/yumi/platform/api/snapshot/SnapshotPointer.java
backend/src/main/java/com/yumi/platform/api/coordination/PreparedScopePointer.java
backend/src/main/java/com/yumi/masterdata/api/model/AssignmentSubjectSnapshotRef.java
backend/src/main/java/com/yumi/masterdata/api/model/WorkTeamSnapshotRef.java
backend/src/main/java/com/yumi/masterdata/api/model/ProductStandardSnapshotRef.java
backend/src/main/java/com/yumi/masterdata/api/model/TeamEfficiencyStandardSnapshotRef.java
backend/src/main/java/com/yumi/scheduling/api/model/DeliveryRouteSnapshotRef.java
backend/src/main/java/com/yumi/scheduling/api/model/WorkloadAssessmentSnapshotRef.java
backend/src/main/java/com/yumi/production/api/model/ProductionVerificationFactRef.java
backend/src/main/java/com/yumi/production/api/model/ProductionSourceFactRef.java
```

```java
record BusinessPointer(
    String ownerModule,
    String resourceType,
    String businessId
) {}

record SnapshotPointer(
    String ownerModule,
    String snapshotType,
    String snapshotBusinessId,
    long version
) {}

record PreparedScopePointer(
    String preparerModule,
    String coordinationType,
    String scopeBusinessId,
    String scopeFingerprint,
    Instant validatedAt
) {}

record WorkTeamSnapshotRef(SnapshotPointer pointer) {
    WorkTeamSnapshotRef {
        requireOwnerAndType(pointer, "master-data", "WORK_TEAM");
    }
}

record ProductionVerificationFactRef(BusinessPointer pointer) {
    ProductionVerificationFactRef {
        requireOwnerAndType(pointer, "production", "PRODUCTION_VERIFICATION_FACT");
    }
}
```

三类结构值的边界固定如下：

- `BusinessPointer` 只标识不可变事实或稳定业务资源，不代表当前状态，也不提供查询、锁定或授权；
- `SnapshotPointer` 只标识业务所有者已物化的不可变快照；所有者的查询接口仍接收自己的强类型 Ref；
- `PreparedScopePointer` 只是同一事务内的准备证明，禁止进入 HTTP JSON、缓存、任务表或长期业务表；应用阶段必须重验 `preparerModule + coordinationType + scopeBusinessId + scopeFingerprint`；
- 三者都不提供通用 Repository、通用查询、反射路由或动态服务定位，因此不形成全局事实中心、快照中心或协调中心；
- 消费者持久化快照时只展开 `owner_module + snapshot_type + snapshot_business_id + snapshot_version`，不复制快照载荷；事实引用只保存指针字段，不复制事实内容；
- 直接引用提供方 Ref 会造成模块环时，消费模块定义本地领域专用 Ref 包装相同结构指针，但不得改变 owner/type。

数据库快照引用不得退化成无类型的 `snapshot_id` 或只有裸版本号。

### 6.3 数量、时间和版本

- 跨模块数量统一使用 Java `long`，构造时校验 `> 0` 或 `>= 0`；数据库使用有符号 `BIGINT + CHECK`。
- 标准分钟和可用分钟使用 `BigDecimal`，精度与舍入由 `calculation` 规则版本解释。
- 比例和负载率使用 `BigDecimal`，不使用 `double`。
- 业务日期使用 `LocalDate`，事实发生时间使用 `Instant`。
- 预期版本使用 `long expectedVersion`，必须大于等于 0。

### 14.4 正式流程

1. 校验权限和幂等指纹，取得命令执行权；
2. 开启或加入 `REQUIRED` 事务；
3. 调用 `WorkTeamPlanReferenceGuardPort.lockAndCheckNoActiveReferences`；
4. `scheduling` 插入或锁定唯一守卫行，在锁内检查 `ARRANGED` 引用；
5. 有活动引用时抛出 `WORK_TEAM_ACTIVE_PLAN_REFERENCED`；
6. 无活动引用时返回准备范围；
7. 调用 `WorkTeamMutationParticipantPort`；
8. `master-data` 锁定小组根和成员关系，重验版本、员工状态、制作资格和目标状态；
9. 追加变更事实、更新当前投影、无条件生成新快照；
10. 保存幂等成功结果、审计和必要提交后任务；
11. 一次提交。

## 16. 核心命令调用链

### 16.1 创建排班任务

| 步骤 | 输入 | 处理与锁 | 写入/输出 | 失败 |
|---|---|---|---|---|
| 1 | HTTP 请求、上下文、幂等键 | 校验格式、权限、请求指纹 | 命令 DTO | 400/401/403/幂等冲突 |
| 2 | 执行主体、日期、工序 | `TEAM` 时先锁 team guard；再锁 subject-day guard | 无 | 并发/锁超时整体失败 |
| 3 | 当前已有计划 | 查询 scheduling 自有活动计划 | `existingPlanLines` | 不跨模块读表 |
| 4 | 主体与计划行 | 调用 `WorkAssignmentSubjectQuery` 和 `WorkloadAssessmentQuery` | 主体快照、评估结果 | 无效、无资格、超标拒绝 |
| 5 | 来源池与数量 | 调用 production 批量占用端口；production 按内部主键锁定完整来源池 | 占用引用 | 余额不足或版本冲突回滚 |
| 6 | 全部已验证结果 | 写任务、明细、分配、评估快照和占用引用 | `CreateScheduleTaskResult` | 任一插入失败全部回滚 |
| 7 | 结果 | 保存幂等成功、审计、提交后动作 | HTTP 201 | 提交失败不返回成功 |

同一任务多行占用必须使用 `ProductionTaskReservationPort.reserveForTask(ReserveTaskSourcesCommand)`，由 production 一次解析全部来源池后按内部主键锁定；禁止 scheduling 循环调用单行占用导致锁序不稳定。

### 16.2 调整执行主体或日期

1. `TEAM` 涉及时，按小组业务标识排序锁定旧小组和新小组 guard；
2. 按 `(subjectType, subjectBusinessId, date, processCode)` 排序锁定旧、新 subject-day guard；
3. 锁定任务、明细和当前分配，要求状态为 `ARRANGED` 且版本一致；
4. 汇总目标主体目标日期的已有活动计划，排除当前任务；
5. 调用主数据主体查询和工作量评估；
6. 追加分配变更事实，结束旧分配，插入新分配和新评估快照；
7. 任务版本递增；生产占用不变；
8. 保存幂等与审计并提交。

### 16.3 直接取消任务

1. 锁定任务、明细和当前分配；
2. 校验 `ARRANGED`、版本和取消权限；
3. 一次传入全部占用引用，调用 production 批量释放；
4. 追加取消事实，任务和分配迁移为 `CANCELLED`；
5. 更新占用引用摘要，保存幂等和审计；
6. 一次提交。

### 16.4 核验任务

1. 锁定任务、明细和当前分配；
2. 校验 `ARRANGED`、任务版本、明细完整性和数量守恒；
3. 调用 `ProductionVerificationPort.verifyTask`；
4. production 锁定需求、来源池和占用，追加核验/质量/报废/来源事实，消费占用并更新投影；
5. 调用 `CostRecognitionParticipantPort.recognizeProductionCost`；
6. cost-ledger 形成成本确认事实；
7. scheduling 插入核验提交头明细，任务和分配迁移为 `VERIFIED`；
8. 保存幂等、审计和提交后任务；
9. 一次提交。

若第 5 步成本确认失败，第 4 步 production 的全部事实和投影必须回滚；不得留下“生产已核验、排班未核验”的中间状态。

## 17. 事务传播与锁序

### 17.1 注解规则

- 完整命令实现：`@Transactional(propagation = REQUIRED)`；
- 跨模块事务参与实现：`@Transactional(propagation = MANDATORY)`；
- 纯查询：`@Transactional(propagation = SUPPORTS, readOnly = true)`；
- 禁止 `REQUIRES_NEW`；
- 禁止在事务内执行外部 HTTP、文件上传、打印、通知发送和长时间计算；
- 提交后副作用只登记 `platform_action_tasks`，由提交后 worker 执行。

### 17.2 全局锁序

```text
orders / after-sales
→ scheduling
→ master-data
→ production
→ payroll
→ finance
→ cost-ledger
```

本范围具体锁序：

```text
小组配置：scheduling → master-data
任务创建：scheduling → master-data(只读) → production
任务调整：scheduling → master-data(只读)
任务取消：scheduling → production
任务核验：scheduling → production → cost-ledger
履约协调：orders(如有) → scheduling → production
```

只读调用也不能反向触发调用方。任何参与模块不得回调协调器或上游模块。

## 19. 错误与 HTTP 映射

| 错误类别 | HTTP | 处理 |
|---|---:|---|
| 格式、必填、数量守恒失败 | 400 | 返回稳定 code 和安全字段参数 |
| 未认证 | 401 | 不进入业务用例 |
| 无权限 | 403 | 不泄露来源余额和其他订单信息 |

| 版本冲突、唯一约束竞态、prepared scope 冲突 | 409 | `retryable` 按错误类型设置 |
| 死锁、锁等待超时 | 409 或 503 | 命令边界按平台策略有限重试，耗尽后返回稳定基础设施错误 |
| 未预期异常 | 500 | requestId 可追踪，不返回 SQL 和堆栈 |

协调器不得创建同义错误码。错误的 `module`、`code`、`businessId`、`conflictResource` 和 `retryable` 原样保留。

## 20. 幂等与重复提交

- 外部命令所有者使用 `platform` 幂等能力；范围包含操作者、操作类型、业务根、幂等键摘要和请求指纹。
- 同键同指纹返回原结果；同键不同指纹返回幂等冲突。
- 跨模块参与端口接收同一个 `operationId`，不接收外部幂等键。
- production 通过任务占用、核验事实和来源事实的领域唯一键防重复。
- scheduling 通过任务、取消和核验提交的领域唯一键防重复。
- prepared scope 不承担幂等，只约束同一事务中的锁定范围。
- 只有命令边界可以在确认幂等安全后重试死锁或锁等待；参与端口不得内部静默重试。

## 21. 设计级验收矩阵

| 场景 | 预期 |
|---|---|
| 个人正常任务创建 | 使用个人可用标准分钟，成功后同时存在任务、分配、评估快照和 production 占用引用 |
| 小组正常任务创建 | 使用完整小组快照人数和全局效率因子，不产生成员个人任务或产量 |
| 小组超标 | `WorkloadAssessment` 返回 `OVER_STANDARD`，任务和占用均不落库 |
| 小组配置被活动任务引用 | `WORK_TEAM_ACTIVE_PLAN_REFERENCED`，主数据不变、不生成新快照 |
| 活动任务取消后改小组 | 不再被活动引用阻止，变更成功并生成新快照 |
| 已核验任务后改小组 | 历史任务仍引用原快照，新配置生成新快照 |
| 并发创建同主体同日任务 | 由 subject-day guard 串行化，后一个基于最新计划重新评估 |
| 小组变更与 TEAM 任务并发 | 由 team guard 串行化，不能同时基于“无引用/旧配置”成功 |
| 取消任务时 production 释放失败 | scheduling 不写取消事实，任务仍为 `ARRANGED` |
| 核验 production 成功但 cost-ledger 失败 | 同一事务整体回滚，production/scheduling/cost-ledger 均无成功事实 |
| 重复核验 | 返回原幂等结果或稳定重复错误，不形成第二套生产来源和成本事实 |
| 履约 prepared scope 被扩大 | `*_PREPARED_SCOPE_CONFLICT`，全部回滚 |
| 查询历史小组成员 | 通过 `WorkTeamSnapshotQuery` 解析原版本，不读取当前成员覆盖历史 |
| 排班工作台当前试算 | 明确标记为当前试算，不覆盖历史评估快照 |
| 跨模块底层访问 | 设计上无合法依赖路径；从 G1 起由 Modulith/ArchUnit 和 SQL 扫描持续固化 |
