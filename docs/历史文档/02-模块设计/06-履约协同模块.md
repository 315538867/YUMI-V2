## 2. 模块定位

### 2.1 拥有与不拥有

`fulfillment-coordination` 只拥有应用编排代码和公开协调契约，不拥有：

- 订单、排班、生产、来源、占用、质量、成本或售后事实；
- 业务根投影、业务编号或业务查询结果；
- 业务表、业务 Repository 或业务领域聚合；
- 可重试的通用工作流状态；
- 业务错误码的最终归属。

它负责：

- 在一个已有或新建的业务事务内按固定顺序调用参与模块；
- 把命令所有者的意图转换成两个模块均能理解的专用参与端口输入；
- 汇总不可变参与结果，返回给命令所有者；
- 传播任一参与模块的业务拒绝、并发冲突和基础设施异常；
- 保证协调器不会被参与模块回调。

### 2.2 依赖图

```text
orders / 生产业务 HTTP 命令适配层
             │
             ▼
fulfillment-coordination
       ┌─────┴─────┐
       ▼           ▼
  scheduling    production
```

允许：

```text
orders → fulfillment-coordination
fulfillment-coordination → scheduling
fulfillment-coordination → production
scheduling → production（仅已登记的一向参与端口）
```

禁止：

```text
production → scheduling
production → fulfillment-coordination
scheduling → fulfillment-coordination
fulfillment-coordination → 任意第三个业务模块
scheduling / production → 回调 fulfillment-coordination
```

## 3. 编排用例

### 3.1 `OrderFulfillmentChangeCoordination`

命令所有者仍是 `orders`。当订单变更会影响未核验任务、生产来源或任务占用时，`orders` 锁定订单根和变更意图后调用协调器。

协调步骤固定为：

```text
orders 锁订单根、交付约定和变更明细
→ 调用 scheduling，锁全部受影响任务并重验 scheduling 自己拥有的取消确认、任务状态和任务版本
→ 调用 production，锁生产需求、来源、占用和物理状态并重验生产缺口
→ scheduling 统一取消受影响任务并释放排班侧分配
→ production 释放任务来源占用并执行需求调整
→ orders 写入新约定版本、金额和应收调整事实
→ 主事务登记幂等、审计和 platform_action_tasks
```

任何任务已核验、未获得管理员确认、生产来源不可释放或任一版本变化时整体失败。

### 3.2 `PackagingRestorationCoordination`

命令所有者为协调器自身，通常由生产工作台 HTTP 命令适配层调用。只有包装还原会影响未核验任务或来源占用时才使用协调器；不影响排班的纯生产阶段更正可以由 `production` 直接执行。

固定步骤：

```text
scheduling 锁受影响任务、分配和取消状态，返回完整已锁定任务集
→ 重验任务未核验、未取消和版本
→ production 锁物理状态、来源占用和生产需求
→ scheduling 使用已锁定任务集追加取消/调整并结束活动分配，不再获取新锁，也不修改可变产能余额
→ production 释放任务来源池占用，追加包装还原事实并更新阶段/数量投影
→ 一次提交
```

协调器不得把生产计算出的阶段或数量目标直接写入排班。排班只能根据自己的参与端口规则追加任务调整事实。

### 3.3 `QualityDispositionCoordination`

命令所有者为协调器自身，适用于质量处置、报废、修复池转移等同时影响生产和未核验任务的动作。

固定步骤：

```text
scheduling 锁任务和活动分配，返回完整已锁定任务集
→ production 锁质量范围、物理状态、来源和修复池并完成处置预校验
→ scheduling 使用已锁定任务集调整/取消任务并释放分配，不再获取新锁
→ production 追加质量处置、责任、修复池和来源调整事实
→ 一次提交
```

质量待判断只登记待处理状态，不得因为协调器执行就自动恢复制作缺口。只有明确的处置结果才能改变修复池、来源资格或任务状态。

## 4. 公开契约

### 4.1 对命令所有者公开的协调端口

协调器按用例拆成三个最小专用接口，使 `orders` 只依赖订单变更协调能力，生产工作台只依赖包装还原或质量处置能力；不提供汇总式 `FulfillmentCoordinationPort`、通用 `execute`、`save`、`update` 或工作流接口：

```java
interface FulfillmentOrderChangeCoordinationPort {
    OrderFulfillmentChangeCoordinationResult coordinate(
        OrderFulfillmentChangeCoordinationCommand command
    );
}

interface PackagingRestorationCoordinationPort {
    PackagingRestorationCoordinationResult coordinate(
        PackagingRestorationCoordinationCommand command
    );
}

interface QualityDispositionCoordinationPort {
    QualityDispositionCoordinationResult coordinate(
        QualityDispositionCoordinationCommand command
    );
}
```

所有协调输入的公共语义固定如下；精确 Java record 字段以 `docs/历史文档/02-模块设计/07-生产排班与小组协同开发细化.md` 第 15.2 节为唯一实现定义：

```text
operationId
actorBusinessId
businessScope
expectedResourceVersions.orders（如有）
expectedResourceVersions.scheduling
expectedResourceVersions.production
明确的业务根标识
明确的数量、原因、来源和由所有者定义的强类型 `SnapshotRef`
```

协调器不得接收：

- 调用方计算出的生产余额或排班剩余容量；
- 目标投影值；
- 数据库行模型；
- 可任意扩展的 JSON payload；
- 用于跳过参与模块校验的管理员标志。

输出只返回不可变结果：

```text
operationId
参与模块执行标识
各模块新增事实标识
各模块更新后的版本
来源占用/释放/消费明细
任务调整结果
```

### 4.2 参与模块提供的两阶段端口

协调流程需要先锁定并校验完整范围，再按同一范围生效。为避免协调器持有领域实体或使用通用工作流接口，`scheduling` 和 `production` 分别拥有以下专用端口：

```java
interface SchedulingOrderChangeParticipantPort {
    PreparedSchedulingTaskSet lockAndValidate(
        LockOrderChangeTasks command
    );
    SchedulingTaskMutationResult cancelLockedTasks(
        CancelLockedOrderChangeTasks command
    );
}

interface SchedulingDispositionParticipantPort {
    PreparedSchedulingTaskSet lockAndValidatePackagingRestoration(
        LockPackagingRestorationTasks command
    );
    SchedulingTaskMutationResult applyPackagingRestorationToLockedTasks(
        ApplyPackagingRestorationTasks command
    );
    PreparedSchedulingTaskSet lockAndValidateQualityDisposition(
        LockQualityDispositionTasks command
    );
    SchedulingTaskMutationResult applyQualityDispositionToLockedTasks(
        ApplyQualityDispositionTasks command
    );
}

interface ProductionOrderChangeParticipantPort {
    PreparedProductionScope lockAndValidate(
        LockOrderChangeProductionScope command
    );
    ProductionOrderChangeResult applyLockedOrderChange(
        ApplyLockedOrderChange command
    );
}

interface ProductionDispositionParticipantPort {
    PreparedProductionScope lockAndValidatePackagingRestoration(
        LockPackagingRestorationProductionScope command
    );
    PackagingRestorationResult applyLockedPackagingRestoration(
        ApplyLockedPackagingRestoration command
    );
    PreparedProductionScope lockAndValidateQualityDisposition(
        LockQualityDispositionProductionScope command
    );
    QualityDispositionResult applyLockedQualityDisposition(
        ApplyLockedQualityDisposition command
    );
}
```

每个 `lockAndValidate*` 命令传入业务根、影响范围和预期版本，由提供方重新解析完整行集并按内部主键升序加锁；不能只相信调用方传入的任务或来源列表。每个 `apply*` 只能使用同一 `operationId`、协调类型和已准备范围，不能扩大范围或补锁新业务行。

### 4.3 已准备范围 DTO

`PreparedSchedulingTaskSet` 和 `PreparedProductionScope` 分别由 scheduling 与 production 拥有，只是在当前事务内传递的不可变值对象，不是持久化工作流状态，也不能包含 JPA Entity、Repository、数据库连接或可变集合。两个提供方分别定义自己的协调类型，不导入 `FulfillmentCoordinationType`；协调器负责显式映射。准备结果固定包含以下语义；精确 Java record 字段以 `docs/历史文档/02-模块设计/07-生产排班与小组协同开发细化.md` 第 15.2 节为唯一实现定义：

```text
operationId
提供方自有 coordinationType
sortedBusinessIds
resourceVersions
PreparedScopePointer
```

`PreparedScopePointer` 固定包含准备模块、协调类型、作用域业务标识、范围指纹和校验时间，禁止进入 HTTP JSON、缓存、任务表或长期业务表。第二阶段参与端口必须重验 `operationId + coordinationType + scopeBusinessId + scopeFingerprint`，并确认当前版本仍与已准备范围一致。指纹不一致、集合扩大、出现遗漏对象或事务上下文丢失时返回并发错误并整体回滚；不得重新查询出新增对象后继续提交。

## 5. 事务与锁序

### 5.1 事务传播

- 从外部命令开始时，命令所有者开启 `PROPAGATION_REQUIRED`；
- 协调器参与现有事务，不自行开启第二个事务；
- `scheduling` 和 `production` 参与端口使用 `PROPAGATION_MANDATORY`；
- 不使用 `REQUIRES_NEW`；
- 不在协调器中执行外部 HTTP、通知、打印、文件上传或长时间批处理。

如果协调器直接作为命令所有者，它负责开启完整事务；如果由 `orders` 调用，它只加入上层事务。`after-sales` 首期没有已登记的履约协调用例；未来只有在定义具名用例、参与端口和锁定计划后才能成为调用方。

### 5.2 全局锁序

```text
orders（当前已登记命令所有者）
→ scheduling
→ production
```

`after-sales` 不属于当前已登记的履约协调锁图。未来若售后动作需要同时修改既有排班与生产，必须先回到 G0 增加具名协调用例、参与端口、资源版本、锁定对象、失败语义和并发测试，再把 `after-sales` 加入全局锁序；不得仅凭模块名称预留位置。

协调器自身不持有业务行锁。每次调用 `scheduling` 前必须一次解析并传入完整受影响任务集合；每次调用 `production` 前必须一次解析并传入完整受影响来源/需求集合。参与模块内部按各自分册的主键升序锁定，不能先锁一部分、返回协调器后再补锁。

调用层级和锁序不是同一维度：协调器可以作为调用层级中的中间入口，但真实业务锁仍由命令所有者和参与模块按全局顺序取得。

### 5.3 版本校验

协调器不使用一个订单版本代表所有模块。必须把 `expectedResourceVersions` 按模块传给对应参与端口：

```text
scheduling.expectedVersion  → scheduling 锁内重读并比较
production.expectedVersion   → production 锁内重读并比较
orders.expectedVersion       → orders 自己锁内重读并比较
```

版本不一致时返回稳定并发错误，禁止协调器自动刷新版本后继续提交。

## 6. 结果、错误与幂等

### 6.1 错误归属

参与模块拥有业务错误码，协调器只负责保留错误码、模块标识、业务范围和可安全展示的参数：

```text
module
code
businessId
retryable
conflictResource
```

协调器不得把 `PRODUCTION_SOURCE_INSUFFICIENT_AVAILABLE` 改写成通用“协调失败”，也不得把排班取消确认缺失降级为警告。

### 6.2 失败语义

任一步失败时整体回滚：

```text
任务取消和活动分配结束
来源占用释放
生产阶段/质量/责任处置
需求缺口调整
订单变更事实
幂等记录
审计记录
提交后任务登记
```

协调器不创建补偿事务，不发布“部分成功”事件，也不把参与模块的拒绝转成成功响应。

### 6.3 幂等

- 外部请求幂等记录由命令所有者和 `platform` 在同一主事务中登记；
- 协调器透传同一个 `operationId`，不为参与模块生成新的外部幂等键；
- 参与模块使用自己的领域唯一约束防止事实重复；
- 同一 `operationId` 重试必须返回原结果或原始业务错误；
- 协调器不在内存中保存执行状态，不把 JVM 锁当成幂等机制。

## 7. 权限与审计

协调器只校验编排层通用条件：认证上下文存在、业务范围完整、操作人可识别、命令类型合法。订单、任务、来源、质量和生产权限分别由各自拥有模块在锁内重新校验。

审计至少记录：

```text
operationId
coordinationType
actorBusinessId
commandBusinessIds
expectedResourceVersions
参与模块执行结果
最终状态 = COMMITTED | ROLLED_BACK
错误模块和错误码（如失败）
```

协调器不得保存业务事实副本。审计引用使用稳定业务标识和参与结果标识。

## 8. 测试与结构门禁

实现前必须通过：

1. Spring Modulith 结构测试：协调器只能依赖 `production`、`scheduling` 的公开参与端口，不依赖业务表和内部 Repository；
2. 三个编排用例的成功路径、业务拒绝和基础设施异常回滚测试；
3. `orders → scheduling → production` 锁序和死锁测试；
4. `expectedResourceVersions` 分模块冲突测试；
5. 参与模块回调协调器的结构和运行时防护测试；
6. 重复 `operationId`、重复提交和唯一约束冲突测试；
7. 协调器不产生业务表、不持有业务事实、不提供通用 CRUD 的架构检查；
8. `platform_action_tasks` 与主事务同提交、提交后 worker 执行的集成测试。

未通过真实 MySQL 原子性、并发和回滚测试前，不得把协调器接入正式业务命令。
