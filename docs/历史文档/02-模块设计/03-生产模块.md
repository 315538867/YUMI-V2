## 2. 权威边界

### 2.1 `production` 拥有

- 生产需求当前投影及制作缺口；
- 制品的数量事实、物理阶段和加工历史；
- 包装、可选缝边和包装还原事实；
- 质量问题、质量处置、报废和责任判定；
- 修复池及修复后重新进入生产的来源；
- 生产核验产生的正式生产事实；
- 生产来源、来源可用余额、来源占用、来源消费和来源更正；
- 发货资格所需的生产侧只读查询结果。

### 2.2 `production` 不拥有

- 排班任务、员工或小组日程、工作量评估快照、任务取消确认和核验提交状态；
- 订单、交付约定、普通发货事实和订单累计发货数量；
- 售后案例、售后义务和售后完成事实；
- 工资封账、经营成本和真实现金；
- 订单或排班模块的表、行模型和内部 Repository。

### 2.3 依赖方向

```text
scheduling → production
orders → production 参与端口
after-sales → production 参与端口
fulfillment-coordination → production 参与端口
production → calculation / platform 公开能力
production → scheduling   禁止
production → fulfillment-coordination   禁止
```

`scheduling → production` 只允许创建/取消排班、排班核验和来源占用等已登记参与端口。生产模块涉及排班任务的动作必须由 `fulfillment-coordination` 作为入口，生产内部不得反向调用排班。

## 3. 核心领域模型

### 3.1 需求、来源和消费是三个不同层次

```text
生产需求：还需要完成多少制作、包装加工或修复
任务池占用：排班对正常需求池、包装加工池或修复池的计划数量占用，不代表已产出实物
生产来源：核验或接管后已经形成、可以被指定交付用途使用的实物数量
来源消费：已经被普通发货或售后交付正式消费的已产出来源数量
```

生产需求不能直接减少已产出来源余额，任务池占用也不能作为发货来源。排班通过 `production` 公开参与端口申请或释放任务池占用，由 `production` 产生或释放 `task_source_reservations`；`scheduling` 只保存稳定占用引用，不产生制品和生产事实。普通发货和售后交付不保存服务端草稿或提前占用，正式交付命令直接锁定符合条件的生产来源并原子消费。只有核验、已有订单接管或售后重新加工等有证据的动作，才能形成生产来源。

### 3.2 物理阶段与质量状态分离

物理阶段固定为：

```text
NOT_MADE   尚未制作
MADE       制作完成
BAGGED     捏毛装袋完成
SEAMED     缝边剪袋完成
```

质量状态独立为：

```text
NORMAL
QUALITY_PENDING
REPAIR_REQUIRED
SCRAP_PENDING
SCRAPPED
AFTER_SALES_REWORK
```

系统不维护固定 `READY` 或 `SHIPPABLE` 节点。可交付资格由当前交付约定要求的最低阶段与来源当前阶段动态比较：要求 `MADE` 时 `MADE/BAGGED/SEAMED` 均可满足，要求 `BAGGED` 时 `BAGGED/SEAMED` 可满足，要求 `SEAMED` 时仅 `SEAMED` 满足；同时还必须质量为 `NORMAL`、未冻结且来源可用余额大于零。质量待判断不能提前恢复制作缺口，也不能形成可交付来源。

### 3.3 固定路线

每个交付约定组在确认时冻结路线快照。首期只支持：

```text
NOT_MADE → MADE → BAGGED → [SEAMED]
```

`SEAMED` 是否存在由冻结路线决定，不能由当前商品主数据回读改变。包装还原只允许 `BAGGED → MADE` 或 `SEAMED → MADE`；首期不支持 `SEAMED → BAGGED`。已经消费、报废或处于不可还原状态的数量不能被账面还原。

### 4.1 统一字段规则

除专项字段外，所有表遵守公共基础文档的类型和时间规则：

```text
内部 id              BIGINT，不对外暴露
稳定 business_id     VARCHAR(64)，创建后不可变
数量                 BIGINT + CHECK(value >= 0)，按业务单位保存，不允许隐式小数
当前实体乐观版本     BIGINT + CHECK(version >= 0)，创建固定为 0，每次成功修改加一；快照版本另从 1 单调递增
业务发生时间         occurred_at，表示事实发生时间
系统记录时间         created_at / updated_at，表示系统写入时间
操作者               actor_business_id，引用平台认证上下文中的稳定标识
```

事实表的业务字段不可更新；只能追加更正、冲销、取消或失效关系。投影表只允许更新当前值、版本和维护时间，不能被人工直接改成目标数字。

本章各表代码块列出最终业务字段；每表另含 `id BIGINT PRIMARY KEY`，并按 4.1 补齐对应实体、事实或投影公共字段。除明确标注“可空”外均为 `NOT NULL`，不得在 Flyway 中增加未登记业务列。

### 4.2 `production_demand_projections`

最终业务字段如下（另加 4.1 公共字段）：

```text
demand_business_id
demand_type = MAKE | BAGGING | SEAMING | REPAIR
source_business_type = ORDER | AFTER_SALES | LEGACY_INTAKE | REPAIR
source_business_id
agreement_group_business_id
parent_demand_business_id（可空）
route_snapshot_owner_module = orders
route_snapshot_type = DELIVERY_AGREEMENT
route_snapshot_business_id
route_snapshot_version
target_stage = MADE | BAGGED | SEAMED
required_quantity
reserved_quantity
verified_quantity
qualified_quantity
consumed_quantity
open_quantity
blocked_quantity
schedulable_quantity
```

约束：

- `UNIQUE(source_business_type, source_business_id, agreement_group_business_id, demand_type)`；
- `verified_quantity >= qualified_quantity >= consumed_quantity >= 0`；
- 当前有效 `required_quantity` 已经包含订单变更、售后义务、接管和更正事实的净效果，不直接用当前订单行覆盖；
- `open_quantity = required_quantity - qualified_quantity`；
- `schedulable_quantity = open_quantity - reserved_quantity - blocked_quantity`，且不得小于零；
- `reserved_quantity` 只能由活动 `task_source_reservations` 汇总得到，不能由排班传入目标值；
- `MAKE` 没有父需求；`BAGGING`、`SEAMING` 和 `REPAIR` 必须引用可追溯的上游需求、来源或问题事实；
- 已形成生产事实的数量不因订单变更直接删除，只能形成新的有效需求或缺口调整事实。

### 4.4 `task_source_reservations`

最终业务字段如下（另加 4.1 公共字段）：

```text
reservation_business_id
task_business_id
source_pool_type = NORMAL_DEMAND | PACKAGING_DEMAND | REPAIR_POOL
source_pool_business_id
reserved_quantity
status = ACTIVE | RELEASED | CONSUMED | CANCELLED
active_unique_key
origin_operation_id
released_fact_id（可空）
consumed_fact_id（可空）
```

约束：

- 同一个活动占用关系使用稳定 `reservation_business_id`；
- `ACTIVE` 状态下 `reserved_quantity > 0`；
- `active_unique_key` 在活动状态下由任务、来源池和用途确定，非活动状态使用自身 `reservation_business_id`，并建立唯一约束，避免依赖可空列唯一性；
- 同一任务、同一来源池不能存在重复活动占用；
- 释放、消费和取消必须保留原占用行和状态转换记录，不能物理删除；
- 该表占用的是“待加工需求池”，不是已经形成的可交付生产来源；正式交付只在提交命令时直接锁定并消费生产来源。

## 5. 数量与来源分配规则

### 5.1 需求缺口

生产缺口由生产侧投影根据有效需求和合格完成数量计算；已消费数量只描述合格来源的后续去向，不直接重新打开需求。报废、退回重做或退出履约需要改变缺口时，必须先追加明确的需求调整、质量处置或售后义务事实，再更新 `required_quantity` 或 `qualified_quantity` 的有效汇总。缺口调整必须带有来源操作标识和原因：订单确认、订单变更、售后义务、接管、更正、报废或退出履约。

### 5.2 排班来源池占用

`scheduling` 创建或调整任务时只能提交生产需求/修复池标识、任务标识、工序和请求数量。`production` 在自己的事务锁内：

1. 锁定生产需求投影或修复池投影；
2. 根据任务工序选择 `NORMAL_DEMAND`、`PACKAGING_DEMAND` 或 `REPAIR_POOL`；
3. 在锁内按 `schedulable_quantity = open_quantity - reserved_quantity - blocked_quantity` 重算未占用可排余额，并校验路线兼容性；
4. 写入 `task_source_reservations` 并更新对应需求池/修复池占用数量；
5. 返回占用标识、实际占用数量和新的生产版本。

排班不能把自己的“可排余额”传给生产模块。这里的来源池是待加工数量来源，不是已核验形成的发货来源。

### 5.3 发货来源分配算法

发货调用可以显式传入经过订单冻结快照确定的 `sourceSelection`，也可以请求生产模块自动分配。

自动分配固定为：

1. 仅筛选同一交付约定组、当前阶段满足交付约定最低阶段、质量为 `NORMAL` 且没有冻结的来源；
2. 业务候选排序使用 `available_since_at ASC, source_business_id ASC`，保证同一数据集结果稳定；
3. 实际获取行锁时按 `source_business_id ASC`，避免候选排序造成交叉锁顺序；
4. 从最早可交付来源开始分配，最后一个来源允许部分消费；
5. 任一来源版本、归属、资格或可用量发生变化时整体失败，不部分提交；
6. 返回来源消费明细、实际数量和来源版本，不返回可被调用方回写的余额。

显式来源选择必须满足同一交付约定、来源归属、用途和资格校验；客户端不能借此跨订单或跨路线领用来源。

## 6. 公开应用命令与参与端口

### 6.1 需求与占用端口

```java
interface ProductionDemandPort {

interface ProductionTaskReservationPort {
    TaskSourceReservation reserveForTask(ReserveTaskSource command);
    TaskSourceReservationAdjustment replaceTaskReservation(ReplaceTaskSourceReservation command);
    TaskSourceReservationRelease releaseTaskReservation(ReleaseTaskReservation command);
}
```

`ProductionDemandPort` 由 `production` 提供并拥有接口与 DTO，`docs/历史文档/02-模块设计/02-订单模块.md` 只登记调用方依赖，双方签名必须一致。`applyOrderChange` 只允许处理影响评估声明没有排班任务的变更；生产锁内仍必须确认目标需求范围不存在活动 `task_source_reservations`。同时影响排班和生产时必须改用 `FulfillmentOrderChangeCoordinationPort`。输入必须包含业务来源、需求标识、请求数量、`operationId`、操作者和 `expectedResourceVersions` 中的 production 版本。输出固定返回需求版本、来源占用明细和执行标识。

### 6.2 核验端口

```java
ProductionVerificationPort.verifyTask(VerifyTaskCommand command)
ProductionVerificationPort.correctVerification(CorrectVerificationCommand command)
```

`verifyTask` 接收排班在锁内确认的任务稳定标识、任务来源占用标识、计划数量、结果分桶、production 自有执行主体类型、执行主体稳定标识、执行主体 `SnapshotPointer`、工作量评估 `SnapshotPointer` 和核验发生时间。调用方负责把领域专用 Ref 解包为结构指针，生产在边界重验固定 owner/type。生产模块不得反向依赖或查询 `scheduling`、`master-data`；它只保存这些引用和共同产出事实，不复制员工或小组成员载荷。生产只校验自己拥有的需求池/修复池占用、生产版本、路线和数量守恒，不接受调用方直接传入的目标生产投影。成功结果必须返回稳定的 `ProductionVerificationFactRef` 和必要来源事实引用，供命令所有者继续调用 `cost-ledger.CostRecognitionParticipantPort`；production 本身不依赖或编排 cost-ledger。

`ShipmentSourcePort` 由 `production` 提供并拥有接口与 DTO，`docs/历史文档/02-模块设计/02-订单模块.md` 只登记调用方依赖，双方签名必须一致；`consume` 只能由 `orders` 或售后交付编排调用。两类协调参与端口只允许 `fulfillment-coordination` 在已有事务中调用：第一阶段重新解析并锁定完整生产范围，第二阶段只操作同一 `PreparedProductionScope` 指纹对应的已锁定需求、来源、占用和状态，不得补锁新业务行。包装还原和质量处置如果影响未核验任务，必须分别从 `PackagingRestorationCoordinationPort`、`QualityDispositionCoordinationPort` 进入，不提供生产到排班的反向调用。

## 7. 状态迁移和事实规则

### 7.1 允许的物理阶段迁移

```text
NOT_MADE → MADE
MADE → BAGGED
BAGGED → SEAMED         仅路线包含缝边
BAGGED → MADE           仅包装还原协调命令
SEAMED → MADE           仅包装还原协调命令
```

已经消费、报废、冻结或质量待判断的数量不能参与新的包装加工或交付。首期禁止 `SEAMED → BAGGED`。每次迁移必须追加对应事实，并在同一事务更新 `product_state_projections`。

### 7.2 核验结果

```text
QUALIFIED       形成合格生产来源
REPAIR_REQUIRED 进入修复池，不形成可发货来源
SCRAPPED        形成报废事实并减少可恢复数量
INCOMPLETE      恢复对应有效需求缺口，不形成来源
```

核验结果按数量分桶，分桶数量之和必须等于本次核验实际数量。生产模块拒绝负数、重复提交、超出任务占用或已核验数量的结果。

### 7.3 责任与处置

责任判定是独立事实，不等于执行人。执行员工、修复员工和责任员工分别保存。责任错误通过 `responsibility_corrections` 追加，不覆盖原判定；工资和成本模块只能读取生产公开结果，不能修改生产责任事实。

## 8. 事务矩阵

| 命令 | 命令所有者 | 参与模块 | 生产写入 | 事务边界 |
|---|---|---|---|---|
| 初始化订单制作需求 | `orders` | `production` | 需求事实/投影、路线快照引用 | `REQUIRED` + 生产端口 `MANDATORY` |
| 创建/取消排班 | `scheduling` | `production` | 任务池占用/释放事实和投影 | `REQUIRED` + 生产端口 `MANDATORY` |
| 排班核验 | `scheduling` | `production`、`cost-ledger` | production 写核验、阶段、质量、来源和需求投影；cost-ledger 写归集事实 | `REQUIRED` + 两个参与端口 `MANDATORY` |
| 普通发货 | `orders` | `production` | 直接锁定并消费来源、追加来源消费事实并更新来源投影 | `REQUIRED` + 生产端口 `MANDATORY` |
| 包装还原 | `fulfillment-coordination` | `scheduling`、`production` | 还原、占用释放、阶段和需求调整 | 一个 REQUIRED 事务 |
| 质量处置/报废 | `fulfillment-coordination` | `scheduling`、`production` | 处置、责任、修复池和来源调整 | 一个 REQUIRED 事务 |
| 售后退回接收 | `after-sales` | `production` | 退回实物和质量待判断状态 | `REQUIRED` + 生产端口 `MANDATORY` |

所有参与端口不得自行开启新事务，不得吞掉业务拒绝或并发异常。

## 9. 锁定顺序、索引和并发

### 9.1 生产模块内锁序

在满足全局模块顺序后，生产模块统一使用：

```text
production_demand_projections
→ product_state_projections
→ production_source_projections
→ task_source_reservations
→ 追加事实
→ 更新投影
```

批量对象先解析稳定业务标识，再按各表内部主键升序锁定。发货来源分配和排班来源占用不能一边按业务优先级、一边按数据库顺序交叉取锁。

### 9.2 必要索引

```text
UNIQUE(demand_business_id)
UNIQUE(source_business_id)
UNIQUE(active_unique_key)
INDEX(agreement_group_business_id, eligibility_status, available_since_at, source_business_id)
INDEX(origin_demand_business_id, eligibility_status, available_since_at, source_business_id)
INDEX(task_business_id, status, source_pool_business_id)
INDEX(route_snapshot_owner_module, route_snapshot_type, route_snapshot_business_id, route_snapshot_version, physical_stage, quality_status)
```

`active_unique_key` 在活动状态下由业务作用域生成，失效后改为包含自身稳定标识的历史键，避免依赖 MySQL 对 `NULL` 唯一性的偶然行为。

### 9.3 并发失败

生产端口遇到版本变化、锁等待超时、死锁、唯一约束冲突或影响行数不符合预期时整体失败。只有命令边界在幂等安全的情况下允许有限重试；参与端口不能静默重试或把失败降级为部分成功。

## 10. 幂等、错误码和权限

### 10.1 幂等

- 外部请求幂等由 `platform` 保存；
- 生产端口使用 `operationId` 记录本次参与结果；
- 领域唯一约束防止同一任务核验、同一来源消费和同一占用重复生效；
- 重试必须复用原 `operationId`，不能生成新的业务事实。

## 11. 投影重建

生产投影的权威输入为：

```text
production_demand_projections  ← 有效需求事实、订单/售后快照引用和更正链
product_state_projections      ← 数量事实、加工事实、质量处置和还原事实
production_source_projections  ← 来源形成事实、占用/释放事实、消费事实和更正链
repair_pools                   ← 修复事实、修复结果和有效需求事实
```

历史业务投影不得读取当前商品主数据替代历史路线快照引用。需要历史内容时通过快照所有者的批量查询接口解析，不能复制或直接查询对方快照表。重建按 `demand_business_id`、`agreement_group_business_id`、`source_business_id` 或明确批次执行，先在临时结果中计算，再使用版本校验原子替换。

## 12. 验证门禁
