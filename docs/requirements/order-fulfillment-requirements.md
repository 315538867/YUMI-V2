# YUMI V2 首期需求基线

## 1. 文档定位

本文是 YUMI V2 首期“订单履约闭环”的正式需求基线。它描述要解决的业务问题、已确认规则、范围边界和验收口径，不规定具体表结构或代码组织。

YUMI V2 是绿地重建，不迁移旧 SQLite 数据，不兼容旧页面、旧 IPC 或旧表结构。旧 `/Volumes/code/YUMI` 仅用于核实仍适用的业务规则和测试场景。

## 2. 首期目标

管理员在同一套联网系统中完成：

1. 维护商品、客户和员工基础资料；
2. 创建并确认订单，冻结客户、商品、价格、成本、数量和流程快照；
3. 使用现有库存或安排生产计划；
4. 按制作、捏毛装袋、缝边剪袋逐工序核验；
5. 管理返工、报废重做、超额任务和其他排班；
6. 从订单可发货数量登记分批发货；
7. 登记收款、退款和订单变更；
8. 关闭已经完成履约且款项结清的订单；
9. 对已确认发货批次中的已发商品独立处理退回、返工、报废、免费补发和退款；剩余订单需求可并行履约。

## 3. 使用者与权限

首期只有管理员账号登录。管理员负责建档、订单确认、库存操作、排班、核验、发货、收退款和售后。

员工仅作为业务档案和执行人员，不登录系统。管理员参与实际生产时，管理员账号仍与员工档案分离：账号表示操作人，员工档案表示执行人。

首期不实现员工账号、角色管理、员工自助报工、二维码临时访问或复杂权限配置，但所有写操作必须记录当前管理员。

## 4. 核心业务对象

- 商品：标准属性、星级、成本参数、默认销售价格和缝边参数。
- 客户：客户资料和一组默认收货信息。
- 员工：人员资料、在职状态和可安排工作类型。
- 订单：围绕订单生命周期管理订单与明细、确认快照、订单变更、履约台账、发货、收退款、售后和关闭。
- 订单商品明细：商品快照、数量、价格、缝边数量、成本快照、冻结流程及独立履约生命周期。
- 订单变更单：已确认订单的结构、数量、价格、交期和收货信息变更。
- 发货批次：订单模块内的分批交付事实及确认快照。
- 收款与退款：订单模块内不可覆盖的资金事实。
- 售后单：订单模块内对已确认发货批次中已发商品的退回、返工、报废、免费补发和退款处理，使用独立台账，不改变订单主状态。
- 库存批次与库存流水：独立库存及不可修改的出入库事实。
- 生产计划与核验：日期、员工、订单明细、工序、数量和一次性核验结果。

发货、收退款、售后和履约台账属于订单模块。它们可以使用独立数据库表，但不是与订单并列的顶级业务模块。库存和生产保持独立模块，通过明确业务命令与订单模块协作。

## 5. 商品与金额

商品编号为 `P00001` 格式。商品支持启用和停用，历史订单不受商品后续修改影响。

商品星级为一星至五星，用于带出标准制作时长和制品人工费；商品星级不映射员工星级。商品保存材料、人工、其他成本和计算快照。缝边人工成本独立保存，不计入商品基础单件总成本。

金额和比例计算必须使用十进制定点或高精度小数，内部统一保留 4 位小数。服务端使用 Java `BigDecimal` 产生权威结果，API 以字符串传输金额；客户端不得使用二进制浮点计算结果覆盖服务端金额。

订单金额：

```text
商品金额 = 商品数量 × 商品成交单价
缝边服务金额 = 缝边数量 × 缝边成交单价
订单原始金额 = 商品金额合计 + 缝边服务金额合计
订单应收金额 = 订单原始金额 - 整单优惠金额
订单预计利润 = 订单应收金额 - 订单总成本
```

## 6. 订单生命周期

订单主状态：草稿、已确认、已取消、已关闭。

- 草稿可编辑，不能收款、排产或产生正式库存流水。
- 确认时完成全部校验并原子冻结订单及明细快照；确认不自动创建生产计划。
- 已确认订单不能直接改写，变化必须通过订单变更单。
- 已取消和已关闭为互斥终态，不能互相转换。
- 已关闭订单不重开，后续问题通过更正、退款或售后处理。

订单只有同时满足以下条件才能关闭：

1. 当前有效客户需求全部有效发货，或剩余需求已通过订单变更明确取消；
2. 当前有效应收金额已经结清；
3. 不存在未处理的应收差额或待退款金额。

生产报废、成品余量和生产处理完成本身不等于客户需求完成。报废或转余量的数量必须通过订单变更从当前有效需求中取消，才能支持订单关闭。

## 7. 数量与工序

订单商品数量是一份共同需求，不同工序是同一批商品的阶段进度，不能相加。

```text
不缝边：制作 → 捏毛装袋 → 可发货
缝边：制作 → 捏毛装袋 → 缝边剪袋 → 可发货
```

同一明细在捏毛装袋合格后，按冻结的缝边数量分流。打包不是逐件生产工序，归入“其他排班”。

每道工序维护计划、完成、合格、返工、报废、未完成、等待上游和当前可执行数量。所有汇总来自生产、库存、订单变更和发货事实，不允许手工覆盖。

生产计划一次性核验：

```text
本次完成数量 = 合格数量 + 返工数量 + 报废数量
未完成数量 = 计划数量 - 本次完成数量
```

返工、报废重做和超额任务不增加订单数量。

## 8. 库存

库存独立存在，不绑定目标订单。库存范围包括期初库存、工序合格库存、订单余量库存和人工盘点调整。

库存批次保存来源、商品、已完成工序、缝边状态和当前数量。库存当前数量由不可修改的库存流水汇总，不允许直接覆盖。

订单通过库存领用流水使用库存：

- 制作合格库存接入捏毛装袋；
- 捏毛装袋合格库存接入可发货或缝边剪袋；
- 缝边剪袋合格库存接入可发货。

库存领用时扣减原库存；正式发货只消耗订单明细可发货数量，不再次扣减原库存。取消领用使用反向流水。已经进入后续生产、质检或发货的领用不得直接取消。

## 9. 生产计划与排班

排班分为生产和其他两类。

生产计划关联订单商品明细、工序、计划日期、执行员工和计划数量。允许提前安排等待上游的下游计划，但创建计划不代表上游完成，也不产生生产或库存事实。

计划状态：待执行、已核验、已取消。已核验计划不可修改或再次核验。

计划类型至少包括：正常生产、返工、报废重做、超额任务、售后返工、售后补发。

超额任务由负责人根据线下沟通直接创建，不设申请审核流程。它只预占未来正常计划中的可选数量，避免重复选择；不自动修改未来计划数量，核验后仅产生调整提醒。

其他排班用于打包和杂活，仅核验小时和分钟，不产生商品数量、库存或订单履约事实。

## 10. 发货

发货批次状态：草稿、已确认、已作废。

草稿不产生履约事实。确认时校验订单状态、未发货数量和订单明细可发货数量，成功后消耗可发货数量并增加累计有效发货数量。

已确认发货批次不可直接编辑。物流公司、物流单号、运费和发货备注通过独立物流修改记录留痕。业务数据导出不包含物流字段；浏览器打印和 PDF 可展示当前有效物流信息。

已有有效售后引用的发货批次不得直接作废或使其售后来源失效；须先处理售后关联。已关闭订单的发货批次原则上不能直接作废。确需更正时，必须在同一业务操作中完成原批次失效和等量替代发货；不能立即替代时使用售后处理。

## 11. 收退款

收款和退款均保存独立记录，原记录不得删除或修改。

```text
订单结清净额 = 累计订单收款 - 累计订单变更退款
订单待退款金额 = max(累计订单收款 - 当前有效应收金额 - 累计订单变更退款, 0)
累计实际净收 = 累计订单收款 - 累计订单变更退款 - 累计售后退款
```

草稿不能收款。订单变更导致超收时产生订单待退款提示；待退款未处理前不能关闭订单。退款必须标明来源：订单变更退款用于订单结清与待退款判定，售后退款必须关联售后单并单列展示，不冲减订单结清净额或使订单重新欠款。退款累计不得超过累计订单收款；已关闭订单不因售后退款重开。

## 12. 售后

售后从发货批次确认后开放，只能针对该批次已发的商品明细创建；发货草稿、已作废批次和未发商品不得作为售后来源。同一批次明细的有效售后受理数量不得超过其有效已发数量扣除其他售后已占用数量。订单仍为已确认且尚有未发需求时，已发部分售后与剩余需求的生产、发货并行。

售后使用独立台账，不改变原订单订购数量、累计有效发货数量、未交付需求、有效应收或主状态；已关闭订单也不重开。作废或更正已被售后引用的原发货批次时，必须先处理售后来源与占用关系，不得留下无效来源。

退回商品核验满足：

```text
客户退回数量 = 返工数量 + 报废数量
```

退回品不自动入库、不恢复原发货库存。返工进入售后返工计划；报废只保留事实。免费补发优先使用兼容库存，缺口进入售后补发生产计划。

库存领用或生产合格只增加售后可补发数量；只有补发发货批次确认后才增加售后已补发数量。

首期售后只允许退款或免费补发，不处理补差价或售后补收款。

## 13. 首期明确不做

- 旧数据迁移和旧架构兼容；
- 离线录入、同步队列和冲突合并；
- 员工登录和复杂角色权限；
- 原材料库存；
- 自动库存批次合并；
- 复杂盘点任务和审批；
- 在线支付；
- 工资计算、结算、调整和发放；
- 售后补差价；
- 客户多地址簿；
- 复杂报表平台。

## 14. 需求变更原则

正式架构和数据库设计必须引用本基线。后续新增或修改规则时，应先更新需求基线，再评估领域、数据库、接口和测试影响，不允许只修改某一张表或某一个页面。
