## 1. 已确认结论

YUMI V2 后端采用模块化单体：

- Java 21；
- Spring Boot 3.5.x；
- Spring Modulith；
- 单一应用、单一部署单元；
- 单一 MySQL 数据库；
- Flyway 管理数据库结构；
- Spring JDBC、`JdbcClient` 与显式 SQL 作为核心持久化方案；
- 不使用 JPA 作为核心业务持久化方案；
- 模块只能通过公开应用接口或端口交互；
- 所有跨模块能力只能通过提供方公开的应用命令、只读查询或事务参与接口调用；
- 禁止跨模块访问 Entity、内部 Repository、基础设施实现或直接读写其他模块表；
- 跨模块强一致业务动作在同一个 MySQL `@Transactional` 事务中完成；
- `calculation` 是无持久化、无业务模块依赖的纯公式模块；
- 不引入微服务、消息队列、事件溯源框架或通用工作流引擎。

## 2. 后端总体结构

```text
HTTP / 文件导入导出 / 运维入口
                │
                ▼
          模块公开适配层
                │
                ▼
          应用服务与用例编排
                │
      ┌─────────┴─────────┐
      ▼                   ▼
领域规则与模块端口     查询服务与读模型
      │                   │
      └─────────┬─────────┘
                ▼
      模块内部持久化适配层
                │
                ▼
       JdbcClient / 显式 SQL
                │
                ▼
              MySQL
```

系统仍是一个进程。模块划分用于隔离业务所有权、依赖方向、数据库写入权和测试边界，不把进程内调用伪装成远程服务。

## 3. 后端模块

```text
master-data    商品、客户、员工、生产小组、静态数据、商品录入默认值
calculation    纯数值公式、精度和代码化规则版本
orders         订单、交付约定、变更、普通发货、订单资金、完成事实、已有订单接管
production     制品物理阶段、加工历史、质量、责任、处置、来源消费和数量投影
scheduling     正常/修复任务、执行主体、工作量评估快照、生产来源占用引用、取消和核验入口
workforce-coordination  只负责 scheduling 与 master-data 的小组配置变更编排，不拥有业务事实
fulfillment-coordination  只负责 production 与 scheduling 的跨模块事务编排，不拥有业务事实
after-sales    订单完成后的售后案例、义务、退回、重新交付、额外补发、售后金额与完成事实
payroll        工资计算、责任修复、扣款、免扣额度、封账与补差
cost-ledger    经营成本归集、分摊、更正与成本查询
finance        真实现金收入、支出、分配与更正
reporting      跨模块只读查询、对账和经营分析
platform       认证、权限、文件、审计、幂等和请求上下文
```

`workforce-coordination` 与 `fulfillment-coordination` 都是无业务事实的窄应用编排模块，不提供通用 CRUD，也不持有业务表。前者只处理“小组配置变更需要先锁定排班活动引用”的事务，后者只处理同一正式命令同时改变 `production` 与 `scheduling` 的履约事务。协调器只确定入口、事务和锁序，不取得参与模块的数据所有权。

模块所有权以业务事实为准，不按 Controller、Service、Repository 等技术层建立顶级模块。

## 4. 模块内部结构

每个有持久化的业务模块采用相同的内部边界：

```text
com.yumi.<module>
├─ package-info.java
├─ api
│  ├─ application
│  ├─ participant
│  ├─ query
│  ├─ model
│  └─ http
├─ application
│  ├─ command
│  ├─ query
│  └─ port
├─ domain
│  ├─ model
│  ├─ policy
│  └─ service
└─ infrastructure
   ├─ persistence
   └─ integration
```

### 4.1 `api`

`api` 同时承载模块公开 Java 契约和系统边界适配：

- `api.application`：完整业务命令用例；
- `api.participant`：加入既有事务的专用参与端口；
- `api.query`：纯只读查询；
- `api.model`：不可变命令、结果、稳定业务标识和强类型引用；
- `api.http`：接收 HTTP 请求或文件输入、完成协议层校验、提取登录人/请求编号/幂等键，并转换响应。

Spring Modulith 只把 `application`、`participant`、`query`、`model` 声明为 named interface；`api.http` 不作为其他模块 Java 依赖入口。Controller 不写 SQL，不直接调用本模块或其他模块 Repository，不承载数量守恒、状态迁移和金额计算规则。Controller 只能调用本模块公开应用用例；即使目标能力位于同一进程，也不能绕过对方应用边界调用其领域对象或基础设施实现。

### 4.2 `application`

负责业务用例和事务编排：

- 一个命令用例对应一个明确业务动作；
- 锁定需要参与判断的记录；
- 调用本模块领域规则；
- 通过公开端口调用其他模块；
- 写入事实、快照和投影；
- 确保同一事务内全部成功或全部回滚。

应用服务拥有事务边界。领域对象和 Repository 不自行开启新事务。

### 4.3 `domain`

负责不依赖 HTTP、数据库和当前登录上下文的业务规则：

- 数量守恒；
- 状态迁移合法性；
- 交付阶段兼容；
- 事实更正限制；
- 责任、处置和成本承担规则；
- 值对象与领域策略。

纯数值公式统一放在 `calculation`，不在各业务模块复制。业务模块只能调用 `calculation` 的公开计算接口，不能依赖公式实现类，也不能取得参数后在本模块重写等价公式。

### 4.4 `infrastructure`

负责技术实现：

- `JdbcClient` Repository；
- SQL 与行映射；
- 外部适配；
- 模块公开端口的内部适配实现。

对象存储、临时文件生命周期、下载入口和文件内容操作统一由 `platform.infrastructure.file` 承担。业务模块只通过平台公开能力校验临时文件，并保存自己拥有的正式业务关联和可见性语义，不直接持有对象存储路径或实现文件删除。

基础设施代码不得绕过应用层直接暴露给 Controller 或其他模块。

## 5. 模块公开边界

模块对外只暴露以下类型：

- 应用命令接口；
- 只读查询接口；
- 跨模块端口；
- 不可变输入与输出记录；
- 稳定的业务标识和值对象。

模块不得对外暴露：

- 数据库行对象；
- 内部 Repository；
- SQL；
- 内部领域聚合的可变引用；
- 仅为数据库映射存在的字段；
- 本模块表结构。

跨模块调用采用同进程 Java 接口，不使用内部 HTTP，也不为未来可能拆分微服务而提前加入序列化、重试和消息中间件。

### 5.1 能力调用红线

跨模块协作的唯一合法路径是：

```text
调用模块 application
→ 提供模块公开命令 / 查询 / 事务参与接口
→ 提供模块 application
→ 提供模块 domain 与 Repository Port
→ 提供模块 infrastructure
→ 提供模块拥有的数据表
```

稳定业务标识只是跨模块引用，不是底层访问句柄。调用方保存提供方返回的业务标识、不可变结果快照或版本摘要后，仍须通过提供方公开接口查询或变更其业务状态，不能据此读取提供方表、拼接跨模块 SQL 或自行推导提供方当前余额。

公开接口按语义分为：

- **应用命令接口**：由提供方校验并修改自己拥有的事实、快照和投影；
- **只读查询接口**：由提供方解释当前值、标准、资格、可用量或评估结果，不授予修改权；
- **事务参与接口**：在既定跨模块事务和锁序中准备、校验并应用提供方拥有的变更；
- **纯计算接口**：只接收不可变输入并返回带规则版本的结果，不暴露公式实现。

提供方拥有自己的公开契约，提供方 API 不得反向导入调用方的 ID、枚举或 Ref 类型。调用方资源需要进入提供方命令时，只能解包为稳定业务 ID，或 platform 提供的无行为结构值：`BusinessPointer(ownerModule, resourceType, businessId)`、`SnapshotPointer(ownerModule, snapshotType, snapshotBusinessId, version)`、`PreparedScopePointer(preparerModule, coordinationType, scopeBusinessId, scopeFingerprint, validatedAt)`。提供方必须在应用边界重新校验 owner/type、准备者、协调类型和作用域；这些结构值不提供查询、存储、锁定、授权、反射路由或动态服务定位，不能成为绕过提供方接口的访问句柄。

调用方不得复制提供方拥有的当前余额、资格判定、公式规则或快照载荷形成第二权威来源。为了历史解释而需要保留的上游状态，必须保存强类型 `SnapshotRef`；快照内容、版本、查询和保留策略仍由提供方管理。领域专用 Ref 可以包装 `SnapshotPointer` 并校验 owner/type；事实 Ref 可以包装 `BusinessPointer` 并校验 owner/type；直接引用提供方 Ref 会造成模块环时，消费模块可以定义本地领域专用 Ref 包装相同指针，但不得复制载荷或改变所有者语义。调用方只有在形成自己模块语义不同的结果时，才能创建本模块快照，并在其中引用上游快照。

## 6. 依赖方向

### 6.1 允许的依赖

```text
api → application → domain
infrastructure → application / domain
业务模块 → calculation 的公开计算接口
业务模块 → platform 的公开能力
reporting → 各模块公开查询端口
```

业务模块之间需要协作时，只能调用提供方公开应用接口，或调用经架构文档明确归属的跨模块端口。调用关系不授予数据所有权，也不允许调用提供方未公开的领域服务、实现类或持久化适配器。

`workforce-coordination` 只允许依赖 `scheduling.WorkTeamPlanReferenceGuardPort` 与 `master-data.WorkTeamMutationParticipantPort`；小组名称、成员或状态的正式变更由它发起，先锁排班引用守卫，再修改主数据。`scheduling` 可以单向调用 `master-data` 的公开只读查询接口，`master-data` 不得反向依赖 `scheduling`。

`fulfillment-coordination` 只允许依赖 `production` 与 `scheduling` 的公开参与端口；当前已登记调用方为 `orders` 和生产业务 HTTP 适配层。`scheduling` 可以单向调用 `production` 的排班占用和核验参与端口；`production` 不得调用 `scheduling`，也不得依赖 `fulfillment-coordination`。需要由生产动作同时改变排班任务时，必须从协调器入口完成，不能从 `production` 反向编排。`after-sales` 首期拥有案例、义务、交付和结算决定，但创建或取消售后排班任务仍调用 `scheduling` 的完整命令能力；未来若一个售后动作需要同时修改既有排班与生产，必须先登记具名协调用例，不能复用未登记的通用入口。

顶级模块依赖图必须保持无环；任何新增依赖都必须先通过 Spring Modulith/ArchUnit 结构测试和事务矩阵评审。

### 6.2 禁止的依赖

```text
Controller → Repository
模块 A → 模块 B 的 infrastructure
模块 A → 模块 B 未公开的 application / domain 实现类
模块 A → 模块 B 的数据库行模型
模块 A Repository → 模块 B 的表
模块 A SQL → JOIN / UPDATE / INSERT 模块 B 的表
模块 A → 复制模块 B 的公式、资格判定或余额规则
production → scheduling
master-data → scheduling
master-data → workforce-coordination
生产模块 → fulfillment-coordination
scheduling → fulfillment-coordination
calculation → 任意业务模块
业务模块 → reporting
```

通过 Spring Modulith、ArchUnit/包可见性、Repository 表所有权检查和 SQL 静态扫描持续验证模块边界。结构测试至少拒绝跨模块基础设施依赖、内部实现类依赖、跨模块 Repository 依赖和跨模块业务表 SQL。

## 7. 持久化架构

### 7.1 核心选择

核心持久化使用：

```text
Spring JDBC
+ JdbcClient
+ 显式 SQL
+ 明确的行映射
+ 明确的事务锁
```

不使用 JPA 的自动脏检查、级联保存和延迟加载表达核心业务写入。

### 7.2 选择依据

目标业务大量包含：

- 不可变事实追加；
- 追加式更正；
- 数量守恒；
- 来源余额占用；
- `SELECT ... FOR UPDATE`；
- 批量数量流转；
- 事实、快照和当前投影同步更新；
- 跨多个模块的同事务写入；
- 面向工作台的组合查询。

显式 SQL 使锁定顺序、写入范围、条件更新和实际受影响行数可审计，避免 ORM 隐式行为改变业务语义。

### 7.3 Repository 职责

写 Repository 只负责本模块表，并提供贴近应用用例的最小操作，例如：

```text
lockOrder(orderId)
appendAgreementVersion(...)
lockDemandProjection(demandId)
reserveQuantity(...)
appendVerificationFact(...)
updateCurrentProjection(...)
```

Repository 不负责：

- 跨模块业务编排；
- 自动计算业务金额；
- 隐式保存对象图；
- 在读取方法中产生业务写入；
- 返回可被任意修改后整体回存的数据库实体。

### 7.4 行模型、领域模型和接口模型

三者分开：

- 行模型对应 SQL 查询结果，仅在持久化适配层使用；
- 领域模型表达规则和值，不要求与表一一对应；
- 接口模型表达公开契约，不泄露数据库列。

简单主数据允许直接从行模型映射为公开只读视图，但写入仍必须经过应用用例。

### 7.5 查询持久化

命令侧与查询侧共享一个 MySQL，不建设独立 CQRS 基础设施。

查询服务可以：

- 使用专门 SQL 连接本模块拥有的事实和投影；
- 返回面向业务页面或报表的不可变读模型；
- 避免为了复用写模型而进行多次逐行查询。

跨模块查询由 `reporting` 或业务工作台所属模块通过公开查询端口组合，不直接联表读取其他模块表。首期高频报表投影、水位和重建范围由 `docs/02-模块设计/12-报表模块详细设计.md` 冻结。

## 8. 数据所有权

每张业务表只有一个写入模块。表位于同一数据库不代表可以跨模块直接访问。

```text
模块所有权
= 定义表结构
+ 执行业务写入
+ 维护表内不变量
+ 提供公开查询或应用能力
+ 负责更正和迁移语义
```

外键可以用于模块内部强约束。跨模块是否使用物理外键需要在数据库设计阶段逐项判断，但无论是否存在物理外键，都不能替代模块公开接口和应用校验。

## 9. 事实、快照与投影

后端必须区分：

- **事实**：已经发生且不可覆盖的业务记录；
- **快照**：业务确认时冻结的标准、约定和金额口径；
- **投影**：为当前判断和查询维护的可更新结果。

典型写入顺序：

```text
锁定当前业务记录与投影
→ 校验命令前置条件
→ 计算本次事实和差额
→ 追加事实
→ 更新当前投影
→ 写入审计与幂等结果
→ 提交事务
```

投影不是事实来源。投影值出现错误时，必须按业务根或受控批次依据有效事实、更正链和历史快照引用重建：先生成影子结果并记录来源水位，再与当前投影核对；无差异时以单事务切换水位和投影版本，有差异时保留当前投影并输出差异记录。在线重建不得跨模块读表，输入只能来自本模块事实或提供方公开批量查询。

快照遵循“定义者拥有、消费者引用”的单一所有者规则：

```text
快照所有者
= 定义语义与结构
+ 创建和版本化
+ 持久化与保留
+ 提供领域专用查询和批量查询

消费模块
= 只保存 SnapshotRef
+ 只保存本模块事实或计算结果
+ 通过所有者公开接口解析历史内容
```

`SnapshotRef` 固定包含 `ownerModule`、`snapshotType`、`snapshotBusinessId` 和 `snapshotVersion` 四个字段；四者均非空，版本必须大于零。消费模块不得复制上游快照载荷，不得直接访问上游快照表、Repository 或 Entity。系统不建设全局通用快照中心；下游模块如果形成语义不同的新快照，只能拥有自己的新结果并引用上游快照。

## 10. 事务架构

### 10.1 事务边界

事务由最外层应用命令用例开启。跨模块同步调用加入同一 Spring 事务，不使用 `REQUIRES_NEW` 切断业务原子性。

示例：

```text
订单确认事务
orders 写订单与交付约定快照
→ production 初始化制作与包装需求投影
→ platform 写审计与幂等结果
→ 一次提交
```

### 10.2 锁定原则

- 先锁业务根记录，再锁明细、来源余额和投影；
- 同类记录按稳定主键顺序锁定；
- 所有余额校验都在锁内重新读取；
- 不以接口提交的派生余额作为判断依据；
- 条件更新必须检查受影响行数；
- 不使用应用内 JVM 锁替代数据库并发控制。

跨模块全局锁序和模块内锁定原则已由模块接口与事务矩阵冻结；各业务用例的具体 SQL 锁定实现、索引命中方式和集成测试覆盖在数据库设计与测试架构中细化。`scheduling` 自己拥有的创建、取消和核验命令可以直接调用已登记的 `production` 参与端口；由 `orders` 或生产业务动作发起、且需要同时改变 `production` 与 `scheduling` 的履约命令必须进入 `fulfillment-coordination`，由协调器按统一锁序调用两个参与端口。任何参与模块都不能在事务中反向回调命令所有者或另一个参与模块。

### 10.3 失败语义

同一业务命令内任一步失败，事实、投影、占用、审计和幂等结果必须整体回滚。禁止捕获异常后提交部分业务结果。

## 11. 公式模块

`calculation`：

- 无数据库表；
- 无 Repository；
- 不依赖业务模块；
- 不读取当前时间、登录人和 Spring Web 上下文；
- 接收不可变输入；
- 返回不可变计算结果；
- 统一金额、比例、数量和舍入精度；
- 使用代码与自动化测试管理公式版本。

业务模块负责取得输入、选择规则版本、调用公式并保存业务快照或结算结果。公式模块不决定业务状态，也不自行持久化结果。

## 12. 数据库迁移

Flyway 是数据库结构的唯一迁移入口。

- 新仓库以目标架构建立新的 `V1` 基线；
- 不复制旧方案已经被否决的表结构；
- 数据库结构、约束、索引和种子数据均由迁移管理；
- 应用启动时校验迁移历史；
- 已进入共享环境的迁移不可改写，后续使用新版本迁移；
- 开发初期是否允许压缩未共享迁移，在正式建立环境策略时确定。

迁移测试至少验证：

- 空库可完整建立；
- 必需表、列、约束和索引存在；
- 静态种子与代码枚举一致；
- 关键唯一约束和数量非负约束有效。

## 13. 后端编码约束

- 金额使用 `BigDecimal`，数据库使用明确精度的 `DECIMAL`；
- 数量使用整数，不使用浮点数；
- 时间按业务含义区分日期、本地业务时间和系统时间戳；
- 业务状态使用明确代码，不用自由文本；
- SQL 参数全部绑定，不拼接用户输入；
- 动态排序和筛选只能从服务端白名单映射；
- 批量命令必须先完整校验，再整体写入；
- 业务事实不提供物理删除接口；
- 录入错误使用明确的取消、失效或更正事实处理。

## 15. 实施关系

完整实施顺序以 `docs/03-实施方案/01-完整系统实施方案.md` 为唯一依据。G0 复核设计一致性；G1 建立工程、模块声明、Flyway、Spring Modulith、ArchUnit、Testcontainers 和 CI 门禁；G2-G12 按提供方先于调用方逐步交付纵向业务闭环；G13-G14 完成迁移、切换、容量、恢复和稳定期。
