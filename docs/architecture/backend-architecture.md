# YUMI V2 后端目标架构

>
> 日期：2026-09-28
>

> 本文只描述后端目标架构，不包含前端技术选型、页面结构和交互设计，也不构成代码实施计划。

## 1. 已确认结论

YUMI V2 后端采用模块化单体：

- Java 21；
- Spring Boot 3.5.x；
- Spring Modulith；
- 单一应用、单一部署单元；
- 单一 MySQL 数据库；
- Flyway 管理数据库结构；
- Spring JDBC、`JdbcClient` 与显式 SQL 作为核心持久化方案；
- 不使用 JPA 作为核心业务持久化方案；
- 模块只能通过公开应用接口或端口交互；
- 禁止跨模块访问 Entity、内部 Repository 或直接读写其他模块表；
- 跨模块强一致业务动作在同一个 MySQL `@Transactional` 事务中完成；
- `calculation` 是无持久化、无业务模块依赖的纯公式模块；
- 不引入微服务、消息队列、事件溯源框架或通用工作流引擎。

## 2. 后端总体结构

```text
HTTP / 文件导入导出 / 运维入口
                │
                ▼
          模块公开适配层
                │
                ▼
          应用服务与用例编排
                │
      ┌─────────┴─────────┐
      ▼                   ▼
领域规则与模块端口     查询服务与读模型
      │                   │
      └─────────┬─────────┘
                ▼
      模块内部持久化适配层
                │
                ▼
       JdbcClient / 显式 SQL
                │
                ▼
              MySQL
```

系统仍是一个进程。模块划分用于隔离业务所有权、依赖方向、数据库写入权和测试边界，不把进程内调用伪装成远程服务。

## 3. 后端模块

```text
master-data    商品、客户、员工、静态数据、全局设置
calculation    纯数值公式、精度和代码化规则版本
orders         订单、交付约定、变更、普通发货、订单资金、完成事实、已有订单接管
production     制品物理阶段、加工历史、质量、责任、处置、来源消费和数量投影
scheduling     正常/修复任务、数量占用、产能分配、取消和核验入口
after-sales    订单完成后的售后案例、义务、退回、重新交付、额外补发、售后金额与完成事实
payroll        工资计算、责任修复、扣款、免扣额度、封账与补差
cost-ledger    经营成本归集、分摊、更正与成本查询
finance        真实现金收入、支出、分配与更正
reporting      跨模块只读查询、对账和经营分析
platform       认证、权限、文件、审计、幂等和请求上下文
```

模块所有权以业务事实为准，不按 Controller、Service、Repository 等技术层建立顶级模块。

## 4. 模块内部结构

每个有持久化的业务模块采用相同的内部边界：

```text
com.yumi.<module>
├─ package-info.java
├─ api
│  ├─ http
│  └─ model
├─ application
│  ├─ command
│  ├─ query
│  └─ port
├─ domain
│  ├─ model
│  ├─ policy
│  └─ service
└─ infrastructure
   ├─ persistence
   └─ integration
```

### 4.1 `api`

负责系统边界适配：

- 接收 HTTP 请求或文件输入；
- 完成协议层格式校验；
- 提取登录人、请求编号和幂等键；
- 调用应用用例；
- 把应用结果转换为公开响应模型。

Controller 不写 SQL，不直接调用其他模块 Repository，不承载数量守恒、状态迁移和金额计算规则。

### 4.2 `application`

负责业务用例和事务编排：

- 一个命令用例对应一个明确业务动作；
- 锁定需要参与判断的记录；
- 调用本模块领域规则；
- 通过公开端口调用其他模块；
- 写入事实、快照和投影；
- 确保同一事务内全部成功或全部回滚。

应用服务拥有事务边界。领域对象和 Repository 不自行开启新事务。

### 4.3 `domain`

负责不依赖 HTTP、数据库和当前登录上下文的业务规则：

- 数量守恒；
- 状态迁移合法性；
- 交付阶段兼容；
- 事实更正限制；
- 责任、处置和成本承担规则；
- 值对象与领域策略。

纯数值公式统一放在 `calculation`，不在各业务模块复制。

### 4.4 `infrastructure`

负责技术实现：

- `JdbcClient` Repository；
- SQL 与行映射；
- 外部适配；
- 模块公开端口的内部适配实现。

对象存储、临时文件生命周期、下载入口和文件内容操作统一由 `platform.infrastructure.file` 承担。业务模块只通过平台公开能力校验临时文件，并保存自己拥有的正式业务关联和可见性语义，不直接持有对象存储路径或实现文件删除。

基础设施代码不得绕过应用层直接暴露给 Controller 或其他模块。

## 5. 模块公开边界

模块对外只暴露以下类型：

- 应用命令接口；
- 只读查询接口；
- 跨模块端口；
- 不可变输入与输出记录；
- 稳定的业务标识和值对象。

模块不得对外暴露：

- 数据库行对象；
- 内部 Repository；
- SQL；
- 内部领域聚合的可变引用；
- 仅为数据库映射存在的字段；
- 本模块表结构。

跨模块调用采用同进程 Java 接口，不使用内部 HTTP，也不为未来可能拆分微服务而提前加入序列化、重试和消息中间件。

## 6. 依赖方向

### 6.1 允许的依赖

```text
api → application → domain
infrastructure → application / domain
业务模块 → calculation
业务模块 → platform 的公开能力
reporting → 各模块公开查询端口
```

业务模块之间需要协作时，调用对方公开应用接口或由本模块定义、对方适配的端口。调用关系不授予数据所有权。

### 6.2 禁止的依赖

```text
Controller → Repository
模块 A → 模块 B 的 infrastructure
模块 A → 模块 B 的数据库行模型
模块 A Repository → 模块 B 的表
calculation → 任意业务模块
业务模块 → reporting
```

通过 Spring Modulith 结构测试和包可见性约束持续验证模块边界。

## 7. 持久化架构

### 7.1 核心选择

核心持久化使用：

```text
Spring JDBC
+ JdbcClient
+ 显式 SQL
+ 明确的行映射
+ 明确的事务锁
```

不使用 JPA 的自动脏检查、级联保存和延迟加载表达核心业务写入。

### 7.2 选择依据

目标业务大量包含：

- 不可变事实追加；
- 追加式更正；
- 数量守恒；
- 来源余额占用；
- `SELECT ... FOR UPDATE`；
- 批量数量流转；
- 事实、快照和当前投影同步更新；
- 跨多个模块的同事务写入；
- 面向工作台的组合查询。

显式 SQL 使锁定顺序、写入范围、条件更新和实际受影响行数可审计，避免 ORM 隐式行为改变业务语义。

### 7.3 Repository 职责

写 Repository 只负责本模块表，并提供贴近应用用例的最小操作，例如：

```text
lockOrder(orderId)
appendAgreementVersion(...)
lockDemandProjection(demandId)
reserveQuantity(...)
appendVerificationFact(...)
updateCurrentProjection(...)
```

Repository 不负责：

- 跨模块业务编排；
- 自动计算业务金额；
- 隐式保存对象图；
- 在读取方法中产生业务写入；
- 返回可被任意修改后整体回存的数据库实体。

### 7.4 行模型、领域模型和接口模型

三者分开：

- 行模型对应 SQL 查询结果，仅在持久化适配层使用；
- 领域模型表达规则和值，不要求与表一一对应；
- 接口模型表达公开契约，不泄露数据库列。

简单主数据允许直接从行模型映射为公开只读视图，但写入仍必须经过应用用例。

### 7.5 查询持久化

命令侧与查询侧共享一个 MySQL，不建设独立 CQRS 基础设施。

查询服务可以：

- 使用专门 SQL 连接本模块拥有的事实和投影；
- 返回面向业务页面或报表的不可变读模型；
- 避免为了复用写模型而进行多次逐行查询。

跨模块查询由 `reporting` 或业务工作台所属模块通过公开查询端口组合，不直接联表读取其他模块表。是否为特定高频跨模块报表建立独立投影，后续在数据与投影架构中确定。

## 8. 数据所有权

每张业务表只有一个写入模块。表位于同一数据库不代表可以跨模块直接访问。

```text
模块所有权
= 定义表结构
+ 执行业务写入
+ 维护表内不变量
+ 提供公开查询或应用能力
+ 负责更正和迁移语义
```

外键可以用于模块内部强约束。跨模块是否使用物理外键需要在数据库设计阶段逐项判断，但无论是否存在物理外键，都不能替代模块公开接口和应用校验。

## 9. 事实、快照与投影

后端必须区分：

- **事实**：已经发生且不可覆盖的业务记录；
- **快照**：业务确认时冻结的标准、约定和金额口径；
- **投影**：为当前判断和查询维护的可更新结果。

典型写入顺序：

```text
锁定当前业务记录与投影
→ 校验命令前置条件
→ 计算本次事实和差额
→ 追加事实
→ 更新当前投影
→ 写入审计与幂等结果
→ 提交事务
```

投影不是事实来源。投影值出现错误时，应能依据有效事实和更正链重新计算；具体重建方式在数据与投影架构中继续确定。

## 10. 事务架构

### 10.1 事务边界

事务由最外层应用命令用例开启。跨模块同步调用加入同一 Spring 事务，不使用 `REQUIRES_NEW` 切断业务原子性。

示例：

```text
订单确认事务
orders 写订单与交付约定快照
→ production 初始化制作与包装需求投影
→ platform 写审计与幂等结果
→ 一次提交
```

### 10.2 锁定原则

- 先锁业务根记录，再锁明细、来源余额和投影；
- 同类记录按稳定主键顺序锁定；
- 所有余额校验都在锁内重新读取；
- 不以接口提交的派生余额作为判断依据；
- 条件更新必须检查受影响行数；
- 不使用应用内 JVM 锁替代数据库并发控制。

跨模块全局锁序和模块内锁定原则已由模块接口与事务矩阵冻结；各业务用例的具体 SQL 锁定实现、索引命中方式和集成测试覆盖在数据库设计与测试架构中细化。

### 10.3 失败语义

同一业务命令内任一步失败，事实、投影、占用、审计和幂等结果必须整体回滚。禁止捕获异常后提交部分业务结果。

## 11. 公式模块

`calculation`：

- 无数据库表；
- 无 Repository；
- 不依赖业务模块；
- 不读取当前时间、登录人和 Spring Web 上下文；
- 接收不可变输入；
- 返回不可变计算结果；
- 统一金额、比例、数量和舍入精度；
- 使用代码与自动化测试管理公式版本。

业务模块负责取得输入、选择规则版本、调用公式并保存业务快照或结算结果。公式模块不决定业务状态，也不自行持久化结果。

## 12. 数据库迁移

Flyway 是数据库结构的唯一迁移入口。

- 新仓库以目标架构建立新的 `V1` 基线；
- 不复制旧方案已经被否决的表结构；
- 数据库结构、约束、索引和种子数据均由迁移管理；
- 应用启动时校验迁移历史；
- 已进入共享环境的迁移不可改写，后续使用新版本迁移；
- 开发初期是否允许压缩未共享迁移，在正式建立环境策略时确定。

迁移测试至少验证：

- 空库可完整建立；
- 必需表、列、约束和索引存在；
- 静态种子与代码枚举一致；
- 关键唯一约束和数量非负约束有效。

## 13. 后端编码约束

- 金额使用 `BigDecimal`，数据库使用明确精度的 `DECIMAL`；
- 数量使用整数，不使用浮点数；
- 时间按业务含义区分日期、本地业务时间和系统时间戳；
- 业务状态使用明确代码，不用自由文本；
- SQL 参数全部绑定，不拼接用户输入；
- 动态排序和筛选只能从服务端白名单映射；
- 批量命令必须先完整校验，再整体写入；
- 业务事实不提供物理删除接口；
- 录入错误使用明确的取消、失效或更正事实处理。

## 15. 后续细化顺序

除前端以外，建议按以下顺序继续确认：

1. 部署、配置、备份和可观测性；
2. 测试架构与质量门禁；
3. 最终事实表、快照表、投影表、索引和数据库约束；
4. 最后单独确定前端架构。
