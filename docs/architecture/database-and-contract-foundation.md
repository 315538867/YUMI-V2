# YUMI V2 数据库与模块契约公共基线

## 1. 文档定位

本文冻结 YUMI V2 后续数据库表设计和模块公开 Java 接口设计必须共同遵守的基础规则。

本文不替代各业务模块的详细设计，不提前决定所有业务表字段，也不定义 HTTP 端点目录。后续 `master-data`、`orders`、`production`、`scheduling`、`after-sales`、`payroll`、`cost-ledger`、`finance`、`reporting` 和 `platform` 的表与接口设计都必须引用本文。

既有架构边界继续有效：

- 模块化单体、单 Spring Boot 应用、单 MySQL；
- Spring JDBC、`JdbcClient`、显式 SQL 和显式行映射；
- Flyway 是数据库结构唯一来源；
- 事实、快照、投影、草稿和占用语义分离；
- 一个正式命令只有一个命令所有者；
- 跨模块写入加入同一事务；
- 模块只能写自己拥有的表；
- 不使用跨模块 SQL 联表完成业务查询或校验；
- 不进入代码实现、OpenSpec 或前端设计。

## 2. 公共设计结论

```text
内部主键用于数据库定位和锁定
稳定业务标识用于公开契约和跨模块追溯
业务编号用于人工识别和检索
三者不得混为一个字段

事实只追加
快照只冻结历史口径
投影允许更新并必须可重建
草稿允许编辑但不代表生效
占用是独立、正式、可释放的业务记录

模块内关系优先使用物理外键
跨模块关系默认使用稳定业务标识和应用校验
确需跨模块物理外键时逐项登记
存在物理外键也不允许跨模块直接读写表

应用命令接口负责完整业务动作
跨模块业务端口负责加入已有事务
查询接口只提供不可变读模型
Repository、行模型和数据库结构不进入公开契约
```

## 3. 标识体系

### 3.1 内部主键

所有需要独立锁定、关联或高频定位的持久化记录使用单列内部主键：

```text
id BIGINT
CHECK (id > 0)
```

使用有符号 `BIGINT` 是为了与 Java `long` 的可表达范围一致，不在 Java 边界引入无符号转换。数据库生成值必须为正数。

规则：

- 内部主键只用于数据库内部关联、稳定排序和锁定；
- 由数据库生成，不承载业务含义；
- 不作为外部 HTTP 标识；
- 不允许客户端根据其递增规律推断记录数量或业务关系；
- 批量锁定同类型记录时按内部主键升序执行；
- 纯粹的一对一从属投影可以使用所属业务根内部主键作为主键，但必须在模块详细设计中明确。

### 3.2 稳定业务标识

需要进入公开 Java 契约、HTTP、审计、幂等结果、文件关联或跨模块来源链的业务对象，使用不可变的稳定业务标识：

```text
business_id VARCHAR(64)
```

具体标识格式和最大实际长度由平台实现设计统一确定，业务表预留类型前缀和未来格式调整空间。建议使用服务端生成的单调、不可猜测字符串标识，并满足：

- 全系统唯一；
- 创建后不可修改；
- 不暴露数据库自增规律；
- 可安全放入日志、URL、接口输入和来源引用；
- 大小写规则固定，数据库比较规则明确；
- 不包含客户名称、日期、状态或模块表名等可变业务含义。

Java 公共类型不直接使用裸 `String` 表达所有标识。每类核心业务根使用不可变值类型，例如：

```java
record OrderId(String value) {}
record ProductionSourceId(String value) {}
record ScheduleTaskId(String value) {}
```

不得把不同类型的稳定标识互换使用。

### 3.3 人工业务编号

需要人工查找、打印或沟通的对象可以另设业务编号，例如订单号、发货单号和售后单号：

```text
business_no VARCHAR(...)
```

规则：

- 业务编号与稳定业务标识分离；
- 业务编号的唯一范围由所属模块定义；
- 业务编号允许采用可读规则，但规则变更不能改变既有编号；
- 不以业务编号承担所有数据库外键；
- 业务编号生成失败不得留下已生效事实或消耗序号后产生重复事实；
- 是否允许号码空洞由具体编号策略决定，不以“必须连续”作为核心事务约束。

### 3.4 请求、命令和动作标识

以下标识语义分离：

```text
requestId             一次外部请求
commandExecutionId    一次完整正式命令执行
operationId           一次平台动作或提交后动作
```

业务模块的正式事实保存 `command_execution_id` 和 `operation_type`，必要时保存 `request_id`；不得把外部幂等键原文写入业务事实。

## 4. 通用数据类型

### 4.1 字符集和比较规则

数据库统一使用 `utf8mb4`。需要唯一性和精确匹配的代码、稳定业务标识、幂等摘要、校验和及状态字段必须使用明确的二进制或大小写敏感比较规则，不能依赖环境默认排序规则。

面向用户的名称、备注和说明使用适合中文检索的排序规则，但其模糊匹配结果不参与业务唯一性判断。

### 4.2 数量

业务数量使用 Java 整数类型和 MySQL 整数列，不使用浮点数。

默认规则：

```text
单条业务数量：INT + CHECK (value >= 0)
跨大量事实累计值：BIGINT + CHECK (value >= 0)
数量差额：有符号 BIGINT
```

使用有符号整数列并通过 `CHECK` 限制非负范围，使数据库类型与 Java `int`、`long` 一致。若某一业务数量可能超过 Java `int` 上限，必须直接采用 Java `long` 和 MySQL `BIGINT`，不能依赖 MySQL 无符号范围。

每个数量字段必须在名称或字段说明中表达业务语义，例如：

```text
ordered_quantity
verified_quantity
qualified_quantity
scrapped_quantity
shipment_quantity
reserved_quantity
```

不得使用缺少语义的通用 `quantity` 承载多个维度。禁止负数的当前数量和余额必须使用数据库 `CHECK` 约束；更正差额允许为负，但累计投影不得因此变为负数。

### 4.3 金额、单价和比例

Java 使用 `BigDecimal`。数据库公共精度为：

```text
金额、成本、单价：DECIMAL(19,4)
比例、效率、损耗率：DECIMAL(12,8)
```

规则：

- 不使用 `FLOAT` 或 `DOUBLE` 保存正式金额和比例；
- 币种默认人民币时仍应在需要跨币种解释的事实或快照中明确 `currency_code`；
- 金额是否允许负数由业务语义决定；冲销和差额事实可以使用有符号金额；
- 当前应收、余额等禁止为负的投影必须使用数据库约束；
- 舍入方式、计算精度和公式版本由 `calculation` 提供，业务事实保存采用的结果与规则版本；
- HTTP 层以十进制字符串传输金额和比例。

### 4.4 标准时间和工时

标准加工时间、冻结估算时间和实际有效时间不得使用浮点数。具体模块可以采用：

- 整数秒或整数分钟；
- 明确精度的十进制分钟或小时。

同一业务维度必须统一单位，字段名必须带单位或由表级契约明确单位。不得在同一累计字段中混合分钟和小时。

### 4.5 日期和时间

时间概念分为：

```text
business_date       业务归属日期，DATE
occurred_at         业务实际发生时间，DATETIME(6)
recorded_at         服务端正式记录时间，DATETIME(6)
created_at          数据库记录创建时间，DATETIME(6)
updated_at          可变记录最后更新时间，DATETIME(6)
```

规则：

- 系统时间戳统一按 UTC 保存；
- Java 使用 `Instant` 表达系统时间点，使用 `LocalDate` 表达业务日期；
- 需要按工作室本地时间解释的输入必须通过明确时区转换；
- 客户端提交的发生时间不能覆盖服务端记录时间；
- 是否允许回填业务发生时间由具体命令校验；
- 不可变事实通常不保存 `updated_at`，因为其业务内容不允许更新；
- 投影、草稿、主数据当前记录和平台动作状态保存 `updated_at`。

### 4.6 状态和类型代码

状态、类型、原因类别和业务方向使用稳定字符串代码，不使用数据库原生 `ENUM`，避免迁移和代码发布被数据库枚举定义耦合。

规则：

- 代码由所属模块定义；
- 代码值创建后不因显示名称变化而变化；
- 显示名称不作为程序分支依据；
- 系统固定代码由代码常量与迁移种子共同校验；
- 用户可维护的静态数据使用独立主数据表，不把用户名称直接写入状态列；
- 不使用自由文本代替受控状态。

### 4.7 文本和 JSON

关键业务字段、来源关系、数量、金额、状态和检索条件必须使用独立列。

JSON 只允许保存：

- 不参与核心校验的历史展示补充；
- 可重放的公开幂等响应；
- 结构变化频率高且不需要数据库筛选的快照补充。

禁止使用 JSON 或 EAV 替代业务表、来源表、明细表和正式约束。JSON 中的数据如果开始参与权限、余额、唯一性、锁定或高频筛选，必须提升为正式列或明细表。

## 5. 表分类与公共结构

### 5.1 主数据当前记录

主数据表表达当前采用的定义和标准。公共字段至少包括：

```text
id
business_id
code（需要稳定代码时）
name
status / enabled
version
created_at
created_by
updated_at
updated_by
```

规则：

- `version` 每次成功业务修改后递增；
- 禁用通常替代物理删除；
- 已被历史事实引用的主数据不得因禁用失去历史解释能力；
- 对历史业务有影响的字段在业务确认时进入冻结快照。

### 5.2 不可变业务事实

每类业务事实使用所属模块的专用事实表，不建立全系统通用事件表。公共语义至少包括：

```text
id
fact_id
fact_type
root_business_id
business_date
occurred_at
recorded_at
operator_id
command_execution_id
operation_type
source_business_id（可空）
source_fact_id（可空）
corrects_fact_id（可空）
rule_version（需要时）
created_at
```

具体事实按业务需要保存数量、金额、状态差额、原因、责任和快照引用。

规则：

- 原始业务内容只允许 `INSERT`；
- 不提供通用 `UPDATE` 或 `DELETE`；
- 更正、取消、失效和冲销通过新增事实表达；
- `corrects_fact_id` 必须引用同一业务语义允许更正的事实；
- 更正链不得形成环；
- 更正时在锁内校验当前有效链和全部下游消费；
- `fact_id` 全局稳定，进入公开查询或跨模块引用；
- `id` 仅用于内部排序、锁定和关联。

### 5.3 冻结业务快照

快照表至少表达：

```text
id
snapshot_id
root_business_id
snapshot_type
snapshot_version
source_master_data_id / source_definition_id（可空）
rule_version（可空）
created_by_fact_id 或 command_execution_id
created_at
```

规则：

- 快照创建后不可覆盖；
- 快照版本属于对应业务根和快照类型，不是全系统版本；
- 快照只保存历史解释所需内容，不机械复制整个主数据对象；
- 关键快照字段使用正式列，JSON 只能补充非检索内容；
- 事实可以直接引用快照，也可以通过业务根和快照版本关联；
- 主数据后续变化不得刷新已冻结快照。

### 5.4 当前投影

投影表至少表达：

```text
id 或所属业务根内部主键
projection_id（需要公开或跨模块引用时）
root_business_id
version
last_fact_id
last_command_execution_id
created_at
updated_at
```

规则：

- 每个投影只有一个写入模块；
- 投影只能与正式事实在同一事务内更新；
- `version` 每次有效业务变更后递增；
- `last_fact_id` 用于追踪最近一次直接影响该投影的权威事实，不替代完整来源链；
- 数量、金额和状态使用明确列，不保存无法解释的混合总量；
- 禁止负值的维度使用 `CHECK`；
- 条件更新必须检查影响行数；
- 投影必须可由有效事实、快照和规则重建；
- 重建不得静默改变权威事实。

### 5.5 草稿与意图

草稿表至少表达：

```text
id
draft_id
owner_operator_id 或所属业务根
status
version
expires_at（需要时）
created_at
created_by
updated_at
updated_by
```

规则：

- 草稿允许编辑和删除；
- 草稿状态不能被当作正式业务状态；
- 草稿中的数量、金额和资格不能作为确认命令的权威输入；
- 正式确认必须重新锁定并校验当前事实和投影；
- 草稿确认后标记已确认或退出可编辑状态；
- 草稿产生的资源占用必须保存为独立正式占用记录。

### 5.6 正式占用

占用表至少表达：

```text
id
reservation_id
root_business_id
source_business_id
purpose_type
purpose_business_id
reserved_quantity
status
created_by_fact_id 或 command_execution_id
released_by_fact_id（可空）
consumed_by_fact_id（可空）
version
created_at
updated_at
```

规则：

- 占用创建、释放和消费必须可追溯；
- 同一有效来源的累计占用不得超过可用数量；
- 占用状态变化与对应业务事实在同一事务内完成；
- 释放和消费互斥；
- 不允许仅通过删除占用行表示释放；
- 必须建立支持按来源锁定、按用途查询和防重复创建的索引与唯一约束。

### 5.7 更正、取消、失效和冲销

优先使用所属事实表中的专用事实类型；只有当更正拥有独立且丰富的业务属性时才建立专用更正表。

公共关系：

```text
original_fact_id
corrects_fact_id
correction_type
quantity_delta / amount_delta / state_delta
reason_code
reason_text（需要时）
```

规则：

- 更正链引用前一条当前有效事实或明确引用原始事实，具体方式由模块固定，不能混用；
- 一个事实是否有效由完整关系和业务规则计算，不使用一个可任意编辑的 `is_valid` 开关替代更正链；
- 投影按本次差额同步更新；
- 已被下游消费的数量和金额必须先满足对应解除关系，不能产生负余额；
- 不建立通用“任意事实失效”管理接口。

## 6. 版本与并发控制

### 6.1 版本分类

```text
aggregate_version     当前业务根并发版本
projection_version    当前投影版本
snapshot_version      同类历史快照序号
rule_version          公式或业务规则版本
schema_version        Flyway 数据库迁移版本
```

这些版本语义不得互换。

### 6.2 乐观版本

需要基于当前读取结果提交的业务根和投影保存无符号整数 `version`，初始值为 `0`。

正式命令输入可以携带 `expectedVersion`。服务端必须：

1. 在事务内锁定目标记录；
2. 读取当前版本；
3. 比较预期版本；
4. 不一致时返回结构化并发冲突；
5. 成功写入后由服务端将版本递增。

调用方不得提交目标版本，参与模块不得信任调用方传入的投影版本替代自身重验。

### 6.3 悲观锁

核心数量、金额、状态和唯一性校验使用明确的 `SELECT ... FOR UPDATE` 或具有同等语义的条件写入。

统一锁序：

```text
orders / after-sales
→ scheduling
→ production
→ payroll
→ finance
→ cost-ledger
```

模块内部：

```text
业务根
→ 明细
→ 来源与占用
→ 当前投影
```

同类型多行按内部主键升序锁定。锁定 SQL 必须命中明确索引；不得依赖无界扫描或数据库偶然返回顺序。

### 6.4 条件更新

所有依赖旧状态或旧版本的更新必须在 `WHERE` 中包含条件，并检查实际影响行数，例如：

```text
WHERE id = ? AND version = ? AND status = ?
```

影响行数不符合预期时，不继续写入后续事实，统一转为并发冲突、状态冲突或程序缺陷。

## 7. 关系、外键和模块所有权

### 7.1 表所有权

每张业务表只有一个写入模块。所有权包括：

- 定义结构和迁移；
- 执行业务写入；
- 维护数据库约束；
- 定义更正和归档语义；
- 提供公开命令、端口或查询能力；
- 负责投影校验和重建。

同一数据库不构成跨模块访问授权。

### 7.2 模块内关系

模块内部稳定且生命周期明确的父子关系默认使用物理外键，并按业务语义决定删除行为。

正式业务事实、快照和投影不使用级联物理删除。草稿内部明细可以在草稿删除时级联删除，但不得级联到正式事实或正式占用。

### 7.3 跨模块关系

跨模块关系默认保存对方的稳定业务标识，并由公开端口和事务内业务校验保证存在性、权限、状态和数量。

默认不使用跨模块物理外键，原因是：

- 物理外键会把迁移顺序和表生命周期耦合；
- 外键不能替代模块公开接口和业务校验；
- 更正、归档和重建需要保持模块所有权清晰；
- 不允许参与模块通过外键关系直接读取提供方表。

确需跨模块物理外键时，必须在模块详细设计中逐项登记：

```text
引用模块和表
被引用模块和表
业务必要性
删除与归档语义
迁移顺序
锁序影响
为什么逻辑引用不足
```

未登记的跨模块物理外键不得进入迁移。

### 7.4 来源引用

跨模块来源关系至少保存：

```text
source_module
source_business_type
source_business_id
source_fact_id（需要精确事实时）
```

来源引用不得只保存表名和内部主键。`source_business_type` 使用受控代码，不允许客户端自由填写。

## 8. 索引和数据库约束

### 8.1 唯一约束

数据库唯一约束是领域唯一性的最后防线。典型模式包括：

```text
UNIQUE(business_id)
UNIQUE(业务编号作用域, business_no)
UNIQUE(command_execution_id, operation_type)
UNIQUE(source_fact_id, purpose_type)
UNIQUE(业务根, snapshot_type, snapshot_version)
UNIQUE(来源, 用途, 有效记录维度)
```

不能只依赖“先查询再插入”防止重复事实。

### 8.2 检查约束

数据库至少对以下内容建立可执行约束：

- 禁止负数的数量、金额和余额；
- `reserved_quantity > 0` 等正式数量下限；
- 状态相关互斥字段；
- 释放事实和消费事实不能同时存在；
- 同一行中必要字段的组合完整性；
- 可由单行判断的日期先后关系。

需要跨行、跨表或跨模块计算的规则由应用命令在锁内校验，不使用触发器隐藏实现。

### 8.3 查询和锁定索引

每张表的索引设计必须从以下访问路径反推：

- 按稳定业务标识定位；
- 按业务根加载事实时间线；
- 按来源事实追溯；
- 按当前状态和工作日期查询工作台；
- 按来源锁定占用和余额；
- 按更正链读取；
- 按 `command_execution_id` 检查参与写入；
- 按投影业务根执行校验和重建。

不为“可能有用”建立无使用路径的索引。所有 `FOR UPDATE` 查询必须说明其命中索引和稳定排序字段。

### 8.4 审计字段边界

可变主数据、草稿和投影使用：

```text
created_at
created_by
updated_at
updated_by
```

不可变业务事实使用：

```text
operator_id
occurred_at
recorded_at
created_at
command_execution_id
```

事实不机械保存 `updated_by`，因为不允许修改其业务内容。审计日志由 `platform` 独立保存，不能用表上的创建修改字段替代正式审计。

## 9. 幂等、审计、文件和提交后动作

### 9.1 外部幂等

正式外部命令的幂等范围至少包含：

```text
command_owner
operation_type
operator_id
idempotency_key_hash
```

幂等记录还保存请求指纹、命令执行标识、状态和允许重放的公开响应。幂等键只保存安全摘要，不保存原文。

成功幂等记录与业务事实、快照、投影、占用、成功审计和正式文件关联在同一事务中提交。事务回滚不得留下成功记录。

### 9.2 领域唯一性

参与模块不解释外部幂等键，只接收 `CommandExecutionContext`，并通过业务唯一约束防止同一命令重复参与。

外部幂等和领域唯一性必须同时存在，互不替代。

### 9.3 审计

平台审计至少关联：

```text
request_id
command_execution_id
command_owner
operation_type
root_business_id
operator_id
result_code
result_category
recorded_at
```

成功审计加入业务主事务。回滚命令的失败信息通过安全日志或专门失败记录保存，不允许为了保留审计而独立提交部分业务结果。

### 9.4 文件

`platform` 拥有临时文件记录和存储引用。业务模块拥有文件与业务根的正式关联语义。

业务命令只接收 `TemporaryFileId`，不接收存储路径或对象键。正式关联在主事务内完成；文件上传、删除、扫描和转码在主事务外执行。

### 9.5 提交后动作

提交后动作记录至少包含：

```text
operation_id
command_execution_id
action_type
business_reference
status
attempt_count
next_attempt_at
last_error_code
created_at
updated_at
```

动作注册加入主事务，执行只发生在提交后。提交后动作不得修改权威业务事实；重试必须通过动作领域唯一性防止重复发送或调用。

## 10. 模块公开 Java 契约

### 10.1 三类公开接口

模块只公开：

```text
应用命令接口
跨模块业务端口
只读查询接口
```

接口和输入输出类型由能力提供方拥有，位于提供方公开 `api` 包。调用方不得复制同义接口或重新定义同义错误码。

### 10.2 应用命令接口

应用命令接口表示一个完整正式业务动作，由命令所有者实现并开启 `REQUIRED` 事务。

命名示例：

```java
interface ConfirmOrderApplication {
    ConfirmOrderResult confirm(
        ConfirmOrderCommand command,
        RequestContext requestContext,
        IdempotencyInput idempotency
    );
}
```

规则：

- 一个方法表达一个完整业务动作；
- 输入类型以 `Command` 结尾；
- 输出类型以 `Result` 结尾；
- 不使用 `execute(String type, Object payload)`；
- 不返回持久化实体；
- 不在 Controller 中编排多个应用命令；
- 应用命令入口接收平台提供的不可变 `RequestContext` 和外部幂等输入，不接收客户端伪造的操作者字段；
- 命令所有者在幂等范围判定后生成 `commandExecutionId`，构造内部 `CommandExecutionContext`；
- 应用命令负责整体授权、幂等语义和参与模块编排。

### 10.3 跨模块业务端口

跨模块业务端口表示参与模块加入一个已有正式命令事务的业务能力，使用 `MANDATORY` 事务语义。

命名应表达提供方完成的业务意图，例如：

```java
interface ShipmentSourcePort {
    ShipmentSourceConsumption consume(ConsumeShipmentSources command);
}
```

规则：

- 没有外层事务时立即失败；
- 参与端口不解释外部幂等键；
- 参与端口在自己的锁内重读事实和投影；
- 参与端口校验本模块业务授权和前置条件；
- 参与端口只写本模块表；
- 参与端口不得再编排第三个业务模块；
- 不暴露为独立 HTTP 端点；
- 输出只包含命令所有者继续编排所需的事实标识、实际数量、来源消费和新版本。

### 10.4 查询接口

查询接口不产生业务写入，返回面向业务上下文的不可变读模型。

命名示例：

```java
interface OrderDetailQuery {
    OrderDetailView get(OrderId orderId, QueryContext context);
}
```

规则：

- 普通查询不加入写事务；
- 需要一致观察的预览和影响评估可以使用短只读事务；
- 查询结果不是正式写入授权；
- 核心数据缺失时明确失败，不静默返回零值；
- 不返回无限嵌套聚合；
- 查询接口不得返回 Repository、行模型或懒加载对象；
- 查询组合最多由业务上下文所属模块或 `reporting` 单层完成，不递归扇出第三个模块。

### 10.5 请求上下文与命令执行上下文

平台在 HTTP 边界建立不可变请求上下文：

```java
record RequestContext(
    RequestId requestId,
    OperatorId operatorId,
    Instant receivedAt
) {}
```

命令所有者接收请求上下文和命令输入，完成幂等范围与请求指纹判断后，生成一次正式命令执行标识，并构造只供命令内部和参与端口使用的上下文：

```java
record CommandExecutionContext(
    CommandExecutionId commandExecutionId,
    String commandOwner,
    String operationType,
    String sourceBusinessId,
    RequestId requestId,
    OperatorId operatorId
) {}
```

规则：

- Controller 和客户端不能生成或覆盖 `commandExecutionId`；
- 同一幂等成功结果重放返回原执行结果，不创建第二个正式命令执行标识；
- `sourceBusinessId` 可以为空，但语义必须由具体命令定义；
- 外部幂等键及其原文不进入参与模块上下文；
- 权限列表、角色和会话对象不在模块之间可变传递；
- 需要权限判断时通过不可变认证上下文或平台公开能力读取；
- 上下文标识不替代业务输入和事实内容。

### 10.6 输入模型

命令输入可以包含：

- 稳定业务标识；
- 本次操作的数量、金额、原因和方向；
- 来源选择；
- 必要的快照标识；
- `expectedVersion`；
- 临时文件标识；
- 命令执行上下文。

命令输入不得包含：

- 调用方计算的可用余额；
- 调用方计算的目标投影；
- 数据库内部主键；
- 数据库行对象；
- Repository；
- 可变聚合；
- 任意 `Map<String, Object>`；
- 通用 JSON 业务负载；
- 客户端身份、角色和权限列表。

列表输入使用不可变集合。方法入口必须复制或拒绝可变集合，不能依赖调用方后续不修改。

### 10.7 输出模型

命令输出仅返回：

- 新增事实稳定标识；
- 实际确认或消费数量；
- 产生的业务差额；
- 更新后的业务根或投影版本；
- 来源消费明细；
- 后续查询所需的稳定业务标识；
- 可公开的结果摘要。

不得返回：

- 内部主键；
- 行模型；
- Repository；
- SQL；
- 表名和列名；
- 可被调用方修改后整体回存的实体；
- 数据库锁和事务对象。

### 10.8 值类型

金额、比例、数量、标识和版本优先使用语义值类型，而不是在所有接口中传递裸基础类型。

示例：

```java
record Quantity(int value) {}
record Money(BigDecimal amount, Currency currency) {}
record ExpectedVersion(long value) {}
```

值类型只验证自身格式和通用不变量；“本次发货数量不得超过可交付数量”等业务规则仍由所属模块在锁内校验。

### 10.9 空值和可选值

公开接口避免用 `null` 表达多个含义。

- 必填字段使用非空类型并在边界校验；
- 真正可选的单值可以使用 `Optional` 作为查询返回的一部分，但不在命令 DTO 字段中大面积嵌套；
- 列表无结果返回空不可变列表；
- 核心业务根不存在必须返回结构化 `NOT_FOUND`，不能返回空对象；
- 金额、数量和状态缺失不得静默转换为零。

## 11. 批量命令

批量命令必须是一个明确的业务动作，不是对单条命令的无界循环包装。

规则：

1. 输入设定明确的最大条数；
2. 先完成整批格式和引用校验；
3. 收集全部需要锁定的业务根、来源和占用；
4. 按全局模块锁序和内部主键升序一次锁定；
5. 在锁内重新校验整批状态和余额；
6. 任一行失败时整批回滚，除非业务明确设计为互相独立的多个命令；
7. 返回结构化的行级输入错误，但不提交部分成功；
8. 不在循环中逐条开启事务；
9. 不通过更换幂等键把一次业务批量动作拆成不可追踪的部分提交。

如果业务确实允许部分成功，必须建模为多个独立命令和独立幂等范围，不能由通用批量框架自行决定。

## 12. 查询分页、筛选和排序

### 12.1 游标分页

高频工作台和长列表使用稳定排序键的游标分页。查询接口使用专用请求和结果类型：

```java
record CursorPageRequest(int pageSize, String cursor) {}
record CursorPage<T>(List<T> items, String nextCursor, boolean hasMore) {}
```

游标必须：

- 由服务端生成和解析；
- 包含稳定排序所需字段；
- 经过签名或结构校验，不能直接拼接为 SQL；
- 不暴露内部 SQL、表名和敏感值；
- 在排序字段相同时使用内部稳定次序消除重复和遗漏。

### 12.2 页码分页

低频、数据量受控且确需跳页的管理列表可以使用页码分页。是否返回总数由具体查询决定；不得为所有列表强制执行高成本 `COUNT(*)`。

### 12.3 筛选和排序

筛选、排序字段和操作符使用接口拥有者定义的受控类型或白名单映射。不得把客户端字符串直接拼接进 SQL。

查询输入不暴露数据库列名。业务字段名与 SQL 映射由查询适配层维护。

## 13. 错误契约

模块之间传递结构化错误，不传递 HTTP 状态码和 Controller 响应类型。

公共错误分类：

```text
VALIDATION
NOT_FOUND
AUTHENTICATION
AUTHORIZATION
BUSINESS_REJECTION
CONCURRENT_CONFLICT
IDEMPOTENCY_CONFLICT
INFRASTRUCTURE_FAILURE
PROGRAMMING_DEFECT
```

业务错误码由发现规则的模块定义。错误至少可以携带：

```text
code
message
fieldErrors
requestId
operationId
currentVersion（并发冲突需要时）
resourceSummary（允许重新读取时）
```

规则：

- 其他模块不重新包装成同义业务错误码；
- 命令所有者不得把参与模块失败降级成警告；
- 错误不得泄露 SQL、表名、列名、堆栈和敏感数据；
- 字段错误使用字段路径到消息列表的映射；
- 跨字段业务规则使用业务错误码，不伪装成格式校验错误。

## 14. Repository 和 SQL 契约

Repository 只属于基础设施适配层，不进入模块公开 API。

写 Repository 使用贴近用例的最小方法，例如：

```text
lockOrder(...)
lockSourcesInIdOrder(...)
appendShipmentFact(...)
insertSnapshot(...)
updateProjectionIfVersionMatches(...)
```

禁止：

```text
save(entity)
updateAnyField(...)
executeDynamicSql(...)
findAllForUpdate()
```

规则：

- SQL 列表明确，不使用 `SELECT *` 作为核心契约；
- 所有参数绑定；
- 动态排序和筛选只通过白名单映射；
- 写方法返回明确影响行数或新内部主键；
- 事实追加和投影更新由应用用例决定顺序；
- Repository 不计算业务金额和业务资格；
- Repository 不访问其他模块表；
- 行模型仅在基础设施层存在。

## 15. Flyway 与迁移治理

Flyway 是结构、索引、约束和系统种子的唯一来源。

规则：

- 目标重建仓库建立新的目标架构基线，不复制已否决的旧表；
- 未进入共享环境的早期迁移是否允许压缩，由环境策略统一决定；
- 已在共享环境执行的迁移不可改写；
- 数据修复使用新的受控迁移或专门运维命令，不手工修改正式结构；
- 模块详细设计必须标明每张表的所有者；
- 跨模块物理外键必须先在设计文档登记；
- 迁移不得建立触发器承载核心业务编排；
- 数据库默认值只用于技术性记录值，不隐式决定业务状态和金额。

迁移验证至少覆盖：

- 空库完整建立；
- 重复执行业务迁移被 Flyway 正确拒绝或跳过；
- 必需表、列、索引、唯一约束和 `CHECK` 存在；
- 系统固定代码种子与代码常量一致；
- 禁止负数和重复来源的约束真实生效；
- 锁定 SQL 的索引存在。

## 16. 公共验证门禁

### 16.1 结构验证

- Spring Modulith 验证模块只依赖公开 API；
- Controller 不依赖 Repository；
- 模块不依赖其他模块的 `infrastructure`、行模型和表；
- `calculation` 不依赖业务模块；
- 业务模块不依赖 `reporting`；
- 参与端口没有独立 HTTP 入口；
- 数据库迁移中的表所有者和跨模块外键均有设计登记。

### 16.2 真实 MySQL 验证

- 事实和投影同事务提交；
- 参与模块失败时整体回滚；
- 条件更新影响行数不符时拒绝提交；
- 并发命令不超卖、不重复占用；
- 相同幂等键不产生第二套事实；
- 领域唯一约束阻止重复参与写入；
- 更正链不能产生负余额；
- 同类多行锁定遵循稳定顺序；
- 投影可按业务根校验和重建；
- 跨模块查询不通过 SQL 联表绕过公开查询接口。

### 16.3 契约验证

- 命令输入不包含内部主键和调用方派生余额；
- 输出不泄露行模型和数据库字段；
- 金额、比例、时间和数量遵守公共类型；
- 错误码归属唯一；
- 查询缺少核心数据时不会静默补零；
- 批量命令任一项失败时按契约整体回滚；
- 游标分页在同排序值下不重复、不漏项；
- 正式命令始终重新校验预览结果。

## 17. 后续分册必须提供的内容

每个业务模块的详细设计至少必须列出：

1. 模块拥有的表清单；
2. 每张表属于主数据、事实、快照、投影、草稿、占用或平台记录中的哪一类；
3. 完整字段、类型、空值、默认值和业务含义；
4. 主键、稳定业务标识和人工业务编号；
5. 模块内外关系及是否使用物理外键；
6. 唯一约束、检查约束和索引；
7. 不可变字段和允许更新字段；
8. 更正、取消、失效、冲销和归档方式；
9. 投影版本、理论值来源和重建范围；
10. 应用命令接口签名；
11. 跨模块参与端口签名；
12. 查询接口和读模型；
13. 命令所有者、参与模块和事务传播；
14. 精确锁定对象、顺序和 SQL 索引；
15. 幂等范围和领域唯一约束；
16. 错误码和权限能力；
17. 必须通过的真实 MySQL 并发、回滚和重建测试。

## 18. 明确不采用

- 一个标识同时承担内部主键、外部标识和人工业务编号；
- 对外暴露数据库自增主键；
- 全系统通用业务事件表；
- EAV 或通用 JSON 承载核心业务事实；
- 数据库原生 `ENUM` 承载持续演进的业务状态；
- 事实记录原地覆盖或物理删除；
- 使用可任意编辑的 `is_valid` 代替更正关系；
- 草稿行隐式充当正式占用；
- 跨模块直接 SQL 联表或直接写表；
- 用跨模块物理外键替代公开接口；
- 使用触发器编排跨模块业务；
- ORM 自动脏检查和级联保存承担核心业务写入；
- 通用 `save(entity)` 或 `execute(type, payload)` 公开接口；
- 调用方提交当前余额或目标投影；
- 参与模块解释外部幂等键；
- 批量接口逐行开启事务并产生隐式部分成功；
- 在事务内上传文件、调用第三方或执行长任务；
- 用 Mock 模块调用替代跨模块原子性和数据库约束验证。
