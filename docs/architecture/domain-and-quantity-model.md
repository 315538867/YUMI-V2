# YUMI V2 领域与数量模型

## 1. 设计目标

本模型把订单需求、逐工序生产、库存接入、可发货、发货和售后分成可追溯但不重复计算的事实。它是数据库设计和业务接口的共同约束。

## 2. 聚合与所有权

### 2.1 订单模块聚合

`Order` 拥有订单主状态、当前有效订单数据、确认快照、金额汇总和关闭规则。`OrderItem` 是订单内的独立履约单位，拥有当前有效订购数量、缝边数量、冻结流程和商品/成本快照。

订单模块还拥有以下内部聚合和事实：

- `FulfillmentEntry` 与 `OrderItemFulfillmentBalance`：履约事实和当前数量投影；
- `Shipment`：发货状态、确认快照、发货明细和物流修改历史；
- `Payment` 与 `Refund`：不可变收退款事实；
- `AfterSalesCase`：售后需求、退回核验、可补发数量、已补发数量和处理状态。

这些对象可以使用独立数据库表和内部包，但均属于 `orders` 顶级模块。售后台账引用原订单和原发货，却不回写原订单履约数量或主状态。

### 2.2 InventoryBatch

属于 `inventory` 模块，拥有库存批次身份和当前数量。数量变化只能由 `InventoryMovement` 产生，批次不拥有目标订单。

### 2.3 ProductionTask / ProductionTaskItem

属于 `production` 模块。`ProductionTask` 是共同日期、员工、工序和类型的任务头；`ProductionTaskItem` 是订单/订单明细/商品/来源/计划量/标准分钟快照和状态的独立明细。两者取代旧的 `ProductionPlan` 目标模型。一个任务头可跨订单、跨商品包含多个明细；头状态不持久化为独立可改状态，只由明细事实派生。明细状态为 `PENDING`、`VERIFIED`、`CANCELLED`，每明细唯一核验。

生产任务类型只有 `NORMAL` 与 `REWORK`；超额预占和售后生产保持独立事实边界，不作为普通生产任务类型。普通制品按产品全局汇总当日未取消 `NORMAL` 计划量，限制为 `mold_quantity * daily_batch_limit`；历史核验不释放当天计划资源。明细保存能力和分钟快照：制作取订单冻结产品星级分钟，捏毛装袋取冻结包装档位分钟，缝边取订单所选缝边种类冻结分钟；不能用 480 分钟或产能代替标准分钟。模具数量和每日批次数为正整数，只派生产能，不影响成本。`NORMAL expected minutes = qty * standard minutes`；`REWORK` 不占正常工时/产能，也不产生虚构返工实际工时。

员工在日期和工序下的制作容量为 `workday hours * 60 * effective rate`，其他工序为 `workday hours * 60`；超出或不足均只提示，不硬拒绝。其他排班独立保存总分钟事实，不带商品数量。

### 2.4 模块协作

订单模块通过公开应用服务请求库存领用和生产任务；库存与生产模块通过明确结果接口向订单履约台账登记来源事实。任何模块都不得直接访问其他模块的 JPA 实体或 Repository。跨模块强一致命令在一个 Spring `@Transactional` 事务中完成。生产任务明细、来源分配和报废回转是跨模块投影的来源，报表与发货来源链接在迁移实施期必须联动更新；旧生产计划实现仅是历史证据，不属于当前契约。

## 3. 数量分层

对每条订单商品明细，数量分为四层：

1. **客户需求层**：当前有效订购数量、累计有效发货数量、未交付需求数量；
2. **工序处理层**：各工序流入、计划、核验、合格、返工、报废和未完成；
3. **最终产品层**：订单可发货数量和成品余量；
4. **售后层**：售后补发需求、可补发和已补发。

这四层不能相加。客户需求层回答“客户还差多少”；工序层回答“同一批需求在哪个阶段”；最终产品层回答“现在能发多少”；售后层回答“已确认发货后额外需要补发多少”。

## 4. 客户需求层

```text
未交付需求数量
= 当前有效订购数量 - 累计有效发货数量
```

约束：

```text
0 <= 累计有效发货数量 <= 当前有效订购数量
0 <= 未交付需求数量
```

订单变更减少当前有效订购数量时，不得低于累计有效发货数量。生产报废不会自动改变当前有效订购数量。

## 5. 流程分流

每条订单商品明细有两个数量：**订购数量**（客户订购的总件数）和**缝边数量**（其中需要缝边剪袋的件数，取值 0 到订购数量之间，0 表示不缝边剪袋）：

```text
不缝边需求 = 订购数量 - 缝边数量
缝边需求 = 缝边数量
制作共同需求 = 订购数量
捏毛装袋共同需求 = 订购数量
缝边剪袋需求 = 缝边数量
最终交付需求 = 订购数量
```

制作、捏毛装袋和缝边剪袋是同一批需求依次经过的阶段，不得计算为「订购数量 + 订购数量 + 缝边数量」。

捏毛装袋合格后才按冻结的缝边数量分流：

- 不缝边部分进入订单可发货；
- 缝边部分进入缝边剪袋有效流入；
- 缝边剪袋合格后进入订单可发货。

## 6. 工序有效流入

除首道制作外，普通工序的正常流入为：

```text
正常实际流入
= 上游合格流入
+ 兼容库存接入
```

首道制作的正常流入是首工序实际缺口；库存若直接进入下游，必须抵扣被跳过工序的需求，不能无条件按订购总量从首道取得。报废回转是原工序普通额度的追加事实，不是上游合格、库存或订单新增。返工来源独立于普通流入。

每一笔正常上游、库存、首工序需求缺口或回转额度都由任务明细自身的 `source_type`/`source_id` 记录来源归属，并由核验事实（`production_verifications`）、来源余额（`rework_sources`/`production_quantity_returns` 的已安排量/已分配量）与取消、未完成回退共同决定消耗；同一来源额度不得二次消费。可用回转余额从回转事实与分配量派生，不使用 `remake_sources`。

### 6.1 普通待安排和普通可执行

严格区分普通 `NORMAL` 与 `REWORK`：

```text
普通待安排
= 当前工序需生产基准
  （扣除库存跳过本工序部分）
+ 累计来自 NORMAL/REWORK 报废回转
- 普通已核验完成
- 普通 PENDING 占用
```

```text
普通可执行
= 原工序正常实际流入
  （首工序实际缺口，其余上游合格 + 兼容库存）
+ 同工序报废回转
- 普通已核验完成
- 分配给其他普通待执行明细的量
```

返工可执行量只来自对应 `rework_source`，每个来源只能被唯一消费；返工不占普通 `PENDING`，不进入普通已核验完成。普通计划可提前创建，能力不足或上游未到位只提示等待，不硬拒绝；核验仍须按相应来源事实校验可执行量。

例：100 件核验为 80 合格、20 返工，则普通待安排为 0，产生 `REWORK=20`；返工核验为 18 合格、2 报废，形成同工序回转 2，后续 `NORMAL=2` 核验后下游得到 100，仍保留 2 件报废事实。下游 100 件若核验为 70 合格、30 报废，回转 30 后下游可执行为 30，无需上游再造 30。不得笼统汇总所有核验来制造负额度。

## 7. 生产核验

```text
本次完成数量 = 合格数量 + 返工数量 + 报废数量
未完成数量 = 计划数量 - 本次完成数量
```

每个生产任务明细只能核验一次；核验结果不可修改，错误使用更正事实处理。

- `NORMAL` 合格：进入冻结流程的下一节点或最终可发货；
- `REWORK` 合格：按普通合格流入进入下一节点，但不回填普通已核验完成；
- 返工：核验先记录发生工序的返工事实；管理员必须基于该事实或上一轮返工事实显式创建唯一 `rework_source`，同一来源可拆多任务；未完成或取消恢复已安排余额，再次返工在显式创建下一轮来源后继续；
- 报废：核验同事务写入一条不可变 `scrap_record` 和一次 `production_quantity_return`，回转为原工序普通待安排和可执行额度，不恢复上游合格、库存或订单新增；后续 `NORMAL` 明细通过来源表关联回转；
- 未完成：恢复该明细类型对应的正常来源分配或返工来源余额；
- 售后与超额不直接套用普通回转公式，迁移实施前必须独立审查预占、未来重复占用和非合格处理；不据此改变未来计划建议或原业务边界。

报废事实永久保留；目标模型删除 `REMAKE`、`remake_sources`、`remake_pending`，以回转事实替代。

## 8. 库存接入

库存领用发生时：

1. 生成库存出库流水并减少原批次；
2. 生成订单履约接入事实；
3. 根据库存阶段进入捏毛装袋、缝边剪袋或可发货；
4. 后续发货不再次扣减原库存。

同一领用数量不能同时作为生产合格流入。取消领用必须反向库存流水并撤销尚未被后续事实消费的履约接入。

## 9. 可发货与发货

```text
可发货流入
= 不缝边捏毛装袋合格
+ 缝边剪袋合格
+ 兼容最终阶段库存接入
```

```text
当前可发货数量
= 可发货流入累计
- 有效发货消耗累计
- 已转成品余量数量
```

确认发货：

```text
本次发货数量 <= 当前可发货数量
累计有效发货数量 + 本次发货数量 <= 当前有效订购数量
```

发货作废恢复订单可发货数量，不自动恢复原库存。若需要撤销库存领用，必须另行满足取消领用条件并生成反向库存流水。

## 10. 减单和成品余量

减单后超出新需求的在制或最终产品必须逐项处理：

- 继续完成并转成品余量；
- 立即报废。

只有订单变更确认后，相关数量才从客户当前有效需求中取消。

成品余量库存保存原订单明细作为来源，但不再计入原订单未交付需求、可发货数量或关闭条件。

## 11. 超额任务

超额预占继续引用未来正常计划并记录预占数量：

```text
同一未来计划的有效超额预占总量 <= 未来计划当前可选数量
```

超额能力独立于普通 `NORMAL`/`REWORK` 回转守恒；不得直接套用普通回转公式。预占不修改未来计划原始数量，不产生工序流入或完成。迁移实施前须独立审查预占、未来重复占用和非合格处理；核验后仅按既有业务边界处理合格事实与未来计划提醒，不发明新的计划决策。

## 12. 售后数量

售后层与原订单层完全分离：

```text
客户退回数量 = 售后返工数量 + 售后报废数量
```

```text
售后可补发数量
= 库存补发接入
+ 售后返工最终合格
+ 售后补发生产最终合格
- 已确认售后补发发货数量
```

```text
售后待补发数量
= 售后补发需求数量 - 售后已确认补发数量
```

售后补发不改变原订单订购数量、累计发货数量和未交付需求。

## 13. 状态视图

不要用一个状态表达所有含义：

- 订单主状态：草稿、已确认、已取消、已关闭；
- 排产状态：未排产、已排产；
- 执行条件：可执行、等待上游；
- 生产进度：未开始、生产中、部分完成、生产处理完成；
- 需求处理状态：仍有待履约、部分处理、全部处理；
- 发货进度：未发货、部分发货、全部发货；
- 生产任务明细状态：`PENDING`、`VERIFIED`、`CANCELLED`；任务头状态只由明细事实派生，不可独立手工修改；
- 售后状态：独立于订单状态维护。

所有状态均由事实派生或通过明确命令转换，不提供手工下拉框直接改状态。

## 14. 不变量

实现和测试必须保证：

1. 各工序数量不相加为订单数量；
2. 一个生产任务头只承载共同日期、员工、工序和类型，数量与来源归属明细；头状态不得独立可改；
3. 每个生产任务明细只能有一次核验，明细状态只能为 `PENDING`、`VERIFIED`、`CANCELLED`；
4. 普通产品全局当日未取消 `NORMAL` 计划量不得超过 `mold_quantity * daily_batch_limit`，历史核验不释放当天资源；
5. 同一正常来源数量不能被两个明细或两个订单重复消费，取消/未完成释放、核验消耗可从事实重建；
6. 库存领用与发货不能重复扣库存，直接下游库存必须抵扣被跳过工序需求；
7. 发货不能超过可发货或当前有效需求；
8. 报废不自动减少客户需求；每个报废事实对应一次原工序回转，回转不产生上游合格、库存或订单新增；
9. 返工来源只在发生工序内部安排，返工不占普通 `PENDING` 或普通已核验完成；
10. 返工和报废回转不增加订单数量，售后补发不回写原订单发货统计；
11. 超额与售后不直接套用普通回转公式，实施迁移前独立审查守恒；
12. 已确认事实不通过物理删除修正；
13. 关闭订单必须同时重新校验履约和款项；
14. 所有汇总均可从来源事实重建。
