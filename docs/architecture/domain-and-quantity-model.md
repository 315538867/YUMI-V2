## 1. 设计目标

本模型把订单需求、逐工序加工额度、实际流入、正常资源占用、库存接入、可发货、发货和售后覆盖分成可追溯但不重复计算的事实。它是数据库设计和业务接口的共同约束。来源/覆盖事实的关系、索引与约束意图同步到 `database-design.md`；具体拆表、逐列 SQL、编号具体值及精确锁行由 1.2 落实，不重新打开已确认业务规则，也不把待评审技术补充当作已批准规则。

## 2. 聚合与所有权

### 2.1 订单模块聚合

`Order` 拥有订单主状态、当前有效订单数据、确认快照、金额汇总和关闭规则。`OrderItem` 是订单内的独立履约单位，拥有当前有效订购数量、缝边数量、冻结流程和商品/成本快照。

订单模块还拥有以下内部聚合和事实：

- `FulfillmentEntry` 与 `OrderItemFulfillmentBalance`：履约事实和当前数量投影；
- `Shipment`：发货状态、确认快照、发货明细和物流修改历史；
- `Payment` 与 `Refund`：不可变收退款事实；
- `AfterSalesCase`：售后需求、退回核验、可补发数量、已补发数量和处理状态。

这些对象可以使用独立数据库表和内部包，但均属于 `orders` 顶级模块。售后台账引用原订单和原发货，却不回写原订单履约数量或主状态。

### 2.2 InventoryBatch

属于 `inventory` 模块，拥有库存批次身份和当前数量。数量变化只能由 `InventoryMovement` 产生，批次不拥有目标订单。

### 2.3 SchedulingTask / SchedulingTaskItem

属于 `scheduling` 模块。排班顶层分为有商品与工序的制作排班，以及无商品、无工序的其他排班。`SchedulingTask` 是共同日期、员工、工序和类型的任务头；`SchedulingTaskItem` 保存普通订单或售后明细业务所有者、商品/订单/路线快照、用途、实际执行工序、来源类型与 ID、计划量、冻结标准分钟、估算分钟、能力快照和取消审计。一个任务头可跨订单、跨商品包含多个明细；头不保存权威数量汇总，状态只由明细事实、业务日期和未完成处理派生，不可手工修改。

商品任务类型只有 `NORMAL` 与 `REWORK`。正常加工、修补后的后续加工、报废制作补做均为 `NORMAL`；只有选定目标上的实际修补段为 `REWORK`。售后所有权和用途不是任务类型。明细只允许 `PENDING → VERIFIED` 或 `PENDING → CANCELLED`，每明细一次核验；创建后不得直接改数量、日期、工序、来源或类型，未执行计划调整须取消后重新安排。任务内同一业务明细、工序、来源的重复有效行拒绝，不同任务可拆分同一来源余额。

正常资源按产品 + 日期 + 工序汇总全部未取消 `NORMAL` 原计划量，跨员工、跨订单校验数量硬产能 `mold_quantity * daily_batch_limit`；历史核验与未完成不释放原日期计划资源。明细保存能力和分钟快照：制作、捏毛装袋、缝边分别取份额 `routeSnapshotId` 绑定的产品星级、包装档位、缝边种类及标准分钟。普通来源沿对应确认/变更新授权快照，退回实物沿原实物快照，售后新授权沿新补发冻结快照；不能把全部售后缝边统一改用受理时的新工艺，也不能用 480 分钟或产能代替标准分钟。模具数量和每日批次数为正整数，只派生产能，不影响成本。`NORMAL expected minutes = qty * standard minutes`；实际 `REWORK` 不占正常工时/产能，也不产生虚构返工实际工时；其后续 `NORMAL`（含售后）仍占正常资源。

工作量提示仅用于管理员安排制作：按员工 + 日期汇总全部未取消 `MAKING NORMAL` 的冻结估算分钟，包含本次草稿且不重复计入已保存任务；包括正常制作、报废补做与售后正常制作，排除实际返工和其他排班。有效制作分钟 = 工作日小时数 × 60 × 制品有效工时率，差额 = 已排分钟 − 有效制作分钟；只提示余量、超出或刚好，不硬拒绝、不扩展到装袋和缝边，也不是工资绩效。服务端在提交前预览、创建响应、详情和工作台统一计算，前端不复制公式；使用 BigDecimal 精确比较，显示舍入不参与判定，提交重读当前配置并返回基准，历史分钟和资源快照不被改写。产品数量硬产能与此提示独立。

其他排班仍独立保存员工、日期、事项和总分钟事实，一次核验、追加工时更正，不带商品数量或订单来源；在同一日期周历与制作排班同级展示，不要求合表。

### 2.4 模块协作

编译依赖固定为 `scheduling → orders`、`scheduling → inventory → orders`。orders 通过自有端口请求排班/库存协作，inventory 通过自有 `InventorySchedulingPort` 请求协调，接口及全部 DTO 均由请求方持有，由 scheduling adapter 转换实现；orders 不引用 scheduling/inventory 类型，inventory 不引用 scheduling DTO。共享返工/加工来源由 `scheduling` 保存并保留售后所有者；售后需求、用途、覆盖、可补发及已补发台账始终由 `orders` 拥有，库存批次、领用头行、流水及 Receipt/writer 由 `inventory` 拥有。不得把售后加工写入原订单履约，或通过普通任务创建绕过售后权限与来源校验。

orders 拥有订单确认/变更及新补发的冻结工艺证据；`order_change_item_applications.route_snapshot_id` 引用 orders 自有的新明细冻结快照，不指向 scheduling 内部表或要求 orders 创建排班快照。scheduling adapter 按该真实证据生成/关联排班份额的 `routeSnapshotId` 并保留起因映射；inventory 同样拥有自己的批次冻结证据，由 adapter 验证后生成/关联排班快照。跨域快照保留证据身份与不可变工艺语义，不假定不同模块的本地 ID 相同，不用反向 Repository/DTO 访问打破 DAG。

任何模块都不得直接访问其他模块的 JPA 实体或 Repository。跨模块强一致命令在一个 Spring `@Transactional` 事务中完成。排班应用服务拥有创建、取消和批量核验，售后应用服务拥有退回核验、需求调整和补发确认，库存提供同事务接口；来源生成、覆盖迁移、报废补做、后续流转与终点入库不得拆成可能留下部分事实的独立提交。统一按业务所有者/来源上限行 → 任务头与明细 → 具体来源/目标及覆盖余额 → 产品日期工序容量锁 → 库存批次加锁，同类稳定排序，锁内重验；精确物理锁行待实施落实。任务明细、来源分配和实际流转为跨模块投影来源，报表与发货来源链接须同步；旧模型仅保留历史证据。

## 3. 数量分层

对每条订单商品明细，数量分为四层：

1. **客户需求层**：当前有效订购数量、累计有效发货数量、未交付需求数量；
2. **工序处理层**：各工序可安排额度、实际流入/可执行量、计划、核验、合格、返工、报废和未完成；另行计算产品日期工序正常产能、员工日期正常估算工时和具体返工来源余额，不与数量余额混算；
3. **最终产品层**：订单可发货数量和成品余量；
4. **售后层**：独立补发需求、按来源链互斥计算的有效覆盖、可补发和已补发。

这四层不能相加。客户需求层回答“客户还差多少”；工序层分别回答“可安排多少、实物能执行多少、占用多少资源”；最终产品层回答“现在能发多少”；售后层回答“补发缺口是否已被来源/在制/最终合格覆盖”。计划不是实物流入，覆盖也不等于已可补发。

## 4. 客户需求层

```text
未交付需求数量
= 当前有效订购数量 - 累计有效发货数量
```

约束：

```text
0 <= 累计有效发货数量 <= 当前有效订购数量
0 <= 未交付需求数量
```

订单变更减少当前有效订购数量时，不得低于累计有效发货数量，并逐有缝/无缝桶校验已经交付的真实份额。生产报废不会自动改变当前有效订购数量。

### 4.1 普通订单确认、变更与终态守卫

所有普通订单变更（ADD、无实物增减、路线/工艺变化、实物及取消处置）统一经 orders 自有 `OrderSchedulingDispositionPort` 整批执行 `inspect → owner锁 → lockAndValidate其余L锁 → orders写真实变更应用结果 → applyLocked`，只用一份 Influence/LockedPlan；不能逐行重走锁序，也不再调用 `OrderSchedulingLifecyclePort.applyOrderChange`。Lifecycle 仅处理确认、取消、关闭守卫及退回核验建源。ADD 确认在同事务由 orders 持久化 `order_change_item_applications(order_change_item_id UNIQUE,created_order_item_id,route_snapshot_id)`，记录真实变更行到新明细及 orders 冻结快照（§2.4）的映射；UPDATE/REMOVE 保留原 orderItemId。同商品双 ADD 分别映射，adapter 不按商品、行号或查询顺序猜来源。所有既有资源先纳入整批锁计划，新行不补锁尚不存在的资源；applyLocked 同时建新源和处置旧份额，任一失败连应用映射、需求、金额、快照、库存全部回滚。

确认订单按冻结路线和扣除库存跳过后的缺口生成初始 root/share 及各段 source；`ADD` 明细、数量增加或工艺版本变化形成的新需求，按增量追加新 source，保留确认/`orderChangeItemId` 起因，不能覆写既有 `total`。普通变更的 `orderChangeItemId` 与售后处置的 `afterSalesDispositionId` 是独立引用，不能拿售后 ID 冒充普通变更起因。自动生成的授权/等待额度不是加工执行事实，不产生任务开始、完成或下游实物流入。

减少数量或替换工艺版本须逐份额处置旧需求：无实物且无执行/核验/下游流入的份额，显式列出全部受影响的制作及下游等待计划并同事务合法取消，追加全链各段额度终止；未占用部分直接追加终止。部分减量不得改旧计划，整条合法取消后保留量待重新安排。已有实物则逐份额选择沿原路线继续转库存或合法报废，不按各工序 `SUM` 重复算同一实物。新工艺只属于新授权快照；旧任务、旧实物及其路线/工艺/分钟快照不变，不隐含工艺改造许可。

取消没有执行、领用、发货等事实的订单时，自动产生但未占用的初始 sources 也须同事务全链终止；不能因存在自动授权就误判为已经执行，也不能只改订单状态遗留可排余额。已有计划须满足显式合法取消前提，不能绕过事实守卫。已取消/已关闭等终态订单禁止新增普通交付安排，但必须按所有者和用途识别：既有合法余量的转库存链、合法售后独立链不得因原订单终态被一刀切禁止。

## 5. 流程分流

每条订单商品明细有两个数量：**订购数量**（客户订购的总件数）和**缝边数量**（其中需要缝边剪袋的件数，取值 0 到订购数量之间，0 表示不缝边剪袋）：

```text
不缝边需求 = 订购数量 - 缝边数量
缝边需求 = 缝边数量
制作共同需求 = 订购数量
捏毛装袋共同需求 = 订购数量
缝边剪袋需求 = 缝边数量
最终交付需求 = 订购数量
```

制作、捏毛装袋和缝边剪袋是同一批需求依次经过的阶段，不得计算为「订购数量 + 订购数量 + 缝边数量」。

捏毛装袋合格后按冻结的适用路线及来源链分流，初始需求以缝边数量确定：

- 不缝边部分进入订单可发货；
- 缝边部分进入缝边剪袋有效流入；
- 缝边剪袋合格后进入订单可发货。

返工、补做和售后须继承业务所有者、用途与适用路线；重过缝边的件数仍须走缝边，不能因历史累计缝边流入已达初始数量而转为无需缝边。下游已处理需重过时增加的是加工额度，不是客户需求。

每个份额必须绑定不可变 `routeSnapshotId`，快照同时确定 `routeSeamRequired`、具体工艺/版本及各适用工序标准分钟；boolean 只用于有缝/无缝数量分桶，不能充当完整路线身份。退回实物沿原发货真实份额的原快照；售后新授权沿受理/需求调整冻结的新补发快照。库存接入、退回修补用于补发及后续承接均须核验完整工艺兼容性，同 boolean 但不同工艺/版本不自动兼容，不得复制当前商品配置覆写原快照。本次不新增工艺改造许可；不兼容实物不能用换标签填补新路线 gap。

## 6. 工序有效流入

除首道制作外，普通工序的正常流入为：

```text
正常实际流入
= 上游合格流入
+ 兼容库存接入
```

首道正常制作执行来自已授权的订单缺口或制作补做来源；库存直接进入下游须先抵扣被跳过工序的初始缺口，不能无条件按订购总量从首道取得。报废意味着实物失效，从来不是发生工序或下游的合格实物流入。返工执行来自具体来源及其目标工序。

每笔初始需求、库存接入、返工、制作补做、后续重过工序或售后来源均须记录业务所有者、用途、适用路线、前序事实、目标工序、数量与分配/消费关系。任务明细以 `source_type`/`source_id` 追溯，`scheduling_verifications`、`rework_sources`、`scheduling_quantity_returns` 及分配、取消、未完成事实共同决定余额。物理拆表待实施落实，但不能仅加枚举而丢失来源链；按具体来源 + 目标分余额，不把同商品不同来源混池。

### 6.1 普通待安排和普通可执行

对每个初始正常工序来源，total保存创建时授权量；后续库存跳过只通过终止事实扣除一次，不再从total或下式工序初始需求预扣同一数量：

```text
初始来源可安排
= 工序初始需求 - 累计终止量 - PENDING原计划占用
- 已核验正常处理数量 - invalidatedUnoccupied（失效口径见§12）
已核验正常处理数量 = 合格 + 返工 + 报废
```

无异常、无库存跳过时，订单 10 件、缝边 4 件，制作/装袋/缝边初始可安排分别为 10/10/4。不能先减全部未取消历史计划再减已核验量，否则重复扣减。返工、报废制作补做、重过工序和售后另用各自来源余额，汇总只加互斥来源，不把异常量全部加回初始需求。

```text
下游正常可执行
= 已登记的兼容上游合格流入 + 兼容库存接入
- 对应已处理量 - 分配给其他待执行计划的量

返工来源可安排余额
= 来源总量 - 累计终止量 - PENDING原占用
- 已核验实际修补处理量 - invalidatedUnoccupied（见§12）
```

同一来源链的真实流入分配采用 §7 的开始保护技术补充（1.1 待评审、尚未批准），不能再对已开始与未开始计划一律按日期重排；核验在锁内重算有效真实份额。正常计划可在上游实物未到时提前安排，但必须满足来源额度、员工资格和产品数量硬产能；计划额度不等于未来实物预占，核验不得超过实际流入。未完成所剩未消费实物继续可用，不额外生成一份流入。资源另按未取消 `NORMAL` 原计划量记录，不能混用可安排公式。

返工完成中的合格、再次返工、报废均消费本轮来源；仅未完成中的有效未处理份额退回原来源可排余额，取消释放未执行占用；二者均不得复活失效份额（§12）。再次返工在本次核验同事务按目标创建新来源，不加回旧来源。同一核验分配行只生成一次来源；来源允许跨任务拆分，禁止用 `UNIQUE(source_id)` 限制安排次数，累计占用与消费须锁内防超量。

只有实际修补段为 `REWORK`；合格后按适用路线走后续 `NORMAL`。已处理需重过的工序须新增加工额度；未处理且已有原额度或等待计划的工序只补实际流入，不重复增加额度。必须记录与既有需求/等待计划的承接关系，不能用全局取最大值或负数截零掩盖重复。

例：需缝边的 10 件在缝边核验合格 8、返工 2，分配制作修补 1、装袋修补 1。第一件走制作 REWORK → 装袋 NORMAL → 缝边 NORMAL；第二件走装袋 REWORK → 缝边 NORMAL。新增正常加工量为装袋 1、缝边 2，最终可发货仍为 10，不是 12。制作首次返工后的修补合格只向原装袋等待计划补流入。装袋报废且仍需履约的量则从制作 NORMAL 重新做，绝不能直接成为装袋可执行实物。

## 7. 排班核验

```text
本次完成数量 = 合格数量 + 返工数量 + 报废数量
未完成数量 = 计划数量 - 本次完成数量
缝边剪袋：报废 = 0，完成 = 合格 + 返工
```

每个任务明细只能核验一次；核验业务日必须晚于任务日期，按统一业务时区比较，不得把录入日期当工作日期。完成不超过计划与锁内重算的可执行量，未完成由服务端计算。核验事实不可修改，不提供普通核验通用编辑/冲销入口。批量逐明细检查归属、状态、日期、数量和来源；任一失败整批回滚。

| 核验入口 / 本次实际加工工序 | 返工目标 | 报废 |
| --- | --- | --- |
| 制作 `MAKING` | 制作 | 允许 |
| 捏毛装袋 `PACKING_BAG` | 制作 | 允许 |
| 缝边剪袋 `SEAM_CUTTING` | 制作、捏毛装袋 | 禁止 |
| 售后退回核验 | 制作、捏毛装袋、缝边剪袋（符合原适用路线） | 可直接登记退回件报废 |

前三行同时适用于正常加工和实际修补核验；再次返工按本次实际修补工序而非最初发生工序判定。只有制作可返到自身，缝边目标只能来自符合路线的售后退回入口。售后退回不是缝边工序核验，不虚构生产发生工序。

- `NORMAL` 合格：按所有者、用途与适用路线进入下一节点或终点；
- `REWORK` 合格：消费当前修补来源，向下游补实际流入，并按是否已处理决定重过额度，不回填普通已核验完成；
- 返工：必须随本次核验完整提交目标分配，合计等于返工总量，例如缝边返工 5 分配制作 2、装袋 3。分配遗漏、不足、超额或目标非法均整批拒绝；核验与每个目标的来源同事务生成，记录发生工序、目标、所有者、用途、路线、轮次及父来源，无之后手工补建来源步骤，也不自动排班；
- 报废：同事务写不可变 `scheduling_scrap_records`。仍需履约或补发的报废一对一生成 `scheduling_quantity_returns`，仅授权从 `MAKING` 开始的 NORMAL 补做，保留原发生工序、所有者、路线和覆盖链；不增加客户需求，不形成原工序合格、库存或实物流入，不恢复旧返工余额。无补发义务且明确库存用途或直接处置的售后报废只留事实、不补做；直接报废也不自动取消独立补发承诺，同一报废量不得重复生成补做；
- 未完成：仅仍有效未处理份额退回同一所有者、同一来源、同一目标可排；失效部分关联原报废不再可排，取消也不得复活（§12）。售后不进入原订单履约，返工不进入普通初始需求；核验、流转、来源、补做、失效、未完成回退和提醒同事务提交。

审查新增待评审设计：实际加工前须登记一次不可逆明细执行标记（服务端时间、登记人、请求ID），部分开始即整条标记；不新增状态、不登记完成量或合格流入。开始须PENDING、无核验、不早于任务日且锁内正可执行；正完成核验须已有执行标记，未开始且完全未做可次日核验0。只允许取消无执行标记且无核验的 `PENDING` 计划，不能仅凭日期或客户端声明判断；原因必填，锁内重验并释放对应来源占用及该计划正常资源，不级联取消上下游、不抹除实际流入。登记开始、取消、核验与减量统一锁序互斥；不宣称系统能识别现场未上报执行。计划 10、次日核验完成 6 后，原明细为 VERIFIED，余下 4 退原来源并另建计划；原日期仍保留计划 10 的资源和估算工时，新日期重新占用。原明细不能再核验、取消或改回 PENDING。报废和核验事实永久保留；目标不使用 `REMAKE`、`remake_sources` 或 `remake_pending`。

### 7.1 开始保护的真实流入分配（1.1 待评审，尚未批准）

执行标记与下列保护规则是同一项待评审技术补充，不因本文同步而获业务批准：开始时锁定该明细已分配的真实流入份额，后续不能被更早日期的未开始计划抢走。后到的兼容真实流入，先补已开始计划尚缺的计划剩余，再分给未开始计划；多个已开始计划按 `execution_started_at / taskItemId` 排序，未开始计划按 `taskDate / taskItemId` 排序。所有分配仍限定同所有者、来源/承接链、用途与完整路线兼容性，不能跨池抢量。

保护只绑定已经存在的真实数量，未到部分只是计划未满足量，不提前生成分配、不新增第四状态、不恢复未来预占，也不生成加工事实。核验消费实际完成份额；核验后有效未完成的真实分配解除保护并释放回同源同目标，失效未完成份额不得释放成可排实物。开始、后到流入分配、核验、取消及普通/售后减量须在统一锁序内互斥重验。

## 8. 库存接入

期初 `OpeningRequest` 与 `InventoryPage` 显式输入 `routeSeamRequired`，正缝边选择合法 `seamTypeId`；inventory 服务端冻结本域不可变路线、具体工艺/版本及标准分钟，`node/seamState` 校验已完成阶段，不接受客户端分钟、不从目标订单或当前配置补猜。单批只有一种工艺/路线，混合实物分批；库存增量调整继承原批证据。scheduling adapter 验证兼容性后生成/关联排班 `routeSnapshotId`，inventory 不引用排班 DTO，期初不要求不存在的终点核验。

普通/售后领用统一扩展既有 `inventory_allocations` / `inventory_allocation_lines`，以 owner_type 及互斥订单/售后归属，同事务真实写 head、line、原出库 movementLine、批次和路线份额；现有售后仅 movement line 不代表已有 allocation line，不造 FK 占位行或售后影子表。

库存领用发生时：

1. 生成库存出库流水并减少原批次；
2. 生成订单履约接入事实；
3. 根据库存阶段进入捏毛装袋、缝边剪袋或可发货；
4. 后续发货不再次扣减原库存。

所有成品直接领用亦须同事务生成真实 `INVENTORY_INFLOW` root/source、`physicalShareId`、初始 `purposeAllocationId` 和终点流入，普通直接可发、售后只记一次 RESERVED。`targetNode=SHIPPABLE` 仅为终点追溯锚点，不属于任务加工 Node（三工序）；其 `total` 只记原接入量，`balance=0`、`executableQuantity=0`，不套加工余额公式、不建加工额度/任务/核验。份额的 `terminalAvailableQuantity` 独立按真实有效终点流入减有效发货（含补发）、转库及接入逆向派生，普通发货作废反向恢复原消费份额，更正传递同份额；非终点份额该值为0。普通 fulfillment、售后 case/scheduling-sources GET 返回真实 source/root、allocationId/physicalShareId/routeSnapshotId、终点可处置量及两类完成证据引用，不用 inventoryAllocationLineId 冒充 sourceId。减需3→1时以前述 GET 返回的 sourceId/allocationId 选择转库2，创建表单过滤 SHIPPABLE，服务端同样拒绝其建任务；GET只读不补建事实。

同一领用数量不能同时作为生产合格流入。普通取消领用及现有 `reverseMovement` 入口必须共用业务反向守卫，反向接入 flow、source、用途/覆盖与库存流水同事务完成，不得仅恢复批次数量。选中接入份额已开始加工、已被后续消费、已补发或已转库存时拒绝；未开始的关联计划也须显式合法取消后才能撤接入，不能留下失去实物流入/额度的悬挂计划。按份额和原流水关联幂等反向，不能绕过业务入口重复恢复。

合法普通领用撤销若需恢复被库存跳过的普通生产需求，须按当前仍有效需求追加恢复授权并关联原领用/反向事实，不能复活旧 `terminated` 来源或给终态普通交付新授权。历史来源总量、终止与快照保留。

终点完成证据互斥区分 `TERMINAL_VERIFICATION`（真实路线终点核验）与 `FINISHED_INVENTORY_ALLOCATION`（兼容成品库存领用），每一完成份额只能引用对应的一种真实证据，不能为成品领用制造假任务/假核验。前者必有 terminalVerificationId；后者必有真实 batch/allocation/line、原出库 inventoryMovementLineId 及份额路线，terminalVerificationId 为空，不能用非终点领用冒用。预留转库存的调整须引用原完成证据、选中份额和调整起因，并同事务产生可追溯的新批次与入库流水。例如成品直接领用并预留 3，需求减到 1，保留预留 1、余 2 入新库存；该过程既不伪造终点核验，也不作为原领用撤销恢复原批次。

Receipt 服务及 DTO 归 inventory：普通余量经 `OrderSurplusReceiptService` 使用 orderItemId/orderChangeItemId，售后经 `AfterSalesInventoryReceiptService` 使用 afterSalesItemId 及适用 demandAdjustmentId/处置引用，不能混用售后 FK。均由 scheduling adapter 解析源/份额/终点后调用库存底层核心，orders 不直接引用库存类型，Receipt 不回调排班。先改用途后完成的入库 origin 为真实终点核验分组、保留原变更/调整；当场终点转库 origin 为真实处置行。originType/id/line 防重，不以单个领用行唯一限制合法分次转库。核验或处置生成的入库不得经通用 reverseMovement 孤立冲销（STATE_CANNOT_CANCEL），本 change 不新增核验/处置逆向；独立期初/库存调整的既有合法冲销保留。

## 9. 可发货与发货

```text
可发货流入
= 不缝边捏毛装袋合格
+ 缝边剪袋合格
+ 兼容最终阶段库存接入
```

```text
当前可发货数量
= 可发货流入累计
- 有效发货消耗累计
- 已转成品余量数量
- 合法库存接入逆向数量
```

该终点余额与 §8 的 terminalAvailableQuantity 按有效消费/反向事实一致重建，不取加工 balance；普通发货作废恢复同份额可发，更正仅传递原消费，不能重复扣或释放。

普通发货草稿/确认显式提交 `quantity` 与 `seamQuantity`，`0 <= seamQuantity <= quantity`；有缝消费 seamQuantity，无缝消费 quantity−seamQuantity，零缝边也须明确，不按总量猜配。

```text
本次发货数量 <= 当前可发货数量
累计有效发货数量 + 本次发货数量 <= 当前有效订购数量
各桶本次发货 <= 该桶当前未消费可发份额及剩余交付需求
```

确认只分配并消费当前未消费、未转库存、仍有效的可发份额；不能每批重扫原始 `IN` 流入再从头链接或累计消费同一份额。每条发货来源链接保存真实 `sourceLineId`、`physicalShareId`、数量与不可变 `routeSnapshotId`，冻结路线、工艺和分钟身份；不得以聚合订单行或占位 ID 代替真实来源行。可发投影由这些有效消费及反向事实重建。

普通发货作废逐链接反向原消费份额，恢复同一来源与路线的可发量，不重新择源，不自动恢复原库存。等量更正原子转移原份额及其各桶数量至替代批次，不能先释放后重新扫描抢配，也不能改变工艺/路线组成。确认、作废及等量更正均不扣/恢复库存；若需要撤销库存领用，必须另行满足 §8 的反向条件。

## 10. 减单和成品余量

减单后超出新需求的数量须按真实份额而非逐工序求和处理：无实物份额按 §4.1 全链终止及显式合法取消；已有在制或最终产品逐项选择：

- `CONTINUE_TO_INVENTORY`：沿原冻结路线继续完成并转成品余量；
- 合法报废：遵守发生入口/工序限制，不能以减单绕过缝边工序禁报废等规则。

已有非终点实物（库存接入或前段合格）即使没有任务、或者当前任务尚未开始，也可选择 `CONTINUE_TO_INVENTORY`；是否已有实物与任务是否开始是不同条件。追加用途处置并承接已有下游额度/合法计划，不伪造开始，不重复授权，仍须沿路线加工到终点才能真实入库。终点实物按 §8 的互斥完成证据直接入库，不强制补造核验。

只有订单变更确认后，相关数量才从客户当前有效需求中取消。处置保存 `orderChangeItemId`、份额和数量，不回写旧任务及实物快照。

成品余量库存保存原订单明细和真实份额/完成证据作为来源，但不再计入原订单未交付需求、可发货数量或关闭条件。

## 11. 删除超额任务与未来预占

目标删除 `overtime_tasks`、`overtime_task_items`、`overtime_preemptions` 及对应服务、端点、DTO、前端类型/入口、预占/释放、未来计划减少建议和超额专属错误码。不是并入统一任务，不新增 `OVERTIME` 类型，也不保留改名后的预占表。

删除 `OVERTIME_PENDING_VERIFY`、`PLAN_ADJUSTMENT` 及未来计划调整机制，保留 `INCOMPLETE` 等未完成提示。制作工作量为服务端查询/预览结果，不落独立提醒表，也不是数量事实。超出提示不是超排许可，正常来源余额和产品日期工序硬产能仍须校验；工作量不足不自动生成任务或预占未来计划。

## 12. 售后数量

售后需求、用途、覆盖及台账归 `orders`，与原订单层完全分离；共享执行来源留在 `scheduling` 并保留售后所有者。退回数量与补发需求独立，允许只退不补、仅退款或无退回补发。受理显式提交 `returnedQuantity` 与 `returnedSeamQuantity`，`0 <= returnedSeamQuantity <= returnedQuantity`，零退回 seam 也显式为0；分别从原发货明细真实链接的有缝/无缝份额核验剩余可退上限，扣除其他有效退回占用，不能仅按原批总量验证。既有受理占用上限仍适用，不自行增加受理次数规则。

补发独立填写/确认 `replacementRequiredQuantity`（总量）和必传 `replacementSeamQuantity`（其中缝边量，`0 <= seam <= total`）。总量仅未提供时默认退多少补多少，显式0保留；零补发 seam 也必须显式为0。`returnedSeamQuantity` 与 `replacementSeamQuantity` 互不推导，不复制原订单 seam、不按比例猜测。服务端冻结新补发的合法 `routeSnapshotId`、缝边种类及标准分钟；没有合法工艺快照时拒绝正 seam，不擅造配置。退回原实物引用原发货份额快照，新补发授权引用新补发快照，兼容性遵守 §5。

```text
实退数量 = 修补用于补发 + 修补用于库存 + 直接报废
```

退回一次核验显式提交实际 `returnedQuantity/returnedSeamQuantity`，满足 `0 <= returnedSeamQuantity <= returnedQuantity <= acceptedQuantity`，允许与受理预录总量及路线组成不同。核验同事务重新锁原发货与售后明细，以原发货真实路线份额扣除其他有效退回占用重验实际两桶，记录预录到实际差异并原子替代本明细未核验占用、保留旧引用历史；不双扣本明细预录、不影响其他有效退回或独立补发承诺。不能依赖既有 correct 先修改占用；RETURN_VERIFICATION correct 仅审计，不覆盖数量/来源/覆盖/库存，本 change 不新增核验逆向。分桶等式使用本次锁内验证的实退，而非受理预录。

退回一次核验须同时完整分配修补用途与目标，分配显式标 `routeSeamRequired`，并引用原真实份额的 `routeSnapshotId`；合法目标须符合原实物适用路线。每桶修补用于补发与库存的分配之和不得超过该桶实退量，剩余全部记为该桶直接报废：`scrap[r] = returned[r] - repairForReplacement[r] - repairForInventory[r] >= 0`，两桶 scrap 之和必须等于提交的 `scrapQuantity`；不能只验证总量等式而把另一桶实物拿来补分配。补发用途既须匹配对应桶 gap，又须完整工艺兼容，库存用途不覆盖。分配、逐桶报废及共享来源同事务生成。用途（补发/库存）与实际执行类型（NORMAL/REWORK）是不同维度。

```text
r ∈ {有缝, 无缝}
required[有缝] = replacementSeamQuantity
required[无缝] = replacementRequiredQuantity - replacementSeamQuantity
gap[r] = required[r] - shipped[r] - reserved[r] - covered[r]
covered[r] = 本路线用途为补发的未排/待加工/在制有效来源覆盖
reserved[r] = 本路线终点且仍预留补发的未发出合格数量
              （含兼容最终库存、修补终点及正常加工终点）
待补发[r] = required[r] - shipped[r]
需求/覆盖/预留/已发/gap各项总量 = 该项有缝桶 + 无缝桶
```

不得用总 gap 抵另一线路超额或截零掩盖负桶。库存领用须绑定真实兼容路线份额并不超对应 gap；补发确认按真实预留份额消费对应 route，逐路线不超 reserved 及 required-shipped，不能只收总量而任意猜配。

显式正常缺口授权提交 `quantity`、`seamQuantity`、明细与原因，quantity为正且 `0 <= seamQuantity <= quantity`；锁内验证 seam 不超有缝 gap、quantity-seam 不超无缝 gap，同事务创建 quantity 的 MAKING/PACKING_BAG 额度及 seamQuantity 的 SEAM_CUTTING 等待源，同 root 的物理份额覆盖仅一次，不产生实际下游流入、不自动任务、不手工建返工源。

覆盖按物理数量/来源链互斥计一次，不能按工序累加；未排班的补发返工来源已覆盖需求，来源转待加工、在制、最终合格仅迁移覆盖，不重复生成补发制作缺口。报废结束失败覆盖，仍须补发时由同一缺口的制作补做承接，不重复创建。库存用途返工或在制不覆盖补发，也不计可补发。退回用途分配、库存补发接入、正常来源创建等新增补发覆盖均不得超过锁内重算的未覆盖缺口，超出实物须显式决定库存用途或合法报废，不能默改用途或截零；这不限制实退量，也不另加受理上限。

任意中间工序合格不等于可补发或入库，必须完成全部适用加工。库存用途在路线终点必须通过 `inventory` 同事务落可追溯批次与入库流水，不能只改用途标签或计数。补发确认才增加已补发；售后补发不改变原订单订购数量、累计发货数量和未交付需求。

补发批次从草稿创建起固化补发身份与全部售后关联，不与普通明细混批；普通发货草稿修改/确认/作废/等量更正须服务端拒绝补发身份，不能写原订单履约。专用售后确认锁内校验整批归属，仅消费售后预留；当前无补发草稿改量、作废或等量更正，通用更正也不可绕过。可复用只读/物流，但不改数量、身份、关联或履约状态。原发货被售后受理不等于该批次是补发。

补发需求调整显式提交新 `replacementRequiredQuantity` + `replacementSeamQuantity`，满足范围/冻结工艺约束且逐路线 `newRequired[r] >= shipped[r]`。每路线独立算 `reduction[r] = max(oldRequired[r] - newRequired[r], 0)`，先消减本路线调整前 gap，`max(reduction[r] - gap[r], 0)` 的已覆盖部分须明确去向；保留原因、前后值、源明细和历史。增量只产生该路线 gap，不自动来源或任务；等总量换路线仍一减一增，不能互抵 gap 或直接改实物路线。未执行计划可取消，但实物仍须修补转库存或报废；在制沿适用路线完成入库，已合格超出量解除补发预留并真实入库。退 5、补 5 改补 3：若已合格 5，3 件保留补发、2 件入库；若已补发 4，不得改为 3。无补发义务的库存用途售后报废只记事实，不派生制作补做；报废不能替代对独立补发需求的显式调整。

无实物正常制作授权的减量例外：锁内证明选中份额无退回/库存接入、无执行标记/核验处理、无实际下游流入后，可按数量追加终止事实并解除覆盖。原授权不覆写，有效授权=原授权−累计终止，可安排=有效授权−PENDING原占用−已核验处理−invalidatedUnoccupied（见本节失效口径）；已终止不得再安排或重复终止。若已排，调整显式列出制作和后续等待计划并同事务合法取消、释放正常资源、终止各段对应额度，不自动级联或遗留失去额度的计划。原计划5不能改成3，须整条取消后终止2，余3待重新安排。需求5→3后有效来源/覆盖3、库存0、报废0；与开始执行/排班/核验竞争须锁内重验，任一前提失败整笔回滚。退回、库存接入和在制实物不得冒用该分支。

普通及售后实物处置共用 §8/§10 的证据边界：退回件、库存接入或前段合格等已有非终点实物，无任务或当前未开始也可 `CONTINUE_TO_INVENTORY`，无需冒充已开始在制；沿原路线完成才入库。终点预留转库存须引用真实终点核验或成品领用的互斥完成证据，不能强制要求所有来源都有核验。

物理 `physicalShareId` 贯穿 root、来源、任务分配、用途与 flow；源创建同事务生成初始真实 `purposeAllocationId`，单用途也必须有。已开始明细部分改库存（change细化任务6.5）只追加选中未处理份额的用途替代映射，并在锁内传播到既有下游等待源及计划对应 share；不是首次初始化，不改整条 `source.purpose`，不新增加工额度、不改原计划/历史资源或已处理历史。已被下游消费的 share 拒绝冒用上游在制分支。HTTP核验以allocationId引用真实purposeAllocationId，用途、physicalShareId与路线由服务端解析；仅唯一有效份额可省组规范化，同用途但不同路线的多份额也必须逐组提交，组完成不超有效未处理份额/可执行、组汇总等于明细结果；子源和下游 flow 继承有效用途与路线。

补做必须生成新的 `physicalShareId`，保存 `replacesPhysicalShareId`、替代 `quantity`、原报废事实与新补做来源关系；失败旧实物永久失效，不能因补做合格重新激活旧 share。按数量把旧 share 尚未处理的等待 source/task 额度承接映射到新 share，保留原计划/历史资源，只有已处理且需重过的段才新增额度。承接映射不是用途调整，也不能只记 root 关系而遗漏既有等待计划。新补做再次报废时，再生成替代本轮失败 share 的新份额；按每轮失败份额的有效数量防超量/重复替代。旧失败覆盖结束、新补做承接同一需求覆盖，全链任一时点只覆盖一次，不按轮次或工序累加。

库存 share 上游报废不补做时，同事务向下游未处理对应额度追加按 `scrap + target + share` 幂等的失效事实，关联原报废。对退回实物选择 `SCRAP_RETURNED`，还必须使当前源及未处理下游的对应份额一并失效，不能只记报废而保留当前可排余额；已处理历史不改写。报废失效不是细化任务6.2无实物终止，不再记一次报废、不冒充 processed/terminated、不再次释放覆盖/计划资源。PENDING 原计划不改，失效份额可执行0；后续 `unfinished = 原计划 - completed`，仅有效未处理部分回同源同目标可排，失效部分关联原报废不再可排；合法取消也不能复活失效量。若仍需补发，只能由独立新授权/合法补做承接，原报废实物及来源份额永不重新可排。

加工来源/目标的完整余额为 `total - terminated - pending原占用 - processed - invalidatedUnoccupied`；SHIPPABLE 终点锚点不适用此式，balance/executable恒0，terminalAvailableQuantity 按§8独立重建。`invalidatedUnoccupied` 仅是不再由PENDING原占用扣除且未处理的失效份额，不能将仍在PENDING中的失效量再扣一次；View可列 `invalidatedQuantity` 和 `invalidatedUnoccupiedQuantity`。§6.1及本节公式均按此口径重建，不涉及终止/失效时相应减项为0，失效不算 completed。

固定回归（目标未实施）：同一无缝链制作5 + 装袋等待5，制作开始后分为补发3/库存2；制作核验补发合格3、库存合格1、库存报废1。下游原计划5、有效4（补发3/库存1）、失效1；装袋核验4后 unfinished=1 但可重排=0，终点预留3、库存1，无补做。两段各自历史资源仍按原计划5保留。

## 13. 状态视图

不要用一个状态表达所有含义：

- 订单主状态：草稿、已确认、已取消、已关闭；
- 排产状态：未排产、已排产；
- 执行条件：可执行、等待上游；
- 生产进度：未开始、生产中、部分完成、生产处理完成；
- 需求处理状态：仍有待履约、部分处理、全部处理；
- 发货进度：未发货、部分发货、全部发货；
- 排班任务明细状态：`PENDING`、`VERIFIED`、`CANCELLED`；任务头状态只由明细事实、业务日期和未完成处理派生，不可独立手工修改；全部取消才已取消，部分核验不能整头已核验，全部有效明细已核验则头已核验，未完成待处理是独立提示；
- 售后状态：独立于订单状态维护。

所有状态均由事实派生或通过明确命令转换，不提供手工下拉框直接改状态。

## 14. 不变量

实现和测试必须保证：

1. 各工序数量不相加为订单数量；客户需求、可安排额度、实际流入、资源占用与售后覆盖分层守恒；
2. 排班模块为 `scheduling`，顶层制作/其他，商品任务仅 `NORMAL`/`REWORK`；头只承载共同日期、员工、工序和类型，数量与来源归属明细，头状态不得独立可改；
3. 每明细在任务日期之后只能核验一次；状态只有 `PENDING`、`VERIFIED`、`CANCELLED`，已核验不能取消、二次核验或继续填剩余；
4. 产品日期工序未取消 `NORMAL` 原计划量受数量硬产能约束；历史核验及未完成保留原日期资源，新日期重新占用；制作工作量仅软提示，不扩到其他工序；
5. 按来源 + 目标分余额，同一物理数量不得重复消费；可跨任务拆分来源，不以来源 ID 唯一限制安排次数；正常可安排不重复扣已核验计划；
6. 库存领用与发货不能重复扣库存，直接下游库存必须抵扣被跳过工序需求；
7. 发货不能超过可发货或当前有效需求；
8. 报废不自动减少客户需求；仍需履约/补发才生成从制作开始的 NORMAL 补做，不虚构发生工序实物流入，不恢复旧返工余额；无补发义务的售后库存用途报废只留事实；
9. 返工发生工序与目标分开，目标按本次实际工序矩阵，只有制作可返自身；缝边核验允许分目标返工但禁止报废；以缝边为修补目标的来源只能来自合法售后退回；分配完整且与核验同事务生成来源，无手工补建来源；
10. 只有实际修补段豁免正常资源，后续 NORMAL 仍占资源；已处理工序增加重过额度，未处理已有等待额度只补流入，客户需求不增加，适用缝边路线不丢失；
11. 删除超额、未来预占及计划调整建议，不并表或保留改名模型；未完成退同源同目标，只取消未执行计划，不级联抹除上下游事实；
12. 已确认事实不通过物理删除修正；
13. 关闭订单必须同时重新校验履约和款项；
14. 所有汇总均可从来源事实重建，来源、分配、核验、补做、覆盖与终点入库幂等，统一锁序且批量失败整笔回滚；
15. 售后共享来源由 scheduling 保留售后所有者，需求/用途/覆盖/台账归 orders，不回写原订单数量；未排补发来源也已覆盖，同一来源链覆盖只计一次；
16. 仅适用路线终点可补发/入库，库存用途真实落批次与流水，确认补发才增加已补发；减少需求不得低于已补发，已覆盖实物须显式解除预留并安排去向；完成证据区分真实终点核验与成品领用，不补造核验。
17. 普通确认/ADD/增量/新工艺授权追加来源，旧 total/任务/实物快照不变；无实物减量全链终止及显式合法取消，已有实物逐份额处置；普通变更和售后处置起因独立，无事实取消不留初始可排源，终态守卫不误禁合法余量/售后。
18. routeSnapshotId 绑定具体工艺/版本/分钟，boolean 仅分桶；退回沿原实物、新授权沿新补发快照，不以同 boolean 推定兼容或授权工艺改造。
19. 补做使用新 share 及 replacesPhysicalShareId + quantity，按量承接旧未处理等待额度，已处理段才新增重过；重复报废逐轮替代，旧失败实物不可复活，覆盖不重复。
20. SCRAP_RETURNED 失效当前源和未处理下游，以 invalidatedUnoccupied 入余额、不冒充 processed/terminated，取消/未完成不使原报废再次可排。
21. 普通发货显式 quantity/seamQuantity，只消费当前未消费真实 sourceLine/share；作废反向原份额，更正原子传递同份额，均不改变库存。退回显式 returnedSeamQuantity 且独立于补发 seam，原批两桶上限及分桶报废余量分别守恒。
22. 非终点实物无任务或未开始不妨碍 CONTINUE_TO_INVENTORY，但不能提前入库/伪造开始；成品预留 3→需求1→新库存2 使用真实成品领用证据。
23. 普通取消领用与 reverseMovement 反向接入 flow/source/覆盖，消费/开始/补发/转库守卫一致；合法恢复需求只追加授权，不复活旧 terminated。
24. 开始保护分配及执行标记仍为 1.1 待评审、尚未批准：只保护已分配真实流入，后到先补已开始（执行时间/ID）再未开始（日期/ID），有效未完成释放；不新增状态、未来预占或加工事实，不以此次修复作为业务签字。
