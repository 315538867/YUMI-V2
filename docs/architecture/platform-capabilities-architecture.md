> 本文确定 `platform` 模块的认证上下文、权限基础、请求追踪、幂等、审计、文件、提交后动作和通用错误基础能力边界。不确定具体认证供应商、文件存储产品、完整权限目录和部署运维实现，也不承载业务模块规则。

## 1. 平台模块定位

`platform` 是模块化单体中的通用基础能力模块，为业务模块和 HTTP 外部适配层提供稳定能力，但不拥有订单、生产、排班、售后、工资、成本或现金业务规则。

平台能力的边界是：

```text
认证结果
→ 操作者上下文
→ 请求追踪与基础权限能力
→ 业务模块执行具体授权和业务规则
```

平台不把所有业务动作抽象成一个万能权限判断，也不通过通用工作流、事件总线或异步消费者承载核心业务写入。

## 2. 能力组成

```text
platform
├─ authentication       认证与会话上下文
├─ authorization        基础角色和权限能力
├─ request-context      请求、操作者和执行上下文
├─ idempotency          外部命令幂等记录
├─ audit                操作审计
├─ file                 临时文件和正式文件关联
├─ error-foundation     结构化错误基础类型
├─ tracing              请求与命令追踪
└─ post-commit-actions  提交后动作基础设施
```

这些能力可以在代码中按包或适配器拆分，但必须保持平台对外公开接口与业务规则的边界。

## 3. 认证与操作者上下文

### 3.1 认证职责

平台负责：

- 识别外部认证凭证；
- 验证会话或访问令牌；
- 判断会话是否有效和是否过期；
- 生成不可变的操作者上下文；
- 把认证失败映射为 HTTP 层的认证错误。

平台不负责判断某个订单是否可以变更、某个任务是否可以核验或某笔现金是否可以更正。

### 3.2 上下文内容

应用命令和查询可以读取以下不可变上下文：

```text
operatorId
sessionId / authenticationId
requestId
tenant/workspace context（未来需要时）
authenticatedAt
```

上下文由服务端认证结果产生。客户端传入的 `operatorId`、角色、权限列表或组织标识不能覆盖服务端上下文。

`requestId` 用于追踪本次请求；`commandExecutionId` 用于标识一次正式命令执行；两者不互相替代，也不作为业务事实本身。

### 3.3 错误区分

认证、授权和业务规则分开处理：

```text
未认证或会话失效       → 401
身份已确认但基础无权    → 403
权限满足但业务状态不允许 → 409 / 422
```

平台不能把所有失败统一成“无权限”，也不能用业务模块的状态错误替代认证失败。

## 4. 基础权限能力

### 4.1 平台持有的内容

平台可以提供：

- 角色和权限标识的解析；
- 操作者与角色的关联；
- 基础资源范围上下文；
- 对公开权限能力的查询；
- 权限判定所需的不可变输入。

权限标识示例：

```text
ORDER_EDIT
ORDER_SHIP
PRODUCTION_DISPOSITION
SCHEDULE_VERIFY
FINANCE_RECEIPT
PAYROLL_CLOSE
REPORTING_VIEW
```

完整权限目录、角色组合和组织范围仍在平台具体权限模型中细化。

### 4.2 业务模块解释权限

平台提供权限基础数据，但业务模块决定权限在具体动作中的含义：

- `orders` 判断订单变更、普通发货、收款和完成确认；
- `production` 判断质量处置、包装还原和来源消费；
- `scheduling` 判断排班创建、取消和核验；
- `after-sales` 判断售后受理、补发和结算；
- `payroll` 判断工资计算、封账和调整；
- `cost-ledger` 判断成本归集和更正；
- `finance` 判断现金事实登记和更正；
- `reporting` 判断报表和经营分析的访问范围。

例如，拥有 `ORDER_SHIP` 只表示操作者具备发货能力，不表示当前订单一定可以发货。`orders` 仍要校验订单履约状态，`production` 仍要校验有效来源和可交付数量。

### 4.3 授权时机

正式命令必须在业务事务内、锁定并重新读取业务状态后完成授权和前置条件校验。预览接口或页面加载时的“允许执行”不构成正式授权结论。

参与模块对自己拥有的敏感规则仍需重新校验，不能因为命令所有者已完成基础授权就完全信任调用方。

## 5. 请求与命令上下文

### 5.1 请求上下文

HTTP 适配层为每个请求建立请求上下文，至少包含：

```text
requestId
operatorId
认证上下文
请求接收时间
HTTP method and route template
```

服务端可以接受客户端提供的 `X-Request-Id` 候选值，但必须校验格式、长度和敏感内容；不合规时生成新的服务端标识。

### 5.2 正式命令上下文

命令所有者将请求上下文转换为正式命令执行上下文：

```text
commandExecutionId
commandOwner
operationType
sourceBusinessId
requestId
operatorId
idempotencyKeyHash
```

参与模块只能接收稳定的内部执行标识，不解释外部幂等键，不接收客户端身份字段。

### 5.3 上下文不可变

进入应用层后的认证上下文、操作者身份和请求追踪标识不可由业务模块修改。业务模块可以把上下文中的标识写入事实、审计和幂等记录，但不能把它们当作业务事实内容本身。

## 6. 幂等记录能力

### 6.1 平台职责

平台提供幂等记录的存储、锁定和结果读取能力。命令所有者负责定义：

- 幂等键作用范围；
- 请求指纹组成；
- 成功结果；
- 重放结果；
- 不同指纹冲突规则；
- 已回滚尝试的处理方式。

平台不替命令所有者决定“同一个业务命令是否可以重放”。

### 6.2 记录内容

幂等记录至少表达：

```text
commandOwner
operationType
operatorId
idempotencyKeyHash
requestFingerprint
commandExecutionId
status
responseCode
responseBody
createdAt
completedAt
```

`responseBody` 只能保存允许重放的公开结果，不能保存认证凭证、内部堆栈、数据库信息或敏感文件内容。

### 6.3 事务规则

幂等记录和业务事实、快照、投影、占用、审计结果在同一事务中提交：

```text
读取并锁定幂等记录
→ 判断重放或冲突
→ 执行完整业务命令
→ 保存成功结果
→ 一次提交
```

平台不能使用 `REQUIRES_NEW` 单独提交“命令成功”。业务事务回滚时不能留下已成功的幂等结果。

并发使用相同幂等键时，只允许一个请求进入正式执行；其他请求等待已提交结果或得到明确并发冲突。

### 6.4 幂等与领域唯一性

幂等记录只解决外部请求重复执行问题。业务模块仍必须通过领域唯一约束防止重复业务事实，例如：

```text
UNIQUE(command_execution_id, operation_type)
UNIQUE(order_receipt_fact_id)
UNIQUE(verification_fact_id, cost_category)
UNIQUE(shipment_item_id, production_source_id)
```

平台不以一个通用拦截器替代业务模块的领域唯一性。

## 7. 审计能力

### 7.1 审计目的

审计记录回答：

```text
谁在什么时候发起了什么操作
操作针对什么业务根
使用哪个请求和命令执行标识
结果是成功、拒绝、冲突还是失败
```

审计日志用于安全追踪、问题排查和操作责任追溯，不是业务事实来源。

```text
业务事实 ≠ 审计日志
```

审计不能替代订单变更、生产核验、质量处置、发货、收付款、工资封账或成本归集事实。

### 7.2 审计状态

至少区分：

```text
命令开始
命令成功
命令业务拒绝
命令并发冲突
命令幂等重放
命令基础设施失败
```

成功审计与正式业务事实在同一事务中提交。失败审计不能通过提交部分业务事务来实现；如果需要保留回滚事务中的失败信息，使用事务外的安全日志或专门失败记录机制，并明确它不属于正式业务事实。

### 7.3 审计内容边界

审计可以保存：

- 操作类型；
- 命令所有者；
- 业务根标识；
- 操作者标识；
- 请求和命令执行标识；
- 结果码；
- 必要的差异摘要；
- 时间和来源入口。

审计不得保存：

- 认证凭证和会话令牌；
- 幂等键原文；
- 数据库密码和连接串；
- 完整文件内容；
- 不必要的客户敏感信息；
- SQL 和内部堆栈。

## 8. 文件与附件能力

### 8.1 所有权

`platform` 拥有文件元数据、临时文件生命周期和授权文件引用能力。业务模块拥有文件与业务根之间的正式业务关联语义。

业务模块不直接持有对象存储路径，不直接删除对象，也不绕过平台返回任意下载地址。

### 8.2 临时文件流程

```text
上传临时文件
→ platform 保存临时文件记录
→ 正式业务命令提交临时文件标识
→ 事务内校验归属、用途、状态和有效期
→ 转为正式业务关联
→ 业务事实、投影、幂等和审计一次提交
→ 未关联临时文件过期清理
```

文件内容上传、对象存储写入、删除、转码和病毒扫描不进入正式业务数据库事务。

### 8.3 临时记录

临时文件记录至少需要表达：

```text
temporaryFileId
uploaderId
storageObjectReference（仅平台内部）
contentType
size
checksum
purpose
status
expiresAt
createdAt
```

文件引用必须绑定操作者和用途，不能让一个操作者上传文件后被其他业务根任意关联。

### 8.4 正式关联

业务命令只接收临时文件标识，不接收对象存储路径：

```json
{
  "attachments": [
    {"temporaryFileId": "file_tmp_01J..."}
  ]
}
```

平台在主事务内校验并执行元数据状态转换；外部存储动作不能作为事务内的数据库写入条件。

### 8.5 下载和清理

下载必须同时校验：

```text
文件存在
文件已经正式关联
操作者可以访问关联业务根
文件未被撤销或过期
```

未关联临时文件由过期清理任务删除。清理失败必须可观察、可重试，并且不能影响正式业务事务。

## 9. 提交后动作基础设施

### 9.1 允许范围

平台可以为以下非权威动作提供提交后注册、状态追踪和重试能力：

```text
通知
打印
文件转码和派生文件生成
缓存刷新
可重建报表生成
外部 HTTP 调用
```

这些动作不产生当前核心业务事实，不参与订单、生产、发货、收款、售后、工资或成本事务的成功判断。

### 9.2 执行规则

提交后动作必须：

- 只在主事务成功提交后执行；
- 带有稳定动作标识；
- 具备幂等语义；
- 支持安全重试；
- 保存待处理、成功、失败和下次重试时间；
- 记录最后错误，但不泄露敏感信息；
- 不修改已经提交的权威事实。

外部动作失败不能回滚已经提交的核心业务，也不能把尚未执行的通知、打印或第三方调用伪装成成功。

### 9.3 当前实现边界

当前不引入消息队列或通用工作流引擎。单体内可以采用提交后事件监听或受控任务记录承载可重建动作，但该基础设施不得承载核心强一致写入。

未来接入第三方支付、回调或外部业务系统时，必须另行设计外部状态机、外部幂等、回调验证和对账机制。

## 10. 结构化错误基础

平台提供错误分类、错误载体和统一响应转换的基础类型，但业务错误码由发现规则的模块拥有。

错误至少区分：

```text
业务拒绝
并发冲突
幂等键冲突
幂等重复成功
外部输入错误
认证失败
基础权限不足
基础设施失败
程序缺陷
```

模块之间传递结构化业务异常，不传递 HTTP 状态码、Controller 响应对象或通用错误字符串。HTTP 层把错误转换为统一信封：

```text
code
message
fieldErrors
requestId
operationId
```

平台不重新解释订单、生产、财务等业务规则，也不生成与业务模块同义的错误码。

## 11. 追踪、日志与安全

### 11.1 追踪字段

请求、命令、平台动作和日志至少可以关联：

```text
requestId
operatorId
commandExecutionId
operationId
moduleOwner
operationType
resultCode
latency
```

`requestId` 追踪一次外部请求；`commandExecutionId` 追踪一次完整命令；`operationId` 追踪具体平台或外部动作。它们必须保持语义区分。

### 11.2 脱敏规则

日志和审计采用字段白名单或脱敏策略，不记录：

- 认证凭证、会话令牌和幂等键原文；
- 数据库密码、连接串和 SQL 参数中的敏感值；
- 完整客户敏感信息；
- 文件内容和内部存储路径；
- 第三方响应中的敏感字段。

错误响应也不得泄露 SQL、表名、列名、堆栈、文件路径或其他内部实现细节。

### 11.3 安全责任

平台负责认证、基础权限、文件访问入口和敏感日志保护。业务模块负责业务根授权、状态校验、数量和金额规则，以及跨模块命令的业务前置条件。

## 12. 平台与业务模块边界

| 能力 | `platform` 负责 | 业务模块负责 |
|---|---|---|
| 认证 | 验证凭证、会话、身份上下文 | 读取上下文，不自行解析凭证 |
| 权限 | 角色、权限标识、基础范围 | 解释业务动作含义并完成业务授权 |
| 幂等 | 记录存储、锁定、结果读取 | 键范围、请求指纹、重放语义和领域唯一性 |
| 审计 | 操作记录基础设施、追踪关联 | 提供业务操作语义和业务根 |
| 文件 | 临时记录、存储引用、生命周期、访问入口 | 正式业务关联和业务可见性 |
| 错误 | 结构化载体、HTTP 转换基础 | 业务错误码和业务规则解释 |
| 提交后动作 | 注册、状态、重试基础设施 | 定义动作触发条件和业务内容 |
| 业务状态 | 不拥有 | 订单、生产、排班、售后、工资、成本、资金模块各自拥有 |

平台对外提供能力，不拥有业务数据的最终解释权。

## 13. 事务边界

### 13.1 事务内允许

```text
读取和锁定平台幂等记录
保存与业务命令同一事务的成功审计
关联已暂存文件的元数据
保存业务命令执行上下文
注册已经提交后才执行的动作元数据
```

上述平台写入必须加入命令所有者的主事务，参与能力使用 `PROPAGATION_MANDATORY` 等价语义。

### 13.2 事务内禁止

```text
文件上传和删除
对象存储写入
病毒扫描
第三方 HTTP
邮件、短信和通知发送
打印
文件转码
大型报表生成
启动操作系统程序
```

平台不能因为自身能力通用，就使用独立事务提交这些外部副作用或提交“业务成功”状态。

### 13.3 回滚语义

命令失败时，与业务动作绑定的幂等成功记录、成功审计、正式文件关联和提交后动作注册必须回滚。外部系统已经发生的动作不属于本地事务，必须由对应的外部状态和对账机制处理，不能假设本地回滚可以撤销它。

## 14. 验证要求

平台能力进入实现后至少需要以下验证：

### 14.1 认证和授权

- 无凭证和过期会话返回 `401`；
- 已认证但基础无权返回 `403`；
- 业务状态错误不被误报为认证或基础权限错误；
- 客户端不能伪造 `operatorId`、角色、权限或组织上下文；
- 业务模块仍在事务内完成最终授权。

### 14.2 幂等和事务

- 相同幂等键和指纹只产生一套业务事实；
- 相同幂等键不同指纹被拒绝；
- 回滚不会留下幂等成功记录；
- 并发相同幂等键不会并行执行；
- 参与模块唯一约束能阻止重复业务事实；
- 业务失败时幂等、审计和正式文件关联整体回滚。

### 14.3 文件

- 临时文件只能由有权操作者关联；
- 过期临时文件可以清理且清理可重试；
- 正式命令不会把客户端对象路径写入业务关联；
- 提交前不会执行文件删除、转码和外部存储副作用；
- 未授权操作者不能下载其他业务根的文件。

### 14.4 审计和日志

- 成功命令具备可追踪审计；
- 业务事实与审计不互相替代；
- 失败不会通过提交部分事务来保留错误业务结果；
- 日志不包含令牌、幂等原文、密码、路径和敏感业务数据。

### 14.5 提交后动作

- 主事务回滚时不执行提交后动作；
- 主事务提交后动作失败不会篡改正式业务事实；
- 重试不会重复发送、打印或调用外部系统；
- 动作状态和失败原因可观察。

## 15. 明确不采用

- 平台直接决定订单、生产、排班、售后、工资、成本或现金业务规则；
- 一个万能 `hasPermission()` 替代业务模块授权；
- 客户端身份字段覆盖服务端认证上下文；
- 平台用 `REQUIRES_NEW` 单独提交幂等或业务成功；
- 审计日志替代业务事实；
- 文件路径或对象存储键由客户端直接控制；
- 文件上传、删除、扫描和转码放入核心业务事务；
- 提交后动作失败回滚本地核心业务；
- 消息队列或通用工作流引擎承载当前核心强一致写入；
- 通用平台错误码覆盖业务模块错误码；
- 在日志中记录凭证、幂等原文、密码、文件内容或敏感数据。

## 16. 已确认不变量

```text
platform 提供通用能力，不拥有业务规则
认证上下文由平台生成且不可由客户端或业务模块覆盖
基础权限由平台提供，具体业务授权由业务模块完成
幂等记录与正式业务事实在同一事务中提交
参与模块不解释外部幂等键
审计日志不能替代业务事实
正式文件关联与业务命令同一事务提交
文件外部操作在业务事务外执行
提交后动作只在主事务提交后执行
提交后动作必须可观察、可重试且不改变权威事实
结构化错误由平台提供载体，业务模块拥有业务错误码
平台不直接访问或修改业务模块表
平台不使用通用工作流承载核心业务写入
```

## 17. 后续细化内容

本文已经冻结平台能力的职责边界和事务规则。后续仍需独立细化：

1. 认证方式、会话存储、凭证生命周期和失效策略；

3. 幂等记录、审计记录、临时文件和提交后动作的最终字段与索引；
4. 文件存储后端、内容安全扫描、清理任务和保留期限；
5. 日志、指标、链路追踪和敏感字段脱敏配置；
6. 部署、配置、备份恢复和可观测性架构；
7. 测试分层、真实 MySQL 集成测试和质量门禁；
8. 最后确定前端技术、目录、路由、状态和交互架构。
