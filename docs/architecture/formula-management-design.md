# 公式集中管理方案（评审稿）

日期：2026-09-24  
修改人：chen  
状态：已评审并实施（2026-09-24）。方案已按 OpenSpec 任务 2.13–2.19 落地：公式代码迁入 `com.yumi.calculation`，商品预估改为认证的服务端试算；逐项公式清单与测试编号见 `formula-catalog.md`，实施证据见 `openspec/changes/build-yumi-v2-order-fulfillment/tasks.md`。第 2 节的“当前位置”保留迁移前快照作为历史记录，第 10 节清单由 tasks.md 的 2.13–2.19 取代。

## 1. 目标与决策

所有业务计算公式集中在后端 `com.yumi.calculation` 模块，内部按业务分类；商品、订单、生产及未来工资、财务服务只准备输入、调用计算、保存结果。前端不保留公式副本，通过后端试算接口展示预估。

集中管理的验收标准是“一个后端计算模块、一份公式实现、试算与保存调用同一个入口”，不是仅集中目录或测试。模块内部允许多个具名计算类，不建立万能大类、表达式引擎或动态编辑功能。

本期先迁移已有商品公式。实施时盘点当时已存在的其他计算代码，一并列明迁移范围；尚未建设的业务不提前实现。以后新增业务公式只能放入 calculation 对应分类，不能重新散落回业务模块。

本方案明确替换上一版“业务模块分别持有公式 + 前端 decimal.js 本地预估”的设计。原有本地预估和不新增试算 API 的决定不再作为本方案约束；正式实施前同步相关架构与 OpenSpec 接口矩阵。

## 3. 目标结构与依赖

建议结构如下；订单、生产、工资、财务分类随实际实现加入，不提前创建空文件。

```text
com.yumi.calculation
├── package-info.java          模块定义
├── DecimalPolicy.java         金额、比例的精度与舍入基础方法
├── product
│   ├── package-info.java      商品计算公开命名接口
│   └── ProductPricing.java    商品输入、结果、计算链及相关常量
├── order                     订单金额与收退款计算（随业务接入）
├── production                标准工作量、数量余额计算（随业务接入）
├── payroll                   工资计算（业务确认后接入）
└── finance                   财务汇总计算（业务确认后接入）
```

调用方向固定为：

```text
前端表单 → 商品试算接口 → 商品输入解析 → calculation.product
商品保存 → 商品输入解析 → calculation.product → 保存快照
订单/生产/工资/财务服务 → calculation 对应公开接口 → 业务持久化
```

- calculation 不依赖 catalog、orders 等业务模块，不访问 Repository、数据库、HTTP、当前时间或登录上下文。
- 输入与输出为有明确字段、单位和类型的不可变对象，不传 JPA 实体、通用 Map 或任意表达式。
- 各业务模块通过 Spring Modulith 公开命名接口依赖 calculation；不依赖其内部实现。实施时通过模块边界测试验证无循环依赖。
- 不增加按字符串公式编码执行的通用分发器。稳定标识用于目录和测试，调用仍使用具名方法。
- 相同已解析输入必须产生相同结果；业务常量在相应计算分类中维护，不建立含义混杂的全局常量类。

## 4. 集中管理边界

### 4.1 必须放入 calculation 的内容

材料耗用、成本、单价推导、利润及利润率、标准工作量、订单金额与收退款派生值，以及后续已确认的计薪和财务汇总公式。其逐步舍入规则也属于公式实现，不允许前端或 SQL 重新实现。

数值余额公式可接收业务服务读取的事实或聚合输入进行计算。数据库可以做事实筛选和基础聚合，但不能在查询中另写成本、利润、工资等计算链；同一口径的有效事实筛选由所属业务模块统一维护。

### 4.2 仍属于业务模块的内容

输入校验、引用选择、快照读取、权限、业务状态、事务、并发锁、事实入账、幂等和结果持久化。

例如“可执行数量如何计算”归集中计算模块，“核验时锁定哪些记录、是否允许扣减、如何防重复核验”仍属于生产领域服务。不能把所有业务规则都变成数值函数。

商品标准人工成本与工资应发金额即使形式类似，也不等价；工资须使用已确认的生产与工时事实及独立计薪政策。

### 4.3 前端职责

仅负责录入、格式校验、发送试算、加载/错误/过期状态及结果展示。允许金额文本格式化，不允许用原生浮点数或 decimal.js 在前端重新推导成本、利润、标准产量等业务结果。

## 5. 精度与公式基线

| 数值 | 规则 |
| --- | --- |
| 金额、成本、单价 | 后端 BigDecimal；金额结果 4 位、HALF_UP；API 十进制字符串 |
| 损耗率 | 页面提交百分比文本，后端转换为内部比例；沿用 6 位 HALF_UP |
| 商品预计利润率 | 沿用 6 位；接口同时提供可直接展示的百分比文本，前端不另算比例 |
| 胶水克重 | 运算后 HALF_UP 取整数 |
| 工作日标准数量 / 有效工时产量 | 向下取整数，然后参与人工费计算（有效工时产量 = `floor(工作日小时数 × 60 × 制品有效工时率 ÷ 星级标准分钟)`） |
| 工时 | 保持既有分钟/时长精度，不按金额规则截断 |

金额统一 4 位不代表任意步骤都截断。公式目录逐项记录舍入节点，后端按既有已确认运算顺序执行。

商品零售价利润率沿用当前接口语义；订单零应收利润率遵守其“—”的需求，不复用商品零值口径。缺失与非法输入不能统一静默转换为零。

胶水/色浆单价、星级时长、包装档位、时薪、工作日小时数、制品有效工时率、目标利润率及已开放的默认费用继续使用现有设置入口。**2026-09-25 起**：时薪、工作日小时数、制品有效工时率与目标利润率都是全局设置（`hourly_wage`、`workday_hours`、`making_effective_hour_rate`、`target_margin_rate`），不再是代码常量。

## 6. 后端试算与保存

### 6.1 试算接口

建议在商品业务 API 下新增两个认证接口，采用项目统一响应信封，不暴露 calculation 为可执行任意公式的 HTTP 服务：

- `POST /api/products/preview`：新建商品试算。
- `POST /api/products/{id}/preview`：已有商品编辑试算，携带现有版本号，使用与更新相同的缺省字段合并语义。

路径为拟新增契约，实施前与现有控制器前缀统一并同步接口矩阵。

请求只包含影响计算的商品输入、星级/档位引用及明确的刷新意图（`refreshGlobalReferences` 一键按最新全局设置重算星级/档位/材料单价，或 `refreshMaterialPrices` 仅刷新材料单价）；客户端不能提交派生总成本、人工费或利润作为权威值。名称、图片等不影响计算的必填资料不阻止试算，但正式保存仍执行完整校验。

响应包含胶水克重、材料分项、人工分项、其他成本、总成本、参考售价、参考缝边收费、标准数量、利润及利润率等完整预估结果。金额与比例为字符串，展示百分比字段由后端生成；输入错误通过 fieldErrors 返回。

试算仅读取数据和计算：不得分配商品编号、持久化商品、刷新已有快照、写业务变更日志或产生资金/生产事实。这两个 POST 不要求 Idempotency-Key，不写幂等记录或业务写审计；保留认证、安全日志与 requestId。实现时仅按上述精确方法/路径组合豁免写过滤器，不按通用 preview 后缀放行，其他业务写命令规则不变。

### 6.2 输入解析复用

在商品业务模块内提取明确的输入解析能力，供新建、更新及对应试算调用；此能力读取设置和商品资料，但不包含成本公式。

- 新建：取当前设置与用户覆盖字段。
- 编辑未换星级或档位：取商品原有快照；选择同一引用不等同于刷新。
- 编辑换成不同星级或档位：按现有规则取对应当前配置。
- 材料单价：仅明确刷新时读取当前全局价格，否则保持商品快照。
- 管理员显式请求按最新设置重算时（`refreshGlobalReferences`），星级/档位/材料单价一并读取当前全局值；编辑页仅在检测到差异时展示提示与该入口。
- 每次试算所需配置在一致的读取边界内解析，避免同一响应混用变更前后的配置。

### 6.3 保存时再次计算

保存不接受前端预估结果，不复用前端传回的总金额；在业务事务内重新校验、解析输入并调用同一 ProductPricing 入口，然后保存快照。

预估不占用配置，也不保证此后配置永远不变。同一输入及同一配置下预估与保存必须相同；若两次请求间配置发生变化，保存以事务内重新解析结果为准，页面展示保存结果并在金额变化时明确提示。商品版本冲突沿用现有冲突处理，不默默覆盖。

## 7. 前端交互

保留现有表单与右侧预估布局，仅更换计算来源。

- 计算相关字段有效且齐备后，输入停止约 300ms 发起试算；修改名称或备注不触发试算。
- 每次输入变化立即将旧结果标记为非当前结果；取消旧请求并使用递增请求标识，仅接受最新请求结果。
- 字段不完整时显示“待填写”，非法文本走字段提示；加载时显示“计算中”。
- 网络错误显示“试算失败，可重试”，不得把失败显示为零或继续把旧金额展示为当前结果。
- 不提供本地公式降级，断网时不产生新的预估。
- 保存独立执行完整后端计算，不以试算成功作为唯一安全校验；保存成功后取消在途试算并显示保存响应，避免迟到响应覆盖。

代价是增加网络请求并依赖服务端可用性；通过防抖和小体积响应控制开销，不在本期增加计算结果缓存或另一个计算服务进程。

删除页面 computePreview 与相关 Decimal 全局配置。是否移除 decimal.js 依赖须先检查全站真实调用，并在另获依赖移除授权后执行；不能因为商品页不再用就直接删除依赖。

## 8. 历史与版本

本期不新增公式表、公式版本表、数据库迁移、发布审批或历史重算任务。代码变更通过 Git 与发布记录追踪；已保存商品、订单等结果快照不因模块迁移或新公式发布而批量更新。

编辑商品继续按现有规则触发重算；已确认订单仍读取其自身快照。不能用当前公式重新计算历史详情以替代已冻结结果。现有明确的读时派生字段保持其原语义，不新增隐式历史重算。

没有逐笔公式版本与完整输入快照时，只能承诺保存历史结果，不能承诺任意旧版本精确复算。未来工资若要求可重演，应另行设计规则版本、来源事实、输入快照和更正机制，不能用中央模块的当前代码冒充历史版本。

## 9. 公式目录与扩展

建立集中公式目录，记录公式标识、中文名称、分类、输入和单位、表达式、舍入节点、结果含义、集中模块代码位置及测试编号。目录与实现、测试一同更新，但目录不作为运行配置。

新增订单、生产、工资、财务公式必须实现于 calculation 对应分类，业务服务不得持有副本。只复用业务含义真正相同的公式，不因表达式形式相同而混淆规则。

以下订单口径需保留区分：

- 订单结清净额 = 累计订单收款 − 累计订单变更退款。
- 订单待退款 = max(累计订单收款 − 当前有效应收 − 累计订单变更退款, 0)。
- 累计实际净收 = 累计订单收款 − 累计订单变更退款 − 累计售后退款。

工资单价、计薪数量、返工计薪及结算周期另行确认；财务登记事实不能由试算接口生成，财务模块不反向接管订单生命周期。

## 10. 实施项与验收

以下仅为设计级清单，评审通过后再细化实施计划。

### A. 固定当前基线与迁移清单

- [ ] 核对商品测试及规格，列出实施时全部已存在的公式和调用点，区分数值公式与业务约束。
- [ ] 建立人工核算期望结果的样例，金额、比例均以字符串保存。
- [ ] 覆盖零售价、零费用、无包装、损耗取整边界、非整除标准产量、高精度单价、小数工时及舍入敏感输入。

验收：明确迁移清单，无遗漏的公式副本；需求与代码冲突单列确认，不借迁移改口径。

### B. 建立统一计算模块

- [ ] 将 ProductPricing 及其常量、输入、结果迁入 calculation；更新全部调用点，移除旧实现。
- [ ] 集中纯数值精度工具，定义 Spring Modulith 公开接口与单向依赖。
- [ ] 迁移已有其他公式时采用同样边界，不建立未实现业务的空分类。

验收：迁移前后基准结果逐项相同；边界测试通过；业务模块和前端不再保留迁移公式的副本。

### C. 接入试算与统一输入解析

- [ ] 新建/编辑试算与保存共用输入解析和计算入口，试算采用一致读取。
- [ ] 验证认证、字段错误、商品不存在、版本冲突及试算无业务写入。
- [ ] 覆盖旧快照、同一引用、换引用、刷新材料价，以及试算后配置变化场景。

验收：相同输入及配置的试算与保存结果一致；保存拒绝或忽略派生金额注入，不信任客户端计算结果。

### D. 前端替换为服务端预估

- [ ] 删除本地计算链，接入防抖请求、加载、字段错误、网络失败与重试状态。
- [ ] 测试快速输入和响应乱序、编辑对象切换、保存时仍有试算在途。
- [ ] 保持原表单布局和快照刷新语义，展示保存后的最终结果。

验收：浏览器验证新建、编辑、配置变动、网络失败；旧响应不能覆盖新输入或保存结果；前端无公式降级副本。

### E. 门禁与文档同步

- [ ] 全量后端测试、前端类型检查与测试；失败逐项归因，补充模块边界与试算集成测试。
- [ ] 启动本地应用实测 API 与浏览器交互，记录证据；不能只用单元测试宣称完成。
- [ ] 同步架构图与模块列表、当前 OpenSpec 设计/接口矩阵/任务，以及前端预估口径，明确替换旧本地预估方案。

验收：全部迁移调用集中到 calculation；文档不存在“前端本地预估”和“不新增试算 API”的冲突要求；保留他人未提交工作，不自动提交 Git。

## 11. 本期不做

- 动态公式编辑、表达式解释器、任意脚本、规则编排。
- 公式管理页面、审批发布、生效时间配置。
- 微服务化或独立计算部署。
- 万能计算大类、无类型通用执行接口、跨业务数据库依赖。
- 公式数据库版本表、批量历史重算或历史快照改写。
- 新增时薪/利润率设置或改变已定公式。
- 未确认的工资和财务实现、UI 重设计、自动 Git 提交。

## 12. 结论

公式代码真正集中在后端 calculation 模块，分类清楚但不散落在业务模块。试算与正式保存执行同一份代码，前端只展示结果；通过集中测试和模块边界约束防止后续重新分散。
