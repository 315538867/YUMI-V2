## 1. 设计目标

HTTP API 是模块化单体的外部适配层，不是模块之间的内部调用方式。请求进入后必须转换为一个明确的查询用例或一个完整业务命令，由应用层负责事务和跨模块编排。

统一路径为：

```text
HTTP 请求
→ 认证与请求上下文
→ 协议解析和边界校验
→ 一个完整应用查询或命令
→ 统一响应转换
```

HTTP 层不得：

- 直接访问 Repository、数据库或其他模块表；
- 在 Controller 中编排多个模块；
- 根据页面需要拼装多个写操作；
- 重算数量、金额、余额或业务状态；
- 把内部 Java 接口包装成内部 HTTP 调用；
- 把数据库异常原文返回给客户端。

## 2. API 总体边界

### 2.1 外部 API 与内部模块接口分离

外部 HTTP 契约和内部模块 Java 契约是两层不同边界：

```text
HTTP DTO
→ 应用命令/查询输入
→ 模块公开应用接口
→ 领域规则与 Repository
```

HTTP DTO 不直接复用数据库行模型、内部领域聚合或跨模块端口输入。HTTP 层可以对外部字段、旧协议和权限上下文做适配，但不能改变应用层的业务语义。

模块之间继续使用同进程 Java 接口，不通过 HTTP 自调用，也不在单体内部增加序列化、网络重试和网关式编排。

### 2.2 API 根路径和版本

外部业务 API 采用明确的版本根路径：

```text
/api/v1/...
```

版本表示外部协议契约，不表示数据库版本、Flyway 版本或内部模块版本。

同一单体内部不维护多套 Java 接口兼容版本。外部协议发生不兼容变更时，新建 `/api/v2` 适配层；可以兼容的字段扩展优先保持 `/api/v1` 向后兼容。

不把版本号放在业务资源名称、数据库表名或模块包名中。

### 2.3 资源按业务所有权划分

路径按命令所有者和业务上下文划分，不按数据库表或技术层划分：

```text
/api/v1/orders
/api/v1/production
/api/v1/scheduling
/api/v1/after-sales
/api/v1/payroll
/api/v1/cost-ledger
/api/v1/finance
/api/v1/reporting
/api/v1/master-data
/api/v1/files
```

这些是资源边界示例，不意味着每个模块必须把所有内部对象都公开为 HTTP 资源。

公开资源必须对应真实业务能力。禁止暴露以下数据库式路径：

```text
/api/v1/tables/{tableName}
/api/v1/{module}/projections/{id}/update
/api/v1/{module}/facts/{id}/edit
/api/v1/{module}/execute
```

## 3. 查询与命令协议

### 3.1 查询接口

无请求体的普通资源读取使用 `GET`，只读且不得产生业务写入：

```text
GET /api/v1/orders/{orderId}
GET /api/v1/orders
GET /api/v1/production/workbench
GET /api/v1/scheduling/tasks
GET /api/v1/reporting/costs
```

查询返回当前投影、有效事实关系和必要冻结快照。查询接口不得返回一个可以直接作为正式命令输入的“授权结果”。预览、影响评估和试算结果只代表查询时点的观察结果。

### 3.2 正式命令接口

正式业务动作使用明确的命令端点，由一个 HTTP 请求调用一个完整应用命令：

```text
POST /api/v1/orders/{orderId}/confirm
POST /api/v1/orders/{orderId}/changes
POST /api/v1/orders/{orderId}/shipments
POST /api/v1/orders/{orderId}/receipt
POST /api/v1/orders/{orderId}/complete
POST /api/v1/scheduling/tasks
POST /api/v1/scheduling/tasks/{taskId}/cancel
POST /api/v1/scheduling/tasks/{taskId}/verify
POST /api/v1/production/items/{itemId}/restore-packaging
POST /api/v1/after-sales
POST /api/v1/after-sales/{caseId}/redelivery
POST /api/v1/after-sales/{caseId}/replacement
```

命令端点表达业务动作，不暴露参与模块的内部写入动作。例如普通发货由 `orders` 的命令端点负责协调 `production`，不提供让客户端直接调用 `production.consumeForShipment` 的 HTTP 端点。

资源的普通创建、替换和取消也必须经过业务命令语义；不默认提供通用 `PUT` 或 `PATCH` 让客户端直接编辑事实和投影。

### 3.3 草稿与正式命令

草稿可以通过资源接口保存和修改，但草稿持久化不表示业务事实已经生效：

```text
POST   /api/v1/orders/drafts
GET    /api/v1/orders/drafts/{draftId}
PUT    /api/v1/orders/drafts/{draftId}
DELETE /api/v1/orders/drafts/{draftId}
POST   /api/v1/orders/drafts/{draftId}/confirm
```

草稿确认端点必须重新读取当前订单、余额、价格、资格和权限。不能使用草稿创建时缓存的状态直接提交。

### 3.4 预览与影响评估

不需要复杂请求体的预览可以使用 `GET`；包含拟变更明细、来源选择或试算参数的复杂预览使用 `POST`。这里的 `POST` 只表示复杂查询输入，不产生业务写入。例如：

```text
POST /api/v1/orders/{orderId}/changes/preview
POST /api/v1/orders/{orderId}/shipments/preview
POST /api/v1/after-sales/preview
```

预览可以返回差异、预计金额、可选来源和校验提示，但不得写入正式事实、投影、占用、幂等成功记录或审计结果。正式命令必须再次校验；预览响应中的余额、状态和授权结论不能作为提交依据。

## 4. 统一成功响应

### 4.1 响应信封

所有业务 API 成功和失败都使用统一响应信封：

```json
{
  "code": "OK",
  "message": "操作成功",
  "fieldErrors": {},
  "requestId": "req_01J...",
  "data": {}
}
```

字段语义：

| 字段 | 语义 |
|---|---|
| `code` | 稳定机器可读结果码 |
| `message` | 面向操作者的简短说明，不作为程序分支依据 |
| `fieldErrors` | 字段级错误，成功时为空对象 |
| `requestId` | 本次 HTTP 请求的追踪标识 |
| `data` | 业务数据；无数据时为 `null` |

客户端只根据 `code`、HTTP 状态和结构化字段处理逻辑，不解析 `message`。

### 4.2 成功 HTTP 状态

按业务语义使用标准状态：

```text
200 OK          查询成功、命令成功
201 Created     创建正式资源成功
```

所有业务 API 都返回统一信封；没有业务数据时返回 `data: null`，不使用 `204 No Content`。核心业务命令不使用 `202 Accepted` 假装已经完成；只有真正异步、结果尚未形成且另有任务状态模型的操作才可使用 `202`。

### 4.3 响应数据边界

成功响应只返回公开接口模型：

- 稳定业务标识；
- 当前状态和必要投影；
- 业务事实摘要；
- 冻结快照摘要；
- 版本和时间；
- 后续操作所需的业务链接或能力标识。

不得返回 SQL、数据库列、内部类名、Repository 信息、锁信息或未经授权的敏感字段。

金额、比例和高精度数值以字符串传输，避免不同客户端的浮点精度损失：

```json
{
  "amount": "128.50",
  "marginRate": "0.3125"
}
```

数量使用明确单位的整数，并在字段名或契约说明中区分订购数量、制作完成数量、缝边数量、发货数量等业务含义。不使用浮点数表示数量。

## 5. 统一错误响应

### 5.1 错误信封

失败仍使用同一信封：

```json
{
  "code": "PRODUCTION_SOURCE_INSUFFICIENT",
  "message": "可用于本次发货的制作来源数量不足",
  "fieldErrors": {
    "requestedQuantity": ["不得超过当前可交付数量"]
  },
  "requestId": "req_01J...",
  "data": null
}
```

错误响应不得包含：

- SQL 语句；
- 表名、列名和数据库连接信息；
- Java 堆栈；
- 文件系统路径；
- 第三方响应中的敏感内容；
- 其他客户或订单的数据。

### 5.2 HTTP 状态映射

HTTP 状态表达协议层和错误类别，`code` 表达稳定业务原因：

| HTTP 状态 | 典型含义 |
|---|---|
| `400` | 请求格式、字段类型或参数组合不合法 |
| `401` | 未认证、会话无效或认证凭证过期 |
| `403` | 已认证但无权执行该业务动作 |
| `404` | 资源不存在，或当前操作者不可见 |
| `409` | 业务状态冲突、版本冲突、幂等键冲突、重复业务事实 |
| `422` | 请求格式正确但违反业务规则 |
| `429` | 请求频率或并发限制 |
| `500` | 未预期程序缺陷 |
| `503` | 当前依赖不可用或系统暂时无法处理 |

认证失败、业务无权、资源不可见和业务状态冲突不得混成一个通用错误。

业务错误码由发现规则的模块定义。例如：

```text
ORDERS_STATUS_INVALID
PRODUCTION_SOURCE_INSUFFICIENT
SCHEDULING_TASK_NOT_CANCELLABLE
AFTER_SALES_ROUTE_INVALID
PAYROLL_SETTLEMENT_LOCKED
FINANCE_AMOUNT_MISMATCH
COST_LEDGER_SOURCE_INVALID
CONFLICT_IDEMPOTENCY
CONFLICT_EXPECTED_VERSION
```

同一业务错误码只由一个模块拥有。HTTP 层只负责映射，不重新解释业务规则。

### 5.3 字段错误

`fieldErrors` 使用字段路径到错误信息列表的映射，支持嵌套对象和数组：

```json
{
  "fieldErrors": {
    "items[0].requestedQuantity": ["必须大于 0"],
    "deliveryAgreementId": ["不属于当前订单"]
  }
}
```

跨字段规则没有单一字段归属时使用业务错误码和空字段路径，不把复杂业务规则伪装成字段格式错误。

## 6. 请求上下文、认证与权限

### 6.1 请求标识

每个请求都必须有服务端可追踪的 `requestId`：

- 客户端可以通过 `X-Request-Id` 提供候选值；
- 服务端必须校验格式、长度和敏感内容；
- 不合规时由服务端生成新的标识；
- 响应信封和响应头返回最终 `requestId`。

请求标识用于日志、审计和跨模块执行上下文，不作为业务事实唯一键。

### 6.2 认证上下文

HTTP 层从认证机制取得不可变操作者上下文并传入应用命令：

```text
operatorId
session/authentication context
requestId
tenant/workspace context（如未来启用）
```

认证机制、会话存储和角色权限基础能力由 `platform` 设计；Controller 不自行解析令牌后决定业务授权。

具体业务授权由命令所有者和参与模块在事务内重新判断。客户端传入的 `operatorId`、角色或权限列表不能覆盖服务端认证上下文。

### 6.3 认证与业务授权的区分

```text
401：服务端无法确认操作者身份
403：身份已确认，但没有执行该业务动作的权限
422/409：身份和基础权限满足，但业务状态或规则不允许
```

不得用隐藏资源返回 `200` 来掩盖所有权限失败，也不得让平台通用权限检查器绕过模块业务授权。

## 7. 幂等、重试与并发控制

### 7.1 外部命令幂等

所有会产生正式业务事实的 `POST` 命令必须支持幂等，客户端通过请求头提交：

```text
Idempotency-Key: <opaque-key>
```

幂等键的规则：

- 在“命令所有者 + 操作者 + 业务命令类型”范围内解释；
- 服务端保存请求指纹，不能只保存键名；
- 相同键、相同指纹、已成功时返回第一次成功结果；
- 相同键、不同指纹时返回 `409 CONFLICT_IDEMPOTENCY`；
- 已回滚的尝试不留下成功记录，允许重新执行；
- 并发相同键请求不得并行产生两套事实；
- 幂等成功记录与业务事实、快照、投影在同一事务中提交。

查询请求不需要 `Idempotency-Key`，文件上传临时记录和正式业务命令分别拥有自己的幂等语义。

### 7.2 并发版本

需要基于当前读取结果提交的命令必须携带预期版本：

```json
{
  "expectedVersion": 7
}
```

服务端在锁内重新读取当前版本。版本不一致返回：

```text
409 CONFLICT_EXPECTED_VERSION
```

响应可以返回当前版本和重新读取所需的资源摘要，但不能自动合并具有业务含义的数量、金额或状态变更。

`expectedVersion` 是并发校验输入，不是调用方可以直接写入的目标版本。服务端决定新版本并在成功响应中返回。

### 7.3 重试边界

客户端只可对明确标记为可重试的基础设施失败或网络未知结果进行重试，并必须复用同一 `Idempotency-Key`。不能通过更换幂等键规避未知结果而再次执行收款、发货、核验或退款。

业务拒绝、版本冲突和幂等键冲突不应自动重试。服务端不使用死锁重试掩盖未设计好的模块锁序；数据库瞬态错误是否重试属于后端基础设施策略，不能改变业务命令语义。

## 8. 分页、筛选和排序

### 8.1 列表请求

列表接口统一使用明确参数：

```text
pageSize
cursor
sort
filter
```

长列表和工作台优先采用基于稳定排序键的游标分页：

```text
GET /api/v1/orders?pageSize=50&cursor=...
```

分页响应：

```json
{
  "items": [],
  "nextCursor": "...",
  "hasMore": true
}
```

确需页码跳转的低频管理列表可以使用 `page` 和 `pageSize`，但必须明确总数计算成本和数据变化时的非稳定性。

### 8.2 排序和筛选

排序字段、方向和筛选操作符只能映射到服务端白名单，不能把客户端字符串直接拼接进 SQL：

```text
sort=createdAt.desc
filter=status:eq:IN_PROGRESS
```

实际字段映射由查询模块维护。未知字段、未知操作符和超出范围的 `pageSize` 返回结构化输入错误。

列表查询不保持长事务，不保证用户翻页期间的数据快照完全不变。正式命令必须重新读取和校验当前状态。

### 8.3 查询返回边界

列表返回面向页面和业务工作台的不可变摘要，不返回无限嵌套的完整聚合。详情接口按业务上下文返回必要的组合数据；跨模块组合由业务上下文所属模块或 `reporting` 完成。

查询缺失核心数据时必须明确失败或标记数据不完整，不能把异常转换为零值、空列表或“无记录”。

## 9. 文件 API

文件不直接作为正式业务命令的隐式副作用处理，采用临时文件和正式关联两步流程。

### 9.1 临时上传

```text
POST /api/v1/files/temporary
GET  /api/v1/files/temporary/{fileId}
DELETE /api/v1/files/temporary/{fileId}
```

临时上传接口负责：

- 文件大小、类型和数量限制；
- 内容校验和安全扫描入口；
- 暂存记录、上传人和过期时间；
- 返回不可变的临时文件标识。

文件内容上传、对象存储写入和临时文件删除不放入正式业务数据库事务。

### 9.2 正式关联

正式业务命令只提交临时文件标识：

```json
{
  "attachments": [
    {"temporaryFileId": "file_tmp_01J..."}
  ]
}
```

命令事务内由 `platform` 校验临时文件归属、用途、状态和有效期，并将其转为正式业务关联。文件元数据关联与业务事实、投影、幂等和审计结果一起提交。

临时文件未关联成功时，不得假设业务已经产生文件结果。未关联临时文件由过期清理任务回收；清理失败必须可观察和可重试。

### 9.3 下载

业务模块只通过公开文件查询能力获得授权后的文件引用。Controller 不把内部存储路径返回给客户端，也不允许客户端任意传入对象存储路径。

下载授权至少校验：

```text
文件存在
文件已正式关联
操作者可以访问关联业务根
文件未被业务撤销或过期
```

## 10. 时间、金额、数量和标识

### 10.1 时间

HTTP 使用 ISO 8601 格式：

```text
2026-09-28T15:30:00+08:00
2026-09-28
```

业务日期、本地业务时间和系统记录时间分开命名和传输。客户端提交的业务发生时间不能直接覆盖服务端记录时间；服务端保存接收时间和实际采用的业务时间，并按业务规则判断是否允许回填。

### 10.2 金额和比例

金额、单价、成本、利润和比例使用十进制字符串传输：

```json
{
  "unitPrice": "12.00",
  "expectedCost": "7.35",
  "profitRate": "0.3875"
}
```

服务端负责精度、舍入、币种和非负规则。客户端传入的计算结果不能替代服务端计算；如果命令需要显示用户确认的金额，必须同时传入规则允许的意图字段，服务端重新计算并比较。

### 10.3 标识

外部标识使用不可猜测、稳定且不暴露数据库自增规律的业务标识。客户端不依赖数据库主键格式、表名或内部模块前缀推断业务关系。

## 11. HTTP 事务与外部副作用

一个同步命令请求对应一个事务结果：

```text
请求进入
→ 认证和输入校验
→ 命令所有者开启事务
→ 跨模块同步参与
→ 事实、快照、投影、幂等和审计写入
→ 一次提交
→ 返回成功
```

HTTP 响应返回成功前，正式业务事实必须已经提交并可由查询读到。不能先返回成功，再异步写入核心事实。

以下动作在提交后执行，不影响主事务结果：

- 通知；
- 打印；
- 文件转码和派生文件生成；
- 缓存刷新；
- 可重建报表生成；
- 外部 HTTP 调用。

这些动作必须能安全重试，并记录可观察的处理状态。外部动作失败不能回滚已经提交的订单、生产、发货、收款或售后事实，也不能把未执行的外部动作伪装为已完成。

## 12. 可观测性与安全边界

每次请求至少关联：

```text
requestId
operatorId
HTTP method and route template
command or query name
module owner
operationId / commandExecutionId
result code
latency
```

日志和审计中不得记录：

- 认证凭证、会话令牌和幂等原文；
- 完整客户敏感信息；
- 文件内容和内部存储路径；
- 数据库密码、连接串和 SQL 参数中的敏感值。

请求体和响应体日志采用字段白名单或脱敏策略。业务审计记录由 `platform` 关联正式业务操作，但审计记录不能替代业务事实。

HTTP 层必须防止：

- 未授权的跨订单资源访问；
- 将客户端字段直接映射到 SQL；
- 任意文件路径和对象键访问；
- 通过错误响应泄露内部结构；
- 重放导致重复收款、发货、核验或退款；
- 过大的分页、批量和上传请求造成资源耗尽。

## 13. API 契约测试要求

HTTP API 进入实现后至少需要以下验证：

### 13.1 协议测试

- 成功和失败都符合统一响应信封；
- `code`、`message`、`fieldErrors`、`requestId`、`data` 字段语义稳定；
- 金额、比例和时间格式符合契约；
- 未知字段、未知排序和非法分页参数得到明确错误；
- 认证失败、无权、资源不可见和业务冲突映射正确；
- 错误响应不泄露 SQL、表名、堆栈和敏感数据。

### 13.2 命令集成测试

- 一个 HTTP 命令只触发一个完整应用命令；
- 同一幂等键重放不产生第二套事实；
- 同一幂等键不同请求指纹被拒绝；
- 版本冲突不会覆盖他人更新；
- 参与模块失败时 HTTP 返回失败且全部回滚；
- 命令成功后事实和投影立即可查询；
- 提交前不执行通知、打印、第三方调用和文件删除；
- 文件临时记录只能在授权的正式命令中关联。

### 13.3 安全测试

- 不同操作者不能访问无权订单、文件或工资信息；
- 修改路径标识不能越过业务根授权；
- 客户端不能伪造 `operatorId`、角色、金额、余额或状态；
- 大分页、批量命令和上传限制有效；
- 重复提交、网络重试和未知结果恢复符合幂等规则。

## 14. 明确不采用

- Controller 直接访问 Repository 或数据库；
- 一个 HTTP 请求编排多个独立命令；
- 模块之间通过内部 HTTP 调用；
- `POST /execute` 或通用 JSON 命令入口；
- 对事实、投影和余额提供通用 `PUT/PATCH`；
- 用 HTTP `202` 掩盖核心事实尚未提交；
- 以客户端提交的金额、余额、状态或权限作为权威；
- 只根据 `message` 文本判断业务结果；
- 用页码分页承载所有高频工作台列表；
- 把文件上传、通知和第三方调用塞入核心数据库事务；
- 把数据库主键、内部表名和对象存储路径暴露给客户端；
- 让报表查询直接联表读取业务模块数据库；
- 使用多个 HTTP 版本的内部 Java 模块接口。

## 15. 已确认不变量

```text
HTTP 只是外部适配层，不拥有业务规则
一个正式请求只调用一个完整应用命令
Controller 不编排多个模块、不访问 Repository、不计算余额和金额
查询与命令分离，预览结果不构成正式授权
所有核心命令使用统一响应信封
业务错误码由发现规则的模块定义
认证上下文由平台提供，业务授权由业务模块负责
正式写命令通过 Idempotency-Key 防止重试重复执行
版本冲突返回结构化 409，不自动覆盖或合并业务变更
金额和高精度数值以十进制字符串传输
数量使用明确单位的整数
列表查询使用受白名单约束的筛选、排序和分页
临时文件先上传，正式命令事务中只关联元数据
核心业务成功响应前事实、投影、幂等和审计已经提交
通知、打印、第三方调用和文件外部操作在提交后执行
外部协议版本与内部模块版本、数据库迁移版本分离
```
