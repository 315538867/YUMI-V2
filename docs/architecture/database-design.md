## 1. 设计状态

本文是目标逻辑模型，不是 SQL 或已存在的数据库。物理方案本轮只落实关系、索引与约束意图；共享来源、目标分配、重过工序和覆盖事实的具体拆表、逐列 SQL/字段映射、编号具体前缀/值及精确锁行清单仍由 1.2 负责，下文逻辑对象不表示都已落为同名物理表。实体所有权、来源守恒、不可变事实及事务关系不得因物理映射改变；工程设计待落实不意味着已否决的执行登记/C9仍待审批。

本机未上线，基线计划为直接改写单一 `V1__yumi_v2_schema.sql` 并清库重建，不做兼容迁移、历史数据搬迁或双读双写；实施前须确认目标连接和本机数据边界。本轮不执行该计划，不新增共享环境部署需求。

## 2. 通用约定

- 主键使用 `BIGINT UNSIGNED` 内部 ID；业务编号另设唯一索引；
- Java 金额和单价使用 `BigDecimal`，MySQL 使用 `DECIMAL(19,4)`；比例使用 `BigDecimal` 与 `DECIMAL(9,6)`；
- 数量使用 `INT UNSIGNED`，不得为负；单件标准分钟、冻结估算分钟及其他排班实录分钟沿用整数口径；工作日小时、有效率与有效制作分钟使用 BigDecimal/对应 DECIMAL 精确计算，不提前取整，显示舍入不参与超出判定；
- 业务日期使用 Java `LocalDate` 和 MySQL `DATE`，操作时间使用 `Instant` 或明确时区的时间类型并映射到 `DATETIME(6)`；
- 所有可并发修改的 JPA 聚合根保存 `version` 并使用 `@Version`；
- 表默认保存 `created_at`、`created_by`，需要变更的当前资料保存 `updated_at`、`updated_by`；
- 不可变事实表不提供通用更新或软删除；更正使用关联原记录的新事实；
- 状态使用受控字符串或小型代码表，禁止数据库自由文本；
- JSON 仅用于非检索型快照补充，不替代关键字段、外键和约束；
- 需要锁定关键数量余额时使用 JPA 悲观写锁或显式 `SELECT ... FOR UPDATE`；
- Flyway SQL 是数据库结构唯一来源，Hibernate 仅以 `ddl-auto: validate` 验证映射。

## 3. 模块与表归属

| 顶级模块 | 主要表 |
| --- | --- |
| `identity` | `admin_accounts` |
| `catalog` | `products`、`customers`、`employees`、`employee_work_types`、`employee_employment_events`、`master_data_change_logs`、静态数据目录 `star_levels`/`packaging_tiers`/`seam_types`/`work_types` |
| `orders` | `orders`、`order_items`、订单快照和变更表、履约表、草稿库存计划表、发货表、收退款表、售后表 |
| `inventory` | `inventory_batches`、库存流水表、库存领用表 |
| `scheduling` | `scheduling_tasks`、`scheduling_task_items`、`scheduling_verifications`、`rework_sources` 及核验目标分配、`scheduling_scrap_records`、`scheduling_quantity_returns`、来源分配/实际流转/重过工序事实、`scheduling_reminders` 和其他排班表；共享来源保留普通订单或售后业务所有者 |
| `calculation` | 无表（无持久化的集中计算支撑模块，只接收不可变数值输入并返回结果） |
| 基础设施 | `number_sequences` 及文件元数据表（实现时定义） |

业务 Java DAG 固定为 `scheduling → orders`、`scheduling → inventory → orders`。反向调用经请求方自有 port 及全部 DTO，由 scheduling adapter 实现；orders 不引用 scheduling/inventory 类型，inventory 不引用 scheduling 类型。orders 持有确认/变更应用与冻结需求工艺证据，inventory 持有批次冻结工艺证据，scheduling 持有执行份额 routeSnapshotId 并关联真实上游证据；不能用同名 route_snapshot_id 推定跨域表所有权或直接跨模块写表。底层 ledger 只依赖本域 repo，Receipt/writer 不回调上层服务或反向端口。

`shipments`、`payments`、`refunds` 和售后需求/用途/覆盖/台账 `after_sales_*` 使用独立表是为了保存独立事实和约束，不代表它们是独立顶级业务模块；这些业务命令、状态和事务边界由 `orders` 拥有。售后共享加工来源则属于 `scheduling`，保留售后业务所有者并通过接口接入 orders 台账，不能因物理表名前缀或共享任务转移所有权。库存批次与终点入库流水属于 `inventory`。未来完整财务模块只能读取或订阅订单收退款事实，不在首期接管这些表。

## 4. 身份与基础资料

### `admin_accounts`

`id`、`username`、`password_hash`、`status`、`linked_employee_id`、登录安全字段、版本和时间字段。

约束：用户名唯一；关联员工可空；首期只有管理员类型。

### `products`

当前商品资料、启停状态、销售单价、重量、损耗率、材料单价与成本、星级与制作成本快照、包装档位快照、缝边默认值（默认缝边剪袋类型 id + 名称与标准分钟快照 + 单件缝边人工成本快照 + 缝边价格）、模具数量 `mold_quantity`、每日批次数 `daily_batch_limit`、其他单件成本和总成本。`mold_quantity` 与 `daily_batch_limit` 均为正整数；当前产品最大日产能由两者乘积派生，不作为独立可编辑事实持久化。模具数量和日产批次数只参与产能，不影响成本。

业务编号 `product_no` 唯一。

商品**不保存缝边数量与缝边成本**：`total_cost`/`reference_price` 始终按**不缝边剪袋**口径落库；缝边剪袋变体预算（不缝边剪袋总成本 + 单件缝边人工成本，后者 = 缝边标准分钟 × 全局时薪 ÷ 60）由 `calculation` 的 `FP-PROD-20/21` 读时派生，只出现在商品试算与详情响应里。`seam_type_id` 可空（空＝默认不缝边剪袋），非空时外键指向 `seam_types`。

### `customers`

客户编号、名称、联系人、联系电话、备注，以及一组默认收货信息。

客户名称和电话不唯一；重复仅提示。

### `employees`

员工编号、姓名、电话、状态、首次入职日期、备注和版本。

### `employee_work_types`

员工与制作、捏毛装袋、缝边剪袋、其他的多对多关系。

### `employee_employment_events`

入职、离职、重新入职事件及日期、原因和操作人。

### `master_data_change_logs`

商品、客户和员工当前资料的变更前后值、原因和操作人。关键可检索字段可拆专表，首期允许结构化 JSON 保存前后快照。

## 5. 订单模块：订单核心

### `orders`

订单编号、客户引用、主状态、下单日期、期望交付日期、当前收货信息、备注、金额汇总、款项汇总缓存、确认/取消/关闭信息和版本。

业务编号 `order_no` 唯一。

### `order_items`

订单、商品引用、当前有效数量、缝边数量、成交价格、金额、备注、当前需求处理汇总和版本。

每个明细有稳定 ID，订单变更不通过删除重建改变其历史身份。

### `order_confirmation_snapshots`

订单确认时的客户、收货、金额、备注和确认人快照。

### `order_item_snapshots`

商品名称、编码、图片、说明、星级、成本组成、成交价格、数量、缝边参数和冻结流程快照。

### `order_change_orders`

变更单编号、订单、状态、原因、创建和确认信息。

### `order_change_items`

变更路径、变更前后值，以及数量减少/工艺版本替换时的逐份额处理方案。涉及数量的变更必须保存结构化字段，不能只保存文本 diff。普通来源/处置保存独立 `order_change_item_id`（`orderChangeItemId`）起因，不借用 `after_sales_disposition_id`（`afterSalesDispositionId`）；按命令类型校验对应真实起因关系。

`order_change_item_applications` 是 orders 拥有的 ADD 确认应用事实：`order_change_item_id UNIQUE` 关联真实变更行，`created_order_item_id` 关联本次新明细，`route_snapshot_id` 关联 orders 自有的该明细冻结路线/工艺快照。该快照属于 orders 的确认/变更证据，不指向 scheduling 内部快照表，不要求 orders 创建或直接写排班快照；scheduling adapter 读取公开证据后生成/关联自身份额 routeSnapshotId，保留两者追溯映射，不假设跨模块本地 ID 相同。两条同商品 ADD 各保存独立真实映射，不以商品、行号、查询顺序择行；UPDATE/REMOVE 仍用原 orderItemId。映射与明细、快照、需求和来源在同事务写入，重放不重复映射或授权，失败全部回滚；逐列类型及 FK 映射归 1.2，不虚构已存在物理列。

ADD、无实物增减、路线/工艺变化及实物/取消处置全部使用 orders 自有 `OrderSchedulingDispositionPort` 一份 Influence/LockedPlan：整批 inspect → owner锁 → lockAndValidate其余L锁 → orders写真实应用结果 → applyLocked 建新源并处置旧份额。不能逐行反复走 L 或另调用 Lifecycle.applyOrderChange；Lifecycle 仅确认/取消/关闭/退回建源。既有资源先全部纳入锁计划，新建行无需补锁不存在资源；发现遗漏既有资源须整笔重试或拒绝，不能拿库存锁后回锁来源。

订单确认按冻结路线和库存跳过后的缺口生成初始 root/share/各段 source；`ADD`、数量增加与工艺版本变化带来的新需求只追加有起因的新授权来源，既有 `total` 不覆写。无实物减量按选中份额全链追加终止，并同事务显式合法取消制作及下游等待计划；部分减量先取消整条旧计划，余量仅待重排。已有实物逐份额继续转库存或合法报废，不能把同一份额各工序额度 `SUM` 成实物量。新授权使用新工艺快照，旧任务及实物快照不改，不产生工艺改造许可。

取消无执行/领用/发货等事实订单时，未占用初始 sources 同事务全链终止；自动授权不是执行事实，既不能误阻取消，也不能遗留可排额度。有关联计划时仍需显式合法取消及事实守卫。终态订单禁止新增普通交付安排，但守卫须识别所有者/用途，不误禁既有合法余量转库存或独立售后链。

## 6. 订单模块：履约台账

推荐使用“不可变事件 + 当前投影”组合，而不是给每个数量来源建立可随意编辑的计数器。

### `fulfillment_entries`

每条数量事实：订单明细、来源类型、来源记录、工序或最终节点、方向、数量、业务时间、操作人、冲销关系。

来源类型覆盖订单需求、订单变更、库存接入、加工合格、返工目标来源与合格流转、制作补做额度、下游重过工序额度、转成品余量、发货消耗和发货恢复，须区分额度事实与实际流入事实。报废本身不登记为同工序合格或实物流入；补做与重过额度不增加客户需求。`scheduling_task_items` 及 `source_type`/`source_id`、分配/消费和前序事实关联为加工事实的追溯入口；跨模块投影、报表和发货来源链接须同步到新来源链。售后所有者的事实进入 orders 的独立售后台账，不进入原订单履约。

唯一约束：同一来源记录、来源明细、目标节点和方向不能重复入账；不能把分配给不同任务的合法来源拆分误判为重复来源。

### `order_item_fulfillment_balances`

订单明细当前投影：当前有效需求、各工序可安排额度、实际流入/可执行量、`NORMAL PENDING` 占用、已核验正常处理量、按来源与目标区分的返工/制作补做/重过余额、可发货、累计有效发货、成品余量和版本。初始可安排 = 创建时初始授权量− 累计终止量（含后续库存跳过，仅扣一次） − PENDING原占用 − 已核验正常完成 − invalidatedUnoccupied（见§8），完成含合格、返工、报废，不先扣历史计划再重复扣完成。异常来源分别守恒，汇总只合并互斥来源；产品日期工序资源与员工估算分钟按未取消 NORMAL 原计划量另算，不用可安排公式替代。

此表只能由领域服务在写入 `fulfillment_entries` 的同一事务中更新，并定期与事件重建结果校验。

### `order_inventory_plan_lines`

草稿订单的库存计划行：订单明细、批次、计划数量。**计划只是参考、不占用库存**：本表不产生库存流水、不改批次当前数量；确认时按批次聚合重验余额，不足须管理员明确转生产。同一明细同一批次唯一。

表归属 `orders`，因外键依赖 `inventory_batches` 而排在库存迁移之后建立。

## 7. 库存模块

### `inventory_batches`

批次编号、商品、来源类型和来源记录、已完成工序、缝边状态、当前数量缓存、创建时间、备注和版本。

批次不保存目标订单。期初与所有入库生产者须持久化 inventory 自有不可变路线/具体缝边工艺证据；既有 `OpeningRequest` 与 `InventoryPage` 期初入口显式 routeSeamRequired，正缝边选择合法 seamTypeId，由服务端冻结工艺/版本及分钟，node/seamState 校验已完成阶段，不接受客户端自填分钟。同批仅一种路线/工艺，混合实物分批，不靠目标订单或当前配置补猜。scheduling 领用 adapter 验证批次证据及工艺兼容性后生成/关联自身 routeSnapshotId，保留本域证据映射，不假设跨模块 ID 相同；inventory 不引用 scheduling DTO/Repository，不要求期初有不存在的终点核验。库存调整增量继承原批证据。目标 SQL 归1.2/1.4，真实期初 API 和无缝3/有缝指定工艺版本夹具归3.2，界面归8.7。

### `inventory_movements`

流水编号、业务类型、业务时间、原业务记录、操作人、原因和冲销原流水。

### `inventory_movement_lines`

流水、批次、方向、数量、变动前后数量、商品、工序、缝边状态和按需关联的订单明细。

一次业务操作的所有明细在同一事务中提交。有效流水行汇总必须等于批次当前数量。

### `inventory_allocations`

扩展现有库存领用业务头：owner_type、互斥订单/售后所有者、状态、原因、创建和取消信息。普通与售后领用均在实际扣库事务中写入头/行，不新增第二套售后影子表；当前售后仅movement line的实现须由任务5.6补齐真实领用生产者。

### `inventory_allocation_lines`

领用的批次、对应所有者明细、数量/缝边数量、接入节点、实物/用途/路线快照份额，以及原出库movement_line_id与对应普通履约或售后台账。互斥归属及来源FK由1.2落定，inventoryAllocationLineId必须来自真实该行，不以0或伪关联满足完成证据。

领用接入保存真实来源行、share 与 `route_snapshot_id`，按完整工艺兼容性接入，不只比较缝边 boolean。普通取消领用及现有 `reverseMovement` 必须共同反向 flow/source/用途/覆盖、履约及库存流水，并保存原接入/原流水与反向事实的幂等关系。任一接入份额在接入后已实际加工、已核验、已被后续消费、已补发或已转库存则拒绝整笔逆向；关联计划须显式合法取消，不得仅恢复库存或留下悬挂额度。未核验或计划已取消不证明实际未加工，服务端按既有来源、flow、核验及消费证据锁内重验，不用开始标记或新增人工确认操作/字段，也不宣称能自动感知未登记现场加工。合法普通撤销按当前有效需求追加被跳过工序的恢复授权，关联原领用/反向起因，不复活旧 `terminated` 来源，不给终态普通交付新授权。

成品直接领用同事务产生真实 `INVENTORY_INFLOW` root/source、physicalShare、初始 purposeAllocation 及终点 flow，普通直接可发、售后直接 RESERVED 且覆盖只计一次。`scheduling_sources.target_node=SHIPPABLE` 仅为终点追溯锚点，任务 node 仍限定三加工工序；终点 total 记录原接入量，无加工额度、任务或核验，balance/executableQuantity 恒0，不套工序余额公式。各份额 terminalAvailableQuantity 从有效终点流入扣有效普通/补发消费、转库及接入逆向独立重建，普通发货作废反向原消费、更正只传递同份额；非终点该值为0。source/root ID 不以 inventoryAllocationLineId 代替。普通 fulfillment、售后 case/scheduling-sources GET 返回持久化真实 sourceId/allocationId/physicalShareId/routeSnapshotId、终点可处置量及完成证据引用；减量以返回的真实 ID 选份额，GET 不补建，SHIPPABLE 不可建任务。

### 终点完成证据与转库存关联

完成份额必须互斥引用一种真实证据：`TERMINAL_VERIFICATION` 指向路线终点核验及分配行，`FINISHED_INVENTORY_ALLOCATION` 指向兼容成品领用明细。证据类型与引用一致且不得双填/虚填；完成数量按真实证据和有效份额约束，不能给成品领用补造任务或终点核验。转库存关联保存完成证据、share、数量、普通变更或售后处置起因、新库存批次及流水，按被处置份额防重复。

成品领用预留 3、需求减至 1 时，保留预留 1、选中余量 2 以原 `FINISHED_INVENTORY_ALLOCATION` 证据转入新库存批次；不伪造 `TERMINAL_VERIFICATION`，不恢复原批次。非终点实物（库存/前段合格）即使无任务或当前尚未加工也可 `CONTINUE_TO_INVENTORY`，保存用途调整与下游承接关系，沿原路线到终点再入库，不设置开始记录、不提前入库。上述证据/调整的具体表列由 1.2 设计。普通余量入库使用orderItemId/orderChangeItemId，售后入库使用afterSalesItemId及适用的afterSalesDispositionId/demandAdjustmentId，两类业务起因互斥，不能用售后FK承载普通订单。排班终点核验/需求处置生成的入库不允许通用reverseMovement孤立冲销（STATE_CANNOT_CANCEL），本change不新增核验或处置逆向；独立期初/调整的合法冲销保留。普通领用cancel与通用reverse须对同一原起因去重，不能重复回库。

普通余量和售后 Receipt 的服务/DTO 均归 inventory、由 scheduling adapter 调用且共用库存底层写核心，不让 orders 直接引用库存类型。`OrderSurplusReceiptService.OrderReceiptRequest` 使用必填 orderItemId/orderChangeItemId，不带售后 FK；`AfterSalesInventoryReceiptService.ReceiptRequest` 使用 afterSalesItemId 及适用 demandAdjustmentId/售后处置引用。完成证据严格二选一：终点核验必有 terminalVerificationId；成品领用必有真实 inventoryAllocationLineId、原出库 inventoryMovementLineId、batch/share/路线，terminalVerificationId 为空。先改用途再到终点的 origin 是本次真实核验分组且追溯原变更/调整；当场终点转库 origin 是真实处置行。唯一性取 originType/id/line，不以单个领用行唯一禁止合法分次转库；Receipt 复核库存自身事实和防重、不回调排班、不跨模块写表。

## 8. 排班模块

### `scheduling_tasks` / `scheduling_task_items`

`scheduling_tasks` 是任务头：任务编号、共同任务日期、员工及姓名快照、工序及快照、`task_type`（仅 `NORMAL`/`REWORK`）、备注、版本和审计。一个头可跨订单、跨商品包含多个明细；不保存权威数量汇总或独立可改头状态。正常加工、返工后续加工、报废制作补做均为 NORMAL，只有实际修补段为 REWORK；售后所有者和用途不构成新任务类型。

`scheduling_task_items` 保存任务引用、明细编号、业务所有者（普通订单或售后明细）、商品/订单/适用路线快照、用途、实际执行 `node`、计划量、来源类型与 ID、冻结标准分钟、估算分钟、能力快照、状态和取消审计。REWORK 的 node 必须等于来源目标工序，NORMAL 消费对应工序正常额度。只有 `PENDING → VERIFIED` 或 `PENDING → CANCELLED`，每明细一次核验；创建后数量、日期、工序、来源和类型不可直接改，未核验计划调整须显式取消后重排。任务内同一业务明细、工序、来源的重复有效行拒绝，但不同任务可拆分同一来源余额。

产品 + 日期 + 工序下跨员工、跨订单汇总全部未取消 NORMAL 原计划量，以 `mold_quantity * daily_batch_limit` 校验数量硬产能，含报废补做、返工后续加工和售后 NORMAL。核验及未完成不释放原日期资源；计划 10 次日核验完成 6 后原明细 VERIFIED、余下 4 退原来源，原日期仍占计划 10 的资源和估算分钟，新日期重排另占资源，不得二次核验或取消原明细。所有未核验计划均可取消并记录原因，不论任务日期或现场是否加工；释放本计划有效来源占用、实物流入分配及正常资源，不级联取消上下游、不抹除实际流入，失效不复活。取消后已有实物沿原份额、用途及工艺继续处置，不代表可撤销领用或加工/消费。

每明细保存能力和分钟快照：各工序标准分钟取所绑定 `route_snapshot_id` 中的产品星级/包装档位/缝边种类及工艺版本。普通来源沿确认/变更新授权快照，退回实物沿原份额快照，售后新授权沿新补发冻结快照；不能将退回实物也改用新补发工艺，不能用 480 分钟或产能代替。`NORMAL expected_minutes = planned_quantity * standard_minutes`；实际 REWORK 不计正常工时/产能，不虚构实际返工工时，但后续 NORMAL 仍计正常资源。

制作工作量提示仅按员工 + 日期汇总全部未取消 MAKING NORMAL 冻结估算分钟，含本次草稿且不重复计入已保存任务，包括售后正常制作和补做，排除实际返工及其他排班。有效制作分钟 = 工作日小时数 × 60 × 制品有效工时率；服务端提交前预览、创建响应、详情及工作台一致计算已排/本次/合计/有效/差额分钟，返回配置基准版本并在提交重读配置。只提示余量/超出/刚好，不扩展为装袋或缝边可用工时提示，不作工资绩效或数量超排许可，不落提醒数量事实。BigDecimal 精确比较，显示舍入不参与判定，历史标准分钟和资源快照不随配置改写。

不设置开始时间、登记人、开始请求ID、开始保护绑定或隐式开始字段；此前执行登记及 C9 候选已否决，不再待审批。取消仅须PENDING且无核验事实，并保留原因和取消审计；不以任务日期或现场加工与否拒绝取消。正完成核验无需开始标记，零完成也可在任务日期之后直接核验。取消/核验/普通及售后减量共享锁序及版本校验，幂等与唯一核验约束防重复。

真实流入关系仍追溯实际 flow/share、数量、来源/目标及任务消费，不设置开始优先或保护。所有有效未核验计划在同所有者、来源/承接链、目标、有效用途及完整路线兼容池内按 `taskDate/itemId` 稳定分配；读模型与核验锁内重算共用算法，读不落绑定事实，后到流入及新建更早计划也沿同一排序。只分配已存在实物，不绑定未来量、不增额度/覆盖；核验消费实际完成，释放有效未完成分配，取消释放本计划有效占用及正常资源，失效份额不复活，既有真实流入不删除。关系和索引的逐列设计归1.2，不因此新增开始字段或人工确认操作。

### 来源归属与消耗（物理拆表待工程落实）

逻辑来源须表达初始订单缺口、返工、报废制作补做、后续重过工序及售后来源，保存所有者、用途、适用路线、前序事实、目标工序、不可覆写的总量、分配/消费与承接关系。确认/普通变更起因与售后处置起因独立建关系，不用同一售后字段充当所有授权原因。共享来源在 scheduling 保存售后所有者，不用一个枚举替代业务链。具体来源分配/流转事实如何拆表由 1.2 落实，不预设“不设独立来源表”。

每个 share 绑定不可变 `route_snapshot_id`（契约 `routeSnapshotId`），快照绑定 `route_seam_required`、具体工艺/版本及标准分钟；源、用途、任务分配、flow、发货来源及退回引用须能验证同一份额路线身份。退回沿原发货实物快照，售后新授权沿新补发快照；同 boolean 不同工艺/版本不自动兼容，不能只存 boolean 或用当前商品配置代替。跨快照兼容须有既有规则依据，不新增工艺改造许可；关系/外键与索引意图由本文约束，逐列 SQL 归 1.2。

初始正常来源可安排 = 创建时初始授权量− 累计终止量（含后续库存跳过，仅扣一次） − PENDING原占用 − 已核验正常处理量 − invalidatedUnoccupied；处理量含合格、返工、报废，不重复扣历史计划。返工来源可安排 = 来源总量 − 累计终止量 − PENDING原占用 − 已核验实际修补处理量 − invalidatedUnoccupied；失效口径见下文，未涉及的减项为0。异常来源分别按来源 + 目标守恒，只汇总互斥来源，不混同商品池。投影必须可从分配、取消、核验、失效和未完成回退重建。

可安排额度和实际流入是不同维度：下游只消费完整路线兼容的已登记合格流入或库存接入，扣除对应处理量和分配给其他待执行计划的量，按上文同兼容池taskDate/itemId向所有有效未核验计划稳定分配，读与核验锁内重算共用算法，现场加工与否不改变排序，不设开始保护。可提前安排未到实物的下游，但计划额度不等于未来实物预占，核验不能超实物；未完成留下的未消费实物继续可用，不再追加流入。首道 NORMAL 由授权订单缺口或制作补做来源执行，返工由具体目标来源执行。

修补合格后按路线进入后续 NORMAL：已加工需重过的工序新增加工额度，未加工且已有原额度/等待计划的只补实际流入；记录承接关系，不能用全局最大值或负数截零掩盖重复。订单需缝边 10 件，缝边合格 8、返工 2 分制作 1/装袋 1，后续新增装袋 NORMAL 1、缝边 NORMAL 2，最终仍交付 10。缝边路线随来源链保留，不以历史累计已达初始缝边数跳过重过缝边。

物理 `physical_share_id`（契约 `physicalShareId`）贯穿 root、源、任务分配、用途及 flow；源创建同事务即保存初始真实 `purpose_allocation_id`（`purposeAllocationId`），单用途亦须真实引用。用途事实保存 share、路线、用途、数量、前序/替代引用及调整引用，不能用整条 `source.purpose` 充当当前真值。change细化任务6.5仅追加选中未处理份额的用途替代映射，并在锁内传播到既有下游等待源/计划对应 share；不首次初始化、不新增等待加工额度、不改原计划及历史资源/已处理历史，下游已消费份额拒绝冒用上游在制分支。HTTP核验以allocationId引用真实purposeAllocationId，用途、physicalShareId与路线从持久化分配解析；仅唯一有效份额可省组规范化，同用途多路线也须逐组，保存各组合格/返工/报废/未完成及目标；组完成不超有效未处理份额/可执行、组汇总等于明细结果，子源和 flow 继承对应用途/路线。

库存 share 上游报废且不补做时，须同事务保存下游未处理对应额度的失效事实（原报废ID、目标/承接来源、share、失效量、审计及幂等键），逻辑唯一键为 `scrap + target + share`；物理映射须保证 target 能定位对应额度。退回实物处置 `SCRAP_RETURNED` 仍仅适用于退回后实际尚未修补加工、未消费且符合直接报废条件的份额，须显式解除占用；未核验或已取消不是该条件的证明，不使用开始字段判定。合法处置必须同时覆盖当前源及未处理下游份额的失效，不能只落报废记录而遗漏当前源余额，已处理历史不改。报废失效不是细化任务6.2无实物终止，不冒充 processed/terminated、不重复报废、不再次释放覆盖或计划资源。PENDING 原计划及原占用不改，失效份额可执行0；后续 unfinished 仍为原计划−completed，但仅有效未处理份额回可排，失效份额关联原报废不再可排，合法取消同样不得复活。仍需补发须由独立新授权/合法补做承接，不能恢复旧失败实物。

加工来源/目标的完整余额 = `total - terminated - pending原占用 - processed - invalidatedUnoccupied`；SHIPPABLE 终点锚点不套此式，balance/executable恒0，terminalAvailableQuantity按§7独立重建。`invalidatedUnoccupied` 仅包含已不再由PENDING原占用扣除且未处理的失效份额，不能用全部失效量再扣一次；核验/取消解除占用时须原子重建这一投影。View 可列 `invalidatedQuantity`、`invalidatedUnoccupiedQuantity`，事实可重建；本节及§11按该完整余额重建，不涉及终止/失效时相应减项为0，失效不混入已处理量。

### `scheduling_verifications`

任务明细唯一外键、计划快照、完成/合格/返工/报废/未完成、备注、操作人、任务业务日期、实际核验时间和审计。按统一业务时区，核验业务日须晚于任务日期。完成 = 合格 + 返工 + 报废，未完成 = 计划 − 完成，完成不超过计划与锁内重算的可执行量。缝边报废必须为 0，完成 = 合格 + 返工。每明细一次核验，已核验不得修改、取消或再次核验，不新增普通核验通用编辑/冲销能力。

核验目标分配明细保存核验引用、目标工序、数量和生成来源关联；售后退回分配另含补发/库存用途。返工目标合计必须等于返工总量，遗漏、不足、超额或非法目标使整批失败；与核验同事务生成每个目标来源，不再手工补建，不自动排班。一次批量事务提交核验、分配、流转、返工来源、报废补做、未完成回退和提醒，任一失败全部回滚。

### `rework_sources`

保存来源类型、原核验/退回核验及分配行、原任务明细、发生工序 `origin_node`、目标工序 `target_node`、订单或售后明细、产品、用途、适用路线、总量、有效占用/消费、轮次、父来源、版本和审计。售后退回用入口类型追溯，不虚构加工发生工序。

目标矩阵同时适用于 NORMAL 和实际 REWORK 核验：制作 → 制作；装袋 → 制作；缝边 → 制作或装袋且禁止报废；售后退回 → 符合原路线的制作/装袋/缝边并允许直接退回件报废。再次返工按本次实际修补工序判定，只有制作能返自身，缝边目标只能来自合法售后退回入口。

同一核验分配行只生成一次来源；同一来源可跨多任务拆分，禁止以 `UNIQUE(source_id)` 限制任务安排次数，锁内检查累计占用/消费不超量。合格、再次返工、报废均消费本轮实际处理量；只有未完成中的有效未处理份额退回同一所有者/来源/目标的可排余额；取消释放本计划有效占用，二者均不得复活失效份额（见本节失效公式）。再次返工创建关联父源的新来源，不把不合格加回旧余额；售后未完成不进入原订单，返工未完成不进入初始普通需求。

### `scheduling_scrap_records` / `scheduling_quantity_returns`

报废事实保存发生工序/退回入口、数量、原因、业务所有者、任务/核验、返工父源、用途、操作人与时间，不可编辑删除。新任务再次报废是新事实，不得重验旧明细追加。

`scheduling_quantity_returns` 仅表示报废后从制作重新做的 NORMAL 额度，保存报废事实、原所有者、目标 MAKING、数量、分配/消费、后续路线和原覆盖链；不是发生工序实际流入。仍需履约或补发的报废须同事务一对一生成相应补做额度，防止同一报废量重复补做；无补发义务且明确库存用途或直接处置的售后报废只留事实，不生成补做。不得建立“每条报废必有回转”的无条件约束。报废不增加客户需求、不虚构合格或库存、不恢复旧返工余额，也不自动取消独立补发需求。补做后已处理的下游需重过额度，未处理已有等待计划不得重复增需求。

补做份额关系保存新 `physical_share_id`、`replaces_physical_share_id`（契约 `replacesPhysicalShareId`）、替代 `quantity`、原报废与补做来源引用。旧失败实物不可复活；按数量把旧未处理等待 source/task 额度承接映射到新 share，记录原来源/任务分配、新份额及数量，不改原计划或历史资源，不重复新增未处理工序额度。已处理且需重过的工序才新增额度。新 share 再报废则再次替代本轮失败 share，防重复/超量替代；覆盖结束旧失败、由新补做承接，同一需求全链只覆盖一次。替代关系、额度承接与用途替代为不同关系，不得互相冒充。

### 删除超额任务与未来预占

删除旧 `overtime_tasks`、`overtime_task_items`、`overtime_preemptions` 及其服务/端点/DTO/前端类型入口、预占释放、未来计划减少建议和专属错误码；不创建 `scheduling_overtime_preemptions`，不加入 OVERTIME 类型，不做超额并表。原 `production_tasks`、`production_task_items`、`production_verifications`、`production_reminders`、`production_quantity_returns` 改为对应 `scheduling_*`；真实旧报废表为 `scrap_records`，目标为 `scheduling_scrap_records`。旧名仅作重命名/删除或历史证据说明。取消手工创建返工来源入口，来源由核验分配同事务产生。

### `scheduling_reminders`

保留 INCOMPLETE 等未完成处理提示，取消 OVERTIME_PENDING_VERIFY、PLAN_ADJUSTMENT 和未来调整机制。提醒可重建，不是数量事实来源；制作工作量只是查询/预览结果，不存独立提醒事实。全部有效明细核验后任务头为已核验，未完成待处理是独立提示；部分核验不能整头已核验，全部取消才已取消。

### `other_schedules` / `other_schedule_verifications`

其他排班无商品、无工序，不关联商品数量、订单来源或实际流入。保留员工、日期、事项、小时/分钟/总分钟、一次核验与 `other_schedule_time_corrections` 追加更正；总分钟为正整数，录入分钟 0–59。三张表保持独立，仅在同一日期周历与制作排班同级展示，不要求并表，也不计制作工作量提示。

## 9. 订单模块：发货

### `shipments`

发货批次编号、订单、状态、发货日期、原始物流快照、当前有效物流值、确认/作废/更正信息和版本。补发身份及售后归属从草稿创建起与全部关联原子持久化且不可更改；不可混普通/补发明细，物理标识与关联一致性按排班重构细化任务1.2设计、1.4建约束、5.8–5.9接入写命令。不能以备注或客户端类型判定，也不能把原发货售后受理占用当补发身份。

普通发货草稿修改、确认、作废、等量更正须锁内识别补发并拒绝，不得写普通履约或创建普通替代批次。专用售后确认验证整批及全部明细归属，仅写售后台账；当前不支持补发草稿改量、作废或等量更正，通用售后更正亦不可绕过。只读/物流复用不改数量、身份、关联或履约状态。

### `shipment_items`

发货批次、订单明细、本次 `quantity` 与 `seam_quantity`、商品及收货展示快照、确认后的累计发货和未发货快照。普通发货契约显式提交 `quantity` / `seamQuantity`，范围 `0 <= seamQuantity <= quantity`；确认逐有缝/无缝桶校验当前未消费可发份额及剩余交付需求，不能按总量猜配。

### `shipment_source_links`

每条链接保存真实 `source_line_id`（`sourceLineId`）、`physical_share_id`、消费数量、`route_snapshot_id` 与对应发货明细，冻结完整路线/工艺身份，不能用订单聚合 ID 或占位来源行代替。确认仅分配当前未消费、未转库存且有效的可发份额，不每批重扫原始 `IN` 从头重建链接。允许一个来源拆给多个合法批次，约束累计有效消费不超真实可发量；唯一键用于一次分配/消费幂等，而非限制来源只能发一次。

普通作废追加逐链接反向事实，恢复原份额及原路线可发量；等量更正在一个事务内把原份额、各桶数量和工艺快照传递给替代批次，不先释放再重新择源。链接、消费与反向/更正关系共同构成当前可发投影的重建依据，确认/作废/更正均不扣减或恢复库存，库存领用撤销另走 §7 守卫。

### `shipment_logistics_changes`

物流公司、单号、运费、备注的修改前后值、原因、操作人和时间。

### `shipment_corrections`

已关闭订单的普通原批次和等量替代批次关系；同一事务完成并验证交付数量及逐路线份额不变，关联每条原消费和承接链接，原份额只能传递一次；不重新扫描可发源，不改变库存。补发批次仍不可使用此入口。

## 10. 订单模块：收退款

### `payments`

收款编号、订单、金额、日期、方式、备注和操作人。不可修改。

### `refunds`

退款编号、订单、金额、日期、方式、原因、备注、操作人、来源类型，以及订单变更或售后单引用。不可修改。订单变更退款参与原订单结清，售后退款仅进入累计实际净收，不产生新的原订单待收或待退。

订单结清净额、订单待退款和累计实际净收可分别缓存，但须按来源类型从不可变收退款事实重建。

## 11. 订单模块：售后

### `after_sales_cases`

售后编号、原订单、类型、状态、问题、处理方案、创建和完成信息。

### `after_sales_items`

原订单明细、必须关联的有效已确认原发货批次明细、真实原发货来源链接/份额及其 `route_snapshot_id`、受理数量、`returned_quantity`、`returned_seam_quantity`、`replacement_required_quantity`、`replacement_seam_quantity`、独立新补发路线/工艺/标准分钟冻结快照及分路线数量投影。原发货批次明细的有效已发数量减其他售后有效占用为剩余可受理量；保留既有有效占用约束，不扩展受理次数规则。另须按原批真实有缝/无缝份额分别锁定剩余可退上限，扣除其他有效退回占用，不只按总量检查。退回与补发需求独立，允许只退不补、仅退款、无退回补发。

受理契约显式提交 `returnedQuantity` / `returnedSeamQuantity`，满足 `0 <= returnedSeamQuantity <= returnedQuantity`；独立填写/确认 `replacementRequiredQuantity` 与必传 `replacementSeamQuantity`，`0 <= seam <= total`。补发总量未提供才默认实退量，显式0保留；零退回/零补发各自 seam 也显式为0。两种 seam 互不推导，不复制原订单 seam 或按比例猜测。退回引用原实物快照；新补发冻结合法新 `routeSnapshotId`、缝边种类及分钟，无合法工艺快照拒绝正 seam，不擅造配置。boolean 相同不证明工艺兼容，不改变退回原实物路线，不新增工艺改造许可。

补发需求、用途、覆盖及调整事实均归 orders。调整保存新旧总量及 seam、原因、逐路线 reduction/gap 处置与引用；新需求提交 `replacementRequiredQuantity` + `replacementSeamQuantity`，逐路线不低于 shipped。每路线 `reduction[r] = max(oldRequired[r] - newRequired[r], 0)`，先消减本路线调整前 gap，`max(reduction[r] - gap[r], 0)` 的已覆盖部分须明确去向。增加只产生该路线 gap、不自动来源或任务；等总量换路线也是一减一增，不能用总 gap 抵另一线路超额或覆写实物 route。取消任何未核验计划均不消灭实物，未核验/取消状态不能证明未加工：退回件仍须修补转库存或报废，在制沿路线完成入库，终点合格超出量解除补发预留并真实入库。退 5、补 5 改补 3，已合格 5 则 3 件保留补发、2 件落库存批次和入库流水；已补发 4 则拒绝改为 3。需求/用途/覆盖调整的物理表拆分待工程落实。

无实物NORMAL制作授权允许按份额追加终止事实，关联原来源、目标工序、终止量、需求调整、原因、操作人、请求ID及幂等键；保留原授权总量，有效授权=原授权−累计终止，可安排=有效授权−PENDING原占用−已核验处理−invalidatedUnoccupied（见§8失效口径）。终止须实际无实物且无加工，锁内重验既有来源、退回/库存接入、核验处理及下游流入证据，且显式列出的制作/后续等待计划全部合法取消释放占用；PENDING、未核验或已取消不足以证明无实物/无加工，不使用开始标记，不新增人工确认操作或字段；对应各段额度同步终止，不能遗留失去额度的计划。部分减量不修改原计划，取消整条后余量仅待重排，不自动任务。需求、计划、资源、终止与覆盖同事务且可重建；终止量不能再分配/重复释放，不生成库存或报废，不删除来源历史。该逻辑事实归属沿用scheduling来源与orders需求调整边界，物理拆表按排班重构细化任务1.2设计、1.4建约束、6.2–6.3实现终止及计划处置。

### `after_sales_return_verifications`

核验请求必须显式提交实际 returnedQuantity/returnedSeamQuantity，满足 `0 <= returnedSeamQuantity <= returnedQuantity <= acceptedQuantity`，允许不同于受理预录。核验事务重新锁原发货及售后明细，按原发货真实路线份额扣除其他有效退回占用重验实际两桶；追加预录到实际的前后差异及原引用历史，原子替代本明细未核验占用，不把自身预录再扣一次，不改变其他有效占用或独立补发承诺。核验实际量及锁内选中份额才是分配/分桶报废依据。现有 correct 仅审计，不提供先改未核验占用的生产者；RETURN_VERIFICATION 更正不能改数量、来源、覆盖或库存，不新增核验逆向。差异、占用替代、核验及以下全部派生事实同事务，任一步失败或非法实际量均全部回滚，核验后不得覆盖。

售后明细一次退回核验：实退总量及有缝量、修补用于补发数量、修补用于库存数量、直接报废 `scrapQuantity`、原因、核验人和时间。分配行显式保存 `route_seam_required`（契约 `routeSeamRequired`）、真实 share 及不可变 `route_snapshot_id`。逐桶 `scrap[r] = returned[r] - repairForReplacement[r] - repairForInventory[r] >= 0`；修补分配后的两桶剩余全部为报废，且两桶 scrap 合计必须等于提交的 scrapQuantity，不能仅校验总等式。用途与目标分配总和仍满足「修补用于补发 + 修补用于库存 + 直接报废 = 实退」。修补选择符合原实物路线的制作/装袋/缝边目标；补发用途须匹配对应 gap 且完整工艺兼容，库存用途不覆盖。核验、分配、逐桶报废、共享返工来源及初始真实用途分配与覆盖同事务落地；售后退回以入口类型标记，不虚构生产发生工序，直接退回报废不等于缝边工序核验报废。退回来源后续 `SCRAP_RETURNED` 依 §8 使当前源及未处理下游份额失效，不能遗漏余额反向。

### `after_sales_fulfillment_entries`

orders 拥有售后需求、用途、覆盖、可补发与已补发独立台账。记录业务所有者、用途、路线、来源链、前序事实、覆盖迁移及实际终点流入；来源包括兼容库存接入、修补/正常加工的适用路线终点、补发确认消耗、用途调整和终点入库关联；合法库存撤销的反向接入依 §7，不代表新增补发批次作废/更正/恢复入口。不把任意工序合格直接记为可补发，也不写入原订单履约。

需求、覆盖、预留、已发、gap 均保存/派生有缝和无缝两桶：`required[有缝] = replacementSeamQuantity`，`required[无缝] = replacementRequiredQuantity - replacementSeamQuantity`；每路线 `gap[r] = required[r] - shipped[r] - reserved[r] - covered[r]`，各项总量为两桶之和。reserved为终点合格补发预留，covered为补发用途的未排/待加工/在制有效来源；不能用总 gap 抵另一线路超额。减项按物理数量/来源链互斥计一次，不按工序叠加。未排班补发返工来源已经覆盖；来源到在制到最终合格只迁移覆盖，不能重复生成正常制作来源。报废结束失败覆盖，仍有补发义务时由同一缺口的制作补做承接，不能双重覆盖或重复补做。退回用途分配、库存补发接入及正常来源创建等新增覆盖须在同一所有者锁内校验不超过未覆盖缺口；不同实物链也不能重复满足同一承诺，超出实物须显式处置，不以负数截零掩盖。

只有完成全部适用加工且预留补发的未发出合格量才可补发；库存用途不计可补发，在终点须通过 inventory 同事务落可追溯批次与入库流水，并建立源事实/批次/流水的幂等关联，不能只改标签或计数。无补发义务的库存用途或直接处置报废只记录事实，不派生补做；报废不自动取消独立补发承诺。

### `after_sales_shipment_links`

售后明细与补发发货批次、具体合格预留来源、真实share和route份额的关系。补发确认按真实预留份额消费并逐路线校验不超reserved和required-shipped，不能按总量猜配；售后库存领用同样记录真实批次/路线份额，新增覆盖不超对应gap。补发批次确认后才增加对应桶已补发，同事务消费覆盖/可补发且防重复，不二扣库存；不改变原订单订购、累计发货、未交付需求或主状态。

### 售后共享排班来源（归 scheduling，物理拆表待落实）

旧 `after_sales_production_sources` 的命名和跨模块接口须同步到 scheduling 模型；不在本文预先承诺一个新的独立物理来源表名。共享返工来源使用 §8 的 `rework_sources` 及目标分配，其他售后正常加工/补做/后续工序来源使用 scheduling 的可追溯来源分配和流转事实，均保留售后明细所有者、用途、适用路线、目标、前序事实、总量、分配/消费及覆盖链。

用途为补发/库存，不是“返工/补发生产”；任务类型仍只有 NORMAL/REWORK。退回修补来源由核验分配产生，补发正常制作只针对逐路线未覆盖缺口，不能用「需求 − 已补发 − 可补发」遗漏未排/在制覆盖。缺口授权契约提交正 `quantity`、`seamQuantity` 与原因，`0 <= seam <= quantity` 且 seam/quantity-seam分别不超有缝/无缝gap；同事务创建quantity的MAKING/PACKING_BAG额度、seamQuantity的SEAM_CUTTING等待源及初始真实用途分配，记录同root物理share承接，同root份额跨各段只覆盖一次而非逐段重复覆盖，不自动任务或实际流入。取消释放本计划有效占用，但不能复活失效份额；未完成仅有效未处理部分退回同一售后所有者/来源/目标。各工序合格仅按路线流转，终点才进入 orders 的可补发或 inventory 的真实入库。共享物理来源归 scheduling 不改变需求、用途、覆盖、售后台账由 orders 拥有的边界。

## 13. 索引

最低索引集合：

- 所有业务编号唯一索引；
- 订单按状态、客户、下单日期；
- 订单明细按订单和商品；
- 排班任务头按日期、工序、员工、类型；明细按状态、业务所有者、订单/售后明细、商品、具体来源及目标；
- 返工来源按原核验/退回分配、发生工序、目标、父来源、用途和所有者；分配/消费/覆盖迁移与终点入库按来源链和业务幂等键，具体复合键待物理映射落实；
- 库存批次按商品、工序、缝边状态和当前数量；
- 库存流水按批次、来源业务和时间；
- 履约事实按订单明细、节点、来源记录；
- 发货按订单、状态和发货日期；
- 收退款按订单和业务日期；
- 售后按原订单、状态和创建时间；
- 普通授权/处置按确认起因、`order_change_item_id`、所有者与 root/share；orders 的 ADD 应用映射按 order_change_item_id 唯一、created_order_item_id 及本域 route_snapshot_id 追溯，不用商品索引代替真实映射；售后处置按独立 `after_sales_disposition_id`，终止事实按来源/目标/share/起因与请求幂等键；
- 路线快照按不可变 ID 关联 share/source/flow/发货/退回；补做替代按 `replaces_physical_share_id`、报废事实及新 share，额度承接按旧 source/task 分配、新 share 与数量；
- 真实流入分配按来源/目标/share/任务明细追溯；同兼容池所有有效未核验计划统一按任务日期/明细ID（taskDate/itemId）排序，不建开始时间排序或保护索引，不建立未来流入预占索引；
- 发货链接按真实 sourceLine/share、发货明细和路线快照；消费/反向/更正按原链接及幂等键，退回占用按原批明细/桶/真实份额以支持上限锁内重验；
- 完成证据按证据类型及真实引用，转库存调整按完成份额/处置起因/批次/流水；领用反向按原接入/flow/source/流水引用及请求幂等键。

以上是关系与索引意图，不预先约定所有复合键逐列顺序；具体物理映射、SQL 及锁行由 1.2 落实。

## 14. 数据库级约束

以下为待实施约束。行内等式/唯一性由数据库检查、外键、唯一键与应用校验共同落实；跨行累计、用途/路线及事务规则须在统一锁序下由领域服务重验，不能把无记录的 SUM 查询当容量互斥锁。物理拆表与精确约束清单待工程首步落实：

- 金额和数量非负；
- 缝边数量不超过商品数量；售后 `0 <= replacement_seam_quantity <= replacement_required_quantity`，正缝边需求必须有合法冻结工艺；受理 seam 必传且显式总量0不得被默认值覆盖；
- 核验完成 = 合格 + 返工 + 报废，完成不超过计划或锁内可执行量；缝边报废 = 0；
- 未完成 = 计划 − 完成；核验业务日晚于任务日期，每明细唯一核验，已核验不可取消或再核验；
- 退款累计不超过收款累计；
- 发货累计不超过当前有效订购数量；
- 库存批次数量不得为负；
- 实退 = 修补用于补发 + 修补用于库存 + 直接报废；退回与补发需求独立；
- 终态订单转换合法；
- 商品任务类型仅 NORMAL/REWORK；来源所有者、用途、路线、执行工序及返工目标合法，任务内重复有效来源行拒绝；
- 核验目标分配合计等于返工总量，与核验同事务；同一分配行只生成一次来源，不提供手工补建；
- 同一报废量不得重复生成制作补做；仅仍需履约/补发的报废一对一产生 MAKING NORMAL 额度，无补发义务的售后库存用途/直接处置报废除外，不约束每条报废必有补做；
- 具体来源 + 目标的 `terminated + pending原占用 + processed + invalidatedUnoccupied <= total`，失效量与PENDING占用不得双扣；仅有效未处理份额可排/可执行，核验或取消不复活失效量。允许跨任务拆分，不建立 `UNIQUE(source_id)` 或“来源只能安排一次”；唯一约束用于事实幂等，不禁止合法拆分；
- 源创建同事务生成初始真实purposeAllocationId（含单用途）；share贯穿源/任务/用途/flow，替代映射不改已处理历史。库存报废下游失效按scrap+target+share幂等，不二次报废/释放覆盖或资源；
- 正常来源可安排不重复扣历史已核验计划，未完成退原所有者/来源/目标；核验合格、返工、报废均消费本轮，再次返工另建父子关联来源；
- 已处理需重过的工序新增额度，未处理既有等待额度只补实际流入，不增加客户需求、不丢适用缝边路线；
- 未取消 NORMAL 原计划量受产品日期工序硬产能限制，历史核验/未完成保留原日期资源；制作工作量为精确计算的软提示，不作全工序工时硬约束；
- 补发需求/来源覆盖/终点预留/已补发/gap分有缝与无缝桶，同root物理份额互斥覆盖一次，库存用途不覆盖；授权、退回补发及库存接入逐路线不超gap，不以总gap抵超额；调整逐路线不低于shipped，等总量换路线也一减一增，已覆盖减量须显式处置和审计；
- 仅适用路线终点可补发或入库；终点库存批次与入库流水、覆盖迁移、分配与补做均具事实幂等键，补发确认才增加已补发；
- 确认/ADD/增量/新工艺授权只追加新 source，旧 total、任务和实物快照不覆写；普通 `orderChangeItemId` 与售后 `afterSalesDispositionId` 起因独立有效，无实物减量全链终止并显式合法取消，不能逐工序重复计实物；
- 无事实订单取消同步终止未占用初始 sources；自动授权不等于执行事实，终态守卫禁止普通新交付安排但不误禁合法余量与售后；
- share 的 routeSnapshotId 不可变且绑定 boolean、具体工艺/版本/分钟；相同 boolean 不自动兼容，退回沿原快照、新授权沿新快照，不隐含工艺改造；
- 新补做 share 按 replacesPhysicalShareId + quantity 关联失败实物，旧失败 share 永不复活；按量承接旧未处理等待 source/task 额度，已处理段才新增重过，重复报废逐轮替代而非重复覆盖；
- SCRAP_RETURNED 的当前源及未处理下游失效均进入 invalidatedUnoccupied 口径，不能记为 processed/terminated 或再次可排，PENDING 失效不双扣；
- 普通发货 quantity/seamQuantity 逐桶消费当前未消费份额，保存真实 sourceLineId 和路线快照；作废反向原份额，更正原子传递同份额，不扣/恢复库存；
- returnedSeamQuantity 与 replacementSeamQuantity 独立；核验显式实际两桶满足0≤seam≤total≤acceptedQuantity，允许与预录不同，锁内按原批真实剩余份额重验并记录差异/替代本明细未核验占用，不双扣自身预录，不改其他有效占用或补发承诺；修补分配按实际两桶的非负余量为报废，两桶之和等于 scrapQuantity；correct仅审计，不新增核验逆向；
- 非终点真实实物无任务/尚未加工仍可 CONTINUE_TO_INVENTORY，但须沿路线到终点；完成证据 TERMINAL_VERIFICATION 与 FINISHED_INVENTORY_ALLOCATION 互斥且真实，成品领用转新库存不伪造核验；
- 普通取消领用/reverseMovement 同事务反向接入 flow/source/覆盖及库存；接入后已实际加工/核验/消费/补发/转库拒绝，未核验或计划已取消不证明可逆向，合法恢复普通需求只追加授权、不复活旧 terminated；
- 不设置开始任务/登记开工的字段或命令；所有有效未核验计划在同兼容池按taskDate/itemId稳定分配已有流入，读与核验锁内共用算法；完成消费、有效未完成释放、取消释放本计划有效占用及正常资源，不删真实流入、失效不复活，不绑定未来量、不增额度/覆盖。

排班应用服务拥有任务创建/取消/批量核验；orders 的售后应用服务拥有退回核验、需求调整和补发确认；inventory 提供同事务批次/流水接口。来源、核验、分配、报废补做、覆盖迁移、后续流转及终点入库不能拆成会留下部分事实的独立提交，批量任一失败整笔回滚。

统一锁序：业务所有者/来源上限行（订单或售后明细，受理先原发货明细）→ 任务头与明细 → 具体来源/目标及覆盖余额 → 产品日期工序容量锁 → 库存批次；同类按稳定 ID/复合键排序，无对象则跳过。先只读收集引用，再按序加锁并重验归属、版本、来源、覆盖、实际流入与产能。创建、真实流入分配重算、取消、核验、普通确认/变更/取消、库存接入及 reverseMovement、发货消费/作废/等量更正、退回和需求调整的物理锁行须由 1.2 逐条映射，避免反向加锁；真实份额、完成证据、替代/失效与恢复授权均在同一事务内重验。

写命令沿用 Idempotency-Key：同键同请求返回首次结果，同键不同请求冲突；查询/预览不写事实、不占额度。核验唯一键、目标分配唯一键、报废补做幂等键及分配/覆盖迁移/终点入库唯一键共同防重复。
