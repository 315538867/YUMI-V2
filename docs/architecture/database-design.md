# YUMI V2 逻辑数据库设计

## 1. 设计状态

本文是目标逻辑模型，不是已存在的数据库。物理字段名可在实现计划中微调，但实体边界、唯一约束、精度、不可变事实和事务关系必须保持。

## 2. 通用约定

- 主键使用 `BIGINT UNSIGNED` 内部 ID；业务编号另设唯一索引；
- Java 金额和单价使用 `BigDecimal`，MySQL 使用 `DECIMAL(19,4)`；比例使用 `BigDecimal` 与 `DECIMAL(9,6)`；
- 数量使用 `INT UNSIGNED`，不得为负；工时使用总分钟整数；
- 业务日期使用 Java `LocalDate` 和 MySQL `DATE`，操作时间使用 `Instant` 或明确时区的时间类型并映射到 `DATETIME(6)`；
- 所有可并发修改的 JPA 聚合根保存 `version` 并使用 `@Version`；
- 表默认保存 `created_at`、`created_by`，需要变更的当前资料保存 `updated_at`、`updated_by`；
- 不可变事实表不提供通用更新或软删除；更正使用关联原记录的新事实；
- 状态使用受控字符串或小型代码表，禁止数据库自由文本；
- JSON 仅用于非检索型快照补充，不替代关键字段、外键和约束；
- 需要锁定关键数量余额时使用 JPA 悲观写锁或显式 `SELECT ... FOR UPDATE`；
- Flyway SQL 是数据库结构唯一来源，Hibernate 仅以 `ddl-auto: validate` 验证映射。

## 3. 模块与表归属

| 顶级模块 | 主要表 |
| --- | --- |
| `identity` | `admin_accounts` |
| `catalog` | `products`、`customers`、`employees`、`employee_work_types`、`employee_employment_events`、`master_data_change_logs`、静态数据目录 `star_levels`/`packaging_tiers`/`seam_types`/`work_types` |
| `orders` | `orders`、`order_items`、订单快照和变更表、履约表、草稿库存计划表、发货表、收退款表、售后表 |
| `inventory` | `inventory_batches`、库存流水表、库存领用表 |
| `production` | `production_tasks`、`production_task_items`、生产核验、返工、报废回转、明细来源、超额任务和其他排班表 |
| `calculation` | 无表（无持久化的集中计算支撑模块，只接收不可变数值输入并返回结果） |
| 基础设施 | `number_sequences` 及文件元数据表（实现时定义） |

`shipments`、`payments`、`refunds` 和 `after_sales_*` 使用独立表是为了保存独立事实和约束，不代表它们是独立顶级业务模块。它们的写入命令、状态和事务边界均由 `orders` 模块拥有。未来完整财务模块只能读取或订阅订单收退款事实，不在首期接管这些表。

## 4. 身份与基础资料

### `admin_accounts`

`id`、`username`、`password_hash`、`status`、`linked_employee_id`、登录安全字段、版本和时间字段。

约束：用户名唯一；关联员工可空；首期只有管理员类型。

### `products`

当前商品资料、启停状态、销售单价、重量、损耗率、材料单价与成本、星级与制作成本快照、包装档位快照、缝边默认值（默认缝边剪袋类型 id + 名称与标准分钟快照 + 单件缝边人工成本快照 + 缝边价格）、模具数量 `mold_quantity`、每日批次数 `daily_batch_limit`、其他单件成本和总成本。`mold_quantity` 与 `daily_batch_limit` 均为正整数；当前产品最大日产能由两者乘积派生，不作为独立可编辑事实持久化。模具数量和日产批次数只参与产能，不影响成本。

业务编号 `product_no` 唯一。

商品**不保存缝边数量与缝边成本**：`total_cost`/`reference_price` 始终按**不缝边剪袋**口径落库；缝边剪袋变体预算（不缝边剪袋总成本 + 单件缝边人工成本，后者 = 缝边标准分钟 × 全局时薪 ÷ 60）由 `calculation` 的 `FP-PROD-20/21` 读时派生，只出现在商品试算与详情响应里。`seam_type_id` 可空（空＝默认不缝边剪袋），非空时外键指向 `seam_types`。

### `customers`

客户编号、名称、联系人、联系电话、备注，以及一组默认收货信息。

客户名称和电话不唯一；重复仅提示。

### `employees`

员工编号、姓名、电话、状态、首次入职日期、备注和版本。

### `employee_work_types`

员工与制作、捏毛装袋、缝边剪袋、其他的多对多关系。

### `employee_employment_events`

入职、离职、重新入职事件及日期、原因和操作人。

### `master_data_change_logs`

商品、客户和员工当前资料的变更前后值、原因和操作人。关键可检索字段可拆专表，首期允许结构化 JSON 保存前后快照。

## 5. 订单模块：订单核心

### `orders`

订单编号、客户引用、主状态、下单日期、期望交付日期、当前收货信息、备注、金额汇总、款项汇总缓存、确认/取消/关闭信息和版本。

业务编号 `order_no` 唯一。

### `order_items`

订单、商品引用、当前有效数量、缝边数量、成交价格、金额、备注、当前需求处理汇总和版本。

每个明细有稳定 ID，订单变更不通过删除重建改变其历史身份。

### `order_confirmation_snapshots`

订单确认时的客户、收货、金额、备注和确认人快照。

### `order_item_snapshots`

商品名称、编码、图片、说明、星级、成本组成、成交价格、数量、缝边参数和冻结流程快照。

### `order_change_orders`

变更单编号、订单、状态、原因、创建和确认信息。

### `order_change_items`

变更路径、变更前后值，以及数量减少时的超出数量处理方案。涉及数量的变更必须保存结构化字段，不能只保存文本 diff。

## 6. 订单模块：履约台账

推荐使用“不可变事件 + 当前投影”组合，而不是给每个数量来源建立可随意编辑的计数器。

### `fulfillment_entries`

每条数量事实：订单明细、来源类型、来源记录、工序或最终节点、方向、数量、业务时间、操作人、冲销关系。

来源类型包括订单需求、订单变更、库存接入、生产合格、返工流入、报废回转流入、转成品余量、发货消耗和发货恢复。生产任务明细及其 `production_task_item_sources` 是生产事实的追溯入口；跨模块投影、报表和发货来源链接在迁移实施期必须同步切换到任务明细/来源事实，不得继续依赖旧生产计划或虚构重做来源。

唯一约束：同一来源记录、来源明细、目标节点和方向不能重复入账。

### `order_item_fulfillment_balances`

订单明细当前投影：当前有效需求、各工序有效流入、有效 `NORMAL` 计划占用、普通已核验处理、返工待安排、报废回转待安排、可发货、累计有效发货、成品余量和版本。返工来源、报废回转余额及普通来源分配均由生产事实派生。

此表只能由领域服务在写入 `fulfillment_entries` 的同一事务中更新，并定期与事件重建结果校验。

### `order_inventory_plan_lines`

草稿订单的库存计划行：订单明细、批次、计划数量。**计划只是参考、不占用库存**：本表不产生库存流水、不改批次当前数量；确认时按批次聚合重验余额，不足须管理员明确转生产。同一明细同一批次唯一。

表归属 `orders`，因外键依赖 `inventory_batches` 而排在库存迁移之后建立。

## 7. 库存模块

### `inventory_batches`

批次编号、商品、来源类型和来源记录、已完成工序、缝边状态、当前数量缓存、创建时间、备注和版本。

批次不保存目标订单。

### `inventory_movements`

流水编号、业务类型、业务时间、原业务记录、操作人、原因和冲销原流水。

### `inventory_movement_lines`

流水、批次、方向、数量、变动前后数量、商品、工序、缝边状态和按需关联的订单明细。

一次业务操作的所有明细在同一事务中提交。有效流水行汇总必须等于批次当前数量。

### `inventory_allocations`

库存领用业务头：订单、状态、原因、创建和取消信息。

### `inventory_allocation_lines`

领用的批次、订单明细、数量、接入节点，以及对应库存流水和履约台账记录。

取消必须关联反向库存流水和反向履约记录。

## 8. 生产模块

### `production_tasks` / `production_task_items`

`production_tasks` + `production_task_items` 取代 `production_plans`，是当前生产计划的目标模型。`production_tasks` 是生产任务头：任务编号、共同计划日期、执行员工及姓名快照、共同工序、共同类型（仅 `NORMAL`/`REWORK`）、备注、创建人和版本。一个任务头可包含多个明细，支持跨订单、跨商品；头状态不作为独立可改状态持久化，只由明细事实派生。超额预占使用独立事实表和独立命令，不进入普通生产任务类型。

`production_task_items` 是生产任务明细：订单明细/订单、商品、来源、计划数量、标准分钟快照、明细状态（`PENDING`/`VERIFIED`/`CANCELLED`）、任务内核验事实引用和版本。来源与订单、工序边界必须由服务和检查约束保证；每明细最多一次有效核验。`NORMAL`/`REWORK` 是普通履约核心；超额预占与售后使用独立事实，不得污染普通订单数量。

普通制品按产品全局、员工无关、订单无关汇总当日未取消 `NORMAL` 计划量，并要求不超过当前产品最大日产能：`mold_quantity * daily_batch_limit`。历史核验不释放当天已计划资源。每个明细保存能力和分钟快照。制品单件分钟取订单冻结的产品星级分钟，捏毛装袋取冻结包装档位分钟，缝边取订单所选缝边种类冻结分钟，不得用 480 分钟或产能替代标准分钟。`NORMAL expected_minutes = planned_quantity * standard_minutes`；`REWORK` 不计入正常工时/产能，也不输出虚构返工实际工时。

员工在日期和工序下的制作容量为 `workday_hours * 60 * effective_rate`，其余工序为 `workday_hours * 60`；超出或不足只产生提示，不作硬拒绝。其他排班仍独立记录总分钟事实，不带商品数量。

### `production_task_item_sources`

生产任务明细分配的正常上游合格流入、兼容库存、首工序实际需求缺口或报废回转额度来源：来源类型、来源记录、归属订单明细/工序、分配量、已核验消耗量、取消/未完成释放事实和版本。取消释放，未完成释放，核验消耗；同一来源额度不得二次消费。可用报废回转余额只能从分配与核验事实派生，不使用 `remake_sources`。

### `production_verifications`

任务明细唯一外键、完成、合格、返工、报废、未完成数量、核验备注、核验人和时间。每明细只能核验一次，数量等式必须由应用和数据库检查约束同时保证。一次核验事务中，每个报废事实对应一次 `scrap_records` 与 `production_quantity_returns` 回转事实；回转进入原工序普通待安排和可执行额度，不成为上游合格、库存或订单新增。后续 `NORMAL` 明细可通过 `production_task_item_sources` 关联回转记录。

### `rework_sources`

原核验、发生工序、返工数量、已安排数量和版本。核验只记录返工事实；管理员必须基于已存在的返工事实或上一轮返工事实显式创建唯一返工来源，该来源只能在发生工序内部安排，可拆到多个任务。未完成或取消恢复来源已安排余额；再次返工在显式创建新来源后关联上一轮。返工合格按正常流入进入下一节点，但不计入普通 `PENDING` 占用或普通已核验完成。

### `scrap_records` / `production_quantity_returns`

不可变报废事实与不可变生产数量回转事实。一次生产核验中一条报废记录对应一次回转；回转数量作为原工序普通待安排和可执行额度，不恢复上游合格、库存或订单新增，也不使用 `remake_sources`。

### `overtime_preemptions`

超额预占、未来正常计划明细、预占数量、状态和释放/处理信息。超额预占不属于 `production_tasks` 或 `production_task_items`，不改变未来正常计划原数量，也不产生普通生产流入。唯一约束防止同一来源数量重复预占。

### `production_reminders`

未完成提醒、超额待核验和计划待调整提醒。提醒只辅助工作台，不是数量事实来源。

### `other_schedules` / `other_schedule_verifications`

其他排班及唯一工时核验。总分钟为正整数，更正另建 `other_schedule_time_corrections`。

## 9. 订单模块：发货

### `shipments`

发货批次编号、订单、状态、发货日期、原始物流快照、当前有效物流值、确认/作废/更正信息和版本。

### `shipment_items`

发货批次、订单明细、本次数量、商品及收货展示快照、确认后的累计发货和未发货快照。

### `shipment_source_links`

发货明细与库存领用、生产合格或其他可发货来源的追溯关系。它只追溯来源，不再次改变库存。

### `shipment_logistics_changes`

物流公司、单号、运费、备注的修改前后值、原因、操作人和时间。

### `shipment_corrections`

已关闭订单的原批次和等量替代批次关系；同一事务完成并验证交付数量不下降。

## 10. 订单模块：收退款

### `payments`

收款编号、订单、金额、日期、方式、备注和操作人。不可修改。

### `refunds`

退款编号、订单、金额、日期、方式、原因、备注、操作人、来源类型，以及订单变更或售后单引用。不可修改。订单变更退款参与原订单结清，售后退款仅进入累计实际净收，不产生新的原订单待收或待退。

订单结清净额、订单待退款和累计实际净收可分别缓存，但须按来源类型从不可变收退款事实重建。

## 11. 订单模块：售后

### `after_sales_cases`

售后编号、原订单、类型、状态、问题、处理方案、创建和完成信息。

### `after_sales_items`

原订单明细、必须关联的有效已确认原发货批次明细、商品和缝边快照、受理数量、退回数量、补发需求数量和数量汇总。原发货批次明细的有效已发数量减其他售后有效占用为剩余可受理量；事务锁与来源唯一约束防止并发超量。

### `after_sales_return_verifications`

售后明细唯一核验、返工数量、报废数量、原因、核验人和时间。

### `after_sales_fulfillment_entries`

售后可补发和已补发独立台账，来源包括库存接入、售后返工合格、售后生产合格、补发发货消耗和恢复。

### `after_sales_shipment_links`

售后明细与补发发货批次关系。补发批次确认后才增加已补发数量。

### `after_sales_production_sources`

售后生产来源（表归生产模块）：售后明细、用途（售后返工/售后补发生产）、目标工序、总额度与已安排数量。额度 = 退回核验返工数量，或「补发需求 − 已补发 − 可补发」；合格只增加可补发，未完成与取消退回来源余额。

## 12. 编号

商品、客户、员工、订单、生产任务、库存批次、库存流水、发货、收退款和售后使用独立编号空间。

建议建立 `number_sequences`：

`sequence_key`、`current_value`、`updated_at`。编号分配在事务中锁定对应行并递增，数据库对最终业务编号建立唯一索引。

## 13. 索引

最低索引集合：

- 所有业务编号唯一索引；
- 订单按状态、客户、下单日期；
- 订单明细按订单和商品；
- 生产任务头按日期、工序、员工；生产任务明细按状态、订单明细、商品和来源；
- 库存批次按商品、工序、缝边状态和当前数量；
- 库存流水按批次、来源业务和时间；
- 履约事实按订单明细、节点、来源记录；
- 发货按订单、状态和发货日期；
- 收退款按订单和业务日期；
- 售后按原订单、状态和创建时间。

## 14. 数据库级约束

至少建立以下检查或等价触发前应用校验：

- 金额和数量非负；
- 缝边数量不超过商品数量；
- 核验完成 = 合格 + 返工 + 报废；
- 未完成 = 计划 - 完成；
- 退款累计不超过收款累计；
- 发货累计不超过当前有效订购数量；
- 库存批次数量不得为负；
- 售后退回 = 售后返工 + 售后报废；
- 终态订单转换合法；
- 每个生产任务明细最多一次核验，报废核验与回转事实一一对应；
- 正常来源分配、取消/未完成释放和核验消耗不得重复消费；
- 唯一核验和唯一来源消费。

## 15. Flyway 迁移与测试门禁

迁移文件位于 `backend/src/main/resources/db/migration`，按 `V<版本>__<说明>.sql` 命名。已经在任何共享环境执行过的版本迁移不得修改；修正必须新增更高版本迁移。**上线前**（开发期、未部署到任何共享环境）允许在清库重建的前提下改写早期迁移为最终结构（2026-09-24 已按此重写 `V4`/`V5`：新增 `seam_types`/`work_types`，`packaging_tiers` 去提成并预置 6 分钟档，`products` 去缝边数量/成本列并新增缝边默认值四列，`packaging_commission` 语义改为商品提成，`employee_work_types` 改 `work_type_id`），上线后该禁止条款立即生效。`V6` 为 2.23 追加的全局参数（`packaging_commission_default`、`hourly_wage`、`workday_hours`、`making_effective_hour_rate`、`target_margin_rate`）。**2026-09-25**：用户确认「把所有 Flyway 版本压缩到一个」，原 V1–V14 已合并为**单一基线** `V1__yumi_v2_schema.sql`（章节横幅保留原版本号便于对照历史证据），空库执行即得完整结构。

每次数据库变更必须具备：

1. 可向前执行的 Flyway 迁移；
2. 在 Testcontainers MySQL 空库执行成功；
3. 从上一已发布结构升级成功；
4. Hibernate `ddl-auto: validate` 通过；
5. 关键约束集成测试；
6. 事务并发、`@Version` 和关键悲观锁测试；
7. 汇总投影与事实重建一致性测试；
8. 不依赖手工修改生产数据或改写 Flyway 历史。
