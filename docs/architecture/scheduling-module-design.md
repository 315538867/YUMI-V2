## 0. 重构原因与迁移方式

### 0.1 交错现状（要修的就是这三条）

顶层只有两个类型，但当前实现拆成了三套平行体系：

| 交错点 | 现状 | 依据 |
| --- | --- | --- |
| 超额独立成体系 | 独立的 `overtime_tasks` + `overtime_task_items` + `overtime_preemptions`，独立 API，工作台上一张独立「超额预占提醒」表 | 阶段五 5.14 |
| 返工归属错 | 三道工序都能开返工；返工来源归属「发生工序」，返工在发生工序内部处理 | `ProductionNodes.isNode` 只校验三值之一；旧文档 §5.5/§6.3 |
| 其他排班位置错 | 独立三张表 + 工作台下方独立表格，不进周历 | `OtherScheduleSection.tsx` |

### 0.2 迁移方式

本机未上线、允许清库：**直接改写 `V1__yumi_v2_schema.sql` 基线并清库重建，不写兼容迁移、不保留双读双写**。重命名与拆并的表在基线内一次到位，历史数据不迁移。

## 1. 模块模型

### 1.1 顶层两类

```text
排班
├─ 制作排班            有工序流程、产生商品数量事实
│   ├─ 制作 工序       → 正常排产 / 超额任务 / 返工（修补）
│   ├─ 捏毛装袋 工序   → 正常排产 / 返工（退回制作修补）
│   └─ 缝边剪袋 工序   → 正常排产（无返工、无报废、多少进多少出）
└─ 其他排班            无工序流程、只记工时事实，不产生商品数量
```

- 顶层只有 **制作排班** 与 **其他排班** 两个类型；二者是同类事物（都是排班），区别只在制作排班有工序流程。
- **「正常排产 / 超额任务 / 返工」是制作排班内部的形态**：正常排产与超额任务只有制作工序有；返工只有制作与捏毛装袋发生，且一律回到制作修补。
- 模块名称统一为**排班**：侧栏、路由、包名、表名不再使用「生产」。

### 1.2 工序 × 形态矩阵（后端硬校验的唯一真表）

| 工序 | 正常排产 | 返工 | 报废 | 超额任务 | 合格流向 |
| --- | --- | --- | --- | --- | --- |
| 制作 | ✓ | ✓ 退回制作修补 | ✓ 报废回转 | ✓ | 捏毛装袋 |
| 捏毛装袋 | ✓ | ✓ 退回制作修补 | ✓ 报废回转 | ✗ | 按订单冻结的缝边数量分流到缝边剪袋，其余到可发货 |
| 缝边剪袋 | ✓ | ✗ 拒绝 | ✗ 拒绝 | ✗ | 可发货 |

### 1.3 其他排班

其他排班保存员工、日期、事项、小时、分钟、总分钟、核验与工时更正事实，不关联工序、商品、订单、库存、来源、任务明细或履约事实。它在工作台上与制作排班卡片**同处一个周历**，不是并列的另一张列表。

## 2. 数据结构

### 2.0 命名

一个任务头 + 多条明细承载制作排班的全部形态（正常/返工/超额）；其他排班独立。表名提案（**待确认**，见 §15）：

| 逻辑对象 | 表名提案 |
| --- | --- |
| 排班任务头 | `scheduling_tasks` |
| 排班任务明细 | `scheduling_task_items` |
| 核验事实 | `scheduling_verifications` |
| 返工池来源 | `rework_sources` |
| 报废事实 | `scheduling_scrap_records` |
| 数量回转 | `scheduling_quantity_returns` |
| 超额预占 | `scheduling_overtime_preemptions` |
| 提醒 | `scheduling_reminders` |
| 其他排班 | `other_schedules`、`other_schedule_verifications`、`other_schedule_time_corrections` |

### 2.1 `scheduling_tasks`（任务头）

字段：`task_no`、`task_date`、`employee_id` / `employee_name_snapshot`、`work_type_id` / `work_type_name_snapshot`、`task_type`、`note`、版本与审计字段。

- `task_type` 只允许 `NORMAL`、`REWORK`、`OVERTIME`；
- `task_type = REWORK` 或 `OVERTIME` 时，工序固定为**制作**，由服务端强制，不接受客户端选择；
- 任务头不保存任何数量汇总列，不参与数量流转；`task_no` 唯一。

### 2.2 `scheduling_task_items`（任务明细）

字段：`task_id`、`item_no`、订单/订单明细/产品引用与冻结快照、`node`、`planned_quantity`、`source_type` / `source_id`、标准分钟与估算分钟、能力/时间快照、状态、取消字段、版本与审计字段。

- `planned_quantity > 0`；
- `source_type` 取值：`ORDER`（正常需求与库存跳过后缺口）、`QUANTITY_RETURN`（同工序报废回转）、`REWORK_SOURCE`（返工池来源）、`OVERTIME_PREEMPTION`（超额明细预占来源）、`AFTER_SALES_SOURCE`（阶段八）；
- `REWORK` 明细的 `node` 恒为**制作**，且必须指向仍有余额的返工池来源；
- 明细状态只能 `PENDING → VERIFIED` 或 `PENDING → CANCELLED`；
- 明细创建后不得直接修改订单、产品、工序、类型、来源与计划数量。

### 2.3 `scheduling_verifications`（统一核验事实）

所有形态共用一张核验事实表，一条明细最多一条有效核验。字段：`task_item_id`、订单/产品冗余引用、工序、`planned_quantity` 快照、`completed_quantity`、`qualified_quantity`、`rework_quantity`、`scrap_quantity`、`incomplete_quantity`、备注、操作人、时间与审计字段。

不变量：

```text
completed_quantity = qualified_quantity + rework_quantity + scrap_quantity
incomplete_quantity = planned_quantity - completed_quantity
```

超额明细不再把核验结果直接写在明细行上；`overtime_task_items` 的核验列在重构中并入本表。

### 2.4 `rework_sources`（返工池）

返工池只有**制作**一个，存放制作与捏毛装袋明细核验产生的返工数量。字段：`id`、`source_no`、`origin_verification_id`、`origin_task_item_id`、`origin_node`（发生工序：制作或捏毛装袋，仅用于追溯）、订单/订单明细/产品、`total_quantity`、`arranged_quantity`、`round_no`、`previous_source_id`、`reason`、版本与审计字段。

- 归属工序不由字段保存，按模型恒为制作；
- `available_quantity = total_quantity - arranged_quantity`；
- 来源总量不得超过对应返工事实尚未建来源的额度；
- 可拆成多个 `REWORK` 明细安排；该明细核验再次产生返工时，显式创建下一轮来源（`round_no + 1`、`previous_source_id` 指向上一轮）；
- 返工池余额与正常待安排额度完全分离。

### 2.5 `scheduling_scrap_records`（报废事实）

不可变事实，字段：来源任务明细、核验事实、订单/订单明细/产品、发生工序、数量、原因、操作人、时间与幂等信息。**发生工序只可能是制作或捏毛装袋**；缝边剪袋不得写入报废。

### 2.6 `scheduling_quantity_returns`（数量回转）

报废同事务一对一写入，记录数量回到发生报废工序的普通待安排额度。字段：`scrap_record_id`（唯一）、订单/订单明细/产品、发生工序、回转总量、已分配量、可分配余额、审计字段。回转余额只能被后续 `NORMAL` 明细消费。

### 2.7 `scheduling_overtime_preemptions`（超额预占）

关联**超额明细**与**未来正常明细**：`overtime_task_item_id`、`future_task_item_id`、预占数量、已释放数量、状态、处理信息与审计字段。

- 只能是执行当天创建；来源必须为未来日期、状态 `PENDING` 的 `NORMAL` 明细；
- 同一（超额明细，未来明细）组合唯一；
- 有效预占合计不得超过未来明细当前可被预占的数量；
- 预占不修改未来明细原计划数量，不产生流入。

### 2.8 `scheduling_reminders`（提醒）

只用于待处理提示，不是数量事实来源。类型保持三类：`INCOMPLETE`、`OVERTIME_PENDING_VERIFY`、`PLAN_ADJUSTMENT`。全部可由明细、核验、来源、预占事实重建。

### 2.9 其他排班

`other_schedules`（员工、日期、事项、小时、分钟、总分钟、状态、取消与审计）、`other_schedule_verifications`（对 `schedule_id` 唯一）、`other_schedule_time_corrections`（原有效分钟 → 新分钟、原因、操作人、时间）。

### 2.10 旧表处置（基线内一次到位）

| 旧表 | 处置 |
| --- | --- |
| `production_tasks` / `production_task_items` / `production_verifications` | 改名（§2.0），`task_type` CHECK 增加 `OVERTIME` |
| `overtime_tasks` / `overtime_task_items` | **删除**；超额并入任务头/明细 |
| `overtime_preemptions` | 改名并改指向统一明细（§2.7） |
| `rework_sources` | 保留，增加 `origin_node`，去掉「发生工序即归属工序」语义 |
| `scrap_records` / `production_quantity_returns` | 改名（§2.0），约束限定工序 |
| `production_reminders` | 改名（§2.0） |
| `other_schedules` 三表 | 保留表结构，**改变使用位置**（进周历） |

## 3. 数量流转

### 3.1 基本原则

计划只是组织安排，不是实际流入。实际流入只能来自已登记事实：上游实际合格流入、兼容库存接入、同工序报废回转、首道制作的订单实际缺口（扣除库存已满足与可跳过制作部分）、返工池余额。

不得用上游计划数冒充下游流入，不得把三道工序数量相加为订单数量，不得把全部核验数量求和当作负额度。

### 3.2 正常待安排

```text
normal_pending
= normal_demand
- 未取消 NORMAL 明细 planned_quantity
- 已核验正常处理数量
+ 可分配数量回转余额
```

已核验正常处理数量按工序、订单明细与来源边界汇总，不混入返工、售后或其他排班分钟。

### 3.3 当前可执行

```text
current_executable
= 实际合格流入
+ 兼容库存接入
+ 同工序报废回转可分配余额
- 已核验处理数量
- 其他待执行 NORMAL 明细已分配的可执行数量
```

核验时必须在锁内重算，完成数量超过可执行量即拒绝。

### 3.4 合格流向（修订）

| 核验工序 | 合格事实去向 |
| --- | --- |
| 制作 | 捏毛装袋的实际合格流入 |
| 捏毛装袋 | 按订单冻结的缝边数量分流到缝边剪袋，其余进入可发货事实 |
| 缝边剪袋 | 可发货事实 |

**返工**：返工明细工序恒为制作；修补合格后沿制作的正常流向进入捏毛装袋。返工不制造新的正常需求，不回写普通计划完成量，不占正常产能、不计正常工时。

**缝边剪袋**：多少进多少出——核验中返工与报废恒为 0，完成多少就合格多少（`completed = qualified`），不产生报废、不产生回转、不产生返工事实。

## 4. 核验规则

### 4.1 批量核验入口

前端一次提交任务内多条明细。后端必须：

1. 校验任务头存在、员工与工序上下文一致；
2. 按明细逐条锁定 `PENDING` 明细；
3. 逐条重算来源余额、当前可执行流入、已占用数量与产能相关事实；
4. 逐条校验核验等式、数量上限、来源合法性与工序能力矩阵（§1.2）；
5. 任一明细失败则整批回滚，不产生任何部分核验、流入、返工事实、报废、回转或提醒；
6. 全部通过后在同一事务内写入全部事实；
7. 使用幂等键保证重复提交返回首次成功结果。

批量只是提交边界，不是放宽校验边界：不得只校验任务头总量，也不得用任务头状态代替明细校验。

### 4.2 单明细核验等式

```text
completed = qualified + rework + scrap
incomplete = planned - completed
```

数量必须为非负整数，`completed <= planned`，且不得超过锁内重算的可执行上限。`incomplete` 由后端计算并落事实。

工序约束（硬校验）：

- 缝边剪袋：`rework_quantity` 与 `scrap_quantity` 必须为 0，否则拒绝；
- 制作、捏毛装袋：允许返工与报废；
- 超额明细：只核验自身预占来源，不进入普通流入；
- 其他排班使用独立分钟核验，不进入本等式。

### 4.3 返工事实与返工池来源

明细核验产生 `rework_quantity > 0` 时，事务只记录返工事实（含发生工序）。管理员随后基于该事实显式创建**制作返工池**来源：

- 来源归属恒为制作，`origin_node` 记发生工序（制作或捏毛装袋）用于追溯；
- 来源总量不得超过对应返工事实尚未建来源的额度；
- 返工明细工序恒为制作，可拆成多条；
- 返工明细核验再次产生返工时，基于新的返工事实显式创建下一轮来源；
- 返工池余额与正常待安排额度完全分离。

未完成数量按来源类型回退：

- `NORMAL`：未完成部分回到该工序普通待安排额度，并产生未完成提醒；
- `REWORK`：未完成部分回到返工池来源的已安排余额；
- 阶段八售后类型：按阶段八来源边界处理。

### 4.4 报废处理

核验产生报废时，事务内同时写入不可变报废事实与一对一数量回转（回到发生报废工序的普通待安排额度）。

报废不得：产生替代来源或替代类型、增加订单需求、生成上游合格事实、生成库存合格事实、直接产生新任务、释放报废发生日期已占用的正常资源。后续重新安排必须创建 `NORMAL` 明细，用新的日期重新参与容量与工时校验。

### 4.5 超额核验

超额明细的核验仍遵守核验等式，但核验后的处理为：未完成部分释放对应预占；只有合格部分形成未来计划调整提醒，提醒按预占顺序分摊且不超过各未来明细的预占数量；返工、报废、未完成不作为未来正常计划减少依据。

## 5. 取消、状态与来源余额

### 5.1 明细取消

只能取消单个仍为 `PENDING` 的明细，必须记录原因、操作人与时间。取消事务内：明细转为 `CANCELLED`；释放该明细尚未消费的正常额度、返工池余额或超额预占；不删除已存在的核验、报废、回转与审计事实；不改变其他明细；任务头只有在全部明细取消后才派生为已取消。

已核验明细不能通过取消撤销已发生事实；阶段五不实现通用生产核验更正。

### 5.2 状态与投影

明细事实状态只有 `PENDING`、`VERIFIED`、`CANCELLED`。任务头状态完全派生（已排班 / 进行中 / 待核验 / 部分核验 / 已核验 / 已取消），不提供人工选择状态的写接口。待安排、当前可执行、来源余额与提醒必须能从事实重建；投影只作查询优化。

## 6. 超额任务

### 6.1 创建边界

- 只能在执行当天创建，日期由服务端业务时钟读取；
- 工序固定为制作；
- 每条来源必须明确关联一条未来日期、状态 `PENDING` 的 `NORMAL` 明细与预占数量；
- 预占合计不能超过来源明细尚未被其他有效预占的数量；
- 不修改未来明细原计划、不提前减少未来需求、不产生流入。

### 6.2 核验后的处理

- 未完成部分释放对应预占；
- 合格数量按预占顺序形成未来计划调整提醒；
- 返工、报废不形成未来计划减少提醒；
- 合格数量为零时，超额待核验提醒转为无需调整；
- 提醒是待处理事项，不是未来计划数量变更事实；未来计划是否调整必须通过明确的计划调整命令并保留审计，不由核验事务隐式修改。

## 7. 安排时的工作量提示（工时口径）

**这不是数量校验，是工时负荷提示。**

- 维度：**员工 + 日期 + 工序**；
- 汇总：该员工该日期该工序全部未取消 `NORMAL` 明细（含本次新增）的 `estimated_minutes` 合计；
- 容量：
  - 制作：`workday_hours × 60 × making_effective_hour_rate`（制品有效工时）；
  - 捏毛装袋 / 缝边剪袋：`workday_hours × 60`（完整工作日分钟）；
- 判断：合计 > 容量 → **超出**（排不下）；合计 < 容量 → **还有余量**（少了）；相等不提示；
- 性质：**只提示，不拦截**；不改变产品 `dailyMaxCapacity` 的正常硬约束；
- 位置：新建页在该员工/日期/工序的明细区实时显示「已排合计 / 有效工时 / 超出或余量」；工作台在该员工当日位置显示同一口径的负荷。
- 删除：工作台上独立的「超额预占提醒」表。**超额待核验**提醒跟超额任务卡走，**未来计划调整**提醒附着在受影响的未来正常明细上。

数量口径（§3.2 待安排量）用于判断能否安排、是否形成超额，与本节工时口径分开展示，不混为一谈。

## 8. API 契约

写接口必须支持 `Idempotency-Key`；重复请求返回首次成功结果，不重复消费来源或生成事实。

| 能力 | 方法与路径 | 说明 | 主要拒绝码 |
| --- | --- | --- | --- |
| 任务列表 | `GET /api/scheduling-tasks` | 按日期、员工、工序、类型、状态、订单、产品筛选 | `AUTH_REQUIRED`, `NOT_FOUND` |
| 创建任务 | `POST /api/scheduling-tasks` | 一个头 + 多条明细；`taskType=NORMAL/REWORK/OVERTIME` 决定明细请求形状（超额明细提交未来明细引用与预占数量） | `VALIDATION_INVALID`, `EMPLOYEE_NOT_ELIGIBLE`, `SOURCE_INSUFFICIENT`, `CAPACITY_EXCEEDED`, `OVERTIME_DATE_INVALID`, `OVERTIME_RESERVATION_EXCEEDED` |

| 事实时间线 | `GET /api/scheduling-tasks/{id}/facts` | 单一只读端点聚合事实，按 `factTime ASC, factType ASC, factId ASC` | `NOT_FOUND` |
| 取消明细 | `POST /api/scheduling-tasks/{id}/items/{itemId}/cancel` | 只能取消待执行明细，恢复对应余额 | `STATE_NOT_CANCELABLE`, `CONFLICT_VERSION` |
| 批量核验 | `POST /api/scheduling-tasks/{id}/verify` | 一次提交多条明细；逐明细校验、整批原子提交 | `VERIFICATION_EQUATION_INVALID`, `QUANTITY_NOT_EXECUTABLE`, `STATE_ALREADY_VERIFIED`, `SOURCE_INSUFFICIENT`, `CONFLICT_VERSION` |
| 返工池来源 | `GET /api/rework-sources`、`GET /api/rework-sources/{id}`、`POST /api/rework-sources` | 返回发生工序、轮次、已安排、余额与关联明细 | `SOURCE_INSUFFICIENT`, `SOURCE_INVALID` |
| 从返工池创建明细 | `POST /api/rework-sources/{id}/tasks` | 强制 `taskType=REWORK`、工序=制作 | `SOURCE_INSUFFICIENT`, `VALIDATION_INVALID` |
| 报废事实 | `GET /api/scheduling-scraps`、`GET /api/scheduling-scraps/{id}` | 只读不可变报废记录 | `NOT_FOUND` |
| 数量回转 | `GET /api/scheduling-quantity-returns` | 发生工序、回转数量、已分配与可分配余额 | `NOT_FOUND` |
| 提醒 | `GET /api/scheduling-reminders`、`POST /api/scheduling-reminders/{id}/defer` | 未完成、超额待核验、未来计划调整 | `NOT_FOUND`, `VALIDATION_INVALID` |

## 9. 前端页面与工作台

### 9.1 路由

| 路由 | 页面 | 关键行为 |
| --- | --- | --- |
| `/scheduling` | 排班工作台 | 日期横向周历；制作排班卡片与其他排班卡片同处一格；显示等待上游、待核验、未完成与负荷 |
| `/scheduling/tasks/new` | 全页统一新建 | 先选顶层类型（制作排班 / 其他排班）；制作排班再选工序与形态（正常/返工/超额）；逐明细显示来源、标准分钟、估算分钟与工作量提示 |
| `/scheduling/tasks/:id` | 只读任务详情 | 头、明细、来源、快照、核验、返工/报废/回转关联与派生状态；查看页不是编辑表单 |
| `/scheduling/tasks/:id/verify` | 多明细核验 | 一次提交多条明细；按工序能力矩阵显示字段（缝边剪袋不出现返工/报废）；显示等式、可执行上限与失败明细定位 |

### 9.2 工作台交互原则

- 周历是唯一导航骨架，其他排班不再有独立列表；
- 统一新建入口只有一个，不按来源类型拆成多个隐藏入口；
- 员工是卡片属性与筛选条件，不是主导航；
- 任务头显示派生状态，明细显示事实状态，禁止手工下拉覆盖；
- 来源、额度、返工池余额在明细上下文中解释展示，不作为进入页面的前置知识；
- `REWORK` 标记为「制作返工（修补）」并显示发生工序，不显示为普通产能任务；
- 页面区分「计划数量」「实际流入」「当前可执行」「本次完成」「回转余额」与「已排工时 / 有效工时」。

## 10. 事务、锁定顺序与幂等

### 10.1 事务拥有者

以下命令由排班模块应用服务在一个事务内完成：创建任务及明细；取消明细；批量核验；从返工池创建明细；超额任务创建、核验与提醒处理；其他排班核验与工时更正。跨模块写入订单履约、库存接入或流入事实时，必须通过已登记的模块接口在同一事务内完成，不得复制订单数量规则。

### 10.2 锁定顺序

1. 锁定任务头（批量核验先锁头）；
2. 按 `item_id` 升序锁定任务明细；
3. 锁定对应订单明细/履约余额与库存接入事实；
4. 按来源 id 升序锁定返工池来源或数量回转余额；
5. 锁定报废记录关联的可分配回转记录；
6. 创建或核验超额任务时锁定预占记录及未来正常明细；
7. 最后写入核验、来源、报废、回转与提醒事实。

创建任务没有既有明细可锁定时，必须锁定所有涉及的订单明细、库存/履约余额、返工池来源或回转余额，再校验容量与来源。所有竞争性查询使用 `FOR UPDATE` 或等价锁定读，不能依赖普通快照读。

阶段八售后任务使用售后来源与售后明细的独立锁定顺序，不得借普通订单履约余额实现售后额度。

### 10.3 幂等与并发

- 所有写命令要求 `Idempotency-Key`；
- 数据库唯一约束与幂等记录共同保证重复请求不重复写事实；
- 批量核验的幂等键以任务与请求为边界，重复提交返回首次成功结果；
- 版本冲突返回 `CONFLICT_VERSION`，不静默覆盖；
- 并发创建任务、消费来源、分配回转、核验明细、预占未来明细时，必须在锁内重算余额与上限；
- 任一明细失败，批量事务整体回滚。

## 11. 模块边界与错误码

### 11.1 模块边界

- `scheduling` 负责任务、明细、核验、返工池来源、报废、数量回转、超额预占、提醒与其他排班事实；
- `orders` 负责订单需求、订单明细与履约事实的所有权；排班模块只能通过约定的只读引用与履约事实接口访问；
- `catalog` 负责员工在职与工种资格、产品星级、包装档位、缝边种类与标准分钟配置；
- `inventory` 负责库存事实与兼容库存接入；
- `after-sales` 在阶段八拥有售后来源与售后生产边界；**售后的退回返工同样只允许落到制作返工池，不得在捏毛装袋或缝边剪袋开返工**；
- 其他排班不向任何订单或商品模块产生数量事实。

不得出现 `orders → scheduling` 的业务规则反向依赖；订单侧展示排班进度时使用只读查询或投影引用。

### 11.2 错误码

沿用既有分层错误，优先复用而不为文案重复新增：

`VALIDATION_INVALID`、`NOT_FOUND`、`CONFLICT_VERSION`、`STATE_ALREADY_VERIFIED`、`STATE_NOT_CANCELABLE`、`STATE_NOT_EDITABLE`、`QUANTITY_INVALID`、`QUANTITY_NOT_EXECUTABLE`、`VERIFICATION_EQUATION_INVALID`、`SOURCE_INSUFFICIENT`、`SOURCE_INVALID`、`EMPLOYEE_NOT_ELIGIBLE`、`CAPACITY_EXCEEDED`、`OVERTIME_DATE_INVALID`、`OVERTIME_RESERVATION_EXCEEDED`、`AFTER_SALES_SOURCE_INVALID`。

缝边剪袋出现返工或报废、返工目标非法、超额工序非制作，统一返回 `VALIDATION_INVALID` 或 `SOURCE_INVALID`，并在 `fieldErrors` 指向具体明细与字段。错误响应必须指出任务明细、字段与事实冲突位置，尤其是批量核验中的失败明细。

## 12. 不变量

1. 任务头只保存共同组织信息，不参与任何数量流转；明细是最小事实边界。
2. 顶层只有制作排班与其他排班两个类型；「正常排产 / 超额任务 / 返工」是制作排班内部形态，不是第三、第四套体系。
3. 超额任务与正常排产、返工共用同一个任务头/明细模型与同一张核验事实表；超额只多一张预占关联。
4. 超额任务只有制作工序有；返工只有制作与捏毛装袋发生。
5. 缝边剪袋无返工、无报废，多少进多少出（`rework = scrap = 0`，`completed = qualified`）。
6. 返工池只有制作一个；制作与捏毛装袋的返工都回到制作修补；返工明细工序恒为制作，`origin_node` 记发生工序用于追溯。
7. 明细核验满足 `completed = qualified + rework + scrap` 与 `incomplete = planned - completed`；每条明细最多一次核验，批量逐明细校验、整批原子提交。
8. `NORMAL` 计划按产品、日期、工序汇总，未取消计划不得超过 `moldQuantity * dailyBatchLimit`；历史核验计划仍占历史资源。
9. `REWORK` 不占普通产能、不计正常工时、不产生虚构正常工时；修补合格沿制作正常流向。
10. 标准分钟来自冻结的产品星级、包装档位或缝边种类，不得用工作日分钟或最大产能反推。
11. 工作量提示按「员工 + 日期 + 工序」的工时口径：制作比制品有效工时（`workday_hours × 60 × making_effective_hour_rate`），其他工序比完整工作日分钟；超出与不足只提示，不拦截。
12. 下游可执行上限只能来自实际合格、兼容库存、同工序回转等当前事实，不能来自上游计划数。
13. 首道制作缺口扣除库存已满足与跳过工序部分，不以订购总量笼统覆盖。
14. 普通排产额度与返工池余额分开计算，不得把全部核验数量求和作为负额度。
15. 返工量先形成不可变返工事实；管理员基于事实显式创建返工池来源；再次返工须显式创建下一轮来源。
16. 报废事实不可变；报废不增加订单需求、不产生上游合格或库存事实、不产生替代类型；数量回转只回到发生报废工序的普通可安排额度。
17. 后续使用回转余额必须创建 `NORMAL` 明细，并由新的日期重新占用资源。
18. 取消只针对单个待执行明细；任务头仅在全部明细取消时派生为已取消。
19. 超额预占关联明细，不改未来原计划；只有合格才产生未来计划调整提醒，返工与报废不减少未来计划。
20. 其他排班只产生独立总分钟事实，不产生商品数量、库存事实或订单履约事实，且与制作排班同处一个周历。
21. 所有汇总都能从不可变或可追溯事实重建；投影、提醒与派生状态不能成为唯一事实来源。
22. 所有竞争资源使用统一锁定顺序和锁定读；写命令幂等，批量失败整体回滚。
23. 阶段八售后来源、权限与事实边界不得被普通排班任务绕过。

## 13. 不做项

- 不提供普通核验的编辑、冲销或物理删除；
- 不提供来源数量的手工改写；来源余额只能由创建、核验、取消、未完成回退与回转分配事实改变；
- 不提供自动选择员工、自动选择来源或自动排产；
- 不把来源/额度/返工池作为进入排班页面前必须掌握的导航概念；
- 不把任务头数量当作订单履约数量；
- 不以核验完成释放历史日期的正常排班资源；
- 不以返工或报废推导未来正常计划减少；
- 不把其他排班分钟转换成商品数量；
- 不为其他排班引入工序；
- 不恢复已废弃的替代生产模型或基于工序顺序限制返工目标的模型；
- 不为超额再建第二套任务头/明细/核验表；
- 不保留任何未经证实的实施结论。

## 14. 实施顺序与验收口径

实施按下列顺序逐条推进，每条都要有机器证据：

1. **基线重写**：按 §2 改写 `V1__yumi_v2_schema.sql`，删除超额两表、改名列、加 `OVERTIME` 类型约束、`rework_sources` 加 `origin_node`；清库重建通过。
2. **后端包与路由重命名**：`com.yumi.production` → `com.yumi.scheduling`，API 路径按 §8；全仓库搜索确认无 `overtime_tasks`/`overtime_task_items` 与旧路径残留。
3. **返工池改造**：返工明细工序固定制作；缝边剪袋核验拒绝返工与报废；`origin_node` 落库并在事实时间线展示。
4. **超额并表**：超额明细走统一核验表与统一核验端点；预占表改指向统一明细；超额头工序固定制作。
5. **工作量提示**：新建页与工作台按「员工 + 日期 + 工序」显示已排估算分钟与有效工时对比；删除独立「超额预占提醒」表。
6. **其他排班进周历**：删除 `OtherScheduleSection` 独立表；其他排班卡片进周历并保留核验/取消/更正入口。
7. **门禁与验收**：`./mvnw test` 全量、前端 `typecheck` / `test` / `build` 全绿；`openspec validate --strict`；浏览器按新路由走一遍主链路。

验收必须覆盖：缝边剪袋不得返工与报废；捏毛装袋返工落到制作返工池且工序为制作；超额与正常任务同表且预占不改未来计划；工作量提示的工时口径正确；其他排班在周历中可见且不产生商品数量；批量核验整批回滚；并发不超卖。
