## 1. 设计目标

YUMI V2 是单应用、单 MySQL 的模块化单体。模块之间需要强一致协作，但不能因为共享数据库而互相读写表、复用内部 Repository 或形成隐藏调用链。

跨模块正式写入统一遵循：

```text
外部请求
→ 一个命令所有者
→ 一个完整业务事务
→ 明确的参与模块
→ 各模块只写自己的事实、快照和投影
→ 一次提交
```

这套规则同时解决四个问题：

- 谁拥有一次业务动作的最终结果；
- 哪些模块可以参与同一事务；
- 每个模块分别写入哪些权威数据；
- 查询、错误、幂等和外部副作用如何避免越过模块边界。

## 2. 模块公开边界

### 2.1 公开能力

模块只对外提供三类能力：

```text
应用命令接口
只读查询接口
跨模块业务端口
```

接口由能力提供方拥有。调用方依赖提供方的公开 `api` 类型，不在自己的模块中重新定义同义端口。

跨模块调用采用同进程 Java 接口，不使用内部 HTTP，不为未来可能拆分微服务预先加入序列化、重试或消息中间件。

### 2.2 接口输入

公开输入必须表达业务意图，可以包含：

- 稳定业务标识；
- 操作者和请求上下文；
- 本次操作的数量、金额、方向或原因；
- 必要的冻结快照标识或快照内容；
- 来源操作标识；
- 预期版本号或并发校验值。

输入不得包含：

- 调用方计算出的可用余额；
- 调用方计算出的目标投影值；
- 数据库行对象；
- 内部 Repository 或可变领域聚合；
- 任意 `Map<String, Object>`；
- 用于绕过提供方规则的通用 JSON 负载。

例如，发货调用应表达“请求从指定交付约定中消费数量”，而不是把调用方计算好的余额交给生产模块：

```text
production.consumeForShipment(
    agreementGroupId,
    shipmentItemId,
    requestedQuantity,
    sourceSelection,
    expectedVersion
)
```

不得设计为：

```text
production.decreaseAvailableQuantity(
    demandId,
    quantity,
    callerCalculatedBalance
)
```

提供方必须在自己的锁内重新读取当前事实和投影，重新计算余额并决定实际结果。

### 2.3 接口输出

公开输出使用不可变业务结果，只返回后续编排真正需要的结果，例如：

- 新增事实标识；
- 实际确认数量；
- 产生的业务差额；
- 更新后的版本号；
- 产生或消费的来源标识；
- 可供审计和幂等记录使用的执行标识。

不得对外暴露：

- 数据库行模型；
- SQL；
- 内部 Repository；
- 可被调用方修改后整体回存的实体；
- 仅为数据库映射存在的字段；
- 本模块表结构。

### 2.4 禁止的通用接口

不建立以下接口：

```text
execute(commandType, payload)
save(entity)
updateProjection(...)
decreaseAvailableQuantity(...)
appendGenericFact(...)
```

每项正式业务能力使用明确的方法、专用输入和专用输出类型。接口名称表达完整业务能力，而不是某张表的 CRUD 动作。

### 2.5 接口版本

同一单体内部不维护多套兼容版本。所有模块一起发布，内部 Java 契约随业务语义统一变更。

如果未来外部 HTTP 客户端需要兼容旧协议，只在 HTTP 适配层建立版本转换，不把外部版本兼容扩散到内部模块接口。

## 3. 依赖与编排规则

### 3.1 单层编排

一次跨模块正式写入只有一个命令所有者，由命令所有者完成完整业务编排：

```text
命令所有者
├─ 本模块事实、快照和投影
├─ 参与模块 A 的业务端口
└─ 参与模块 B 的业务端口
```

参与模块不能再调用第三个业务模块的写入接口。禁止形成隐藏链：

```text
orders → production → scheduling
```

如果同一命令需要 `production` 和 `scheduling`，由命令所有者直接协调两者：

```text
orders
├─ production
└─ scheduling
```

参与模块可以在自己的边界内调用本模块领域服务和 Repository，但不得把跨模块编排下沉到 Repository 或领域对象中。

### 3.2 一个业务动作，一个命令所有者

Controller 只能调用一个完整应用命令，不得自行调用多个模块再拼装写入。

命令所有者按主要业务根确定，而不是按本次写入了哪张表确定。例如：

- 普通发货虽然会更新生产来源，仍由 `orders` 所有；
- 排班核验虽然会写入生产事实，仍由 `scheduling` 所有；
- 实际工资支付虽然会关联工资结算，仍由 `finance` 所有。

### 3.3 提供方重新校验

查询、预览和影响评估只提供当前观察结果，不提供正式写入授权。

正式命令必须在事务内重新：

- 读取当前业务根和投影；
- 校验权限；
- 校验状态和数量余额；
- 校验版本和唯一性；
- 计算本次差额；
- 判断是否允许写入。

调用方不能用预览时保存的余额、状态或资格替代参与模块的事务内判断。

## 4. 命令事务规则

### 4.1 事务传播

完整业务命令由命令所有者开启事务，使用等价于：

```text
PROPAGATION_REQUIRED
```

跨模块参与端口只加入现有事务，使用等价于：

```text
PROPAGATION_MANDATORY
```

参与端口在没有外层事务时必须立即失败，不得自行开启并提交一段独立业务结果。

核心业务写入禁止使用：

```text
REQUIRES_NEW
```

事实、快照、投影、占用、幂等和审计结果必须与所属业务动作保持同一提交边界。

### 4.2 事务内允许的动作

```text
模块间同步 Java 调用
MySQL 查询、锁定和写入
calculation 纯公式计算
权限、状态、数量和金额校验
幂等和审计写入
已暂存文件的元数据关联
```

### 4.3 事务内禁止的动作

```text
文件上传或删除
第三方 HTTP 调用
邮件、短信和通知发送
打印
大型报表生成
启动操作系统程序
等待人工
长时间批处理
```

### 4.4 失败语义

参与模块的业务拒绝、并发冲突、唯一性冲突和基础设施异常必须传播到命令所有者。命令所有者不得把参与模块的失败降级成警告或部分成功。

同一命令内任一步失败时，以下结果整体回滚：

```text
业务事实
冻结快照
当前投影
来源占用
幂等成功记录
审计结果
暂存文件的正式关联
```

不建立同一数据库内的补偿工作流来掩盖部分提交。

## 5. 全局锁定顺序

跨模块事务统一按以下顺序获取业务锁：

```text
orders / after-sales
→ scheduling
→ production
→ payroll
→ finance
→ cost-ledger
```

这不是要求每个事务锁定所有模块，而是要求同一事务涉及多个模块时不得逆序获取锁。

模块内部统一按以下顺序：

```text
业务根
→ 明细
→ 来源与占用
→ 当前投影
```

同类型的多条记录按稳定主键升序锁定。所有余额和状态校验都必须发生在锁内。条件更新必须检查实际受影响行数。

### 5.1 特殊模块

- `master-data` 通常只读取当前版本，并在业务确认时冻结快照，不进入履约写锁链；
- `calculation` 无持久化、无数据库锁；
- `platform` 的幂等与审计写入附着于主事务，不定义业务锁序；
- `reporting` 只读，不进入正式业务写锁链。

### 5.2 调用方向与锁序

调用方向和锁定顺序是两个维度。命令所有者负责发起锁定计划，但实际数据库锁必须按全局模块顺序和模块内顺序获取。位于全局顺序较前的命令所有者先锁自己的业务根和明细，再依次调用后续模块锁定；命令所有者位于参与模块之后时，必须先通过参与模块锁定全局顺序较前的对象，再锁定自己的对象。不能因为自己是命令所有者就逆序加锁。

例如生产处置影响尚未完成的排班时，命令所有者仍是 `production`，但事务应遵守：

```text
production 命令
→ 先由 scheduling 锁定受影响的未完成任务
→ 再由 production 锁定生产根、来源和投影
→ 同一事务完成处置和任务调整
```

这不允许 `scheduling` 再编排第三个模块，也不改变命令所有者；它只保证锁序不反转。

## 6. 命令所有者与事务矩阵

下表登记正式跨模块写入。模块间的只读查询不替代正式命令矩阵，另按查询契约管理。

### 6.1 订单与履约

| 业务命令 | 命令所有者 | 写入参与模块 | 主要事实与快照 | 主要投影 | 提交后动作 |
|---|---|---|---|---|---|
| 订单确认 | `orders` | `production` | 订单确认、交付约定、金额与预计成本快照；制作需求初始化事实 | 订单、交付约定、制作需求与缺口 | 可选通知或文件处理 |
| 订单取消 | `orders` | `production` | 订单取消事实；未消费生产需求关闭事实 | 订单、交付约定、订单履约、生产需求与缺口 | 可选通知 |
| 订单变更 | `orders` | 受影响任务存在时 `scheduling`；`production` | 订单变更、管理员任务取消确认、任务取消、占用释放、实物影响和归组调整事实；新的约定与金额快照 | 订单、交付约定、生产缺口、受影响排班 | 可选通知 |
| 普通发货 | `orders` | `production` | `orders` 保存普通发货事实、发货明细和交付约定快照；`production` 保存来源消费事实 | 订单累计发货和交付履约；生产来源余额和参与状态 | 可选打印或通知 |
| 订单退款决定 | `orders` | 无写入参与模块 | 订单价款退款义务事实；必要时订单完成失效事实 | 订单付款履约与退款待支付 | 可选通知 |
| 订单收款、退款支付或多收款退回 | `orders` | `finance` | 订单收付款业务事实；真实现金事实 | 订单付款履约、财务现金余额 | 可选对账通知 |
| 订单完成确认 | `orders` | 无写入参与模块；`scheduling`、`production` 参与锁定校验 | 管理员确认完成事实；双方履约状态指纹与版本 | 订单完成状态 | 可选归档或通知 |
| 录入已有订单 | `orders` | `production`、必要时 `finance` | 历史订单、当前履约、已产出状态和历史收付款事实；录入时状态快照 | 订单、制作状态、付款履约 | 可选导入报告 |

订单完成必须同时满足工作室交付履约和客户付款履约。完成命令按 `orders → scheduling → production` 锁序读取并锁定各模块权威摘要，`scheduling` 和 `production` 只参与校验、不写入；管理员确认事实才是订单完成时间。后续事项由 `after-sales` 承担，不重新打开订单。

订单变更影响未核验任务时，正式流程固定为：`orders` 锁订单根和变更明细，`scheduling` 锁全部受影响任务并重验管理员取消确认，`production` 锁来源、占用和投影，随后统一取消任务、释放占用并应用订单变更。任一任务已经核验、未获管理员确认或版本变化时整体回滚。

普通发货固定为：`orders` 锁订单根、交付约定和发货草稿，`production` 锁生产来源和来源投影，再分别追加普通发货事实与来源消费事实。发货更正恢复来源时沿用同一锁序；存在有效售后引用或实物已经发出时不得恢复来源。

### 6.2 排班与生产

| 业务命令 | 命令所有者 | 写入参与模块 | 主要事实与快照 | 主要投影 | 提交后动作 |
|---|---|---|---|---|---|
| 创建排班 | `scheduling` | `production` | 排班计划、产能分配和占用事实；标准时间与产能快照 | 任务、任务明细、生产来源占用 | 可选工作台刷新 |
| 取消排班 | `scheduling` | `production` | 任务取消和占用释放事实 | 任务状态、来源可用余额 | 可选通知 |
| 排班核验 | `scheduling` | `production`、`cost-ledger` | 核验事实、合格/待修复/报废/未完成数量流转、生产事实；成本基础事实 | 任务核验状态、制作状态、修复池、待归集成本基础 | 可选通知 |
| 包装还原 | `production` | 未完成任务受影响时 `scheduling` | 包装还原和质量处置事实；必要时任务调整事实 | 当前物理状态、制作投影、任务状态 | 可选通知 |
| 生产质量处置或报废 | `production` | 未完成任务受影响时 `scheduling` | 质量问题、责任、处置、报废或补做事实 | 制作状态、可交付数量、修复池、任务状态 | 可选通知 |

排班只代表计划、产能分配和正式占用，不代表生产已经发生。只有核验命令产生生产事实。

生产命令涉及 `scheduling` 时，仍由 `production` 作为命令所有者，但按“先锁排班、后锁生产”的全局顺序执行，避免与排班命令反向加锁。包装还原或质量处置影响未核验任务时，管理员先确认取消影响；正式命令锁内重验确认和版本，统一取消任务、释放占用并追加生产处置事实。任一任务已经核验、管理员未确认或版本变化时整体拒绝。

### 6.3 售后

| 业务命令 | 命令所有者 | 写入参与模块 | 主要事实与快照 | 主要投影 | 提交后动作 |
|---|---|---|---|---|---|
| 售后受理 | `after-sales` | 无强制写入参与模块 | 售后案例、问题、责任初判、处理路线、双方义务和金额决定 | 售后案例、有效义务、处理状态 | 可选通知 |
| 售后退回接收 | `after-sales` | `production` | 退回接收事实；退回实物登记、当前物理阶段和质量待判断事实 | 售后退回义务、退回实物生产状态 | 可选文件归档 |
| 售后生产需求确认 | `after-sales` | `production` | 重新加工、重新交付或额外补发义务；售后生产需求来源和必要快照 | 售后义务、售后生产缺口 | 可选通知 |
| 售后创建或取消排班 | `scheduling` | `production` | 排班计划、产能分配、取消和来源占用事实；售后需求快照 | 任务、任务明细、售后来源占用 | 可选工作台刷新或通知 |
| 售后重新交付 | `after-sales` | `production` | 售后重新交付事实和义务快照；生产来源消费事实 | 售后履约、生产来源余额 | 可选通知或打印 |
| 售后额外替换或补发 | `after-sales` | `production` | 独立替换或补发交付事实和义务快照；生产来源消费事实 | 售后履约、生产来源余额 | 可选通知或打印 |
| 售后收款、退款或赔付 | `after-sales` | `finance` | 售后结算业务事实；真实现金事实 | 售后结算、现金余额和关联 | 可选通知 |
| 售后完成确认 | `after-sales` | 无强制写入参与模块 | 双方有效义务完成快照、售后完成事实 | 售后完成状态 | 可选归档或通知 |

售后重新交付与额外替换是不同义务，均不增加原订单销售数量，也不重新打开原订单。售后受理只形成案例、决定和义务，不预先写入尚未发生的生产、排班或现金事实。

售后排班仍由 `scheduling` 作为命令所有者，并通过 `production` 占用对应售后生产来源。`after-sales` 不直接写排班任务，也不在重新交付命令中临时创建排班。

`after-sales` 拥有售后交付事实和售后履约；`production` 拥有制品物理状态、质量状态、来源消费和来源余额；`finance` 拥有真实现金事实。参与模块不能互相覆盖这些权威结果。

### 6.4 工资、成本与资金

| 业务命令 | 命令所有者 | 写入参与模块 | 主要事实与快照 | 主要投影 | 提交后动作 |
|---|---|---|---|---|---|
| 工资计算、封账或补差 | `payroll` | `cost-ledger` | 工资计算、责任修复、扣款、免扣额度和封账事实；生产事实集合与规则快照 | 工资应付、封账状态、待归集人工成本 | 可选工资单生成 |
| 实际工资支付 | `finance` | `payroll` | 真实现金支付事实；工资结算支付关联事实 | 现金余额、工资支付状态 | 可选通知 |
| 采购、房租、水电等经营支出 | `finance` | `cost-ledger` | 真实现金支出事实；经营成本归集事实 | 现金余额、经营成本投影 | 可选对账 |
| 成本手工调整或更正 | `cost-ledger` | 无强制写入参与模块 | 成本调整或更正事实；来源核验快照 | 成本归集与分摊投影 | 可选对账报告 |

`payroll` 读取生产事实但不能修改生产事实。`cost-ledger` 记录已确认的成本归集，不伪造尚未发生的工资支付或现金支出。`finance` 记录真实现金事实，不直接修改成本归集规则。

### 6.5 投影校验与重建

| 运维命令 | 命令所有者 | 写入参与模块 | 主要写入 | 约束 |
|---|---|---|---|---|
| 模块投影校验 | 投影拥有模块 | `platform` 审计能力 | 校验报告与审计记录 | 只报告差异，不修改业务投影 |
| 模块投影重建 | 投影拥有模块 | `platform` 审计能力 | 目标投影替换或修正、重建批次 | 锁定明确业务范围，原子替换并记录前后值 |
| 跨模块一致性检查 | `reporting` 或平台运维用例 | 各模块公开校验查询 | 对账报告与审计记录 | 不跨模块直接扫描或修改业务表 |

投影重建不是普通管理员自由编辑数字。优先按订单、交付约定组、生产需求来源、修复池、售后单、工资期间或成本范围执行。

## 7. 查询组合边界

### 7.1 模块数据访问

业务模块只能查询自己拥有的事实、快照和投影。需要其他模块数据时，只能调用对方公开只读查询接口。

禁止：

```text
模块 A → 模块 B 的 Repository
模块 A → 模块 B 的行模型
模块 A → 模块 B 的数据库表
跨模块 SQL 联表
```

### 7.2 组合责任

- 订单详情和订单工作台由 `orders` 负责组合订单上下文；
- 生产工作台由 `production` 或 `scheduling` 按业务上下文负责组合；
- 售后详情由 `after-sales` 负责组合售后上下文；
- 跨领域对账、统计和经营分析由 `reporting` 负责；
- Controller 只调用一个完整查询用例，不自行调用多个模块拼装结果；
- 查询服务不得递归扇出调用第三个业务模块。

高频跨模块分析可以建立 `reporting` 自己拥有的可重建读投影。该投影只用于查询和分析，不参与正式命令的余额、资格或状态判断。

### 7.3 查询一致性

- 普通列表和搜索读取最新已提交数据，不保持长事务；
- 业务详情、预览和影响评估可以使用短事务只读快照；
- 正式命令无论此前查询是否成功，都必须在自己的事务内重新读取和校验；
- 核心详情数据缺失时明确报错，不静默转换成零值或空列表。

## 8. 错误归属与传播

### 8.1 错误码归属

错误码由发现业务规则的模块定义：

- 订单状态不允许变更：`orders`；
- 生产来源数量不足：`production`；
- 排班任务不能取消：`scheduling`；
- 付款金额或现金事实不一致：`finance`；
- 售后路线或义务不成立：`after-sales`；
- 工资结算规则不满足：`payroll`；
- 成本来源或更正不成立：`cost-ledger`。

同一业务错误只能有一个归属模块。其他模块复用该能力时不重新定义同义错误码。

### 8.2 错误分类

模块之间传递结构化业务异常，不传递 HTTP 状态码、Controller 响应对象或通用错误字符串。错误至少区分：

```text
业务拒绝
并发冲突
幂等键冲突
幂等重复成功
外部输入错误
基础设施失败
程序缺陷
```

HTTP 层只负责把错误转换为统一响应信封，不重新解释业务语义。错误结果可包含：

```text
code
message
fieldErrors
requestId
operationId
```

不得泄露 SQL、表名、内部堆栈或敏感数据。

### 8.3 失败传播

参与模块发现错误后直接返回失败。命令所有者不得：

- 把业务拒绝转成警告；
- 提交其他模块已经成功的部分结果；
- 捕获异常后继续写入；
- 使用同库补偿流程掩盖事务设计错误。

## 9. 认证、授权与操作者上下文

### 9.1 平台职责

`platform` 负责认证请求并提供不可变的操作者上下文：

```text
operatorId
requestId
session/authentication context
tenant/workspace context（如未来启用）
```

平台提供角色、权限标识和授权基础能力，但不拥有订单、生产、排班、财务等业务规则。

### 9.2 业务模块职责

业务模块负责判断本模块业务授权和业务前置条件：

- `orders` 判断订单变更、发货和收款命令是否允许；
- `production` 判断质量处置、包装还原和来源消费是否允许；
- `scheduling` 判断排班、取消和核验是否允许；
- `finance` 判断现金事实登记和更正是否允许；
- `payroll`、`cost-ledger`、`after-sales` 分别判断本模块敏感业务动作。

跨模块命令由命令所有者完成整体授权判断，参与模块仍必须校验自己拥有的敏感业务前置条件。

授权判断必须发生在正式命令事务内、业务状态重新读取之后。预览接口返回“允许执行”不构成正式授权结论。

认证失败、会话失效和业务无权操作必须使用不同错误语义。

## 10. 外部请求幂等与领域唯一性

### 10.1 命令所有者负责外部幂等

正式外部命令至少识别：

```text
idempotencyKey
requestId
requestFingerprint
operatorId
```

命令所有者负责幂等键的范围、指纹组成、成功结果和重放语义。

同一命令范围内：

```text
相同幂等键 + 相同请求指纹 + 已成功
→ 返回第一次成功结果，不重复写入

相同幂等键 + 不同请求指纹
→ 拒绝，错误码 CONFLICT_IDEMPOTENCY

上次执行已回滚
→ 允许重新执行
```

并发提交相同幂等键时，不得并行产生两套事实。请求必须等待已提交结果，或得到明确并发冲突。

幂等成功记录与业务事实、快照、投影在同一事务中提交。业务事务回滚时不能留下“已成功”的幂等结果。

### 10.2 参与模块负责领域唯一性

参与模块不解释外部幂等键，只接收稳定的内部执行上下文：

```text
commandExecutionId
sourceBusinessId
sourceFactId
operationType
```

参与模块通过自己的唯一约束和业务校验防止重复接收，例如：

```text
UNIQUE(command_execution_id, operation_type)
UNIQUE(order_receipt_fact_id)
UNIQUE(verification_fact_id, cost_category)
UNIQUE(shipment_item_id, production_source_id)
```

幂等键不能替代业务唯一性，业务唯一性也不能替代外部请求幂等性。

不把幂等实现成能够替所有命令解释请求语义的通用拦截器。`platform` 可以提供幂等记录存储能力，但命令所有者决定每个命令的语义。

## 11. 暂存文件与提交后副作用

文件不在正式业务事务中上传或删除。固定流程为：

```text
上传临时文件
→ platform 保存临时文件记录
→ 正式业务命令开启事务
→ 在事务中把临时记录转为正式业务关联
→ 一次提交
→ 提交后执行外部动作
→ 未关联临时文件由过期清理任务删除
```

数据库事务内只保存已暂存文件的元数据关联，不直接依赖文件系统操作成功来决定数据库提交。

提交后的通知、缓存刷新、打印、文件转码、报表生成等动作必须：

- 在事务提交成功后执行；
- 不改变已经提交的业务事实；
- 可以安全重试；
- 失败时进入可观察的待处理或失败状态；
- 不被伪装成主业务事务已经完成。

可靠的第三方支付、回调或外部业务系统接入如果未来出现，必须另行设计状态机、外部幂等和对账机制，不能直接塞入当前本地事务。

## 12. 事务矩阵的强制性与验证

事务矩阵不是参考说明，而是正式架构约束。新增或修改跨模块写入时，必须同步登记：

```text
业务命令
命令所有者
写入参与模块
只读参与模块
全局锁定顺序
模块内锁定对象
新增事实
冻结快照
更新投影
幂等与唯一约束
失败条件
提交后动作
```

未登记的跨模块写调用不得进入实现。

### 12.1 结构验证

Spring Modulith 结构测试和包可见性约束至少验证：

- 模块依赖只指向公开 API；
- Controller 不依赖 Repository；
- 模块不依赖其他模块 infrastructure；
- 模块不依赖其他模块行模型；
- `calculation` 不依赖业务模块；
- 业务模块不依赖 `reporting`；
- 参与模块端口不暴露为 HTTP Controller 入口。

### 12.2 行为验证

真实 MySQL 集成测试按事务矩阵逐条验证：

- 正常路径事实、快照和投影同时提交；
- 参与模块失败时全部回滚；
- 并发命令不会超卖或重复占用；
- 幂等重放不产生第二套事实；
- 不同请求指纹使用同一幂等键会被拒绝；
- 领域唯一约束阻止重复参与写入；
- 取消、更正和处置按规定更新投影；
- 生产处置涉及排班时仍遵守锁定顺序；
- 提交前外部副作用不会被执行；
- 报表投影异常不会改变正式业务结果。

测试必须使用真实事务和真实数据库约束验证，不以 Mock 模块调用代替跨模块原子性验证。

## 13. 明确不采用

- 模块之间直接读写对方数据库表；
- Controller 编排多个模块写入；
- Repository 负责跨模块事务；
- 参与模块自行开启独立业务事务；
- `REQUIRES_NEW` 切断核心业务原子性；
- 参与模块反向编排第三个业务模块；
- 通过通用 JSON 或 `Map<String, Object>` 绕过公开契约；
- 用调用方提交的余额或投影值作为权威判断；
- 用跨模块 SQL 联表替代公开查询接口；
- 用报表投影参与正式业务校验；
- 用审计日志替代业务事实；
- 用消息队列或事件消费者承载当前核心强一致写入；
- 在事务内发送通知、调用第三方或操作文件系统；
- 用死锁重试掩盖不一致的锁定顺序；
- 用通用工作流引擎配置业务事务。

## 14. 已确认不变量

```text
一次正式业务动作只有一个命令所有者
命令所有者负责外层事务和最终结果
参与模块只通过公开业务端口加入现有事务
完整命令使用 REQUIRED，参与端口使用 MANDATORY
核心业务写入不使用 REQUIRES_NEW
各模块只写自己拥有的事实、快照和投影
公开接口表达业务意图，不接收调用方派生余额和目标投影
正式命令在锁内重新校验权限、状态、余额、版本和唯一性
跨模块事务遵守统一全局锁序和模块内锁序
参与模块失败时整个命令回滚
外部请求幂等由命令所有者负责
参与模块通过领域唯一性防止重复业务事实
业务错误由发现规则的模块定义
平台负责认证上下文，业务模块负责业务授权
业务查询通过公开查询接口组合，不跨模块联表
报表投影不参与正式业务写入校验
事务内不执行外部副作用
暂存文件只在正式事务中关联，外部文件动作提交后执行
所有跨模块写入必须登记在事务矩阵中
```
