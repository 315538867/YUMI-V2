本文是 YUMI V2 的唯一实施方案，不是生产、排班或小组功能的单模块方案。模块设计负责说明“模块内部如何实现”，本文负责说明“全系统按什么依赖顺序实施、每一步交付什么证据以及何时允许进入下一步”。

## 2. 当前实施起点

当前仓库以设计文档为主，尚未建立 `backend/`、`frontend/`、Flyway、Spring Modulith、ArchUnit、Testcontainers MySQL 和部署工程。因此第一项工作固定为 G0，不允许从任一业务模块直接开工。

### 2.1 已明确并待 G0 签字生效的系统边界

以下结论不得在实现阶段重新解释：

- 13 个顶级模块及其数据所有权；
- 跨模块只能调用公开应用能力、公开查询或登记的事务参与端口；
- Controller、Repository、SQL 和 reporting 不得绕过模块边界；
- 协调器只编排事务，不拥有业务事实、快照、投影和 Repository；
- 事实只追加；快照由定义它的模块负责创建、版本、持久化、查询和保留，其他模块只保存 `ownerModule + snapshotType + snapshotBusinessId + snapshotVersion` 完整类型化引用，不保存裸版本、内部主键或快照载荷；
- 排班只拥有计划事实，标准工时、有效工作时间和工作量评估由 `master-data` 公开查询提供，纯公式由 `calculation` 提供；
- 小组任务形成共同产出，不拆成员个人产量；小组效率因子只用于工作量规划，不作为工资分配比例；
- 小组配置被有效计划引用时拒绝修改，计划取消或核验后可以修改；历史核算通过不可变小组快照解释；
- `payroll` 结算到人，`cost-ledger` 归集成本，`finance` 记录真实现金，三者口径分离；
- `reporting` 只读，不参与正式业务资格、余额、状态和完成判断；
- Spring Modulith、ArchUnit、Flyway、表所有权检查和真实 MySQL 验证从 G1 起持续执行。

### 2.2 已明确并待 G0 签字生效的首期技术决策

首期按以下基线实施，变更必须先回到 G0 评审：

| 主题 | 决策 |
|---|---|
| 后端 | Java 21、Spring Boot 3.5.x、Spring Modulith、Spring JDBC/JdbcClient、Maven Wrapper |
| 数据库 | MySQL 8.4 LTS、`READ COMMITTED`、Flyway 为唯一结构来源 |
| 前端 | Vue 3、TypeScript、Vite、Vue Router、Pinia；前端只依赖 HTTP 契约 |
| 认证 | 管理端账号密码登录；服务端不透明会话；浏览器使用 `HttpOnly + Secure + SameSite=Lax` Cookie |
| 会话 | 会话摘要保存 MySQL，空闲 8 小时失效，最长 7 天；改密、停用员工和管理员撤销立即失效 |
| 授权 | RBAC 权限能力代码加业务资源范围；Controller 只做入口校验，业务模块重验业务授权 |
| 密码 | BCrypt，强度 12；不记录明文、可逆密文或密码日志 |
| 文件 | S3 兼容对象存储接口；开发测试使用 MinIO；数据库只保存平台文件记录和业务关联，不保存文件内容 |
| 部署 | 容器化应用、前端静态资源、MySQL、对象存储；配置和密钥由环境注入，不写入仓库 |
| 可观测性 | 结构化日志、Micrometer 指标、OpenTelemetry 链路；敏感字段白名单脱敏 |
| 时间与金额 | 数据库存 UTC 时间戳，业务日期显式保存；金额 `DECIMAL(19,4)`，对外展示按业务币种舍入 |

具体表、字段、路由和运行参数分别以平台、HTTP、数据库、前端及部署设计文档为准。

### 2.3 已形成并须在 G0 复核冻结的设计产物

以下设计文档已经建立并完成本轮技术一致性审查，但这不等于 G0 已退出；G0 仍须取得业务、技术和数据三方冻结签字：

- 售后、工资、成本台账、财务和报表模块详细设计；

- 完整 HTTP 端点、权限能力、内置角色和稳定错误码目录；
- UUIDv7 稳定标识、SHA-256 指纹、`GLOBAL/SELF` 资源范围和提交后任务唯一性规则；
- 前端路由、页面、状态和权限入口；
- 部署、备份恢复、迁移、切换和回退设计；
- 每个阶段的可执行验收场景和证据位置。

### 2.4 本轮技术审查结论

本轮已经消除已发现的模块越界、裸快照版本、字段类型歧义、实际锁序占位、小组效率默认值和工资分配口径冲突。当前设计层面不存在需要开发人员临时选择的架构、所有权、跨模块写入、快照管理、表结构或阶段顺序。

仍需在 G0 签字或后续阶段提供的内容不是设计歧义，而是受控输入和实施证据：

- 业务负责人确认各实际人数对应的协作效率因子具体数值；未配置前不得创建该人数的小组任务；
- 提供初始管理员、员工、商品、客户、静态数据和历史数据样本；这些数据必须通过已冻结的导入或迁移契约进入系统；
- 各环境注入真实域名、证书、数据库、对象存储、密钥和容量参数，不得改写模块边界或业务公式；
- G1-G14 产生 Flyway、Modulith、ArchUnit、真实 MySQL、并发、回滚、性能、迁移和上线证据。

因此下一步不是继续创建平行方案，而是由业务负责人、技术负责人和数据负责人完成 G0 签字；签字前只允许修正文档冲突，签字后严格按本文从 G1 起顺序开发。

## 3. 总体实施原则

### 3.1 依赖优先

提供方先于调用方交付可验证契约。顺序由能力依赖决定，不按菜单、文档编号或当前业务关注度决定。

### 3.2 模块允许分阶段扩展

模块建包不等于模块完成。例如 `cost-ledger` 在 G4 只交付生产核验成本内核，在 G11 才补齐完整经营成本；`finance` 在 G4 只交付客户收退款内核，在 G11 才补齐工资支付和经营支出。

### 3.3 每个业务阶段必须纵向闭环

业务阶段必须同时交付必要的数据库迁移、应用能力、HTTP、权限、幂等、前端页面、真实 MySQL 测试、审计和运行指标。禁止以空表、空接口、Mock 参与模块或未接线页面宣称完成。

### 3.4 写入只走公开能力

所有跨模块写入必须登记命令所有者、参与模块、事务传播和锁序。参与模块只写自己的表，不解释外部幂等键，也不得继续编排第三个业务模块。

### 3.5 设计和验证分离

G0 冻结“应该生成什么”，G1 用真实工程证明“能够生成并自动阻断错误”。G0 不以运行 Flyway 或编译代码作为退出条件。

## 4. 完整系统依赖拓扑

```text
G0  设计、数据库蓝图、命令矩阵和验收场景冻结
  ↓
G1  后端/前端工程、模块声明、Flyway/Testcontainers、CI 与运行骨架
  ↓
G2  platform + calculation
  ↓
G3  master-data
  ↓
G4  提供方内核（可并行）
    ├─ production：需求、来源、数量与物理阶段内核
    ├─ cost-ledger：生产核验成本识别内核
    └─ finance：客户收退款现金事实内核
  ↓
G5  orders 核心、订单快照、交付约定与生产需求初始化
  ↓
G6  production + scheduling + 两个协调器的制作执行闭环
  ↓
G7  普通发货与工作室交付履约
  ↓
G8  订单资金、客户付款履约与订单完成
  ↓
G9  after-sales 售后闭环
  ↓
G10 payroll 工资结算闭环
  ↓
G11 cost-ledger + finance 完整经营成本与现金闭环
  ↓
G12 reporting 报表、对账与经营分析
  ↓
G13 已有数据迁移、影子校验、停写切换与回退演练
  ↓
G14 全系统验收、上线与 14 天稳定期
```

说明：

- G4 的三个内核可并行，但必须使用 G0 冻结的同一结构引用和事务规则；
- G5 必须调用 production 初始化需求，orders 不保存生产余额；
- G6 必须等待 master-data、production 和 cost-ledger 前置能力；
- G8 必须等待 finance 客户资金能力以及 production/scheduling 完成校验能力；
- G9 必须等待订单完成、生产、排班和 finance 对应能力；
- G10 的正常生产工资依赖 G3+G6，售后责任和补差集成依赖 G9；G10 阶段统一完成两部分；
- G12 只能调用公开查询或读取 reporting 自有投影；
- G13 前可开发迁移工具和做样本演练，正式全量切换必须等待 G12 通过。

## 7. G0：完整系统设计冻结

G0 不开发业务代码、不要求编译通过、不运行正式 Flyway；它负责冻结实现输入。

- 建立开放决策登记表，任何未决定项必须明确阻塞哪个阶段；
- 删除 `TODO`、`TBD`、“后续适当处理”等不可执行占位。

退出：没有会改变模块所有权、事务、表结构或外部契约的隐含假设。

### 7.2 G0.2：补齐模块详细设计

按依赖顺序完成：

1. `cost-ledger`；
2. `finance`；
3. `after-sales`；
4. `payroll`；

每份设计必须满足数据库与模块契约基线第 17 节的 17 项要求，并明确表、状态、命令、参与端口、查询、锁序、幂等、错误、权限和真实 MySQL 测试。

### 7.3 G0.3：复核命令矩阵

- 禁止同一业务动作出现两个命令所有者。

### 7.4 G0.4：完成数据库蓝图

## 10. G3：主数据与商品能力

按依赖顺序交付；每个聚合的当前记录、事实、必要快照、公开端口和事务测试必须在同一步闭环，不允许先交付可变主表、再在后续步骤补历史快照：

1. 固定静态数据类别、工种定义、时间条目管理，以及商品录入默认值当前配置；默认值只用于新建商品预填，不建立业务快照或历史版本；
2. 商品聚合：完整商品命令、制作工序预算模板、定制方案、内置标准方案自动生成与同步，以及 `PRODUCT`、`PRODUCT_CUSTOMIZATION_PROFILE`、`PRODUCT_MAKING_STANDARD`、`PRODUCT_STANDARD_BUDGET`、`PRODUCT_CUSTOMIZATION_BUDGET` 五类快照和规范化明细；商品与方案不提供服务端草稿，创建或修改必须原子提交完整数据；
3. 客户聚合：客户当前记录、变更事实和 `CUSTOMER` 快照；
4. 员工聚合：员工、在职事实、工种资格事实与投影，以及 `EMPLOYEE_ASSIGNMENT_SUBJECT` 快照；
5. 小组效率标准：固定服务于 `MAKING`、仅按人数配置且启用值必须大于 `1` 的全局协作效率因子、版本化管理端点和 `TEAM_EFFICIENCY_STANDARD` 快照；
6. 生产小组聚合：小组、成员变更事实、当前成员投影、活动计划引用守卫参与端口和 `WORK_TEAM` 快照；
7. 按 V011-V012 完成上述九类快照的表结构、强类型 Ref、专用解析端口、存在性校验和批量查询，禁止任意字符串快照类型和动态表名解析；
8. 公开当前查询、正式预算快照选择、工作量评估和小组变更参与端口，并完成管理页面、导入校验、权限、审计和模块级自动化测试。

退出：业务模块只通过公开能力获取当前资格或历史快照，不能直接读取主数据表；九类快照均能以完整四字段指针精确解析，预算结果还能追溯到计算所采用的商品和方案（如有）快照；商品录入默认值只负责新建商品预填，调用方不保存其快照引用；所有当前数据变更与必要快照在同一事务提交且查询不隐式写快照；小组被活动计划引用时修改失败，引用解除后可修改；每个实际使用的小组人数都有大于 `1` 的 ACTIVE 效率标准，缺失标准不会回退默认值。

## 13. G6：制作、排班与协调闭环

### 13.1 G6.1 阶段契约与迁移

### 13.2 G6.2 production 制作执行能力

实现包装、质量、责任、处置、修复池、生产核验、数量流转和投影重建。

### 13.3 G6.3 scheduling 创建和调整

实现任务、任务明细、执行主体、工作量评估快照、日守卫、来源占用和调整。小组任务只保存完整小组快照引用，不拆个人任务。

### 13.4 G6.4 scheduling 取消

### 13.5 G6.5 核验强一致闭环

```text
scheduling 核验命令
→ production 追加核验与数量事实
→ cost-ledger 识别可立即确认成本

### 13.7 G6.7 履约协调

### 13.8 G6.8 HTTP 与工作台

### 13.9 G6.9 真实 MySQL 验收

覆盖并发占用、活动计划修改小组、任务取消与核验竞态、核验重复提交、参与模块失败、死锁错误传播、全事务回滚和投影重建。

退出：从订单需求到任务、占用、核验、生产事实和成本基础归集形成真实 MySQL 强一致闭环。

## 14. G7：普通发货与交付履约

按顺序实施：

1. 前端查询当前可交付来源并在页面内完成选择，不保存服务端临时数据；
2. orders 接收完整发货确认命令，锁定订单、约定和履约投影；
3. production 按稳定顺序锁定来源和来源投影，重新校验并直接追加来源消费事实；
4. orders 追加发货事实、明细和约定快照；
5. 更新工作室交付履约投影；
6. 实现发货更正、追溯和页面。

所有权：发货事实和履约投影属于 orders；来源消费事实和余额属于 production。已被售后引用或实物已发出的来源不得通过更正恢复。

退出：发货事实和来源消费原子提交，任一数量都可追溯到 production 来源。

## 15. G8：订单资金、付款履约与完成

按顺序实施：

1. orders 当前有效应收和金额调整；
2. orders 收款、退款支付和多收款退回命令；
3. finance 参与并保存真实现金事实与分配；
4. orders 更新客户付款履约投影；
5. orders 读取并锁定 scheduling/production 完成摘要；
6. 同时满足工作室交付和客户付款后形成订单完成事实与快照；
7. 实现收退款、付款履约和完成页面。

退出：页面或报表状态不能替代完成事实；重复收退款不产生第二套业务事实或现金事实。

## 16. G9：售后闭环

固定按实际动作实施，不建立一个同时写完所有模块的“售后总事务”：

1. `after-sales` 受理案例、问题、处理路线和双方义务；
2. 退回接收时，after-sales 保存接收事实，production 保存退回实物状态；
3. 售后生产需求确认时，after-sales 保存义务，production 创建售后来源；
4. 售后任务由 scheduling 完整创建/取消命令负责，after-sales 不写排班表；
5. 重新加工核验复用 G6；
6. 重新交付和额外补发由 after-sales 拥有交付事实，production 参与来源消费；
7. 售后收款、退款和赔付由 after-sales 保存业务事实，finance 保存现金事实；
8. 全部有效客户和工作室义务满足后形成售后完成事实及义务快照；
9. 交付售后工作台和全链路追溯。

退出：售后不重开原订单、不覆盖原完成事实、不预写尚未发生的生产、排班、成本或现金事实。

## 17. G10：工资结算

### 17.1 G10.1 正常生产工资

读取 production 权威核验事实、责任事实、任务工作量评估引用和 master-data 历史员工/小组快照。个人任务直接形成员工工资行；小组任务先计算一份共同工资，再结算到历史成员。

首期小组分配规则固定为：

1. 不使用小组效率因子作为工资比例；
2. 有效成员为任务保存的小组快照全部成员；
3. 总金额转换为最小货币单位后整除成员数；
4. 余数按员工稳定业务标识升序逐个分配一个最小货币单位；
5. 保存规则版本、成员集合、分配前总额和每人结果。

### 17.2 G10.2 责任、扣款和售后补差

实现责任员工、修复员工、报废材料扣款、月度免扣额度、责任更正和售后责任工资。责任未确认时不得默认扣原执行员工。

### 17.3 G10.3 期间、封账和补差

实现工资期间、计算批次、来源防重、员工结果、封账和封账后补发/补扣。封账结果不可覆盖；后续更正只能进入调整事实和后续支付。

### 17.4 G10.4 人工成本与支付关联

工资封账时调用 cost-ledger 形成已确认人工成本；实际工资支付属于 finance，固定锁序 `payroll → finance`，payroll 保存支付关联，finance 保存现金事实。

退出：每一工资行可追溯到生产事实、规则版本和历史快照；同一生产事实不能重复进入多个有效工资结果。

## 18. G11：完整经营成本与现金闭环

### 18.1 G11.1 cost-ledger 扩展

补齐工资、材料、返工、报废、包装还原、普通履约、售后、运费和经营费用的归集、分摊、更正和查询。成本发生、成本归集和预计成本必须分离。

### 18.2 G11.2 finance 扩展

首期不建设采购或库存模块。finance 提供具名经营收支命令，支持工资支付、材料采购付款、房租、水电、运费、报销和其他经营收支；每笔记录必须有交易方向、分类、对方、金额、发生时间、支付方式、附件和来源。

### 18.3 G11.3 经营费用成本参与

需要进入成本的经营支出由 finance 命令同事务调用 cost-ledger。允许一笔现金支出按明确金额分配到多个成本对象；未分配余额保持财务未分配状态，不能自动平均分摊。

材料采购付款只表示现金发生，不表示材料已被某订单消耗；首期没有库存余额、领用和退料模型。

退出：同一来源不重复归集或支付，现金总额等于分配金额加未分配金额，成本更正不覆盖现金事实。

## 19. G12：报表、对账与经营分析

首期必须交付：

1. 订单履约总览；
2. 生产进度与需求缺口；
3. 排班负载和任务状态；
4. 售后处理进度与义务；
5. 工资期间和员工结算汇总；
6. 订单预计成本与已归集成本；
7. 客户收付款和退款；
8. 经营现金流；
9. 订单收入、成本和利润；
10. 跨模块数量、金额、状态和来源一致性对账。

低频详情通过模块公开查询组合；高频聚合保存 reporting 自有可重建投影。投影必须保存来源模块水位、重建批次和最后成功时间。

时效要求：业务详情查询读取最新权威结果；普通聚合延迟不超过 5 分钟；日结报表在业务日结束后 30 分钟内完成。超过水位阈值必须显示“数据延迟”，不能伪装为实时。

退出：reporting 不访问其他模块底层表，不参与正式业务判断；全部投影可按业务范围重建并生成差异报告。

→ 旧系统只读保留
```

禁止新旧系统对同一权威事实双写。影子期间新系统不承担正式业务写入。

### 20.2 批次和映射

迁移工具必须保存批次、旧来源、旧标识、新稳定业务标识、转换版本、状态、错误和重试次数。迁移元数据属于平台运维记录，不成为业务事实来源。

每个批次必须可重复执行、防重、暂停和从明确水位恢复。正式事实迁移必须使用业务模块提供的迁移入口或受控迁移适配器，不能绕过约束直接拼接跨模块 SQL。

### 20.3 对账标准

- 正式事实数量、金额、来源关系和完成状态要求零不可解释差异；
- 可选备注、历史空字段等非权威信息允许进入签字确认的例外清单；
- 每条例外包含旧记录、原因、处理结论、负责人和审批时间；
- 不允许以汇总金额相等掩盖明细来源错误。

### 20.4 切换和回退

切换前完成最终备份、停写确认、最终增量、对账和入口切换演练。入口切换后，在允许新系统正式写入前保留完整技术回退点；一旦产生新系统正式事实，不允许直接切回旧系统继续写入，必须暂停入口并以前向修复或新系统恢复处理。

旧系统只读保留 90 天；迁移映射和差异证据至少保留到稳定期结束后 180 天。

退出：全量重放不产生第二套事实，零不可解释差异，失败可停在批次边界，切换和回退演练均有记录。

## 21. G14：全系统验收、上线与稳定期

### 21.1 功能和架构验收

覆盖订单、生产、排班、发货、资金、完成、售后、工资、成本、现金和报表闭环；Spring Modulith、ArchUnit、表所有权、SQL 扫描和禁止 reporting 反向依赖全部通过。

### 21.2 数据库与并发验收

覆盖空库迁移、升级迁移、全局锁序、锁等待、死锁错误传播、幂等重放、唯一约束、并发竞态、参与模块失败全回滚、投影校验重建、备份恢复和灾难恢复。

### 21.3 首期容量和服务目标

在不少于 100 个并发管理端会话、30 QPS 只读请求和 10 TPS 核心写命令的基线压力下：

- 普通查询 P95 ≤ 2 秒，P99 ≤ 5 秒；
- 核心写命令 P95 ≤ 3 秒，P99 ≤ 8 秒；
- 普通报表 P95 ≤ 10 秒，超大导出改为提交后任务；
- 非业务拒绝的服务端错误率 < 0.5%；
- 不出现未解释死锁、负余额、重复事实和部分提交；
- 数据库恢复点目标 RPO ≤ 15 分钟；
- 服务恢复时间目标 RTO ≤ 4 小时。

### 21.4 上线判定和稳定期

Go/No-Go 由业务负责人、技术负责人和数据负责人共同确认。以下任一项未关闭时不得上线：

- 权威事实或金额存在不可解释差异；
- 核心命令可能部分提交；
- 备份无法恢复；
- 权限可越权访问客户、工资或财务数据；
- 回退或前向修复流程未演练；
- P0/P1 缺陷未关闭。

上线后进入 14 个自然日稳定期。稳定期每天检查错误率、慢查询、任务积压、投影水位、备份、对账差异和用户问题；稳定期出现权威数据不一致时立即停止相关入口并执行故障 Runbook。

只有 G0-G14 的退出证据全部存在，系统才能标记为“已实现并验证”。

## 22. 跨阶段持续工作流

| 工作流 | 起始阶段 | 持续要求 |
|---|---|---|
| 架构边界测试 | G1 | 每次新增包、依赖、Repository 或 SQL 都运行 |
| Flyway 与真实 MySQL | G1 | 每个持久化能力先迁移后实现 |
| HTTP 契约 | G2 | 每个阶段同步维护端点、错误码和权限 |
| 前端页面 | G3 | 每个业务闭环同步交付，不复制后端规则 |
| 审计与幂等 | G2 | 每个正式命令登记并验证 |
| 可观测性 | G1 | 每阶段增加业务指标、错误和慢查询观测 |
| 数据迁移 | G0 | 早期盘点和样本演练，G13 正式切换 |
| 安全与权限 | G1 | 每个端点和敏感动作同步验证 |
| 文档回写 | G0 | 实现偏差先评审再更新，禁止静默偏离 |

## 23. 执行规则

1. 上游阶段退出条件未通过，不启动依赖它的下游业务代码；
2. 同层无依赖任务可以并行，但必须使用同一冻结契约；
3. 每个阶段按本文 `Gx.y` 顺序执行，模块设计不得创建平行阶段编号；
4. 发现所有权、事务、锁序或表设计冲突时返回 G0 修正文档；
5. 临时跨表、跨 Repository、复制公式或 Mock 跨模块事务不得作为过渡实现；
6. 阶段完成时同步更新迁移、接口目录、权限、运行手册和验收证据；
7. 未通过真实 MySQL 事务验证的跨模块写入不得标记完成；
8. 未经用户要求不提交、不推送；提交时使用中文 Conventional Commits。
