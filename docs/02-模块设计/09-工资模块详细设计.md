> 模块：`payroll`
>
> 状态：已完成技术一致性审查，待 G0 多方签字冻结
>
> 版本：v1.1
>
> 日期：2026-09-29
>
> 实施阶段：G10；顺序以完整系统实施方案为唯一依据

## 1. 职责与边界

`payroll` 拥有工资规则版本、工资期间、来源采集、到人计算、责任修复、扣款、免扣额度、封账、补差和支付关联。它不拥有生产数量、当前员工或小组配置、经营成本和现金。

生产事实由 `production` 提供；历史个人与小组信息由 `master-data` 快照查询提供；售后责任由 `after-sales` 提供；封账人工成本由 `cost-ledger` 接收；实际支付由 `finance` 作为命令所有者。

## 2. 首期工资规则

1. 个人产出：按有效生产核验来源数量乘工资规则单价计算。
2. 小组共同产出：先对任务整体计算工资金额，再按历史小组快照完整成员均分，不拆成员个人产量。
3. 均分算法：金额先转业务币种最小单位整数；整数除以成员数；余数按员工稳定业务标识升序每人增加一个最小单位。
4. 小组效率因子只用于排班工作量规划，禁止进入工资公式或分配权重。
5. 责任修复、扣款和免扣额度形成独立明细，不回写生产事实。
6. 封账后原期间结果不可覆盖；遗漏或更正进入后续补差批次。
7. 规则版本一旦被计算运行引用不可修改，只能新建版本。

## 3. 状态

- 工资期间：`OPEN -> CALCULATING -> REVIEWED -> CLOSED`。
- 计算运行：`CREATED -> RUNNING -> SUCCEEDED/FAILED -> SUPERSEDED`。
- 工资结果：`CALCULATED -> REVIEWED -> CLOSED -> PARTIALLY_PAID/PAID`。
- 规则版本：`INACTIVE -> ACTIVE -> RETIRED`；同一规则集只允许一个 ACTIVE。

## 4. 表设计

## 6. 计算流程

1. 锁定期间并创建运行；
2. 从公开查询按截止时间读取 production、after-sales 和 master-data 快照；
3. 固化 `payroll_source_facts`，计算来源指纹；
4. 按规则版本计算个人或小组整体金额；
5. 对小组按第 2 节算法形成 `payroll_team_allocations`；
6. 应用责任、扣款、免扣额度和历史补差；
7. 生成员工结果及明细；
8. 复核后封账，并为进入有效封账结果的每个来源写入 `payroll_effective_source_guards`；
9. 同事务向 `cost-ledger` 提交人工成本并保存提交事实。

重跑同一来源集合会创建新运行并将旧运行标记为 `SUPERSEDED`，不会覆盖旧明细；来源唯一约束只在封账时写入有效来源守卫，因此试算和复核重跑不会被历史运行阻断，同一来源也不能进入两个有效封账结果。

生成列规则：工资规则 `active_unique_key = IF(status = 'ACTIVE', rule_set_code, NULL)`；封账事实 `active_unique_key = IF(is_valid, period_business_id, NULL)`。

## 7. 跨模块事务

| 动作 | 所有者 | 参与模块 | 固定锁序 |
|---|---|---|---|
| 工资封账和人工成本提交 | payroll | cost-ledger | payroll period -> employee result -> cost-ledger source guard |
| 实际工资支付 | finance | payroll | payroll result -> finance account |

工资计算读取采用截止时间快照，不持有其他模块数据库锁；若源数据在截止后更正，进入补差而不是修改已封账期间。

## 8. HTTP、权限与错误

端点：`POST /api/v1/payroll/periods`、`POST /api/v1/payroll/periods/{id}/calculate`、`/review`、`/close`、`POST /api/v1/payroll/adjustments`、`GET /api/v1/payroll/periods/{id}`、`GET /api/v1/payroll/periods/{id}/employees/{employeeId}`。

权限：`payroll.period.manage`、`payroll.calculate`、`payroll.review`、`payroll.close`、`payroll.adjust`、`payroll.read`、`payroll.sensitive.read`。工资明细属于敏感资源，默认仅工资管理员和员工本人可见。

错误码：`PAYROLL_PERIOD_OVERLAP`、`PAYROLL_PERIOD_NOT_OPEN`、`PAYROLL_SOURCE_CHANGED`、`PAYROLL_RULE_VERSION_INVALID`、`PAYROLL_TEAM_SNAPSHOT_INVALID`、`PAYROLL_RESULT_NOT_REVIEWED`、`PAYROLL_PERIOD_ALREADY_CLOSED`、`PAYROLL_COST_SUBMISSION_FAILED`、`PAYROLL_PAYMENT_EXCEEDS_PAYABLE`、`PAYROLL_VERSION_CONFLICT`。

## 9. 并发、舍入与验收

- 期间行串行化计算、复核和封账；同期间同类型只允许一个运行处于 RUNNING。
- 所有中间金额保持四位小数；到人分配按币种最小单位做整数运算，保证分配总和严格等于小组整体金额。
- Flyway 使用 `V070-V079`。
- 真实 MySQL 必测：个人计算、小组 2/3/4 人均分及余数、成员排序稳定、效率因子不进入工资、重复来源防重、封账与成本提交回滚、封账后源更正生成补差、并发封账、部分支付和超额支付、敏感权限隔离、投影重建。
