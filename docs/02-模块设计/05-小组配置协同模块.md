## 2. 模块定位与依赖

`workforce-coordination` 是无业务事实的应用编排模块。它只拥有协调接口与实现代码，不拥有：

- 小组、小组成员、小组快照或资格事实；
- 排班任务、活动引用或引用守卫；
- 业务表、Repository、领域聚合和投影；
- 通用审批、通用工作流或可重试状态机；
- 参与模块业务错误码。

依赖固定为：

```text
HTTP 命令适配层
        │
        ▼
workforce-coordination
      ┌─┴─────────────┐
      ▼               ▼
scheduling        master-data
引用守卫参与端口   小组变更参与端口

scheduling → master-data 公开只读查询
master-data -X→ scheduling
```

允许：

```text
workforce-coordination → scheduling.WorkTeamPlanReferenceGuardPort
workforce-coordination → master-data.WorkTeamMutationParticipantPort
scheduling → master-data.WorkAssignmentSubjectQuery / WorkloadAssessmentQuery
```

禁止：

```text
master-data → scheduling
master-data / scheduling → workforce-coordination
workforce-coordination → production / orders / after-sales / payroll / finance / cost-ledger
workforce-coordination → 任意业务表、Repository 或内部实现类
```

该依赖图用于解除原先“小组由 master-data 修改、又反向调用 scheduling 守卫”形成的模块环。结构测试必须保证顶级模块图无环。

## 3. 业务规则

小组配置只包含编号、名称、状态和完整成员集合：

- 不设置组长；
- 不配置可承接商品或工序范围；
- 不拆分倒胶、填色、画画等内部流水步骤；
- 不保存成员产量、贡献比例或未来生效时间；
- 全部成员必须在职可用；
- 制作小组至少一名成员具有 `MAKING` 工种资格；
- 任务只能引用完整小组快照，不能临时选择成员子集。

只要小组仍被 `ARRANGED` 计划引用，名称、成员和状态都不能变更。计划取消或核验后活动引用释放，可以再次修改。该限制不是永久冻结。

小组快照由 `master-data` 自主管理：创建时立即生成初始版本，每次成功变更名称、成员或状态时生成新版本。`WorkAssignmentSubjectQuery` 和 `WorkTeamSnapshotQuery` 只读取已存在快照，禁止在查询或首次计划引用时隐式创建。

## 4. 公开用例

```java
interface WorkTeamConfigurationCoordination {
    RenameWorkTeamResult rename(
        RenameWorkTeamCommand command,
        RequestContext context,
        IdempotencyInput idempotency
    );

    ChangeWorkTeamMembersResult changeMembers(
        ChangeWorkTeamMembersCommand command,
        RequestContext context,
        IdempotencyInput idempotency
    );

    ChangeWorkTeamStatusResult changeStatus(
        ChangeWorkTeamStatusCommand command,
        RequestContext context,
        IdempotencyInput idempotency
    );
}

interface WorkTeamChangeImpactQuery {
    WorkTeamChangeImpactView preview(
        WorkTeamChangeImpactQueryInput input,
        QueryContext context
    );
}
```

`WorkTeamChangeImpactQuery` 只用于页面提示，可以组合当前小组版本和活动排班引用摘要，不产生事实、快照、幂等成功记录或正式审计结果，也不能作为提交授权。

HTTP Controller 每次只调用上述一个完整用例，不得分别调用 scheduling 与 master-data 再自行拼装事务。

## 5. 参与端口

### 5.1 排班引用守卫

```java
interface WorkTeamPlanReferenceGuardPort {
    PreparedWorkTeamReferenceScope lockAndCheckNoActiveReferences(
        LockWorkTeamReferenceScope command
    );
}
```

该端口由 `scheduling` 拥有，使用 `PROPAGATION_MANDATORY`。`LockWorkTeamReferenceScope`、`PreparedWorkTeamReferenceScope` 和协调类型均由 scheduling 定义；`workforce-coordination` 把自己的变更类型显式映射后调用，scheduling 不依赖协调器。准备结果内含 platform `PreparedScopePointer`，协调器传给 master-data 时只传该结构指针，不把 scheduling 类型泄漏进 master-data 契约。它负责：

1. 插入或锁定 `schedule_team_reference_guards`；
2. 在锁内重新查询 `ARRANGED` 引用；
3. 有活动引用时返回 `WORK_TEAM_ACTIVE_PLAN_REFERENCED`；
4. 无引用时返回与当前事务、操作标识和范围指纹绑定的准备结果；
5. 保持守卫锁到外层事务结束。

### 5.2 主数据变更参与端口

```java
interface WorkTeamMutationParticipantPort {
    WorkTeamMutationResult rename(RenameWorkTeamMutation command);
    WorkTeamMutationResult changeMembers(ChangeWorkTeamMembersMutation command);
    WorkTeamMutationResult changeStatus(ChangeWorkTeamStatusMutation command);
}
```

该端口由 `master-data` 拥有，使用 `PROPAGATION_MANDATORY`。它只允许 `workforce-coordination` 调用，并负责：

1. 校验准备结果属于当前事务、当前小组和当前协调操作；
2. 锁定小组根、当前成员和版本；
3. 重验 `expectedVersion`、成员在职状态、制作资格和目标状态；
4. 追加专用配置变更事实；
5. 更新小组与成员当前投影；
6. 无条件生成新的不可变 `WorkTeamSnapshot`；
7. 返回新版本和 `WorkTeamSnapshotRef`。

它不得回调 scheduling、访问排班表、解释外部幂等键或扩大协调范围。

## 6. 正式事务与锁序

三个变更用例使用同一流程：

```text
workforce-coordination 开启 REQUIRED 事务并取得外部幂等执行权
→ scheduling.WorkTeamPlanReferenceGuardPort（MANDATORY）
   → 锁 schedule_team_reference_guards
   → 重验不存在 ARRANGED 引用
→ master-data.WorkTeamMutationParticipantPort（MANDATORY）
   → 锁 work_teams
   → 锁 work_team_memberships
   → 重验版本、成员状态和资格
   → 追加变更事实、更新当前投影、生成新快照
→ 登记审计和必要提交后动作
→ 一次提交
```

全局锁序固定为：

```text
scheduling
→ master-data
```

同一事务不得先锁 master-data 再调用 scheduling。任一步失败时，排班守卫准备结果、主数据事实、当前投影、新快照、幂等成功记录和审计结果全部回滚。

## 7. 幂等、版本和错误

外部幂等由 `workforce-coordination` 作为命令所有者解释，幂等作用域固定由以下字段组成：

```text
operator_id
operation_type
work_team_business_id
idempotency_key_hash
request_fingerprint
```

参与端口不解释外部 `Idempotency-Key`，只通过操作标识、准备范围指纹和领域唯一约束避免重复事实。

稳定错误归属：

- `WORK_TEAM_ACTIVE_PLAN_REFERENCED`：由 `scheduling` 定义；
- `WORK_TEAM_NOT_FOUND`、`WORK_TEAM_VERSION_CONFLICT`、`WORK_TEAM_MEMBER_INVALID`、`WORK_TEAM_MEMBER_NOT_EMPLOYED`、`WORK_TEAM_MAKING_QUALIFICATION_REQUIRED`、`WORK_TEAM_STATUS_NOT_ALLOWED`：由 `master-data` 定义；
- 幂等键冲突、认证上下文缺失和通用请求错误：按 platform/HTTP 公共基线处理。

协调器原样传播结构化错误，不改写成“协调失败”，也不保存第二套同义错误码。

## 8. 权限与审计

正式命令固定需要：

```text
master-data.work-team.update
```

`workforce-coordination` 校验调用者具备命令级权限，`master-data` 仍在锁内校验业务范围和目标状态。审计记录必须包含小组标识、操作类型、变更前后版本、成员变更摘要、操作者、请求标识和结果；审计不替代主数据变更事实。

## 9. 验证门禁

实现前必须通过：

1. Spring Modulith/ArchUnit 确认 `master-data` 不依赖 `scheduling`，两个参与模块都不依赖协调器，顶级模块图无环；
2. SQL 静态扫描确认协调器没有业务 SQL、Repository 或业务表访问；
3. 小组创建同步生成初始快照，每次成功变更同步生成新快照；
4. 所有 Query 均只读，首次查询和首次计划引用不会产生写入；
5. 小组活动引用与配置变更并发时只有一个先提交，另一个必须在锁内看到最新结果；
6. 取消或核验释放活动引用后可以再次修改；
7. 任一成员非在职时拒绝，至少一名成员具有 `MAKING` 资格时允许制作小组；
8. scheduling 守卫成功但 master-data 变更失败时全部回滚；
9. 重复幂等请求返回原结果，不生成第二个变更事实或快照；
10. `scheduling → master-data` 锁序、死锁和真实 MySQL 回滚测试；
11. Controller 只调用一个协调用例，不直接编排两个参与模块；
12. 历史任务和 payroll 仍能通过旧 `WorkTeamSnapshotRef` 批量解析原成员。

## 10. 已确认不变量

```text
workforce-coordination 不拥有业务事实或业务表
master-data 拥有小组配置、成员事实和小组快照
scheduling 拥有活动引用和引用守卫
master-data 不依赖 scheduling
正式小组变更固定先 scheduling 后 master-data
活动计划引用期间不能修改小组，引用释放后可以修改
小组创建和每次成功变更都生成新快照
Query 严格只读，不在首次引用时创建快照
消费者只保存 WorkTeamSnapshotRef
全部成员必须在职可用，至少一名成员具有 MAKING 资格
小组是共同产出主体，不拆分内部步骤和成员产量
```
