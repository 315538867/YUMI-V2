## 2. 权威边界

### 2.1 `scheduling` 拥有

- 正常、修复和售后生产任务；
- 任务明细、计划数量、执行主体、计划日期和任务状态；
- 员工或小组与任务之间的计划分配关系；
- 创建或调整排班时，由公开接口返回的不可变工作量评估快照；
- 任务取消请求、管理员取消确认和取消事实；
- 排班核验提交及提交状态；
- 排班工作台、待核验任务和排班侧版本。

### 2.2 `scheduling` 不拥有

- 标准工时、有效工作时间、可用工作时间、负载率公式和评估口径；
- 员工、小组、商品、工种资格、有效工作时间标准和小组效率标准的当前值；
- 可变“产能余额”或跨任务共享的产能当前投影；
- 生产来源、生产来源余额和来源消费；
- 制品物理阶段、质量处置、报废、责任判定和生产事实；
- 订单、交付约定、普通发货和售后义务；
- 工资、成本和真实现金事实。

### 2.3 依赖方向

```text
orders → scheduling 公开参与端口
after-sales → scheduling 完整应用命令/公开查询（不直接写排班表）
workforce-coordination → scheduling 小组引用守卫参与端口
fulfillment-coordination → scheduling 公开参与端口
scheduling → production 公开参与端口
scheduling → master-data 公开查询接口
scheduling → platform 公开能力
scheduling → calculation 内部实现 / master-data Repository / 其他模块表   禁止
scheduling → fulfillment-coordination   禁止
```

排班模块可以调用生产参与端口完成来源占用、释放和核验，也可以调用 `master-data.WorkloadAssessmentQuery` 获得标准工作量评估；它不能读取其他模块的表、Repository、Entity、内部 Service 或公式实现。包装还原、质量处置等生产动作如果要改排班，必须从 `fulfillment-coordination` 入口调用排班参与端口。

### 2.4 跨模块调用红线

合法调用链为：

```text
scheduling 应用命令/查询
→ 能力提供模块的公开命令、查询、事务参与或纯计算接口
→ 能力提供模块内部应用层
→ 能力提供模块领域层和 Repository Port
→ 能力提供模块基础设施与自有表
```

稳定业务标识只用于跨模块引用和公开接口入参，不是直接定位其他模块表、恢复内部主键或拼接跨模块 SQL 的句柄。共享进程、共享数据库和同一事务都不构成越过公开接口的理由。

## 3. 任务模型与状态机

### 3.1 任务类别与业务来源

任务类别只表达核验和来源规则：

```text
NORMAL  正常制作或包装加工任务，需要工作量评估
REPAIR  质量修复任务，进入修复规则；首期不计入正常工作量评估
```

业务来源单独表达：

```text
ORDER          普通订单
AFTER_SALES    售后重新加工或补发
LEGACY_INTAKE  已有订单接管后继续履约
```

`AFTER_SALES` 和 `LEGACY_INTAKE` 不是任务类别；它们可以根据实际需求形成 `NORMAL` 或 `REPAIR` 任务。任务必须引用一个生产需求/修复池来源和冻结路线快照。任务不是生产事实；任务完成也不代表生产已核验。

### 3.2 执行主体与小组共同产出

排班执行主体统一表达为：

```text
EMPLOYEE  单个员工
TEAM      小组
```

小组任务按一个执行主体、一个计划任务和一个共同产出核验。系统不把倒胶、填色、画画等组内协作步骤拆成独立排班任务，不记录成员个人完成数量，也不在排班模块内分摊个人贡献。小组当前成员、资格和工作量标准由 `master-data` 通过公开接口提供；排班只保存执行主体稳定业务标识、`WorkTeamSnapshotRef` 和工作量评估结果，不复制成员列表。任务不能选择小组成员子集。

### 3.3 任务状态

```text
ARRANGED   已安排、尚未核验
CANCELLED  已取消
VERIFIED   已核验
```

允许迁移：

```text
ARRANGED → CANCELLED
ARRANGED → VERIFIED
```

系统不设置开工、进行中、暂停和完工待核验状态。未核验任务可以由有权限的排班命令直接取消；订单变更、包装还原或质量处置批量影响任务时，必须额外保存与本次业务操作、具体任务和任务版本绑定的管理员确认，不能复用于其他命令。已核验任务不能取消或再次核验。

### 3.4 核验提交

核验是一个同步强一致命令，不建立异步“待生产确认”状态：

```text
锁定 ARRANGED 任务
→ 校验结果分桶和权限
→ 调用 production.verifyTask
→ production 追加正式生产事实并返回 ProductionVerificationFactRef
→ 调用 cost-ledger.CostRecognitionParticipantPort
→ cost-ledger 依据生产事实引用追加可立即确认的成本归集事实
→ scheduling 追加 verification_submission 并把任务更新为 VERIFIED
→ 一次提交
```

production 或 cost-ledger 参与端口拒绝时整个事务回滚，任务仍为 `ARRANGED`，生产事实和成本归集事实也均不保留。失败原因通过结构化错误和平台请求审计返回，不持久化一个会被误认为生产已发生的 `SUBMITTED` 任务状态。

## 4. 表清单与所有权

| 表 | 类型 | 用途 |
|---|---|---|
| `schedule_tasks` | 当前投影/任务根 | 保存任务类别、业务来源、需求引用、计划数量和任务状态 |
| `schedule_task_lines` | 当前投影 | 保存按商品、工序、路线或数量拆分的任务明细 |
| `schedule_task_assignments` | 当前投影 | 保存任务与员工/小组执行主体的计划关系 |
| `schedule_assignment_change_facts` | 事实 | 保存执行主体或计划日期调整及原因 |
| `task_workload_assessment_snapshots` | 排班自有结果快照 | 保存排班决策结果、规则版本和单值上游快照引用，不复制上游快照载荷 |
| `task_workload_assessment_standard_refs` | 快照明细 | 规范化保存评估涉及的商品标准快照稳定标识和版本 |
| `schedule_subject_day_guards` | 并发守卫 | 串行化同一执行主体、日期和工序的计划创建/调整，不保存产能余额 |
| `schedule_team_reference_guards` | 并发守卫 | 串行化小组配置变更与 `TEAM` 任务创建/调整，防止“检查无引用”与“新增引用”竞态 |
| `task_cancellations` | 事实 | 保存取消申请、管理员确认、取消原因和生效时间 |
| `task_cancellation_confirmations` | 事实 | 保存管理员确认主体、权限和确认版本 |
| `verification_submissions` | 事实头 | 保存成功核验命令的任务级操作者、时间和生产执行标识 |
| `verification_submission_lines` | 事实明细 | 按任务明细保存实际数量与合格、修复、报废、不完整分桶 |
| `verification_submission_corrections` | 事实 | 保存提交错误的追加修正，不能修改已形成的生产事实 |
| `scheduling_workbench_projections` | 当前投影 | 保存排班工作台所需的可重建任务摘要 |

`production.task_source_reservations` 由 `production` 拥有。排班不复制来源占用表，只在 `schedule_task_lines` 保存生产端口返回的 `reservation_business_id`、数量、状态和版本摘要，不直接更新生产来源余额。

本章各表代码块列出最终业务字段；每表另含 `id BIGINT PRIMARY KEY`。稳定业务标识使用 `VARCHAR(64)`，数量使用有符号 `BIGINT`，金额使用 `DECIMAL(19,4)`，分钟计算值使用 `DECIMAL(19,8)`，负载率使用 `DECIMAL(12,8)`，时间使用 UTC `DATETIME(6)`。除明确标注“可空”外均为 `NOT NULL`，不得在 Flyway 中增加未登记业务列。

### 4.1 `schedule_tasks`

最终业务字段如下：

```text
task_business_id
task_category = NORMAL | REPAIR
source_business_type = ORDER | AFTER_SALES | LEGACY_INTAKE
source_business_id
demand_business_id
agreement_group_business_id
route_snapshot_owner_module = orders
route_snapshot_type = DELIVERY_AGREEMENT
route_snapshot_business_id
route_snapshot_version
planned_quantity
verified_quantity
cancelled_quantity
status = ARRANGED | CANCELLED | VERIFIED
scheduled_date
priority
active_task_unique_key
version
created_by_business_id
created_at
updated_at
```

约束：

- `UNIQUE(task_business_id)`；
- `UNIQUE(active_task_unique_key)`；
- 同一业务来源、同一任务类别和有效排班窗口不能重复创建等价任务；
- `planned_quantity > 0`；
- `ARRANGED` 时 `verified_quantity = 0` 且 `cancelled_quantity = 0`；
- `CANCELLED` 时 `cancelled_quantity = planned_quantity` 且 `verified_quantity = 0`；
- `VERIFIED` 时 `verified_quantity = planned_quantity` 且 `cancelled_quantity = 0`；
- 首期不支持任务部分取消或部分核验；需要拆分数量时必须在提交前拆成独立任务；
- 任务创建后不得原地修改路线和需求来源；改变业务来源必须取消旧任务并创建新任务；
- 执行主体或计划日期调整必须追加 `schedule_assignment_change_facts` 并重新获取工作量评估；
- 任务版本每次状态、数量、执行主体、计划日期或取消确认变化时递增。

### 4.3 `schedule_task_assignments`

最终业务字段如下：

```text
assignment_business_id
task_business_id
assignment_subject_type = EMPLOYEE | TEAM
assignment_subject_business_id
assignment_subject_snapshot_owner_module = master-data
assignment_subject_snapshot_type = EMPLOYEE_ASSIGNMENT_SUBJECT | WORK_TEAM
assignment_subject_snapshot_business_id
assignment_subject_snapshot_version
scheduled_date
process_code
status = ARRANGED | CANCELLED | VERIFIED
active_unique_key
version
created_at
updated_at
```

约束：

- 一个任务只有一个当前活动执行主体；
- 四个主体快照指针字段必须同时非空，owner 固定为 `master-data`；`EMPLOYEE` 只能使用 `EMPLOYEE_ASSIGNMENT_SUBJECT`，`TEAM` 只能使用 `WORK_TEAM`；
- `TEAM` 分配引用完整 `WorkTeamSnapshotRef`，不得保存 `member_ids`、成员姓名或成员贡献字段；
- `EMPLOYEE` 与 `TEAM` 都必须通过 `master-data.WorkAssignmentSubjectQuery` 取得主体快照引用；
- 小组任务固定使用快照中的全部成员，任务创建和调整不能选择子集；
- `ARRANGED` 分配构成活动小组引用；取消或核验后不再阻止小组当前配置修改；
- 已核验任务继续保留主体快照引用，历史解释和工资结算由快照所有者接口解析。

`task_workload_assessment_standard_refs` 最终业务字段如下：

```text
assessment_snapshot_business_id
ref_order
product_business_id
standard_snapshot_owner_module = master-data
standard_snapshot_type = PRODUCT_MAKING_STANDARD
standard_snapshot_business_id

```

建立 `UNIQUE(assessment_snapshot_business_id, ref_order)` 和 `UNIQUE(assessment_snapshot_business_id, product_business_id, standard_snapshot_owner_module, standard_snapshot_type, standard_snapshot_business_id, standard_snapshot_version)`；四个快照指针字段必须同时非空，owner/type 必须固定为 `master-data/PRODUCT_MAKING_STANDARD`；不得把引用集合保存为 JSON，也不得复制商品标准快照载荷。

该表是 `scheduling` 拥有的决策结果快照，保存评估输出、计算时实际采用的 `workday_hours` 与 `making_effective_hour_rate` 数值，以及主体、商品制作标准和小组效率标准的上游强类型快照引用。商品录入默认值不参与排班评估，也不存在对应快照引用。小组成员、商品标准和效率标准仍由 `master-data` 拥有，排班不得复制其快照载荷。被拒绝的评估只进入请求审计；成功创建或调整任务时才保存与任务绑定的结果快照。

字段约束固定为：主体引用 owner 必须为 `master-data`，type 与 `assignment_subject_type` 一致；`workday_hours` 必须大于 `0` 且不大于 `24`，`making_effective_hour_rate` 必须大于 `0` 且不大于 `1`；TEAM 时效率引用四字段必须同时非空且为 `master-data/TEAM_EFFICIENCY_STANDARD`，EMPLOYEE 时效率引用四字段必须同时为空。数据库 `CHECK` 与应用校验必须同时覆盖这些互斥规则。

### 4.5 `schedule_subject_day_guards`

最终业务字段如下：

```text
assignment_subject_type
assignment_subject_business_id
scheduled_date
process_code
version
updated_at
```

建立：

```text
UNIQUE(assignment_subject_type, assignment_subject_business_id, scheduled_date, process_code)
```

守卫只用于防止两个并发命令基于同一批已有任务同时通过评估。锁定守卫后，排班汇总自己拥有的活动任务明细并作为 `existingPlanLines` 调用工作量评估接口。守卫不保存标准分钟、已分配分钟或剩余分钟。

### 4.6 `schedule_team_reference_guards`

最终业务字段如下：

```text
work_team_business_id
version
updated_at
```

建立 `UNIQUE(work_team_business_id)`。守卫行不保存小组名称、成员或快照载荷，只负责串行化以下两个动作：

1. `scheduling` 创建或调整 `TEAM` 任务时，先插入或锁定守卫行，再通过 `master-data` 公共接口解析当前小组快照，并在同一事务内形成 `ARRANGED` 分配；
2. `workforce-coordination` 修改名称、成员、状态或停用小组时，先通过 `WorkTeamPlanReferenceGuardPort` 锁定同一守卫行并确认没有 `ARRANGED` 引用，再调用 `master-data.WorkTeamMutationParticipantPort`；锁保持到整个协调事务提交。

采用“唯一守卫行 + `SELECT ... FOR UPDATE`”保证无活动引用时也有可锁对象，避免配置变更与新任务同时通过。守卫属于 `scheduling`，其他模块不得直接访问该表。

## 5. 任务创建、调整与取消

### 5.1 创建任务

创建任务必须一次完成：

1. 锁定任务创建幂等记录并读取生产需求/修复池摘要；
2. 校验任务类别、业务来源、路线快照、数量和当前可排余额；
3. `TEAM` 任务先插入或锁定 `schedule_team_reference_guards`；锁保持到事务结束，防止小组配置变更与新活动引用并发穿透；
4. 通过公开查询接口校验员工/小组当前有效性和工种资格，并取得当前 `AssignmentSubjectSnapshotRef`，不读取主数据表；
5. 锁定 `schedule_subject_day_guards`，汇总同一执行主体、日期和工序下排班自己拥有的活动计划行；
6. 正常任务把已有计划行与候选计划行传给 `master-data.WorkloadAssessmentQuery`，不传入调用方计算的分钟、余额、负载率或状态；修复任务按修复规则保存执行主体，但首期不进入正常工作量评估；
7. 接口返回 `OVER_STANDARD` 或 `UNAVAILABLE` 时整体拒绝；返回可接受状态时保存排班自有评估结果快照及上游 `SnapshotRef`；
8. 调用 `production.reserveForTask` 获取需求池/修复池占用；
9. 写入任务、明细、执行主体快照引用、评估结果快照和生产占用引用；
10. 生成工作台投影并登记提交后动作。

任何一步失败都整体回滚，不能先创建任务再异步补来源占用或工作量评估。

### 5.2 工作量评估接口边界

排班不实现“标准工时 × 数量”“有效工作时间”“日产量”“剩余分钟”或负载状态算法。评估流程固定为：

```text
scheduling 锁定本地执行主体日守卫
→ scheduling 查询自己拥有的活动计划
→ scheduling 组装不可变计划输入
→ master-data.WorkloadAssessmentQuery
→ master-data 读取自己拥有的主体、商品制作标准、有效工作时间标准和小组效率标准
→ master-data 调用 calculation 公开纯计算接口
→ 返回不可变评估结果、规则版本和上游快照引用
→ scheduling 按排班策略接受或拒绝，并保存本模块结果快照
```

`master-data` 不得读取排班表，`scheduling` 不得读取主数据表或调用公式实现。工作量评估是决策依据，不是可写回的“产能账户”。取消任务后不执行“释放分钟”；下一次评估在锁内仅汇总仍为活动状态的任务，自然排除已取消任务。

### 5.3 调整执行主体或计划日期

调整必须在一个事务内：

1. 锁定任务、当前活动分配以及新旧执行主体日守卫；
2. 新旧任一主体为 `TEAM` 时，按小组稳定标识升序锁定对应 `schedule_team_reference_guards`；
3. 校验任务仍为 `ARRANGED`、版本未变化；
4. 通过公开接口校验新的执行主体并取得当前主体快照引用；
5. 基于新执行主体已有活动计划重新调用 `WorkloadAssessmentQuery`；
6. 评估允许后，结束旧分配、创建新分配、追加分配变更事实和新的排班评估结果快照；
7. 更新任务版本和工作台投影。

任务来源不变时不需要为了“重新分配”修改生产来源占用。若调整同时改变业务来源，必须取消旧任务并创建新任务，不能把两个业务含义合并为一个通用更新命令。

### 5.4 取消任务

普通排班取消由有权限的命令直接完成。订单变更、包装还原或质量处置批量影响任务时，命令输入还必须包含与本次操作、具体任务和任务版本绑定的管理员确认。

取消事务内：

1. 锁定任务、活动分配和对应执行主体日守卫；
2. 校验任务仍为 `ARRANGED`、版本未变化；
3. 校验业务场景要求的管理员确认；
4. 调用 `production.releaseTaskReservation` 释放需求池/修复池占用；
5. 结束活动分配、追加取消事实、更新任务为 `CANCELLED`；
6. 写入审计和提交后动作。

取消不更新任何“产能余额”。缺少必要确认、任务已核验、版本变化或生产占用释放失败时整体拒绝。

## 6. 核验提交与生产协作

### 6.1 核验提交

执行员工或小组授权人员提交核验时，排班先验证：任务状态、执行范围、数量分桶、操作者权限、重复提交和版本。然后在同一业务事务内调用 `production.verifyTask`。

生产端口返回 `ProductionVerificationFactRef`、来源形成结果、修复池结果和新的生产版本后，排班把 production 事实 Ref、执行主体 Ref 和工作量评估 Ref 解包为 `BusinessPointer` / `SnapshotPointer`，再调用 `cost-ledger.CostRecognitionParticipantPort.recognizeProductionVerification` 归集本次可立即确认的生产成本。cost-ledger 契约不反向导入 scheduling、production 或 master-data 类型。完成后排班再更新：

```text
verification_submissions + verification_submission_lines = ACCEPTED
schedule_tasks.status = VERIFIED
schedule_task_assignments.status = VERIFIED
schedule_tasks.verified_quantity += submitted_quantity
```

如果生产端口或成本归集参与端口拒绝，排班不插入核验提交事实，也不更新为 `VERIFIED`；production 核验事实与 cost-ledger 归集事实同样回滚。调用方收到发现规则模块拥有的稳定业务错误码。`cost-ledger` 以 `(source_module, source_fact_id, cost_type)` 或等价领域唯一键防止重复归集；该参与端口使用 `PROPAGATION_MANDATORY`，不得异步补记或降级为可选动作。

### 6.2 核验结果责任

排班拥有“谁在何时提交了什么”，生产拥有“实际生产、质量和来源结果”。执行员工或小组不等于责任员工。排班只能传递事实输入和操作者上下文，不能指定生产投影最终值或覆盖责任判定。

小组任务按共同产出核验；排班向生产传递 `WorkTeamSnapshotRef`，生产事实只保存该引用和共同产出，不复制成员列表，也不生成成员个人产出。结算到人由 `payroll` 通过 `master-data.WorkTeamSnapshotQuery` 解析历史成员并应用自己的规则；首期固定均分，但该规则不属于排班或生产。

### 6.3 排班与生产边界

```text
scheduling 创建/取消任务
→ production 占用/释放来源
scheduling 提交核验
→ production 形成核验事实和来源
production 生产处置影响任务
→ fulfillment-coordination
   → scheduling 调整任务
   → production 追加生产处置
```

排班模块不提供“直接修改生产阶段”“直接扣减来源余额”或“直接生成生产事实”的通用接口。

## 8. 事务矩阵

| 命令 | 命令所有者 | 参与模块 | 排班写入 | 事务边界 |
|---|---|---|---|---|
| 创建排班 | `scheduling` | `master-data` 查询、`production` 参与端口 | 任务、明细、分配、评估快照、来源占用引用 | 一个 REQUIRED 事务 |
| 调整执行主体/日期 | `scheduling` | `master-data` 查询 | 分配变更事实、新分配、新评估快照 | 一个 REQUIRED 事务 |
| 取消排班生效 | `scheduling` | `production` | 取消事实、任务和分配状态 | 一个 REQUIRED 事务 |
| 排班核验 | `scheduling` | `production`、`cost-ledger` | 提交记录、逐行结果和任务核验状态；生产、成本事实由参与模块写入各自表 | 一个 REQUIRED 事务；参与端口均为 MANDATORY |
| 订单变更取消任务 | `orders` | `fulfillment-coordination`、`scheduling`、`production` | 取消和任务调整 | `orders → scheduling → production` 锁序 |
| 包装还原 | `fulfillment-coordination` | `scheduling`、`production` | 任务调整事实和生产占用释放引用；占用释放事实由 production 写入 | 一个 REQUIRED 事务 |
| 质量处置/报废 | `fulfillment-coordination` | `scheduling`、`production` | 任务、分配和取消事实 | 一个 REQUIRED 事务 |

参与端口使用 `PROPAGATION_MANDATORY` 语义。只读工作量评估接口不拥有排班事务，也不得写排班表。排班不能把生产端口失败转换为“任务已创建但来源稍后补齐”。

## 9. 锁定顺序、索引和并发

### 9.1 排班模块内锁序

在全局顺序中的 `scheduling` 阶段统一为：

```text
schedule_team_reference_guards（涉及 TEAM 时）
→ schedule_subject_day_guards
→ schedule_tasks
→ schedule_task_lines
→ schedule_task_assignments
→ task_cancellations / confirmations
→ task_workload_assessment_snapshots（排班结果 + 上游 SnapshotRef）
→ schedule_task_lines 中的生产占用引用
→ verification_submissions / verification_submission_lines
```

同一命令涉及多个执行主体日守卫时，按 `assignment_subject_type, assignment_subject_business_id, scheduled_date, process_code` 升序锁定。跨模块调用生产前，先锁定排班侧全部受影响任务和版本；进入生产后按生产模块锁序继续获取来源和状态锁。排班不得在生产调用返回后再回头补锁任务。

### 9.2 必要索引

```text
schedule_tasks: UNIQUE(task_business_id)
schedule_tasks: UNIQUE(active_task_unique_key)
schedule_tasks: INDEX(status, scheduled_date, priority, id)
schedule_tasks: INDEX(demand_business_id, status, id)
schedule_task_lines: INDEX(task_business_id, id)
schedule_task_assignments: UNIQUE(active_unique_key)
schedule_task_assignments: INDEX(assignment_subject_type, assignment_subject_business_id, scheduled_date, process_code, status, id)
schedule_subject_day_guards: UNIQUE(assignment_subject_type, assignment_subject_business_id, scheduled_date, process_code)
schedule_team_reference_guards: UNIQUE(work_team_business_id)
task_workload_assessment_snapshots: INDEX(task_business_id, assessed_at, id)
task_cancellation_confirmations: UNIQUE(scope_type, scope_business_id, task_business_id, expected_task_version)
verification_submissions: INDEX(submitted_at, task_business_id, id)
verification_submission_lines: UNIQUE(verification_submission_business_id, task_line_business_id)
```

`active_task_unique_key` 和分配的 `active_unique_key` 在活动状态下表达业务唯一性，退出活动状态后改为包含自身稳定标识的历史键，避免依赖可空列唯一性。

### 9.3 并发冲突

以下情况整体失败：任务版本变化、执行主体日守卫版本变化、小组引用守卫冲突、管理员确认版本变化、工作量评估不可用或超出标准、来源占用版本变化、重复核验、锁等待超时、死锁和生产参与端口拒绝。`TEAM` 任务创建/调整与小组配置变更必须锁定同一 `schedule_team_reference_guards` 行，保证“无活动引用”检查和活动分配写入不能并发穿透。命令边界可按公共事务规则有限重试，不能在模块内部静默重试。

## 10. 幂等、错误码和权限

### 10.1 幂等

- 创建、取消确认、核验提交和重新分配各自使用明确的 `operationId`；
- 同一 `operationId` 重试返回原执行结果，不重复创建任务、分配、占用或提交；
- 领域唯一约束防止同一有效来源重复排班、同一任务重复核验和同一确认重复生效；
- 生产模块的领域幂等由生产模块自己解释，排班不把外部幂等键传给生产模块代替业务唯一性。

## 11. 投影重建

排班工作台投影的权威输入为：

```text
schedule_tasks                       ← 任务创建、状态、数量和取消事实
schedule_task_lines                  ← 任务明细事实和冻结路线快照
schedule_task_assignments            ← 执行主体、计划日期和状态
schedule_assignment_change_facts     ← 执行主体或日期调整事实
task_workload_assessment_snapshots   ← 排班自有评估结果和上游 SnapshotRef
schedule_task_lines 中的生产占用引用 ← production 返回的占用结果
verification_submissions / verification_submission_lines ← 核验提交事实、逐明细结果和更正链
```

排班历史状态不能用当前员工/小组、当前商品标准工时或当前有效工作时间标准回放。重建使用排班自己的事实、评估结果快照和上游 `SnapshotRef`，必要时通过所有者批量查询接口解析历史内容，并保存输入水位、快照版本和差异摘要；如需按当前标准重新评估，必须通过公开接口形成独立试算结果，不能覆盖历史。生产来源余额仍由 `production` 单独重建，排班不能跨模块直接重建生产投影。

## 12. 验证门禁

实现前必须通过：
