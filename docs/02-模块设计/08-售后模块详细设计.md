## 1. 职责与边界

`after-sales` 拥有订单完成后的售后案例、双方义务、退回接收、处理决定、重新交付、额外补发、售后金额决定、支付关联和售后完成事实。它不修改原订单事实，不拥有制品物理状态、排班任务或现金事实。

- 生产需求和来源消费：调用 `production` 公开能力；
- 售后任务创建、调整和取消：由 `scheduling` 作为命令所有者；
- 现金收款、退款和赔付：由本模块发起，`finance` 保存现金事实；
- 售后完成：只由本模块确认，但必须校验全部有效义务。

## 2. 不变量

1. 一个案例必须引用一个已完成订单和稳定 `orderBusinessId`。
2. 义务只能追加、完成、失效或更正，不覆盖历史。
3. 客户配合义务未完成时不得确认售后完成。
4. 重新交付和补发累计有效数量不得超过对应义务数量。
5. 售后收费、退款或赔付决定与真实现金事实分离。
6. 退回实物只有形成退回接收事实后，才可进入生产处理。
7. 已完成案例新增义务时，先追加完成失效事实，再处理新义务。
8. 跨模块只保存稳定业务标识、事实标识和类型化快照引用。

## 3. 聚合与状态

- `AfterSalesCase`：`OPEN -> PROCESSING -> COMPLETED`；追加完成失效事实后回到 `PROCESSING`。
- `AfterSalesObligation`：`PENDING -> IN_PROGRESS -> FULFILLED`，或 `PENDING/IN_PROGRESS -> VOIDED`。
- 义务类型：`CUSTOMER_COOPERATION`、`RETURN`、`REWORK`、`REDELIVERY`、`REPLACEMENT`、`CHARGE`、`REFUND`、`COMPENSATION`。
- 处理路线：`RETURN_AND_REWORK`、`DIRECT_REPLACEMENT`、`REFUND_ONLY`、`COMPENSATION_ONLY`、`MIXED`。

投影只用于读取；状态以有效事实和义务为准。

## 4. 表设计

所有表使用 `BIGINT` 主键；金额 `DECIMAL(19,4)`；数量为有符号 `BIGINT`；时间为 UTC `DATETIME(6)`；状态使用 `VARCHAR(32)`。事实表公共列为 `id, fact_business_id, case_business_id, occurred_at, recorded_at, operator_id, command_execution_id, corrects_fact_id, is_valid, reason_text`。

| 表 | 类别 | 最终业务字段 | 关键约束与索引 |
|---|---|---|---|
| `after_sales_cases` | 根实体 | `case_business_id, case_no, order_business_id, customer_business_id, intake_type, issue_summary, opened_at, opened_by, version, created_at, created_by` | `UK(case_business_id)`, `UK(case_no)`, `IX(order_business_id, opened_at)` |
| `after_sales_issue_facts` | 事实 | 公共列 + `issue_type, severity, description, evidence_file_count` | `UK(fact_business_id)`, `IX(case_business_id, occurred_at)` |
| `after_sales_obligations` | 义务实体 | `obligation_business_id, case_business_id, obligation_type, bearer_type, target_quantity, currency_code, target_amount, due_date, source_obligation_business_id, created_by_fact_id, version, created_at` | `UK(obligation_business_id)`, `IX(case_business_id, obligation_type)` |
| `after_sales_obligation_facts` | 事实 | 公共列 + `obligation_business_id, operation_type, effective_quantity, effective_amount, completion_note` | `UK(fact_business_id)`, `IX(obligation_business_id, occurred_at)` |
| `after_sales_return_receipt_facts` | 事实 | 公共列 + `obligation_business_id, received_quantity, condition_code, production_source_business_id` | `UK(fact_business_id)`, `IX(obligation_business_id, occurred_at)` |
| `after_sales_production_links` | 关联 | `link_business_id, case_business_id, obligation_business_id, production_demand_business_id, scheduling_task_business_id, created_at, created_by` | `UK(link_business_id)`, `UK(production_demand_business_id)`, `IX(case_business_id)` |
| `after_sales_delivery_facts` | 事实 | 公共列 + `obligation_business_id, delivery_type, delivered_at, recipient_snapshot_json, tracking_no` | `UK(fact_business_id)`, `IX(obligation_business_id, occurred_at)` |
| `after_sales_delivery_items` | 事实明细 | `id, delivery_fact_id, product_business_id, production_source_business_id, quantity, production_consumption_fact_id` | `UK(delivery_fact_id, production_source_business_id)`, `IX(production_source_business_id)` |
| `after_sales_charge_decision_facts` | 事实 | 公共列 + `obligation_business_id, decision_type, currency_code, amount, decision_note` | `UK(fact_business_id)`, `IX(case_business_id, decision_type)` |
| `after_sales_payment_link_facts` | 事实 | 公共列 + `decision_fact_business_id, finance_cash_fact_business_id, linked_amount, currency_code` | `UK(fact_business_id)`, `UK(decision_fact_business_id, finance_cash_fact_business_id)` |
| `after_sales_completion_facts` | 事实 | 公共列 + `obligation_snapshot_fingerprint, completed_at, active_unique_key` | `UK(fact_business_id)`, `UK(case_business_id, active_unique_key)`, `IX(case_business_id, occurred_at)` |
| `after_sales_completion_invalidation_facts` | 事实 | 公共列 + `completion_fact_business_id, invalidation_reason` | `UK(fact_business_id)`, `UK(completion_fact_business_id)` |
| `after_sales_case_projections` | 投影 | `case_business_id, current_status, pending_obligation_count, pending_customer_obligation_count, pending_delivery_quantity, settlement_balance, last_fact_id, updated_at` | `PK(case_business_id)`, `IX(current_status, updated_at)` |

`after_sales_completion_facts.active_unique_key = IF(is_valid, case_business_id, NULL)`，保证同一案例最多一个有效完成事实，同时允许保留多个已失效历史完成事实。

`recipient_snapshot_json` 仅保存售后模块定义的交付接收人值对象，不保存其他模块聚合。售后只保存 `scheduling_task_business_id`，小组快照引用由任务所有者 `scheduling` 管理，售后不复制。

```java
public interface AfterSalesApplicationService {

    DeliveryRef confirmRedelivery(ConfirmAfterSalesDeliveryCommand command);

    CompletionRef completeCase(CompleteAfterSalesCaseCommand command);

public interface AfterSalesParticipantPort {
    PreparedAfterSalesSettlement prepareSettlement(PrepareAfterSalesSettlement command);
    void commitSettlement(CommitAfterSalesSettlement command);
}

public interface AfterSalesQuery {
    AfterSalesCaseView getCase(AfterSalesCaseId id);
    Page<AfterSalesCaseSummary> search(AfterSalesSearchCriteria criteria);

```

参与端口只允许已登记的命令所有者调用。查询 DTO 不暴露数据库行对象。

## 6. 正式命令与事务

| 动作 | 命令所有者 | 参与模块 | 固定锁序 | 原子结果 |
|---|---|---|---|---|
| 售后受理、义务变更 | after-sales | 无 | case -> obligation | 售后事实与投影 |
| 退回接收并进入生产 | after-sales | production | case -> obligation -> production source | 接收事实与生产来源 |
| 创建/取消售后任务 | scheduling | after-sales、production | scheduling guard -> task -> after-sales obligation -> production reservation | 任务、占用和关联 |
| 重新交付/额外补发 | after-sales | production | case -> obligation -> production source | 交付与来源消费 |
| 收款/退款/赔付 | after-sales | finance | case -> decision -> finance account | 业务决定与现金事实 |
| 完成确认 | after-sales | 无 | case -> all active obligations | 完成快照与完成事实 |

参与模块失败时整个事务回滚；外部通知、物流打印和文件处理使用 `platform_action_tasks` 在提交后执行。

## 8. 幂等、更正与并发

- 幂等范围：`operatorId + routeId + Idempotency-Key`；请求指纹不同返回冲突。
- 更正通过追加反向或替代事实，不更新原事实金额、数量和时间。
- `after_sales_cases.version` 用于乐观并发；数量和完成判断同时锁定案例与相关义务。
- 生产来源消费依赖 `production` 自身唯一来源防重，不由售后复制余额。

## 9. 查询、投影与重建

案例详情由本模块 Repository 读取本模块事实并组装；需要订单、生产、排班或现金详情时调用对应公开查询。`after_sales_case_projections` 可从案例、有效义务、有效交付、结算和完成事实全量重建，不作为完成资格来源。

## 10. 迁移与验收

Flyway 使用 `V060-V069`。迁移顺序：案例 -> 义务 -> 退回/生产关联 -> 交付 -> 结算 -> 完成 -> 投影。

真实 MySQL 必测：重复受理、义务并发完成、退回与生产失败回滚、补发超量、现金参与失败全回滚、客户义务未完成、完成后新增义务导致完成失效、投影全量重建、跨模块 SQL 扫描为零。
