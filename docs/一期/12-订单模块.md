# 订单模块

> 模块代码：`orders`

## 1. 模块说明

订单模块管理客户交易、交付约定、订单变更、发货、应收退款、付款履约、订单完成、已有订单接管，以及由已完成订单派生的售后案例。售后作为模块内部独立子域，拥有自己的聚合、状态和表，但不能覆盖原订单、原发货和原生产事实。

## 2. 一期需求、范围与模块功能

- 新订单一次创建并确认；
- 选择商品和标准/自定义方案作为录入起点；
- 取得商品、方案和客户当前快照；
- 冻结本次成交价格、目标工序、材料来源和交付信息；
- 建立生产需求；
- 已确认订单的数量、约定和金额正式变更；
- 直接确认发货；
- 应收、退款义务、收付款关联和履约状态；
- 双向履约满足后完成订单；
- 录入已有订单的当前事实并继续管理；
- 针对已完成订单受理售后，管理退回、返工、补发、收费、退款、赔付和结案。

一期不提供订单草稿、发货草稿、库存出库、物流平台自动同步、无订单售后、跨订单售后案例和独立客服工单平台。

## 3. 业务概念

- **订单项**：一次选定商品、方案、目标工序、材料来源、价格和交付要求的交易明细；同一商品若采用不同方案或约定，必须拆成不同订单项。
- **交付约定组**：订单项的稳定约定根；一期中与订单项一一对应，用于承载不可变约定版本。
- **约定版本**：每次正式变更后不可变的交付约定。
- **当前有效应收**：原始应收加有效调整后的金额。
- **交付履约**：有效发货数量满足当前交付义务。
- **付款履约**：有效净收款满足当前应收。
- **售后案例**：从一个已完成订单派生的问题处理业务根。
- **售后义务**：客户或工作室必须完成的动作、数量或金额责任。

## 4. 模块边界

### 4.1 订单拥有

订单、订单项、交付约定、变更、应收和退款决定、普通发货、付款业务关联、完成和取消事实，以及售后案例、售后义务、退回、售后交付和售后金额决定。

### 4.2 订单不拥有

商品当前定义、生产阶段和数量、作业任务、真实现金、工资和成本台账。

### 4.3 跨模块协作

- 从 `customer` 取得客户快照，从 `product` 取得商品和方案快照；
- 调用 `production` 建立或调整生产需求；
- 生产需求及其作业任务联动由 `production` 在模块内部保持一致；
- 发货调用 `production` 消费合格来源；
- 收退款资格由订单提供，真实现金由 `finance` 保存；
- 售后由本模块内部 `aftersales` 子域管理；退回接收通过 `production` 参与接口登记原制品重入，返工和补发参与接口只建立生产需求/来源，不直接创建任务或选择执行人员。

## 5. 业务规则

1. 新订单不保存半成品，创建命令成功即为 `CONFIRMED`。
2. 商品方案只作为录入模板；订单保存自己的不可变交付约定版本。
3. 一个订单项只能有一个交付约定组，一个交付约定组只对应一个生产需求。
4. 一个约定组的数量、目标工序、材料来源、价格和收货信息必须完整。
5. 订单变更不能覆盖原约定，必须按变更类型生成新约定版本、数量调整或继任订单项，并追加变更事实。
6. 减量或取消不能使已经形成生产事实的数量直接消失；尚未消费的多余制品只有在订单变更事务中同步转线下库存后才能移出订单义务，已发货数量必须先更正发货。
7. 发货必须消费达到约定目标工序且质量合格的生产来源。
8. 发货命令直接确认，不建立发货草稿或长期预留。
9. 已确认发货不能直接编辑，错误通过发货更正事实。
10. 订单完成必须同时满足交付履约和付款履约，并且不存在阻塞完成的有效义务。
11. 当前客户、商品或方案变化不影响已确认订单。
12. 订单资金决定与真实现金事实分开。
13. 售后只能引用已完成订单；一期一个售后案例只属于一个订单。
14. 售后义务只能追加、完成、失效或更正，不能覆盖历史。
15. 售后处理不修改原订单、原发货和原生产事实。

### 5.1 订单数量与金额公式

订单模块拥有“哪些订单事实有效、哪些事实进入合计以及何时满足履约”的业务语义；定点数加减、合计、比较和舍入调用 `calculation` 的通用能力。本节是订单业务聚合公式的权威定义，页面、Repository 和报表不得复制实现：

```text
有效数量调整净额
= Σ（有效数量调整事实的有符号数量增量）

当前有效交付数量
= 原始约定数量 + 有效数量调整净额

有效金额调整净额
= Σ（有效金额调整事实的有符号金额增量）

当前有效应收金额
= 原始应收金额 + 有效金额调整净额

有效收款合计
= Σ（有效收款事实金额）

有效退款合计
= Σ（有效退款事实金额）

订单净收款金额
= 有效收款合计 - 有效退款合计

交付履约
= 有效已发货数量 ≥ 当前有效交付数量

付款履约
= 订单净收款金额 ≥ 当前有效应收金额

订单完成
= 交付履约成立 ∧ 付款履约成立 ∧ 不存在有效阻塞义务
```

数量和金额调整必须按有效事实的有符号增量计算，不能覆盖原始值。已更正的发货、收款或退款事实不再进入有效合计，但原事实和更正链仍保留。当前有效交付数量和当前有效应收金额不得为负；如果调整会使其为负，命令必须拒绝。应收、发货数量和现金支付不是同一事实，不能用一个余额字段代替。`订单完成` 中的 `∧` 是逻辑“且”，不是金额或数量相加。

## 6. 状态设计

- 订单：`CONFIRMED / IN_FULFILLMENT / COMPLETED / CANCELLED`；
- 交付约定组：`ACTIVE / FULFILLED / CANCELLED`；
- 变更：正式命令成功即为有效记录，不使用草稿状态；
- 发货：事实通过有效性和更正链管理；
- 完成：由完成事实表达；后续有效变更或售后义务不直接改写原完成事实，必要时追加完成失效事实。

## 7. 业务流程

### 7.1 新订单确认

```text
校验完整输入和幂等
→ 取得客户当前快照
→ 为每个订单项取得商品及方案当前快照
→ 按最终目标工序和完整供料约定调用 product.resolveProductionBasis，取得不可变生效生产依据及指纹
→ 形成订单自己的交付约定版本和预计成本结果；预计成本与实际生产成本使用同一生效供料依据
→ 写订单、订单项、应收事实
→ production 按每个订单项建立一个生产需求，并同事务保存相同的 ResolvedProductionBasis 及指纹
→ 审计并一次提交
```

取得快照接口保证引用的是调用时最新 `content_version`；订单只保存快照引用和自己的交易约定。

### 7.2 订单变更

```text
锁定订单和受影响约定组
→ 计算允许变更的剩余数量
→ 建立新约定版本和金额调整
→ 调用 production 原子调整生产需求及必要的活动作业任务
→ 写变更确认事实
```

已有活动作业任务的影响通过公开接口校验，订单不得直接查询生产作业表。

订单变更必须先分类，再决定是否触碰生产定义：

1. **仅价格、收件人或收货地址变化**：在原交付约定组内追加新约定版本和金额调整，不改变生产需求、商品快照、方案快照或既有生产事实。
2. **仅数量变化**：保留原订单项、约定组和生产需求，按增量、减量或取消规则调整需求数量；不得把数量变更伪装成商品定义变更。
3. **商品、方案、目标工序、材料来源或其他会改变生产定义的字段变化**：禁止覆盖原订单项和原生产需求。系统在同一变更命令中为尚未开始且允许迁移的数量建立**继任订单项、继任约定组和新生产需求**，同时减少原需求；原已在制、已完成、已消费或已形成质量事实的数量仍按旧约定解释，必须继续履约或按明确的终态规则处置。

继任订单项保存 `predecessor_order_item_business_id` 和变更事实引用，用于展示为一次订单变更；但领域上仍坚持“一个订单项 → 一个交付约定组 → 一个生产需求”，不能让一个生产需求在历史中切换商品或方案快照。

生效生产依据是交付约定的不可变组成部分。材料来源从 `STUDIO` 改为 `CUSTOMER` 或反向变化时，继任项必须取得新依据；原需求、任务和材料成本来源继续使用旧依据。售后返工、补发及已有订单期初初始化也必须在建立需求时传入明确的生效依据：沿用原约定时传原值，已有售后新约定时按相同公开解析契约取得新值，不能静默回退到商品方案默认供料方。

订单减量或取消遵循以下生产联动规则：

- 尚未安排的未开始数量可以减少；
- 已安排但尚未核验的数量由生产模块缩减来源分配，并同步释放人员负载、适用于 `NEW_PRODUCT + MAKING` 的商品新制日产能和来源占用；
- 混合来源任务只调整当前订单来源，生产模块负责重新评估任务，剩余数量为零时取消任务；
- 任何已经形成生产事实的在制品、待返工制品或合格制品均不可被订单变更删除；如果减量后成为多余制品，必须在同一事务转线下库存；
- 已发货数量必须先更正发货并反向冲销生产消费事实，不能直接转线下库存；
- 原报废事实保留，只有尚未开始的补产缺口可以随订单数量减少；
- 整单取消按订单项逐一执行相同校验；已生产未消费数量必须全部提供转线下库存明细，否则整个取消命令失败。

转线下库存是单向业务移交，不是库存管理。订单只保存本次变更与生产移交事实的稳定关联；系统不维护仓库余额，也不允许从订单页面直接取回、占用或发货。未来重新使用时必须通过一期范围外的线下制品接管业务重新进入系统。

订单变更事务中，订单约定版本、金额调整、生产任务缩减和转线下库存任一步失败时全部回滚。

### 7.3 发货

```text
锁定订单和约定组
→ production 校验并锁定合格可交付来源
→ 写发货事实和明细
→ production 写来源消费事实
→ 更新交付履约投影
→ 如满足双向履约则允许确认完成
```

### 7.4 收付款

财务模块发起现金命令时，订单提供可收/可退资格并在同事务写支付关联；订单当前应收和真实现金分开保存。

## 10. 事务与并发

- 订单确认：订单编号/根→商品快照唯一键→生产需求守卫；
- 订单变更：订单根→约定组（稳定顺序）→production 受影响任务/命令守卫→workforce 原预留守卫→员工日期模式、负载及适用产能→需求与来源；受影响集合变化时整笔回滚重试，不持来源锁补拿任务锁；
- 发货：订单根→约定组→生产来源（稳定顺序）；
- 收款/退款：订单应收或退款义务→财务来源收付守卫/投影→订单支付关联；一期不选择资金账户；
- 所有跨模块动作任一步失败全事务回滚；
- 订单行和组使用 `row_version`，金额和数量使用数据库检查约束及应用不变量双重保护。

## 11. 权限、页面和错误

权限：`order.create`、`order.change`、`order.ship`、`order.complete`、`order.cancel`、`order.read`、`order.legacy.intake`。

页面：订单列表、直接确认新订单、订单详情、正式变更、直接发货、付款履约、已有订单接管。

错误码：`ORDER_PRODUCT_SNAPSHOT_INVALID`、`ORDER_AGREEMENT_INVALID`、`ORDER_CHANGE_EXCEEDS_REMAINING`、`ORDER_CHANGE_PRODUCTION_ALREADY_STARTED`、`ORDER_CHANGE_REQUIRES_OFFLINE_INVENTORY_TRANSFER`、`ORDER_CHANGE_HAS_CONSUMED_QUANTITY`、`ORDER_HAS_ACTIVE_FULFILLMENT`、`ORDER_SHIPMENT_SOURCE_INSUFFICIENT`、`ORDER_PAYMENT_NOT_FULFILLED`、`ORDER_DELIVERY_NOT_FULFILLED`、`ORDER_ALREADY_COMPLETED`、`ORDER_VERSION_CONFLICT`。

### 11.1 订单交互原型基线

#### 11.1.3 登记发货与追加更正

| 字段 / 展示 | 当前原型规则 |
|---|---|
| 发货日期 | 必须有效，不早于订单日期，不晚于当天 |
| 物流公司 / 单号 | 最多 40 / 80 字符；发货备注最多 200 字符 |
| 合格来源 | 选择本订单、达到目标工序的示例来源，不按商品同名借用其他订单数量 |
| 本次数量 | 按订单项填写非负整数，正常发货至少一项大于零，不超过当前可发数量 |
| 当前可发 | 受剩余交付约定和合格来源余额双重约束，不把需求量或已排班量当成可发量 |
| 更正原因 | 更正已有有效发货必须填写，最多 200 字符；可调整或撤回该次发货 |

- 发货成功后刷新详情和有效已发数量；不自动产生现金、不自动把订单标为完成。
- 合格来源仍是独立示例池；生产原型的新建任务或核验提示不会直接增加这里的可发数量。

## 12. 验收标准

- 新订单没有草稿，成功即同时形成订单、约定、应收，并为每个订单项形成一个生产需求；
- 商品后续修改不改变已确认约定；
- 订单变更保留旧版本并正确调整生产需求和活动作业任务；
- 减量和取消不会删除生产事实；已生产未消费的多余制品必须同步转线下库存，已消费数量必须先更正下游交付；
- 混合来源任务只缩减目标订单来源，人员负载、适用的商品新制产能和来源占用同步释放；任一订单项无法取消时整单取消整体回滚；
- 并发发货不会超出可交付数量；
- 发货中途失败时订单和生产都不提交；
- 交付和付款均满足前不能完成；
- 现金事实冲销后付款履约正确回退；
- 已有订单接管满足数量和金额守恒并可继续正常履约。

## 13. 售后子域设计

### 13.1 状态和处理路线

- 案例：`OPEN / PROCESSING / COMPLETED`；
- 义务：`PENDING / IN_PROGRESS / FULFILLED / VOIDED`；
- 路线：`RETURN_AND_REWORK / DIRECT_REPLACEMENT / REFUND_ONLY / COMPENSATION_ONLY / MIXED`；
- 金额义务：`PENDING / PARTIALLY_SETTLED / SETTLED / VOIDED`。

### 13.2 业务规则和流程

1. 创建案例时实时校验订单已完成，并冻结订单、客户、订单项和原交付引用。
2. 客户配合义务未完成时，依赖该配合的工作室义务不能完成。
3. 退回必须按接收明细引用最近一次交付明细及其对应消费事实；退回接收事实与生产重入事实原子成功后，才能基于该退回制品来源创建返工需求/来源。最近交付来源既可以是履约生产来源，也可以是此前未修复原样退还时的退回制品池来源；两种情况都必须引用对应消费事实和同一物理根。
4. 同一交付明细累计有效退回数量不得超过该明细交付数量；返工后的再次交付如再次退回，必须引用新的售后交付明细，不能重复引用更早的原始交付。返工、重新交付和补发数量不得超过有效义务数量。
5. 金额决定与真实现金分离；现金关联失败不得标记已支付。
6. 全部有效数量、动作和金额义务满足后才能结案。
7. 已结案后发现问题，追加结案失效事实后恢复，不覆盖原结案事实。
8. 工作室承担的售后成本形成不可变来源，由 `finance.costledger` 下游归集；订单模块不调用财务写接口。
9. 客户尚未退回制品且尚未建立修复生产来源时，可以变更或取消返工义务。
10. 工作室已经接收退回制品后，取消返工义务必须核对全部相关数量，但不要求全部重新处置：池内可用及成功反向路由回池的数量才新增池处置；已形成修复终止缺口的数量引用原终态并走修复失败转路线，不回池、不再次退出。已有修复或交付事实的数量分别预检，未满足退出条件的数量阻止取消，详见 13.2.1。
11. 售后退回制品线上报废与实物去向分别记录：报废可以实际销毁或转线下作瑕疵品处理，报废转线下只发生一次池来源退出；义务取消也可把未报废制品转线下，保留原质量，不伪造报废责任。
12. 转线下库存是单向终态移交，不维护库存余额，也不能从售后案例直接取回；移交不冲销此前已经发生的生产、劳动和成本事实。
13. 售后只创建返工需求/来源；任务由生产排班后续安排。已安排但尚未核验的修复任务可以缩减或取消，但取消任务不代替退回制品处置；已核验事实永久保留。
14. 补发义务减量遵循生产需求减量规则；已生产未交付的补发制品必须继续交付或转线下库存。
15. 已经售后交付的数量必须先更正售后交付并冲销生产消费事实，才能变更相应义务。
16. 退回接收事实或明细发生更正时，必须在同一事务调用 production 对原退回重入版本执行反向更正并提交替代版本；不得只改单侧记录。
17. 售后返工使用 `RETURNED_PRODUCT_REPAIR` 需求，只能修复退回原制品。修复核验发生线上报废（实物销毁或转线下）后，生产侧形成修复终止缺口，订单售后模块必须通过义务变更明确后续路线：减少或作废原返工义务及对应修复需求；选择补发时同时建立继任补发义务和独立 `NEW_PRODUCT` 需求，选择退款、赔付或结束时不得建立生产需求。不得直接把原修复需求改成新制需求，也不得由生产模块自动创建补发。
18. 修复失败转路线只允许处理 production 返回的当前 `fulfillment_gap_quantity`，转换数量不得包含待修复、处理中、已修复待交付或已交付数量；允许分次转换。每次只减少等量原返工义务和修复需求，未转换缺口继续保留并阻止原义务完成；补发路线只为本次转换量建立继任补发义务和 `NEW_PRODUCT` 需求。
19. 未修复原样退还必须由售后交付命令一次完成：锁定退回制品池可用数量，调用 production 退回制品处置参与接口，写 `RETURN_TO_CUSTOMER` 处置、售后交付明细和池来源消费事实；任一步失败全部回滚。以后再次退回必须引用这条最新售后交付明细，不能回指更早交付。

```text
受理：锁订单和完成事实 → 建立案例、问题事实和初始义务
退回接收：校验最近一次交付及可退数量 → production.prepareRegisterReturn → 写退回接收事实/明细 → production.commitRegisterReturn 写退回制品来源和重入事实
返工申请：锁退回接收明细及退回制品来源 → production.prepareRepairDemand 建立 RETURNED_PRODUCT_REPAIR 需求/来源 → 写售后生产需求链接 → production.commitRepairDemand；后续由生产排班安排任务
补发：锁售后义务 → production 建立 NEW_PRODUCT 补发需求 → 后续生产并消费合格来源 → 写售后交付
修复失败转路线：锁返工义务、修复需求/来源及终态事实 → 调用 production.prepareRouteChange 校验可转换数量和不可逆事实 → 写原返工义务减少/作废及继任补发、退款、赔付或结束义务 → 调用 production.commitRouteChange 减少修复需求；只有补发路线同时建立独立 NEW_PRODUCT 需求
原样退还：锁售后义务和退回制品池 → production.prepareDisposition(RETURN_TO_CUSTOMER) → 写退回处置与售后交付事实/明细 → production.commitDisposition 写池来源消费事实
义务变更/取消：production 预检并按统一锁序锁定完整影响集合 → 缩减未核验任务 → 可逆路由 RELEASE_TO_RETURN_POOL → 仅处置池内可用数量；已路由终态引用原退出事实并按缺口变更义务 → 校验 13.2.1 的分支依据并写义务变更事实；任一步失败整笔回滚
退款赔付：写金额决定 → finance 调用支付资格 → 写现金和支付关联
结案：锁案例及全部有效义务 → 校验数量、交付和金额 → 写结案事实
```

#### 13.2.1 取消义务时的数量核对

“全部接收数量已有去向”不等于“全部接收数量都要再生成池处置”。按每条接收明细，通过 production 公开预检取得互不重叠的分支和来源版本，持锁重读后提交：

| 当前分支 | 取消或减少义务时的处理 | 是否新增池处置 |
|---|---|---|
| 仍在退回池可用 | 原样退还、线上报废并指定去向，或非报废义务释放转线下 | 是，只处理本次可用量 |
| 已路由、尚无不可逆事实 | 先缩减未执行任务并释放预留，再写反向路由回池，按上一行处置 | 是，仅成功回池数量 |
| 池内已直接处置 | 引用原有效池处置和消费/退出事实核对，不重复消费或移交 | 否 |
| 修复路线内已报废、实际销毁或转线下 | 引用原唯一终态退出；尚有修复终止缺口的部分通过 `prepareRouteChange / commitRouteChange` 减少相应义务和需求 | 否，不再增加池已处置量 |
| 已有修复事实但仍在系统内 | 不能假装尚未路由退回池，也不能走仅限缺口的转路线接口；保留义务继续处理，或按生产需求减量规则解除占用并同事务非报废移交 | 否，实际移交在修复生产来源退出 |
| 已再次交付 | 保留其已完成义务；如要减少该部分，先合法更正交付及消费，再重新预检，不能借取消直接回池 | 否 |

退回池始终满足 `original_quantity = available_quantity + routed_repair_quantity + disposed_quantity`。路由后报废/移交仍包含在 `routed_repair_quantity`，不得同时放进 `disposed_quantity`。修复需求内部另按当前待修复、处理中、待交付、已交付和未解决缺口守恒；已解决缺口只保留在历史变更依据中，不再计入当前缺口。非报废义务释放与需求同步减少，不创建新缺口。

义务变更事实保存服务端生成的 `quantity_resolution_refs_json`：按接收明细记录分支类型、所关联池处置/反向路由/生产需求变更/终态退出/交付标识及本次数量。不接受客户端自报“已经处置”。原终态已由历史路线变更处理的数量只能作为历史核对依据，不能再次扣减义务；当前可转路线量由生产需求缺口及未分配的终态明细共同限制。部分转路线要按原终态明细累计校验，不能换一个幂等键重复使用相同数量。

所有分支在同一义务变更事务中准备并提交；已有有效历史处置只读引用。取消不得留下相关可用池余额或未解决的活动修复数量。原样退还由同事务交付命令记录实际交付，不为满足“取消”而冲销刚产生的退还事实；完成量与取消量分别保留。完整取消请求若包含不能合法处理的分支，应整笔拒绝并返回该数量和原因，不能强行报废或伪造移交。

验收示例：收到 10 件，其中 3 件已在修复路线报废转线下、7 件仍在池内。结束原修复义务时，3 件引用已有终态并解决缺口，7 件才新增池处置。最终池账为可用 0、已路由 3、池已处置 7；物理退出总量为 10，不是 13，原 3 件的责任和移交都不重建。若 3 件缺口此前已转换 1 件，本次最多再转换 2 件。

## 14. 事务、权限和补充验收

- 售后受理先锁订单完成事实，再锁案例编号守卫。
- 退回接收锁序：售后案例 → 有效义务 → 最近交付明细 → production 对应消费事实、物理根与退回来源守卫；接收事实与生产退回重入事实同事务提交。
- 返工/补发需求建立锁序：售后案例 → 有效义务 → 退回接收明细与生产退回制品来源（返工）→ production 需求/来源守卫；本事务不锁任务或人员。
- 售后义务变更/取消锁序：售后案例 → 有效义务 → 退回接收事实/明细 → production 受影响任务/命令守卫 → workforce 原预留守卫 → 日期模式、负载和适用产能 → 需求、返工来源与物理根 → 处置、消费或转线下库存事实；修复失败转补发时，再按稳定标识锁定继任义务和补发需求守卫。
- 未修复原样退还/池内处置锁序：售后案例 → 有效义务 → 退回接收明细 → production 退回制品池来源与物理根 → 处置事实 → 池来源消费事实或线下移交事实；订单售后处置、交付明细与生产事实同事务提交。
- 售后收退款锁序：金额决定/义务 → finance 来源收付守卫和现金投影 → 支付关联。
- 权限：`order.after-sales.open`、`order.after-sales.process`、`order.after-sales.decide-amount`、`order.after-sales.complete`、`order.after-sales.read`。
- 页面：售后列表、案例详情、退回接收、返工/补发、义务变更、退回制品处置、转线下库存记录、金额决定、售后交付和结案。
- 错误码：`AFTER_SALES_ORDER_NOT_COMPLETED`、`AFTER_SALES_OBLIGATION_NOT_READY`、`AFTER_SALES_QUANTITY_EXCEEDED`、`AFTER_SALES_RETURN_QUANTITY_EXCEEDED`、`AFTER_SALES_RETURN_TRACE_REQUIRED`、`AFTER_SALES_RETURN_SOURCE_MISMATCH`、`AFTER_SALES_RETURN_DISPOSITION_REQUIRED`、`AFTER_SALES_REPAIR_ROUTE_CHANGE_BLOCKED`、`AFTER_SALES_OFFLINE_INVENTORY_IS_TERMINAL`、`AFTER_SALES_AMOUNT_NOT_SETTLED`、`AFTER_SALES_ALREADY_COMPLETED`。
- 验收覆盖：原订单事实不被覆盖；订单生产定义变化生成继任订单项而不重写旧快照；售后退回接收与生产重入不能部分成功；返工义务与返工需求/来源任一步失败全事务回滚且不产生任务；退回可追溯最近一次交付、交付来源类型、消费事实和物理根并防止重复超量退回；未修复原样退还的交付和池来源消费同事务，后续再次退回只能引用该最新交付；退回制品取消返工时按 13.2.1 分支核对，仅可用池及成功回池数量新增处置，已路由终态引用原退出并解决剩余缺口，不重复处置；修复终态损失不能在原修复需求下重新制作，转路线只能转换当前修复终止缺口且支持分次处理，转补发时本次原返工义务/需求减少与等量继任补发义务/`NEW_PRODUCT` 需求必须同事务提交；转线下库存后不能直接取回或再次交付；重复成本来源不重复入账；金额未满足不能结案。

## 15. 待确认问题

本模块已明确交易、履约和售后的主要契约：内置标准方案固定覆盖制作、捏毛装袋、缝边剪袋，短流程通过自定义方案选择；转线下即脱离系统监管，移交事实不可更正、取回或重新纳入，一期不提供线下制品接管；订单收退款凭证为可选附件，并与财务 7.3 的统一规则一致。其他已明确分支不因此改变事实所有权。各类单号展示格式属于编号配置，不影响领域结构。
