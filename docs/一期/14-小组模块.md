# 小组模块

> 模块代码：`team`

## 1. 模块说明

小组模块把多名员工组成一个共同生产主体，用流水线协作提高整体效率。系统不在小组内继续拆分倒胶、填色等步骤；生产和排班只记录小组共同完成的产出。

## 2. 一期需求、范围与模块功能

- 建立、修改、停用生产小组；
- 配置完整成员集合；
- 按小组人数维护全局统一效率因子；
- 为排班提供小组资格、人数、成员和效率标准；
- 小组被活动计划引用时禁止修改；
- 活动计划取消或结束后允许修改；
- 已完成和已核算业务使用历史小组快照；
- 为工资提供当时完整成员集合。

一期不提供组长、组内岗位、可承接范围、组内步骤、成员贡献比例和个性化小组效率。

## 3. 业务概念

- **小组当前定义**：现在的小组名称、状态和成员集合。
- **活动引用**：尚可调整、取消或核验的排班任务对小组的有效引用；活动引用由排班模块拥有。
- **小组快照**：排班正式引用时冻结的小组身份和完整成员集合。
- **效率标准**：按人数配置的全局协作效率因子，与个人标准分开。
- **共同产出**：任务结果属于小组整体，不拆成成员个人数量。

## 4. 模块边界

### 4.1 小组模块拥有

小组当前定义、当前成员关系、成员变化事实、人数效率标准、小组快照和效率标准快照。

### 4.2 小组模块不拥有

- 员工在职和工种资格：由 `base-data` 提供；
- 活动排班引用和冲突时间段：由 `scheduling` 提供；
- 小组修改跨模块事务：由 `workforce-coordination` 提供；
- 工作量计算：由 `calculation` 提供；
- 生产事实：由 `production` 提供；
- 到人工资：由 `payroll` 提供。

小组模块不得直接读取排班表，也不得把“当前无活动任务”的判断复制到本模块。

## 5. 业务规则

1. 小组至少包含 2 名在职且具备相应制作资格的员工。
2. 一期允许同一员工配置在多个小组中，但同一工作日的个人/小组任务都必须计入该员工日负载，由排班统一防止超排。
3. 小组没有组长，不保存 `leader_id`。
4. 小组没有可承接范围，不保存商品、工序或品类范围。
5. 启用的成员人数必须存在唯一全局效率标准，效率因子必须大于 1。
6. 效率标准表示流水线整体提效，不表示成员工资权重。
7. 小组存在活动排班引用时，不允许修改成员、停用或删除。
8. 活动任务取消、完成核验或引用失效后，当前小组可以修改。
9. 历史任务和工资通过小组快照还原当时成员，不回读当前小组。
10. 未被业务引用的小组可停用；存在历史事实的小组不物理删除。
11. 小组修改一次提交完整成员集合，不提供逐步草稿。
12. 小组修改和停用只能通过 `workforce-coordination` 对外用例进入；`team` 的修改参与端口不直接暴露为 HTTP。

## 6. 状态设计

- 小组：`ACTIVE / INACTIVE`；
- 成员当前关系：存在即有效；历史变化由成员事实表达；
- 效率标准：`ACTIVE / INACTIVE`；同一人数只能有一个活动标准；
- 快照：不可变，无生命周期状态。

## 8. 业务流程

### 8.1 创建小组

```text
校验完整成员集合
→ base-data 校验员工在职和制作资格
→ 校验人数对应效率标准存在
→ 写小组、成员事实和当前关系
→ content_version = 1
```

创建时不存在旧小组活动引用，可由 `team` 自己作为命令所有者完成。

### 8.2 修改或停用小组

修改和停用由 `workforce-coordination` 发起。协调器先通过排班公开守卫确认没有活动引用，再调用本模块参与端口锁定小组并提交变化。本模块不能自行查询排班表。

### 8.3 取得小组快照

排班正式引用小组时，`team` 比较小组 `content_version`，创建或复用小组快照；同时取得成员员工快照和当前人数效率标准快照。工资结算只解析任务保存的小组快照。

### 8.4 修改效率标准

效率标准修改递增自己的 `content_version`。既有排班评估记录保持原效率标准快照和计算结果；新建或正式重新评估的任务使用最新标准。

## 9. 公开接口设计

```java
interface TeamApplicationService {
    TeamRef create(CreateTeamCommand command);
    EfficiencyStandardRef createEfficiencyStandard(CreateEfficiencyStandardCommand command);
    EfficiencyStandardRef updateEfficiencyStandard(UpdateEfficiencyStandardCommand command);
}
interface TeamMutationParticipant {
    PreparedTeamMutation prepare(UpdateTeamCommand command);
    TeamRef commit(PreparedTeamMutation prepared);
    PreparedTeamMutation prepareDeactivate(DeactivateTeamCommand command);
}
interface TeamAssignmentQuery {
    TeamEligibility checkEligibility(TeamId teamId, WorkTypeCode workType, LocalDate workDate);
    TeamCurrentView getCurrent(TeamId teamId);
}
interface TeamSnapshotService {
    TeamSnapshotBundle acquireCurrentAssignmentSnapshot(TeamId teamId);
    TeamSnapshotView resolve(SnapshotRef ref);
}
interface TeamEfficiencyQuery {
    TeamEfficiencyStandard getByMemberCount(int memberCount);
}
```

`TeamMutationParticipant` 只允许 `workforce-coordination` 依赖。`scheduling` 只使用资格、效率和快照接口。

## 10. 事务与并发

- 创建小组、修改效率标准由 `team` 开启事务；
- 修改/停用小组由 `workforce-coordination` 开启事务，本模块参与现有事务；
- 小组参与端口锁定顺序：小组根→成员关系；
- 小组快照和效率快照按来源内容版本使用唯一键防重；
- 成员集合替换、成员事实、内容版本和审计原子提交；
- 并发修改冲突使用 `row_version` 拒绝后提交者。

## 11. 权限、页面和错误

权限：`team.create`、`team.update`、`team.deactivate`、`team.read`、`team.efficiency.manage`。

页面：小组列表、小组编辑、成员历史、效率标准配置。页面不显示组长和可承接范围；修改按钮被阻止时必须显示活动任务原因。

错误码：`TEAM_NOT_FOUND`、`TEAM_INACTIVE`、`TEAM_MEMBER_COUNT_INVALID`、`TEAM_MEMBER_NOT_ELIGIBLE`、`TEAM_EFFICIENCY_NOT_CONFIGURED`、`TEAM_ACTIVE_PLAN_REFERENCED`、`TEAM_VERSION_CONFLICT`。

## 12. 验收标准

- 2/3/4 人小组能分别取得对应全局效率标准；
- 效率因子小于等于 1 被拒绝；
- 活动任务引用期间无法修改或停用小组；
- 取消/核验结束活动任务后可以修改；
- 修改后新任务取得新快照，历史任务仍显示旧成员；
- 工资能按历史快照找到完整成员；
- 小组数据中不存在组长、承接范围和成员贡献比例；
- `team` SQL、Repository 和内部包不访问 `scheduling`。
