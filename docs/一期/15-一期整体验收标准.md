# 一期整体验收标准

## 1. 验收目的

本标准用于判断一期是否真正形成可运行、可追溯、边界清晰的完整系统。单个页面可用或单元测试通过不能代替整体验收。

## 2. 业务闭环验收

### 2.1 标准订单闭环

- 创建商品并自动形成内置标准方案；
- 创建并确认订单，取得最新商品/方案/客户快照；
- 建立生产需求；
- 为个人安排作业任务并核验生产；
- 合格来源发货；
- 记录客户收款；
- 双向履约后完成订单；
- 工资自动采集、复核、封账、支付；
- 成本、现金和利润报表一致。

### 2.2 自定义方案和客户供料

- 自定义方案能改变目标工序、材料来源和允许的工序费用；
- 内置方案与自定义方案使用同一套完整方案结构；
- 人工标准、标准分钟和额外单件费用由商品同步且保持只读；
- 客户供料保留全资源价值但不计工作室承担成本；
- 订单冻结本次约定，后续商品修改不回溯。

### 2.3 小组共同产出

- 建立不同人数小组及效率标准；
- 小组作业任务使用效率因子减少整体标准时间；
- 小组任务标准秒数计入每名成员的当日负载，小组可用秒数取成员剩余秒数最小值；
- 生产只记录小组共同产出；
- 活动任务期间不能修改小组；
- 任务结束后可以修改且历史快照不变；
- 工资按历史成员等额分配，效率因子不参与工资。

### 2.4 其他任务和工资来源

- 其他任务直接录入整个执行主体的标准分钟，不套用商品工序分钟和小组效率；
- 其他任务标准秒数计入个人或小组全体成员的当日负载；
- 未关联商品的其他任务核验后不自动产生计件工资；
- 关联商品的其他任务在安排时冻结商品快照和其他任务单件人工费，核验后按完成数量生成工资来源；
- 商品后续修改不改变既有其他任务工资来源。

### 2.5 订单变更和取消

- 仅价格、收件人或地址变化只追加约定版本，不改生产需求；
- 仅数量变化按原订单项和原生产需求增减；
- 商品、方案、目标工序或材料来源变化时，为可迁移数量建立继任订单项、约定组和新生产需求，原历史数量仍按旧快照解释；

- 变更保留旧约定并形成新版本；
- 生产需求和活动作业任务原子调整；
- 已完成或已发货数量受到保护；
- 任一模块失败时无部分提交。

### 2.6 售后闭环

- 已完成订单可受理售后；
- 客户和工作室义务可跟踪；
- 退回、返工、补发、退款和赔付链完整；
- 每个退回接收明细可追溯最近一次交付明细、交付来源类型、对应生产来源或退回制品池来源、消费事实和物理根；接收事实与生产退回重入事实同事务成功，物理余额只从已消费移回系统内且累计制作量不增加；同一交付明细累计退回量不能超过交付量，再次交付后的再次退回必须引用新的交付明细；
- 售后返工只创建 `RETURNED_PRODUCT_REPAIR` 生产需求/返工来源，不创建任务或选择执行人员；售后补发创建独立 `NEW_PRODUCT` 需求；
- 修复中报废或转线下库存形成修复终止缺口，不能在原修复需求下重新制作；修复失败转路线只能转换当前缺口并允许分次处理，转补发时本次原返工义务/修复需求减少与等量继任补发义务/`NEW_PRODUCT` 需求同事务提交；
- 售后退回制品的当前履约来源可以从原订单来源切换到修复来源，但物理根来源保持不变；退回、修复、再次包装和再次交付均不得增加累计新制数量；
- 未修复原样退还从退回制品池直接形成售后交付和池来源消费事实，两者必须同事务；以后再次退回必须从这次最新交付继续追溯，不得跳回更早来源；
- 原订单、生产和现金事实不被覆盖；
- 全部义务满足后才可结案。

## 3. 架构边界验收

- Spring Modulith 验证所有模块依赖无环；
- 逻辑模块代码与 Java 根包遵守架构文档映射，代码中不使用含连字符的非法包名；
- ArchUnit 验证跨模块只能访问公开 `api`；
- Repository、行模型和 `infrastructure` 不跨模块；
- SQL 静态检查确认每个模块只访问自有表；
- `calculation` 无数据库和业务模块依赖；
- 系统不存在独立 `team`、`scheduling`、`workforce-coordination`、`after-sales`、`payroll`、`cost-ledger` 或 `fulfillment-coordination` 顶层模块；
- `workforce` 拥有活动引用守卫且不依赖 `production`，生产通过公开参与接口预留和释放；
- `production` 和 `orders` 不依赖 `finance`；生产材料和售后成本由 `finance.costledger` 读取公开 Source Feed 后归集；
- `finance` 不访问生产、订单、商品或人员表，只依赖公开 Participant、Source Feed、快照查询和计算接口；
- `reporting` 不被业务模块依赖；
- 没有通用 `save/executeSql/getRepository` 跨模块接口；
- 订单模块拥有订单与售后支付资格参与端口，财务结算模块不复制其资格规则；
- payroll、costledger、cash 是 `finance` 内部独立子域，不能直接访问彼此 Repository；
- 售后案例只有通过有原因的工资人工调整才能成为扣减或补偿依据；
- 跨模块接口的请求、结果、准备令牌和增量游标由能力提供方定义，不出现消费者反向类型依赖；
- 各需进入管理报表的业务模块提供自己的 `ReportingFeed` 和 Feed 专属游标；`orders` 的订单/售后、`finance` 的工资/成本/现金分别提供 Feed，报表按 `projection_code + projection_version + source_feed_code` 保存水位且不直读业务表。

## 4. 数据模型验收

- 所有业务表有明确所有者；
- 稳定业务标识和内部主键分离；
- 金额、比例、数量和时间类型符合公共规则；
- 关键唯一约束、检查约束和查询索引存在；
- 当前记录、事实、快照和投影没有概念混用；生产需求显式区分 `NEW_PRODUCT / RETURNED_PRODUCT_REPAIR`，需求义务投影使用通用待执行、处理中、待交付、已交付和履约缺口字段；
- 事实只能通过更正/冲销，不允许覆盖；
- 快照使用完整类型化引用，不保存裸版本；
- 跨模块无数据库外键；
- 服务端不存在业务草稿表和 `DRAFT` 状态。

## 5. 快照和追溯验收

- 商品、客户、员工、小组、效率标准和有效工作时间标准的快照由各自所有者模块管理；
- 同一 `content_version` 重复取得复用同一快照；
- 内容变化后取得新快照；
- 消费模块只保存快照引用；
- 历史订单、任务和工资可以解析当时数据；生产/修复任务标准只从需求冻结的商品和方案快照解析，商品当前值变化不重算历史任务；
- 生产、成本、现金和审计被正确实现为事实/追溯记录，而非快照；
- 公式版本保存为代码规则版本，不建立公式快照。

## 6. 事务和回滚验收

真实 MySQL 环境至少覆盖：

- 商品创建中预算失败，全商品事务回滚；
- 订单确认中生产需求失败，订单和应收回滚；
- 作业任务创建中任一步失败，任务、员工日负载、适用的商品新制日产能和生产/返工来源占用全部回滚；
- 从未核验的任务取消或改期释放原日期任务槽位；已经发生任一有效核验后取消剩余数量，只释放未执行的来源、负载、适用的新制产能预留和 workforce 活动预留，已核验新制完成数量保留在当日已用产能中，原日期任务槽位转为 `RETAINED` 并继续阻止冲突任务；
- 核验命令一次性提交完成/未完成数量、每个缺陷唯一原因、责任或免除结论及返工/转线下库存/报废处置；缺少任一项均不得形成初始核验事实；
- 核验中任一步失败，生产事实、阶段事实、来源数量、返工来源、负载投影和生产材料成本来源项全部回滚；
- 发货中生产消费失败，发货回滚；
- 员工可用性变更、小组变更与作业任务创建并发，必须竞争同一执行主体活动引用守卫，不能漏过活动引用；
- 生产材料成本自动归集失败不回滚已核定生产事实，但保留失败记录、停止越过游标并可重试；
- 工资封账中成本提交失败，封账回滚；
- 财务支付中业务关联失败，现金事实回滚；
- 经营费用支付中成本登记失败，现金事实、余额投影和经营成本事实全部回滚；
- 现金冲销中来源支付关联冲销失败，冲销现金事实和余额变化全部回滚；
- 售后退回接收与 production 退回制品重入不能部分成功；
- 售后返工义务与返工需求/来源不能部分成功；该事务不得创建任务，后续排班失败不回滚已成立的售后义务和返工来源；
- 未修复原样退还时，售后处置、售后交付、production 池内处置与池来源消费不能部分成功；池内报废或转线下库存时，订单售后处置与 production 处置/移交事实不能部分成功；
- 修复终态损失转路线时，只能减少本次确认的修复终止缺口；原返工义务/修复需求减少和继任义务不能部分成功，补发路线还必须原子建立等量新制需求，选择退款、赔付或结束时不得误建补发需求。

## 7. 并发和死锁验收

- 同员工日期的个人/小组并发任务安排不超每日有效分钟，授权超排除外；
- 同商品日期的 `NEW_PRODUCT + MAKING` 并发任务满足“已核验新制完成数量 + 未核验任务预留数量 ≤ 最大新制产能”；修补、包装和其他任务不误占该产能；
- 同生产来源或返工来源并发占用、核验、消费不产生负数；需求义务账与物理制品账分别守恒，未完成只回到对应来源可安排量；`NEW_PRODUCT` 终态损失形成补产缺口，`RETURNED_PRODUCT_REPAIR` 终态损失形成只能由售后义务变更解决的修复终止缺口；
- 同一物理数量不能同时进入两个活动履约来源或同时留在退回制品池；售后路由切换后，生产执行、转线下库存和再次消费事实均能追溯同一物理根；
- 同订单并发变更和发货保持数量守恒；
- 同账户并发付款余额正确；
- 同一生产成本来源并发归集只产生一组有效成本；
- 同期间并发工资计算/封账只有一个成功；
- 同内容版本并发取得快照只产生一个版本；
- 所有多行锁按稳定标识排序；
- 对可重试死锁只重试整个幂等命令，不重试局部 SQL；
- 达到重试上限返回稳定错误，不吞掉异常。

## 8. 幂等验收

每个正式写接口验证：

1. 同幂等键和同输入重复调用只产生一份事实；
2. 返回同一业务结果引用；
3. 同幂等键不同输入返回冲突；
4. 首次事务失败后可以安全重试；
5. 幂等成功记录与业务事实同时提交；
6. 劳动、责任和成本来源重复消费不形成重复结果；更正按 `REVERSE + APPLY/ACCRUE` 生效，任一 Feed 失败未处理前不得推进自己的游标。

## 9. 计算和金额验收

- 商品预算明细合计等于汇总，商品额外单件费用不会被再次按数量分摊；
- 制作、捏毛装袋、缝边剪袋和额外单件费用按固定字段拆解，人工/提成只来自商品继承值，方案不能覆盖；
- 胶水标准用量等于“标准克重 ×（1 + 损耗率）”，胶水和色浆成本均使用该用量，色浆不重复乘损耗率；
- 目标工序正确控制成本范围；每笔商品/方案预算内，基础材料只归入 `MAKING` 一次；每条实际 `MAKING` 生产或修复来源按历史制作成本计算一次，包装工序不重复取用；
- 商品单日最大产能使用模具数量和每日批次，并且只约束会产生新制品的 `NEW_PRODUCT + MAKING` 明细；制作修补、包装和其他任务不占用该产能；
- 当日新制产能满足“已核验新制完成数量 + 未核验任务预留数量 ≤ 商品单日最大产能”；核验完成数量进入已用产能，未完成、取消和调整只释放预留，不会因任务结束而重复释放已完成产能；
- 商品产能参数修改时，生产模块在商品日期产能行锁内刷新当前上限和商品内容版本后再守卫；若新上限小于既有已核验数量，历史事实不回算、不失效，只拒绝新增或扩大安排并返回 `PRODUCTION_CAPACITY_CONFIG_CONFLICT`；
- 多产品任务按明细分别计算“计划数量 × 冻结单件标准分钟 × 60”得到整数秒后再汇总；其他任务录入整数分钟并精确转换成秒；
- 小组效率只在汇总后的基准秒数上除一次，并对最终结果向上取整到秒，不逐明细舍入；
- 个人/小组任务标准秒数、剩余有效秒数和比较结果由计算中心完成，比较不把候选任务重复计入剩余负载；工作量存储和比较统一用秒；
- 预算、生产材料和成本台账明细使用 `DECIMAL(19,4)` 并按 `HALF_UP` 舍入到 4 位；工资、应收、收退款和现金使用 `DECIMAL(19,2)` 并按 `HALF_UP` 舍入到分；工资来源明细分别舍入后再汇总；
- 其他任务直接录入的标准分钟不再应用小组效率，且只有冻结商品其他任务正式引用后才能自动计件；
- 小组基准秒数先汇总全部明细再除以一次效率因子并向上取整到秒，小组可用秒数不乘人数，按成员剩余秒数最小值确定；
- 小组效率因子大于 1 且不参与工资；
- 任意人数（至少 2 人）小组工资均先换算为币种最小单位，余数按稳定员工标识分配，分配合计严格等于任务总金额；
- 正常生产、制作超额生产和修复任务的生产材料成本只取历史方案快照中“当前工序、工作室承担、非人工”的成本行，数量使用完成数量；修复不得改用商品当前值；
- 客户供料不进入工作室生产材料成本，人工、提成和额外预计分摊不被重复归集；
- 订单当前应收、净收款、交付履约和付款履约可以由有效事实重算；
- 生产来源可安排数量由来源进入、工序流转、返工回流、终态处置、消费、需求减少和活动预留重算；未完成释放只减少预留，不重复增加来源余额；
- 需求义务账满足“待执行 + 系统内处理 + 目标工序待交付 + 已交付 + 履约缺口 = 当前有效需求”，物理制品账满足“系统内未终止未消费 + 已消费 + 已报废 + 已转线下库存 = 累计新制品产生量”；
- 现金分配、成本分摊、订单应收和工资支付合计一致；
- 报表不复制业务公式；订单利润只有在收入和成本均有来源关联时才按“当前有效应收 − 订单已归集成本”展示，当前有效应收为 0 时利润率为空，未形成订单经营分摊事实的经营费用不得被报表擅自平均分配；
- 所有历史计算可显示规则版本、舍入版本和输入依据；超额制作激励及责任扣款在未确认前不得被测试当作已确定公式。

## 10. 权限和审计验收

- 未登录和无权限请求被后端拒绝；
- 工资、成本、现金等敏感数据按资源范围限制；
- 所有正式写入记录操作者、请求编号、命令执行标识和结果；
- 审计日志不泄露密码、令牌和敏感明文；
- 文件引用可追溯且被引用文件不能删除；
- 管理员操作与员工生产身份分离。

## 11. 页面和可用性验收

- 页面按业务结构分区，不直接暴露数据库概念；
- 前端按 `app/platform/shared/modules` 组织，业务模块至少保持页面、composable/use-case、service、contract 的职责边界；
- 页面不得直接调用通用 HTTP 客户端或其他模块内部 service；跨模块写操作只能调用命令所有者的一个公开接口；
- 页面不复制计算中心、生产、订单或财务公式，金额、工时、产能、来源余额和工资结果以接口返回值为准；
- 只读继承字段明确标识；
- 禁止操作有明确原因，而不是只隐藏按钮；
- 列表、详情和时间线显示一致状态；
- 关键金额和数量展示来源与单位；
- 工时、金额和快照版本显示精度、单位和引用时间点；
- 权限拒绝、并发冲突、幂等冲突、超时和最终一致延迟有明确反馈；
- 报表显示数据更新时间和延迟；
- 页面未提交数据刷新后可丢失，系统不承诺服务端草稿恢复。

## 12. 报表和重建验收

- 所有投影可从公开数据源重建；
- 增量水位失败不越过；
- 重建前后核心合计一致；
- 对账差异可定位到业务标识；
- 报表损坏或延迟不影响业务写入；
- 报表无跨模块 SQL。

## 13. 文档一致性验收

- 每个模块文档章节完整；
- 表名、字段名、状态和接口名称在全目录中无冲突；
- 所有跨模块调用在架构和事务文档中有记录；
- 开发顺序为：模块骨架与边界测试 → `platform` → `calculation` → 并行完成 `customer`、`product`、`workforce` → `production` → 包含售后的 `orders` → 包含工资、成本和现金的 `finance` → `reporting` → 真实 MySQL 综合验证；
- 不存在旧的通用材料目录、装箱工序、方案默认选择、服务端草稿等已否决设计；
- 所有待确认问题都有明确影响范围；进入对应功能开发前，相关阻塞问题必须清零。

## 14. 一期通过条件

只有同时满足以下条件才可判定一期通过：

1. 核心业务闭环全部通过；
2. 架构边界自动测试通过；
3. 真实 MySQL 事务、并发、死锁和回滚测试通过；
4. 数据迁移在备份副本完成演练和对账；
5. 权限、审计和敏感数据测试通过；
6. 关键报表与来源数据对账无未解释差异；
7. 文档与最终实现同步，不存在已知关键偏差。
