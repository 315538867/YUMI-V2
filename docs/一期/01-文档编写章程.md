# 一期文档编写章程

## 1. 目的

本章程规定一期设计文档如何编写、评审和维护，保证文档是开发和验收依据，而不是讨论记录或概念堆砌。

## 2. 文档面向的读者

- 产品人员：能确认需求、范围、流程和业务规则；
- 后端开发：能确定模块、接口、事务、数据表和错误语义；
- 前端开发：能确定页面、字段、操作条件和错误反馈；
- 测试人员：能从规则和验收标准直接形成测试用例；
- 运维和数据人员：能确定审计、追溯、迁移、备份和重建边界。

## 3. 模块文档统一结构

每个有业务数据或业务能力的模块必须覆盖以下内容。相邻内容可以合并为一个章节，但标题必须让读者能直接看出所覆盖的主题，不能因为合并而省略边界、表、接口、事务或验收信息：

1. **模块说明**：模块为什么存在；
2. **一期需求**：用户需要解决的问题；
3. **本期范围**：本期做什么、不做什么；
4. **模块功能**：对外提供的完整业务能力；
5. **业务概念**：统一名词及其含义；
6. **模块边界**：拥有、不拥有、上游和下游；
7. **业务规则**：必须始终成立的不变量；
8. **业务流程**：正常流程、更正流程和异常流程；
9. **状态设计**：状态、转换条件和禁止转换；
10. **数据模型与表设计**：表用途、关键字段、约束和索引；
11. **公开接口设计**：命令、查询、参与端口和返回值；
12. **事务与并发**：事务所有者、锁序、幂等和冲突；
13. **历史与追溯**：事实、快照、追溯记录和投影处理；
14. **权限、审计与错误**：可操作角色、审计范围和稳定错误码；
15. **页面与交互要求**：页面需要展示和校验的业务信息；
16. **验收标准**：可观察、可验证的完成条件；
17. **明确不采用**：防止旧方案或错误理解重新进入；
18. **待确认问题**：只保留确实未决定且会影响开发的问题。

无数据库的模块必须明确写出“无业务表、无 Repository、无 Flyway”，并说明公式版本或协调结果如何追溯，不能省略数据所有权说明。

## 4. 内容编写规则

### 4.1 写业务能力，不写空泛分层

正确：`订单确认时取得商品和方案当前快照，并建立交付约定。`
错误：`Controller 调用 Service，Service 调用 Repository。`

技术分层可以说明，但不能代替业务规则、输入输出和失败条件。

### 4.2 表设计必须可实施

每张业务表至少说明：

- 表的所有者模块；
- 记录类别：当前记录、事实、快照、追溯记录、投影、关系或守卫；
- 主键和稳定业务标识；
- 关键业务字段；
- 唯一约束、检查约束和必要索引；
- 可否更新、如何更正、如何失效。

### 4.3 接口必须表达业务目的

采用 `confirmOrder`、`acquireCurrentProductSnapshot`、`assessWorkload` 等业务接口。禁止用 `save`、`updateTable`、`executeSql` 等接口跨模块暴露底层能力。

### 4.4 不把推测写成结论

未确认事项放入“待确认问题”，并说明影响范围。禁止用“通常”“大概”“后续看情况”掩盖关键决策。

### 4.5 不写实施计划

本目录可以体现依赖顺序和验收前置条件，但不包含：

- 工期和人日；
- 开发阶段编号；
- 人员安排；
- Sprint 拆分；
- 数据库迁移文件的执行排期；
- “先做第几天、再做第几周”的任务计划。

## 5. 统一术语

| 术语 | 定义 |
|---|---|
| 当前记录 | 表示对象现在可编辑的定义或当前状态 |
| 事实 | 已发生且需要长期保留的业务事件，只能通过新事实更正 |
| 追溯记录 | 用于还原来源、动作和变化链的不可覆盖记录 |
| 快照 | 在某一业务引用点冻结可变定义的不可变版本 |
| 投影 | 为查询和展示派生的可重建结果，不是业务真相 |
| 内容版本 | 聚合业务内容每次成功修改后递增的 `content_version` |
| 乐观版本 | 防止并发覆盖的 `row_version`，与内容版本用途不同 |
| 快照引用 | `ownerModule + snapshotType + snapshotBusinessId + snapshotVersion` |
| 命令所有者 | 对一次正式业务动作负责并开启事务的模块 |
| 参与端口 | 由其他模块在既有事务中调用的受限写能力 |
| 活动引用 | 当前有效计划、任务或业务关系对某可变定义的占用 |

## 6. 文档评审清单

- [ ] 模块拥有和不拥有的内容是否明确；
- [ ] 是否存在直接读取其他模块表的描述；
- [ ] 计算规则是否错误地下沉到调用模块；
- [ ] 当前状态与历史事实是否混在一张可覆盖表；
- [ ] 快照所有者和取得时机是否明确；
- [ ] 是否仍存在服务端草稿或半成品保存；
- [ ] 表字段是否能支撑接口和页面；
- [ ] 状态和更正路径是否完整；
- [ ] 跨模块事务失败时是否整体回滚；
- [ ] 验收标准是否可以直接转成测试。

## 7. 变更方式

任何规则变更按以下顺序更新：

1. 修改对应模块的需求和业务规则；
2. 修改数据表和公开接口；
3. 修改跨模块依赖和事务；
4. 修改页面交互和错误码；
5. 修改整体验收标准；
6. 搜索全目录，清除冲突描述。
