# 生产作业模块

> 模块代码：`production`

## 1. 模块说明

生产作业模块统一管理从生产需求到任务安排、执行核验、工序流转、质量处置和交付消费的完整作业过程。原“排班模块”不再作为独立顶层模块，其计划、人员负载、商品日产能和任务核验能力并入本模块。

合并的是业务边界，不是数据概念：计划任务描述准备怎么做，生产事实描述实际发生了什么。计划可以调整或取消，已经核定的生产事实不能覆盖，只能通过更正事实修正。

## 2. 一期需求、范围与模块功能

### 2.1 本期提供

- 根据订单项、售后义务或已有订单接管建立生产需求；
- 对上线时尚未完成的已有订单执行一次性期初生产状态接管；
- 一个订单项自动建立一个生产需求；
- 维护产品、商品快照、方案快照、目标工序和需求数量；
- 为正常生产、制作工序超额生产、修复和其他任务安排工作日期、个人或小组、工序及数量；
- 调用公开能力评估个人/小组工作量、员工日负载和商品单日产能；
- 调整、取消和核验作业任务；
- 记录制作、捏毛装袋、缝边剪袋和修复的生产事实；
- 记录质量、责任、返工、报废、更正、来源消费和转线下库存事实；
- 维护各阶段可用、已占用、待返工、报废、已消费和已转线下库存数量；
- 公开已核定的正常生产、制作工序超额生产、修复和其他任务劳动来源事实，供下游结算使用；
- 为成本台账提供已核定正常生产、制作超额生产和修复工序的材料成本来源数据，不提供成本金额；
- 为订单发货和售后交付提供合格制品消费能力。

### 2.2 本期不提供

- 小组内部流水线步骤拆分或成员个人产量；
- 小时级班次、时间段冲突、甘特图和考勤；
- 商品标准工时、小组效率、有效工作时间或工资公式的本地复制；
- 工资分配、成本计算、材料管理、库存余额、仓库出入库、领料或设备采集；
- 线下库存查询、系统内取回、再次占用或直接发货；
- 直接读取商品、人员与小组、订单、工资或其他模块的数据表；
- 服务端草稿。

装箱不是生产工序；打包发货作为 `OTHER_TASK` 管理，不改变制品物理阶段。

## 3. 业务概念

### 3.1 制品产生与包装加工

生产作业必须区分“创造制品”和“加工既有制品”：

```text
NEW_PRODUCT + (NORMAL_PRODUCTION / EXTRA_PRODUCTION) + MAKING
→ 唯一可以产生新制品数量的组合，完成物理制品从 0 到 1

RETURNED_PRODUCT_REPAIR、REPAIR、BAGGING / SEAM_CUTTING
→ 只处理已经存在的制品，修复或改变包装阶段，不增加制品数量
```

制作执行事实产生物理制品数量，质量事实再决定该数量是合格、待返工还是报废。捏毛装袋和缝边剪袋执行事实只能移动既有数量的包装阶段，不能生成新制品。

返工始终处理原制品：返工工序为 `MAKING` 时，业务动作固定为修补；返工工序为 `BAGGING` 或 `SEAM_CUTTING` 时，业务动作固定为重做对应包装工序。返工不得增加生产数量。`NEW_PRODUCT` 下原制品线上报废（实际销毁或转线下）后形成一次补产缺口，排班人员可以在原需求下另行建立正常补产任务；`RETURNED_PRODUCT_REPAIR` 下相同终态形成修复终止缺口，只能由订单售后变更义务路线。补产属于 `NEW_PRODUCT + NORMAL_PRODUCTION + MAKING`，不是原制品返工。

### 3.2 核心业务对象

- **生产需求**：某一业务来源要求对指定产品数量完成新制生产或退回制品修复，并达到目标工序的业务义务。
- **生产来源**：生产需求下可独立占用、流转、核验和消费的履约数量来源；新制来源承载待制作数量，售后修复来源承载从退回制品池分配来的既有制品。
- **物理根来源**：标识一批制品最初由哪一个新制生产来源产生；售后退回、修复、再次包装和再次交付始终沿用原物理根来源，用于保证累计制品数量不重复增加。
- **作业任务**：对生产、修复或其他工作的正式安排。
- **任务类型**：`NORMAL_PRODUCTION / EXTRA_PRODUCTION / REPAIR / OTHER_TASK`。
- **执行主体**：`EMPLOYEE / TEAM`。
- **生产事实**：实际数量移动、工序完成、质量、责任、处置或消费的不可覆盖记录。
- **期初生产事实**：系统上线接管已有订单时，对未开始、各在制阶段、待返工、报废和已达到目标工序数量的一次性不可覆盖记录。
- **物理阶段**：`MAKING / BAGGING / SEAM_CUTTING`。
- **质量状态**：`PENDING / QUALIFIED / DEFECTIVE`。
- **线上处理结果**：合格继续履约、`REWORK_REQUIRED`（无责任返工）、`SCRAPPED`（不能用于当前线上履约）；报废不是物理销毁。
- **物理去向状态**：`IN_SYSTEM / DESTROYED / TRANSFERRED_OFFLINE_INVENTORY / CONSUMED`，与线上处理结果分别保存；活动占用另用 `AVAILABLE / RESERVED` 表达。
- **转线下库存事实**：把系统内仍有实物的制品一次性移交给线下库存，并终止其系统内生产、占用和交付资格的不可变记录；它不是库存记录。
- **活动引用**：尚可调整、取消或核验的任务对员工、小组和生产来源的有效引用。
- **工作量评估记录**：保存创建或调整任务时计算中心返回的标准秒数、剩余秒数、评估结果和规则版本；配置与录入的标准时间仍以整数分钟表达。
- **数量投影**：根据有效生产事实计算的阶段余额，可从事实重建。
- **生产材料成本来源项**：由已核定正常生产、制作超额生产或修复工序事实生成的追加式公开数据源项，只表达产品、任务类型、工序、数量和当时方案快照，不包含成本金额。

生产事实是数据库追溯记录，不是快照。

### 3.3 两套数量账

生产需求义务和物理制品必须分账，不能再用一个含义不清的“有效增加”公式混算：

1. **需求义务账**回答“订单或售后义务还有多少处于什么状态”。当前有效需求数量必须拆解为：待执行、系统内处理中（含生产、修补或重做）、已达到目标工序待交付、已完成交付，以及因终态损失仍未解决的履约缺口。
2. **物理制品账**回答“实际制品现在在哪里”。只有 `NEW_PRODUCT + (NORMAL_PRODUCTION / EXTRA_PRODUCTION) + MAKING` 的完成数量增加累计制品产生量；包装、修复和售后退回重入只移动原制品。累计产生量必须能解释为系统内仍存制品、已消费制品、已实际销毁制品和已转线下库存制品之和。线上报废是独立统计维度，其转线下部分不得再次加进物理守恒合计。
3. 任务“未完成”只释放原安排，不产生制品、不产生不合格，也不增加履约缺口。
4. 对 `NEW_PRODUCT` 需求，线上质量报废（无论实物销毁或转线下）形成的履约缺口就是补产缺口，可继续在原需求、原来源和原快照下安排正常制作；对 `RETURNED_PRODUCT_REPAIR` 需求，退回制品线上报废（无论实物销毁或转线下）形成的是修复终止缺口，不能在该修复需求下重新制作，必须由订单售后模块把对应修复义务减少或取消，并按决定另建补发义务及 `NEW_PRODUCT` 需求。
5. 订单减量、取消或售后义务取消导致的转线下库存与上游需求同步减少，不形成履约缺口。
6. 来源预留只是上述余额上的占用维度，不改变需求义务或制品所有权。

## 4. 模块边界

### 4.1 本模块拥有

生产需求、生产来源、期初生产事实、作业任务、任务安排事实、工作量评估、员工日负载、商品日期新制产能投影、生产执行事实、质量、责任、处置、来源消费、转线下库存事实和数量投影。

### 4.2 本模块不拥有

- 订单交易和交付约定：由 `orders` 拥有；
- 商品定义、工序标准、商品产能公式和商品/方案快照内容：由 `product` 拥有；
- 员工、小组、工种资格、人数效率标准、每日有效工作时间标准和执行主体快照内容：由 `workforce` 拥有；
- 个人/小组工作量、剩余时间和商品产能公式：由 `calculation` 拥有；
- 到人工资、小组工资分配、成本金额、费用归集和现金收付：由 `finance` 内部对应子域拥有；
- 执行主体活动引用守卫和预留记录：由 `workforce` 拥有。

本模块可以汇总自己拥有的活动任务和数量事实，但不得复制其他模块公式或访问其他模块底层表。

### 4.3 对外协作

- `orders` 通过生产需求参与端口创建或调整订单及售后需求；
- 本模块通过 `WorkforceActivityReservationParticipant` 预留、调整和释放执行主体活动引用；
- `orders` 通过生产消费参与端口消费合格来源完成普通或售后交付；
- `orders` 在订单减量或售后退回处置事务中，通过转线下库存参与端口将明确数量单向移出系统；
- `finance.payroll` 分别通过 `ProductionLaborSourceFeed` 和 `ProductionResponsibilitySourceFeed` 按独立游标增量消费劳动来源、责任来源及其更正；
- `finance.costledger` 通过 `ProductionMaterialCostSourceFeed` 增量读取已核定正常生产、制作超额生产和修复工序来源；
- `reporting` 通过公开变化数据源建立报表投影。

## 5. 生产需求与产品身份

### 5.1 建立规则

订单正式确认后，订单模块按每个订单项自动创建一个生产需求：

```text
一个订单项
= 一个生产需求
= 一个产品 + 一个方案快照 + 一个目标工序 + 一组需求数量
```

一个生产需求可以拆分为多个作业任务；不得把多个不同订单项直接合并成同一个生产需求。售后返工和补发也分别建立独立需求，不能与原订单需求混用。

生产需求必须明确履约方式：

- `NEW_PRODUCT`：通过制作新制品履约，适用于普通订单和售后补发；待执行数量表示尚未制作数量。
- `RETURNED_PRODUCT_REPAIR`：通过修复已退回的原制品履约，必须关联唯一退回制品来源；待执行数量表示已经重入系统但尚未被修复任务占用或处理的数量，不得据此新增制品。其物理根始终取自退回制品记录携带的原始新制物理根，不因原样退还、再次退回或多次修复而改变。

需求来源类型负责表达“来自普通订单、售后补发还是售后返工”，需求类型负责表达“新制还是修复原制品”，两者不得互相替代。内部质量返工不新建生产需求，而是在原需求下建立返工来源。

### 5.2 目标工序

生产需求只保存最终目标工序：

```text
MAKING        制作完成
BAGGING       捏毛装袋完成
SEAM_CUTTING  缝边剪袋完成
```

目标为后续工序时，必须依次经过前置物理阶段。目标工序由订单采用的商品方案快照提供，生产模块不得读取商品当前数据重新判断。

### 5.2.1 来源数量公式

任务安排、任务调整和生产核验统一使用“当前工序来源”的数量口径，禁止把需求总量、任务计划量和来源可安排量混为一个字段：

```text
当前工序来源总量
= 进入当前工序的有效数量
  + 有效返工/修补回流数量
  - 本来源未制取消数量（仅尚未制作的制作入口，定义见 7.7）

当前工序来源已退出数量
= 合格流转数量
  + 返工/修补转出数量
  + 实际销毁数量
  + 转线下库存数量
  + 已消费数量

当前工序来源可用总量
= 当前工序来源总量 - 当前工序来源已退出数量

来源当前可安排数量
= 当前工序来源可用总量 - 活动任务预留数量
```

- “进入当前工序的有效数量”来自期初接管、上游工序合格流转或售后返工来源；同一数量只能记入一次。
- 核验完成结果三选一：合格、返工/修补、线上报废；线上报废再按实物去向拆为实际销毁或转线下。同一报废处置只发生一次来源退出和一次缺口增加，移交记录是其去向明细，不能再扣一次。非报废的订单减量移交另走上游变更事务。
- 活动任务预留只占用可安排余额，不改变需求义务、物理制品所有权或已发生事实；未完成数量释放时只减少活动任务预留，不再额外加回来源余额，避免同一数量重复计算。
- 安排前必须满足 `来源当前可安排数量 ≥ 本次计划数量`；计算结果不得被 `max(0)` 静默截断，出现负数必须拒绝并报告并发或数量投影错误。

对物理制品还必须满足独立守恒关系：

```text
累计新制品产生量
= 系统内未终止且未消费的制品余额
  + 已消费数量
  + 已实际销毁数量
  + 已转线下库存数量
```

只有 `NEW_PRODUCT + NORMAL_PRODUCTION/EXTRA_PRODUCTION + MAKING` 的完成数量增加“累计新制品产生量”；包装、修补、售后退回重入和再次交付只移动原制品，不得再次增加该累计量。

### 5.3 产品和快照引用

生产需求、生产来源和核心生产执行事实都必须直接保存：

```text
产品编号
商品快照引用
商品方案编号
商品方案快照引用
```

产品编号回答“生产的是什么产品”；商品快照回答“当时产品是什么定义”；方案快照回答“本次订单采用什么制作方案”。三者不能互相替代。每个生产来源还必须保存物理根来源：`NEW_PRODUCT` 来源的物理根是自身；`RETURNED_PRODUCT_REPAIR` 来源的物理根是退回制品记录携带的原始 `NEW_PRODUCT` 生产来源。售后修复可以更换当前履约来源，但不能更换物理根或增加累计制作量。

生产模块只保存类型化快照引用，不复制快照载荷。任务安排时，工序标准分钟、人工依据和工序成本依据必须通过商品模块按生产需求已经冻结的商品/方案快照解析，禁止重新取得商品当前作业标准。只有商品单日产能属于安排当时的当前约束：生产模块按商品编号读取当前产能上限和商品内容版本，并把两者固化到当日产能占用记录。历史展示分别通过 `product` 和 `workforce` 的公开快照解析接口完成。

商品当前产能发生变更时，生产模块在商品日期产能行锁内刷新 `capacity_limit + product_content_version` 后再做守卫判断；已核验的 `committed_new_making_quantity` 和未核验的 `reserved_new_making_quantity` 不回算、不清零。若新上限小于已提交数量，禁止新增或扩大任务并返回明确的产能配置冲突，不能追溯性地使已完成事实失效；只有新上限满足守恒时才允许继续安排。

### 5.4 售后退回制品的履约来源切换

退回接收成功时，原制品从上一次交付消费余额重入物理制品账，并先进入退回制品池；上一次交付来源既可能是普通/修复履约生产来源，也可能是此前原样退还时使用的退回制品池来源，因此退回链必须冻结“上一次交付来源类型 + 对应来源标识 + 消费事实 + 物理根”，不能假设每次退回都直接来自生产来源。此时退回制品不能直接作为原订单的可交付数量，也不能直接安排普通任务。售后决定返工后，orders 通过 production 参与接口在同一事务完成：

1. 从退回制品池路由指定数量；
2. 建立 `RETURNED_PRODUCT_REPAIR` 生产需求；
3. 建立 `RETURNED_EXISTING_PRODUCT` 履约来源并沿用原物理根来源；
4. 建立首个 `AFTER_SALES_RETURN` 返工来源，指定从哪个已历工序开始修复。

返工任务核验合格后，数量回到该修复需求的履约来源阶段投影。若目标工序尚未达到，后续包装工序作为该修复需求下的普通生产任务继续流转，但仍处理原制品，不增加累计制作量；后续再次发现缺陷时，在同一修复需求下建立新的 `INTERNAL_DEFECT` 返工来源。达到目标工序后进入修复需求的待交付数量，再次交付消费该修复履约来源，同时沿用原物理根。

修复需求取消且尚未发生不可逆生产事实，并且不存在活动任务、来源预留或在途占用时，可以通过反向路由事实把未处理数量释放回退回制品池，再选择原样退还、线上报废并指定去向，或非报废义务释放转线下；一旦已经形成有效修复、包装、终态或消费事实，只能按事实更正和售后义务变更规则处理，不能直接改回可用退回数量。退回制品池的 `routed_repair_quantity` 表示已经退出池并归入修复路线的数量，包含后续已修复、再次交付或在修复路线内终态处置的数量；`disposed_quantity` 只表示尚未路由修复前直接原样退还、线上报废并指定去向，或非报废义务释放转线下的数量。

### 5.5 已有订单期初接管

一期只接管系统上线时仍未完成的订单。已完成或已交付订单保留在订单历史中，不为其补建活动生产来源。订单模块先按接管时仍需管理的数量建立生产需求，生产模块再对该需求执行一次性期初初始化。

期初初始化按“当前状态”录入，不反向虚构历史过程：

- 不创建上线前的排班或生产任务；
- 不补录历史执行员工、小组、有效工作时间或个人/小组产量；
- 不补录历史劳动、材料成本或责任来源；
- 只记录接管时各数量所在的工序阶段、质量/处置状态和数量；
- 尚未制作的数量记录为 `NOT_STARTED`，后续从制作工序正常安排；
- 已进入生产的数量只能落在方案快照实际包含且不晚于目标工序的节点；
- 待修补或重做数量必须明确返工工序；线上报废数量按实际销毁或转线下去向进入终态并形成一次需求缺口，但不自动创建补产任务。

一次期初提交可以包含多条状态明细，但必须在同一事务中满足：

```text
期初各状态数量合计 = 该生产来源接管数量
```

提交成功后，根据期初事实一次性建立数量投影。期初事实只用于衔接当前生产进度，不进入劳动来源、责任来源或材料成本来源，因此不会重复核算上线前已经线下处理的工资和成本。上线后对剩余数量创建的任务、核验和更正全部进入正常生产链。

期初状态也按“线上结果 + 实物去向”保存；报废且已转线下的数量只计入一条期初明细，物理投影只计线下去向，不能再计一次销毁或多生成一次缺口。接管时必须明确历史报废的实际去向，不能把报废默认解释为物理销毁。

每个生产来源只能完成一次期初初始化，不能直接修改或删除。录入错误必须通过期初更正命令追加冲销事实和替代事实；更正必须重新校验数量守恒、工序合法性以及已经发生的后续任务、核验和消费，不能使任何下游事实失去有效来源。

### 5.6 订单减量与取消

订单减量和订单取消都由 `orders` 发起，生产模块只通过生产需求变更参与接口判断并执行生产侧影响。订单模块不得查询生产任务、数量投影或生产事实表。

一期直接取消的范围限定为尚未实际制作且能够解除活动任务占用的数量；已经形成制品的减量必须另行匹配同事务线下移交，不得把物理制品当作未制数量取消：

- 尚未安排的未开始数量可以直接减少；
- 已安排但尚未核验的数量可以减少，生产模块在同一事务缩减对应任务明细并释放人员负载、商品日产能、活动主体引用和来源占用；
- 混合多个订单来源的任务只调整当前来源的未核验分配，保留其他来源；调整后必须重新评估任务工作量，任务剩余数量为零时追加取消事实；
- 已形成制作、包装、修复、质量或其他生产事实的数量不能通过订单变更删除、冲销或转成无归属制品；
- 已生产但尚未消费的数量如果因订单减量成为多余制品，只有在同一事务明确转线下库存后才能减少订单数量；未提供移交明细时拒绝变更；
- 转线下库存前必须先解除对应活动任务、来源占用和其他系统内预留；已消费数量不能直接移交；
- 已发货数量必须先由订单模块更正发货，并通过生产消费参与接口反向冲销消费事实，之后才能重新预检减量；
- 原报废事实永久保留，但报废后尚未开始的补产缺口可以随订单减量取消；
- 整单取消等价于把全部订单项活动数量减为零，必须逐项通过相同校验；已生产未消费数量只有同步转线下库存后才不再阻塞取消。

生产需求变更预检至少返回当前需求数量、未制取消数量（含尚未开始的补产缺口）、已制移交数量、不可减少数量、阻塞原因以及受影响的任务和任务明细。每一份数量必须归入唯一类别，且本次需求减量 = 未制取消数量 + 已制移交数量；生产需求变更事实与物理移交事实通过变更业务标识关联。只有全部订单侧和生产侧校验均成功，才能在订单变更事务中提交。

### 5.7 线下库存单向移交

线上结果与实物去向的组合必须明确：

| 场景 | 线上处理/退出原因 | 实物去向 | 报废责任参考 | 需求影响 |
|---|---|---|---|---|
| 不合格但可返工 | `REWORK_REQUIRED` | `IN_SYSTEM` | 不产生 | 继续履约 |
| 不符合线上交付要求，实际销毁 | `SCRAPPED / QUALITY_SCRAP` | `DESTROYED` | 按报废责任判断 | 按需求类型增加一次缺口 |
| 不符合线上交付要求，作为瑕疵品移交线下 | `SCRAPPED / QUALITY_SCRAP` | `TRANSFERRED_OFFLINE_INVENTORY` | 与报废销毁同一规则，不因去向免扣 | 按需求类型增加一次缺口 |
| 订单减量等造成未报废制品退出 | 保留原质量，`UPSTREAM_RELEASE` | `TRANSFERRED_OFFLINE_INVENTORY` | 不伪造报废责任 | 与需求同步减少，不增缺口 |

每条终态退出明细只对应一种原因和一种去向；不同去向需按数量拆分。报废处置、物理退出与线下移交共享同一个 `terminal_exit_business_id`，同事务提交。只有唯一退出事实驱动来源扣减及物理投影；报废事实驱动线上报废统计及责任，移交事实补充实物去向与交接资料，不第二次扣减来源或增加缺口。

线下库存不是系统模块。生产模块不维护仓库档案、库存余额、库位、入库单、出库单或可用库存，只保存一次业务移交事实和完整来源追溯。

允许移交的数量必须满足：

- 已经形成实际制品，并且仍由生产模块管理；
- 没有活动任务占用、来源预留或尚未完成的系统内消费；
- 未被普通发货或售后交付消费；已消费的必须先由下游业务更正并冲销消费事实；
- 移交数量不超过对应生产来源当前可移交余额；
- 命令明确订单变更或售后义务等业务原因，以及线下库存名称/说明、移交人、接收人和移交时间。

移交完成后，对应数量进入 `TRANSFERRED_OFFLINE_INVENTORY` 终态：不能再安排生产或修复任务，不能被订单或售后交付消费，也不能重新取回。移交不冲销已经真实发生的生产、质量、劳动和成本事实。移交全部字段提交后不可在系统内更正；提交前必须核对，提交后录入错误只能在线下处理，边界统一见 7.8。

线上报废与实物转线下不是互斥选项。质量不符合线上订单要求的制品可以记录 `SCRAPPED + TRANSFERRED_OFFLINE_INVENTORY`，在线下作为瑕疵品出售；系统只保存移交，移交后的库存、售价和销售不纳入一期监管。该组合仍属于报废责任参考范围，不能因去向为线下而取消责任。

质量报废的另一实物去向为 `DESTROYED`（实际销毁）。核验提交时必须明确报废去向及数量，不能将计划销毁记为已销毁；报废选择转线下时必须同时完成真实移交信息。线上报废数量等于该次报废下实际销毁与转线下数量之和，均只退出一次线上来源。`NEW_PRODUCT` 下只产生一次补产缺口，`RETURNED_PRODUCT_REPAIR` 下只产生一次修复终止缺口。

订单减量、取消或售后义务取消也可将未报废制品转线下；保留其原质量结果及业务释放原因，不伪造报废或员工责任，并与上游需求减少同事务处理，因此不增加履约缺口。

以后确需重新使用线下制品时，必须以新的“线下制品接管”业务重新进入系统并引用原移交事实；该重新接管能力不属于一期。

## 6. 作业计划与工作量评估

### 6.1 任务类型

- `NORMAL_PRODUCTION`：员工当天的正常生产安排，是承载当天某一个生产工序工作的任务容器；一个任务只能对应一个工序，但可以包含来自多个订单、多个产品的生产明细；同一员工同一工作日期最多一个有效正常生产任务；`NEW_PRODUCT` 可安排制作及后续包装，`RETURNED_PRODUCT_REPAIR` 只可安排修复完成后的后续包装，不得以普通制作任务新增制品；
- `EXTRA_PRODUCTION`：只用于制作工序的额外生产安排；超额任务的任务工序固定为 `MAKING`，任务内可以包含来自多个订单、多个产品的制作明细；同一员工同一工作日期最多一个有效超额任务，并且必须先存在同一员工同一日期、工序同为 `MAKING` 的有效正常生产任务；“超额”表示员工在正常制作任务之外完成的额外制作，允许个人或小组当日累计工作量评估为 `OVER_STANDARD`，但不允许超过订单需求、补产缺口、来源可安排数量或商品单日产能；一期只记录超额任务、评估结果和实际产量事实，不计算或生成激励金额；
- `REPAIR`：只关联一个原不合格来源；返工工序为制作时执行修补，返工工序为后续包装工序时重做该包装工序，完成后重新核验；返工任务不能作为员工当天唯一的作业安排，创建或调整返工任务前必须存在同一员工同一工作日期的有效正常生产任务；返工任务不设置每日唯一槽位，同一员工同一工作日期可以安排多个返工任务；
- `OTHER_TASK`：打包发货等不改变生产阶段的工作，不关联生产来源；同一员工同一工作日期最多一个有效其他任务，并且不能与正常生产任务共存。由于超额任务和返工任务都必须依赖正常生产任务，因此其他任务也不能与超额任务或返工任务共存。

只有 `NEW_PRODUCT` 需求的制作工序允许创建 `EXTRA_PRODUCTION`。捏毛装袋和缝边剪袋只能根据上游工序已经产生并合格的实际数量安排普通 `NORMAL_PRODUCTION` 任务，不设置超额任务。`RETURNED_PRODUCT_REPAIR` 需要回到制作工序时必须使用 `REPAIR` 任务表达修补，禁止使用 `NORMAL_PRODUCTION + MAKING` 或 `EXTRA_PRODUCTION`；修补合格后的后续包装才可使用普通生产任务。

正式创建成功的任务直接进入 `ARRANGED`，不提供草稿。

### 6.2 任务明细与生产来源

生产任务是员工或小组某一工作日期、某一个工序的作业容器。一个生产任务必须且只能对应一个执行工序，但不绑定单一产品或单一商品方案。`NORMAL_PRODUCTION` 和 `EXTRA_PRODUCTION` 均可以包含多条生产任务明细；不同明细可以来自不同订单、不同产品、不同商品快照和不同方案快照，但全部明细必须执行任务头确定的同一个工序。不同商品方案的交付终点可以不同，因此目标工序仍由各任务明细分别保存。

任务头保存任务类型、工作日期、执行主体、唯一执行工序、任务状态和安排版本；任务头还可以保存由明细汇总得到的计划作业数量和任务标准秒数，但不得保存单一产品或单一方案来代表全部明细。每条生产任务明细独立保存：

```text
产品编号
商品快照引用
商品方案编号及方案快照引用
目标工序
计划数量
明细标准分钟
明细顺序
```

每条任务明细直接对应一个生产需求和一个当前履约生产来源，并冻结需求类型、物理根来源以及由该来源确定的订单、产品、商品快照、方案及目标工序。一个明细不能再合并多个订单来源；同一产品来自不同订单或不同生产来源时，必须在新建任务时拆成不同明细。同一个任务中的不同明细可以具有不同的订单、产品、商品快照、方案及目标工序，但执行工序必须与任务头一致。

任务和明细必须同时满足：

```text
任务计划总数量 = 任务内所有明细计划数量之和
明细计划数量     = 该明细对应生产来源的本次安排数量
任务标准秒数     = 计算中心对所有生产明细分别计算后汇总的标准秒数
```

任务计划总数量是该任务同一工序下各产品明细作业数量的汇总值，用于任务展示、负载计算输入校验和数量守恒检查；实际制品数量及所在阶段以生产来源数量投影和生产事实为准。

#### 6.2.1 工作量公式口径

```text
生产/修复明细基准秒数
= 明细计划数量 × 该明细冻结商品/方案的工序单件标准分钟 × 60

个人生产或修复任务标准秒数
= Σ 任务明细基准秒数

小组生产或修复任务标准秒数
= ceil(Σ 任务明细基准秒数 ÷ 小组效率因子)

其他任务标准秒数
= 命令直接录入的整个任务预计经过分钟数 × 60
```

任务工作量使用计划数量；最终工资和生产材料来源使用核验后的完成数量。商品快照中的单件标准分钟、员工每日有效分钟和其他任务录入时间仍以整数分钟保存；生产模块将其作为计算输入，由计算中心统一换算为整数秒。任务标准秒数、成员已占用秒数和剩余有效秒数作为结果与负载投影保存、累加和比较。小组生产/修复任务先汇总全部明细基准秒数，再由计算中心整体除以小组效率因子一次并向上取整到秒；小组标准秒数作为经过时间计入快照成员的日期负载，不乘成员人数。其他任务的录入分钟直接乘 60，不应用小组效率。

`EXTRA_PRODUCTION` 的任务工序固定为 `MAKING`，各明细可以是不同产品，且只能使用 `NEW_PRODUCT` 来源。`NORMAL_PRODUCTION + MAKING` 同样只能使用 `NEW_PRODUCT` 来源；`RETURNED_PRODUCT_REPAIR` 的制作阶段只能通过 `REPAIR` 修补既有制品。`REPAIR` 为保证缺陷、返工及后续可能报废的追溯，只允许包含一条返工明细并关联一个返工来源。返工来源分为 `INTERNAL_DEFECT` 和 `AFTER_SALES_RETURN`：前者由生产核验中的返工处置生成，后者在订单售后已经完成退回接收和重入后，由返工申请参与事务基于退回制品来源生成；两者都必须保存当前履约生产来源、物理根来源、原缺陷/退回依据、返工工序、可用数量、已占用数量和已完成数量。`OTHER_TASK` 不包含生产任务明细，也不关联生产来源，而是使用独立的其他任务详情。

调整任务时可以新增、删除或修改尚未核验的任务明细。任务尚未产生任何有效核验事实时，可以修改任务工序，但必须重新校验全部任务明细、生产来源、工作量和产能；任务一旦产生有效核验事实，任务工序即不可修改。任何情况下都不得把已核验数量转移到其他明细或其他来源。核验正常生产任务、超额任务或返工任务时，直接按任务明细一次性录入最终结果，不允许只录入整个任务的合计数量。每条明细需要录入未完成数量，以及完成数量中的合格、返工/修补、线上报废数量；报废另录实际销毁或转线下去向数量；不再单独要求操作人员录入一个含义重复的“不合格总数”。核验命令只需要提交任务明细编号及该明细的最终核验结果；服务端通过任务明细取得已经冻结的生产需求和生产来源，不要求操作人员再次选择或拆分订单来源。每条生产执行事实仍须关联该任务明细对应的生产需求和生产来源。

### 6.3 个人任务

个人任务按“员工 + 工作日期 + 当日工作模式 + 生产任务槽位”执行约束：

```text
当日工作模式 PRODUCTION：必须存在一个正常生产任务，可以同时存在依赖它的超额任务和返工任务
当日工作模式 OTHER_TASK：可以安排其他任务，但不能存在正常生产任务、超额任务或返工任务

NORMAL_PRODUCTION 槽位：最多一个有效任务
EXTRA_PRODUCTION  槽位：最多一个有效任务
OTHER_TASK       槽位：最多一个有效任务
```

创建、调整或取消任务时，生产模块必须原子维护员工当日工作模式。由于同一员工同一工作日期最多只有一个有效正常生产任务，并且一个任务只能对应一个工序，因此员工当天的正常生产只能负责一个工序；当天已经占用正常生产槽位后，不能再以第二个正常任务安排其他工序。个人任务直接校验执行员工；小组任务对小组快照中的每名成员执行相同校验，只要一名成员发生模式或槽位冲突，整个任务就不能创建或调整。

`OVER_STANDARD` 只是计算中心返回的工作量评估结果，不是超额任务类型，也不能代替 `EXTRA_PRODUCTION`。超额任务不能脱离正常生产任务单独存在：创建或调整超额任务时必须校验任务工序为 `MAKING`，并校验同一员工同一工作日期已经存在未取消且工序同为 `MAKING` 的正常生产任务；不要求正常任务已经核验完成。该依赖关系要求员工、工作日期和制作工序一致，但不要求正常任务与超额任务包含相同的产品、商品快照、方案或生产来源；两个任务分别按各自的任务明细取得产品、快照、工序标准和来源可安排数量并独立核算。返工任务与超额任务一样不能脱离正常生产任务单独存在。创建或调整返工任务时，必须校验同一员工同一工作日期已经存在未取消的正常生产任务；返工任务不能反向占用或补建正常生产任务槽位。同一员工同一工作日期可以存在多个返工任务，每个返工任务仍然只能关联一个原不合格来源，分别保存任务、核验和追溯链，并分别计入员工当日工作负载。在存在有效正常生产任务的前提下，超额任务与返工任务之间不设置互斥或组合数量限制；是否同时安排一个超额任务和一个或多个返工任务由管理员结合现场情况自行判断。系统只执行既有的任务槽位、工作量评估、来源数量和商品产能校验，不增加额外的组合禁止规则。取消正常生产任务、把正常任务调整到其他日期，或者把存在超额任务所依赖的正常任务改为非制作工序前，必须先取消、调整同日全部受影响的超额任务和返工任务，或者在同一事务同步处理。创建或调整其他任务时，如果执行员工当日已经存在正常生产任务、超额任务或返工任务，必须拒绝；反向创建或调整正常生产任务、超额任务或返工任务时，如果员工当日已经存在其他任务，也必须拒绝。

任务的 `work_date` 是任务内全部明细的作业日期和劳动归属日期；当任务工序为制作时，`work_date` 表示实际倒胶生产日期，核验时间是脱模并确认数量、质量的实际时间。由于倒胶后需要等待胶体凝固并脱模，制作任务允许在第二天或更晚核验，不要求在工作日期当天完成核验，也不要求先核验正常任务才能核验超额任务。延后核验不得改变原任务工作日期、员工日任务槽位或劳动归属日期。

```text
逐条使用生产需求冻结的商品/方案快照解析生产或修复标准；其他任务直接录入标准分钟，关联商品时取得并冻结商品当前其他任务引用
→ workforce.prepareReserve 先锁员工与标准活动守卫，再校验状态和工种资格
→ workforce 在员工及标准活动守卫保护下取得一致的员工和每日有效工作时间依据，快照在固定锁序末端固化
→ 汇总该员工当日已核验标准负载与未核验计划占用，口径见 6.4.1
→ calculation 评估个人工作量
→ 保存标准秒数、剩余秒数、评估结果和上游快照引用
```

### 6.4 小组任务

小组任务使用任务创建时取得的小组快照确定参与成员，并占用快照中每名成员同一工作日期的对应个人任务槽位：

```text
小组正常生产任务 → 占用每名成员的 NORMAL_PRODUCTION 槽位，并确定这些成员当天唯一的正常生产工序
小组超额任务     → 占用每名成员的 EXTRA_PRODUCTION 槽位，并要求每名成员当天已有工序为 MAKING 的有效正常生产任务
小组其他任务     → 占用每名成员的 OTHER_TASK 槽位
小组返工任务     → 不占用唯一返工槽位，但要求每名成员当天已有有效正常生产任务
```

只要任意成员的对应槽位已被个人任务或其他小组任务占用，或者任意成员不满足正常任务依赖和当日工作模式要求，整个小组任务都必须拒绝创建或调整。小组任务一旦发生有效核验，成员当天的槽位即成为历史占用；后续取消剩余数量时转为 `RETAINED`。只有任务从未核验且整体取消或改期，才能原子释放原日期全部成员的对应槽位。

任务槽位只表示成员当天已经参与该类任务，不表示把小组共同产量拆分到成员。小组产量、质量和生产事实仍然归属于小组执行主体及任务所使用的小组快照。

```text
锁定小组、成员及所用标准的活动引用守卫
→ workforce 持锁校验小组并取得一致的成员和效率标准依据
→ 逐条使用生产需求冻结的商品/方案快照解析生产或修复标准；其他任务直接录入标准分钟，关联商品时取得并冻结商品当前其他任务引用
→ 持标准守卫取得每日有效工作时间依据，全部快照在固定锁序末端固化
→ 按小组快照成员逐人汇总当日已核验标准负载与未核验计划占用，口径见 6.4.1
→ calculation 评估小组工作量
→ 保存小组标准秒数、成员负载秒数明细、评估结果和上游快照引用
```

生产/修复小组任务由计算中心先将各明细基准分钟精确换算为秒，汇总后整体应用一次小组效率因子并向上取整到秒；其他小组任务直接录入小组整体预计标准分钟并精确换算为秒，不再应用效率因子。小组标准秒数计入快照中每名成员同日负载，小组可用秒数取成员剩余秒数最小值，不能乘以人数。

小组任务形成小组共同产出，不保存或虚构成员个人产量。

### 6.4.1 员工日期负载生命周期

员工日负载同时保存 `committed_standard_seconds`（已核验标准负载）与 `reserved_standard_seconds`（未核验计划占用），传给 calculation 的 `occupied_seconds` 固定为两者之和。该负载是标准工作量，不是打卡时长或工资金额；核验不会让已经完成的工作从当天负载中消失。

- 生产/修复按任务安排版本及冻结主体、标准分组：已核验部分取完成数量，未核验部分取尚有效的计划数量；调用 calculation 按原标准计算，不回读当前工时或小组效率。
- 个人任务按上述两部分分别汇总标准秒数。小组先分别汇总两部分基准秒数，再计算 `committed = ceil(已核验基准秒数 / 效率因子)`、`occupied = ceil((已核验基准秒数 + 未核验基准秒数) / 效率因子)`、`reserved = occupied - committed`；每组只在汇总后取整，避免逐明细取整累计误差。同组负载分别计入每名快照成员，不乘人数。
- 创建只新增计划占用；明细最终核验原子地移除其全部计划数量，将完成数量转入已核验部分，未完成数量不进入已核验负载。取消只释放未执行部分，已核验部分保留；两种投影与核验/取消事实同事务提交。
- 其他任务使用独立录入的整体标准秒数，不以商品数量反推工时；核验时将该标准负载由计划转为已核验，不宣称它是真实耗时。未执行即整体取消时才释放全部标准负载。
- 调整只改变未核验部分的计划占用；已核验部分始终留在原事实的工作日期、主体及标准版本下。更正有效核验事实时，在统一锁序内按替代事实重建相应日期负载，不重复累加。次日核验仍归原 `work_date`，不能挪到核验当天。
- 员工参与个人和不同小组的负载汇总到同一员工日期行；任务槽位、workforce 活动引用与已核验负载分别维护，释放活动引用不清除历史负载。

验收例：日标准 8 小时，正常任务已核验完成 6 小时，再安排 4 小时返工，必须返回 `OVER_STANDARD`，无覆盖权限时拒绝；不能因正常任务已结束而按剩余 8 小时判断。

### 6.5 超时评估

- `UNDER_STANDARD / WITHIN_STANDARD`：所有任务类型均允许正常创建；
- `OVER_STANDARD`：`NORMAL_PRODUCTION / REPAIR / OTHER_TASK` 默认拒绝，具有专门权限时可以显式覆盖并记录原因；`EXTRA_PRODUCTION` 不因该结果被拒绝，也不要求使用超时覆盖权限；
- `UNAVAILABLE`：缺少工时、资格、效率或有效时间依据，所有任务类型都必须拒绝。

超额任务虽然允许突破个人或小组的每日有效工作时间标准，但仍必须通过同员工同日期制作正常任务依赖、制作工序、真实需求、来源可安排数量和商品单日产能校验。评估为 `OVER_STANDARD` 时，生产模块仍然保存计算中心返回的标准秒数、有效时间依据、评估结果和输入快照，供任务核验、审计及财务结算读取。

生产模块只调用计算中心并保存评估结果，不实现或复制计算公式。

### 6.6 商品单日产能

同一商品同一工作日期，所有会新制产品的 `NEW_PRODUCT + MAKING` 已核验完成数量与未核验任务预留数量之和不能超过商品公开接口返回的单日最大产能，包括正常制作、补产制作和超额制作。修补虽然工序代码同为 `MAKING`，但它处理既有制品，不占用模具新制产能；包装和其他任务同样不占用该产能。一个任务包含多个产品时，生产模块必须按产品逐项取得产能上限、逐项占用并分别执行原子校验，不能使用任务总数量代替某个产品的数量。模具数量和每日生产批次必须参与商品侧产能结果；生产模块只维护各产品当日“已核验新制完成数量”和“未核验任务预留数量”两个分量，不自行计算产能公式。

```text
当日已用新制产能
= 已核验新制完成数量 + 未核验任务预留数量

当日可安排新制产能
= 商品单日最大产能 - 当日已用新制产能
```

任务核验时，计划中的完成数量从 `reserved` 转入 `committed`，未完成数量只释放 `reserved`；取消或调整未核验任务只释放 `reserved`。已经核验的新制完成数量不能因为任务进入终态而释放，否则会允许同日重复超产。商品日期产能守卫的唯一不变量是：`committed_new_making_quantity + reserved_new_making_quantity ≤ capacity_limit`；修改商品后如果当前上限不足以覆盖既有 `committed`，只阻止新增安排，不反向修改历史完成量。

### 6.7 可安排数量与禁止主动超产

一期生产必须具有明确的订单或售后业务来源，不允许为了备用、囤货或转入线下库存而主动安排超出需求的生产数量。

`NEW_PRODUCT` 需求的制作可安排数量按生产来源原子计算；`RETURNED_PRODUCT_REPAIR` 需求和内部质量返工只能从对应返工来源的可用数量安排，不能使用下式获得新制作数量：

```text
可安排制作数量
= 尚未制作且未被活动任务占用的原始需求数量
+ 尚未被活动任务占用的补产缺口
```

后续工序的可安排数量不得超过上一有效工序已经合格且尚未进入下一阶段、尚未被占用的数量。正常制作任务和补产任务都不得超过各自上限。任务明细只能提交一次最终核验结果，但允许其中存在未完成数量；未完成数量释放原任务占用并回到该生产来源的可安排数量，后续需要完成时必须通过新的任务明细重新安排。需要超出原需求的额外生产时，必须先由订单或其他正式业务来源增加生产需求。

并发创建或调整任务时必须锁定生产来源及数量投影，再原子占用可安排数量；不能依靠页面查询结果防止多个任务重复占用同一数量。

## 7. 生产执行、质量与数量守恒

### 7.1 创建任务

```text
锁定任务编号、执行主体活动引用守卫和员工日期任务槽位
→ workforce.prepareReserve 持主体、成员与标准守卫取得一致依据；商品/方案使用需求已冻结引用，关联商品的其他任务先取版本依据
→ 调用 calculation 分别计算各任务明细基准秒数并汇总任务工作量
→ 锁定员工日期负载；仅对 `NEW_PRODUCT + MAKING` 明细按产品稳定标识顺序锁定适用的商品日期新制产能
→ 按稳定标识锁定全部生产来源或返工来源，校验任务类型、需求类型、任务工序、每条明细与来源的一致性、可安排数量、禁止主动超产和目标阶段
→ 在快照唯一键阶段固化新增快照并调用 workforce.commitReserve；关联商品当前版本不匹配时整笔回滚重试
→ 写任务、直接关联生产来源或返工来源的任务明细、安排事实、评估记录、参与人引用、任务槽位和来源占用
→ 按员工、产品和来源分别更新负载与数量投影；只有 `NEW_PRODUCT + MAKING` 明细更新商品日期新制产能预留
→ 一次提交
```

任务与生产来源现在同属一个模块，不再使用原 `scheduling → production` 的准备/提交参与端口，也不再保存跨模块的排班—生产关联表。

### 7.2 调整任务

调整日期、主体、任务工序或任务明细时，保留原安排事实、任务明细安排事实和评估记录；先按固定锁序一次性锁定新旧任务、人员活动守卫、负载、适用的新制产能及来源键的并集，重新读取并校验影响集合与成员/标准版本，再在同一事务内释放旧的未核验计划负载（已核验负载留在原日期和主体）、仅适用于 `NEW_PRODUCT + MAKING` 明细的旧新制产能预留和尚未核验的旧来源占用，逐明细校验、评估并建立新安排，最后保存快照引用和活动预留。不得先释放旧占用后再补拿新锁；任一校验失败须回滚全部变更。任务工序只能在任务尚未产生任何有效核验事实时修改；修改后全部明细必须统一继承新工序并重新校验。已核验数量不得转移到其他任务明细或其他来源，不得覆盖历史评估。

### 7.3 取消任务

取消任务只取消尚未核验的剩余安排，并追加取消事实，不删除任务。取消时释放未核验剩余部分对应的计划负载、适用于 `NEW_PRODUCT + MAKING` 明细的商品新制产能预留、活动主体引用和生产/返工来源占用；已有有效核验事实继续保留，不因任务取消而失效。已经核验的生产事实存在错误时，必须通过生产事实更正处理。

员工日工作模式和唯一任务槽位按是否已经发生生产事实分别处理：

- 任务从未产生有效核验事实即整体取消或改期时，可以释放原日期对应模式和槽位；
- 任务已有任一明细完成最终核验后再取消剩余明细时，只释放未执行部分的计划占用，原日期的工作模式和任务槽位保留为 `RETAINED`，不能再创建第二个正常、超额或其他任务；
- 已核验标准工作量继续计入原日期 `committed_standard_seconds`；生产/修复未完成或取消部分不计入已核验标准负载，其他任务按 6.4.1 处理；
- workforce 的活动引用在任务进入终态后释放，因此不会永久阻止员工或小组后续修改；生产模块自己的历史日槽位不因此删除。

### 7.4 核验生产/修复任务

```text
按统一锁序锁任务及明细 → workforce 原活动守卫 → 员工日期模式和负载 → 适用新制产能 → 明细关联的生产来源及阶段
→ 校验每条任务明细此前从未核验，本次提交是该明细唯一一次最终核验
→ 校验：计划数量 = 未完成数量 + 完成数量
→ 校验：完成数量 = 合格数量 + 返工/修补数量 + 线上报废数量
→ 将未完成数量释放回该生产来源的可安排数量；未完成不属于不合格，不生成缺陷、责任或处置事实
→ 按任务明细的完成数量记录生产执行事实，并带出明细对应的生产需求和生产来源
→ 按任务明细记录合格质量事实，并以“返工/修补 + 线上报废”之和记录不合格质量事实
→ 将不合格质量事实按缺陷原因分组记录缺陷事实，每条缺陷事实只包含一个原因及对应产品数量
→ 校验缺陷事实数量均大于 0，且有效缺陷事实数量合计严格等于返工/修补与线上报废数量之和，保证每个实际产品只归属一个原因
→ 将每条缺陷事实数量全部分配为返工/修补或线上报废；报废明细另选实际销毁或转线下去向，去向数量合计必须等于线上报废数量
→ 仅为每条报废处置明细记录明确责任或免除结论，责任数量等于该报废明细数量且不受去向影响；返工/修补不生成扣款责任来源
→ 对返工/修补处置生成可追溯、可占用的返工来源，并保存原生产来源、原缺陷事实和返工工序
→ 对线上报废记录唯一终态退出；去向为转线下时追加关联同一次退出的移交事实，不重复退出、不重复增加缺口
→ 在同一事务写入质量、处置、来源退出、线下库存移交和责任事实
→ 正常生产、超额生产和修复任务按实际完成数量写入不含金额的材料成本来源项；修复按返工工序引用需求冻结的生效生产依据，不使用模板默认供料方替代实际约定
→ 更新工序阶段和数量投影；线上报废按需求类型形成一次补产缺口或修复终止缺口，转线下只记录去向，未完成数量只恢复原来源可安排数量
→ 按 6.4.1 原子移除该明细计划占用并将完成工作量转入原工作日期已核验负载；释放适用的新制产能预留和来源占用，已核验新制完成数量转入当日已用产能
→ 无剩余数量时结束活动引用；仍有剩余数量时保留剩余安排
→ 一次提交
```

一次核验可以选择任务中的一条或多条尚未核验明细，但每条被选中的明细只能提交一次最终结果，不允许以后继续核验同一明细。每条明细必须分别满足：

```text
计划数量 = 未完成数量 + 完成数量
完成数量 = 合格数量 + 返工/修补数量 + 线上报废数量
不合格数量 = 返工/修补数量 + 线上报废数量
```

例如计划 100、实际完成 98 时，可以记录未完成 2；完成的 98 再明确其中合格、返工/修补和线上报废各有多少；报废部分另填实物去向，不再把转线下加进完成数量。未完成的 2 不属于不合格，也不形成报废或履约缺口，而是释放占用并回到原生产来源或返工来源，后续如需继续处理必须创建新的任务明细。不同任务明细之间不得合并录入或相互抵消。任务状态由全部任务明细汇总得出：部分明细已经提交最终核验、仍有其他明细尚未核验时进入 `PARTIALLY_VERIFIED`；全部明细均已核验时进入 `VERIFIED`；尚未核验的明细可以整条取消，已有生产事实继续有效。制作任务可以在工作日期后的任意业务日期核验；生产事实同时保存任务明细、原任务工作日期和实际核验时间，三者不得互相覆盖。

生产执行事实必须直接包含生产需求编号、生产来源编号、任务编号、任务明细编号、产品编号、商品和方案快照引用、工序、执行主体、实际数量、发生时间及更正链信息。

### 7.5 核验其他任务

其他任务不产生工序流转、质量事实或生产数量事实。每个其他任务必须保存工作内容和直接录入的执行主体整体标准分钟：

- **不关联商品**：不填写计划数量，只记录完成结论、结果说明和核验时间，不自动产生计件工资来源；
- **关联商品**：安排时取得并冻结商品当前快照、其他任务单件人工费和计划数量；核验时满足“计划数量 = 完成数量 + 未完成数量”，只有完成数量生成劳动来源；
- 其他任务更正同样发布劳动来源 `REVERSE / APPLY`，不能只修改当前结果。
- 核验同事务按 6.4.1 将整体标准负载由计划转为已核验；核验事实保存安排版本和工作量评估引用，更正时据此重建原工作日期负载，不能从当前任务头推断旧主体或旧标准。

### 7.6 质量、缺陷、返工和报废

- 质量不合格不等于报废；
- 工序核验后的合格制品可以继续履约；线上报废制品可销毁或转线下作瑕疵品处理。订单减量等业务也可以把未报废制品转线下，不能由去向反推质量；
- 不合格制品在线上只选择无责任返工或报废；报废再选择实物去向。人工判断可以满足当前订单交付要求时应核验为合格；只适合线下瑕疵品出售的不应伪装成线上合格；
- 每个实际产品只能归属一个由生产作业模块维护的标准缺陷原因，不能让同一件产品同时计入多个原因；
- 系统一期不为制品建立单件序列号；同一次核验可以包含不同缺陷原因，但必须按“缺陷原因 + 数量”形成缺陷事实，所有有效缺陷事实数量合计必须严格等于对应不合格数量；
- 每条缺陷事实只保存一个缺陷原因；选择“其他”时必须填写说明；标准原因被停用后不得用于新核验，但历史事实继续展示核验时保存的原因编号和名称；
- 缺陷原因只用于生产质量追溯，一期不设置缺陷等级，也不根据缺陷原因自动计算工资、扣款、赔偿或成本；
- 核验提交时必须为全部不合格数量确定处置，不提供“待处置”状态；
- 线上不合格处置只允许 `REWORK_REQUIRED / SCRAPPED`，同一条缺陷事实按数量拆分为返工和报废；报废明细必须另存 `physical_destination = DESTROYED / TRANSFERRED_OFFLINE_INVENTORY`，不同去向拆为明细；
- 每条缺陷事实的有效处置数量合计必须严格等于该缺陷事实数量，不能少处置或超额处置；
- 返工是对原制品进行修复，必须关联原缺陷事实、返工处置事实和生产来源；返工不生成新制品、不增加生产数量，修复后必须重新核验；
- 返工可以选择已经历工序中的具体返工工序；选择制作工序时固定执行“修补”，选择捏毛装袋或缝边剪袋时固定执行对应包装工序的“重做”；
- 人工判断可以继续使用的制品应直接核验为合格；系统不保存“不合格但允许继续使用”的矛盾状态；
- 无法修补至当前订单要求的制品应线上报废，再确定实际销毁或转线下去向；无论去向都不能继续用于原订单生产或交付。其交付缺口通过上游需求允许的补产或售后变更解决，重新制作不是原制品返工；
- `NEW_PRODUCT` 需求核验中的线上报废（含转线下去向）会按处置数量自动更新原需求的补产缺口，但不会自动创建补产作业任务；排班人员必须针对该缺口重新安排 `NORMAL_PRODUCTION + MAKING`，并重新执行人员负载、小组负载和商品单日产能校验；
- 补产继续使用原生产需求、原生产来源以及原商品/方案快照，不创建新的生产需求；订单减量、取消或售后义务取消事务产生的转线下库存不形成履约缺口，而是随上游需求数量同步减少；
- `RETURNED_PRODUCT_REPAIR` 需求核验中的线上报废（含转线下去向）形成修复终止缺口，生产模块不得继续安排制作来填补；订单售后模块必须在同一业务变更中减少或取消对应修复义务及修复需求，并在决定补发时另建补发义务和 `NEW_PRODUCT` 需求；
- 履约缺口不能在生产模块内手动忽略、关闭或核销；新制补产缺口只能由正常补产达到目标工序或上游正式减少需求消除，修复终止缺口只能由售后义务变更消除；
- 返工/修补属于无责任返工，只记录缺陷原因、数量、返工工序和处置，不要求指定责任人，不生成责任扣款来源，也不占用每人每月胶水免扣重量。返工劳动、材料及质量事实仍正常保留，“不扣款”不等于没有生产成本；
- 只有报废处置进入责任认定及成本逐项参考流程。每条报废处置明细在核验提交时同步确定一个责任主体或免除结论，不提供报废“待认定”状态；责任数量等于该报废明细数量，而非整条缺陷数量。相同缺陷中有不同报废责任主体时，应拆成互不重叠的报废处置明细；
- 转线下库存只是实物去向：因线上报废而移交时保留报废责任，纳入逐项成本参考及胶水减免；因订单减量等非报废原因移交时不新增报废责任。不能根据去向直接推导扣款或免扣资格；
- 责任主体只允许员工、小组、工作室或客户；客户责任用于客户提供的材料或客户要求直接导致质量问题的场景，不使用含义不明确的“外部责任”；
- 个人任务认定员工责任时，责任员工必须是该任务的个人执行主体；不得认定为无关员工或小组；
- 小组任务可以认定为执行小组的共同责任；能够明确到具体成员时，也可以认定为任务所用小组快照中的成员责任，不能选择快照外员工；
- 报废责任录入时，个人任务可以预填执行员工，小组任务可以预填执行小组；预填只用于减少录入，必须由核验人员主动确认，系统不得直接根据执行主体自动认定责任。返工和非报废业务移交不显示必填责任输入；报废选择转线下仍须保留报废责任/免除结论；
- 生产模块只记录员工责任或小组共同责任事实，不计算扣款，也不把小组责任分摊到成员；成员参考分摊和工资核算时的人工处理明细属于财务结算模块能力，生产不接收处理金额；
- 质量、处置与责任事实分别保存，即使在同一核验事务中产生，也必须能够独立更正；
- 责任可以更正或免除，原责任事实不得覆盖；责任更正不影响已经确定的返工、转线下库存或报废处置；
- 返工、转线下库存、报废和责任只记录业务事实，不在本模块计算工资扣款或成本金额。

同一缺陷数量 5 件、其中返工 3 件和报废 2 件时，只为报废的 2 件记录责任，不能以全部 5 件计算报废成本参考。返工后来合格不产生责任；返工后来确实报废时，基于新的报废处置认定责任，不能追溯把此前无责任返工也计为扣款来源。

报废 2 件即使全部转线下作瑕疵品出售，报废数量和责任候选数量仍为 2，不变为零，也不增加成 4。报废责任属于质量处理维度；线下售价、是否卖出及回款不参与一期责任参考，也不用于反冲既有生产成本。

#### 7.6.1 售后退回池直接报废的责任

退回制品没有进入修复任务，也可以在售后处置命令中直接线上报废。该命令由 orders 拥有，通过 `ProductionAfterSalesReturnParticipant.prepareDisposition / commitDisposition` 在同一事务保存生产侧池处置、责任/免除结论、来源上下文、唯一退出及可选移交，随后由生产发布责任 Feed。不得为满足原任务字段而伪造修复任务、核验、生产缺陷、劳动或材料事实。

责任来源使用带类型的联合引用：`TASK_DISPOSITION` 关联工序报废处置及其缺陷、任务和生产来源；`RETURN_POOL_DISPOSITION` 关联退回池报废处置及退回来源，前述任务处置、缺陷和当前任务引用必须为空。两类都必须是有效 `SCRAPPED`，数量等于所关联的报废明细；一条报废明细只对应一条有效责任链，不同责任或去向须拆分互不重叠的明细。售后问题描述、退款、赔偿或接收退回本身不能发布工资责任。

池内报废必须由经授权人员明确选择 `EMPLOYEE / TEAM / STUDIO / CUSTOMER / WAIVED`，不预选原制作人。认定员工或小组时必须选择同一物理根链路上的一条历史作业事实作为 `attribution_evidence_fact_business_id`，填写归责原因并保存其安排主体快照；员工须是该事实个人执行者或历史小组成员，小组须是该事实的执行小组。跨批次、无关任务、当前小组成员不能作为证据；多条历史作业分别归责时按数量拆明细。无法确定个人或小组责任时必须明确工作室、客户或免除结论，不能由系统替负责人认定。客户责任须校验本售后客户，免除须填原因；已离职人员或停用小组的有效历史快照仍可被归责，不因此新增活动人员占用。

两类来源都保存不可变 `source_context_ref`：记录物理根、原订单/售后及接收引用、历史商品/方案/生效生产依据引用与指纹、相关阶段事实及归责证据。它只冻结可追溯依据，不选择报废成本项目、不计算金额。生产公开查询提供上下文；财务不得联表或回读当前商品替代历史。若历史链缺少计价依据，责任事实仍可保存，但上下文须列出缺失项，财务参考为 `INCOMPLETE` 而非伪造零成本。

池内直接报废必须选择处置业务日期，不早于退回接收时间按工作室时区折算的日期、不晚于工作室当前业务日期；该日期单独保存，责任 Feed 以此归月，实际录入时间另存 `occurred_at`。任务报废仍使用任务工作日期。责任更正保持原处置业务日期，按原、新责任版本发布 `REVERSE / APPLY`；不得把责任更正变成新的物理退出。已转线下时仍只允许独立责任主体/免除更正，不能改变数量、处置、日期或去向。两类初始报废都必须原子保存责任结论，后续责任更正统一使用 `production.responsibility.manage`。

### 7.7 数量守恒

数量守恒必须同时通过两套投影校验，不再使用含义不明确的“初始数量 + 有效增加”表达：

```text
需求义务账：
当前有效需求数量
= 待执行数量
+ 系统内处理数量（含生产、修补或重做）
+ 已达目标工序待交付数量
+ 已完成交付数量
+ 履约缺口数量

物理制品账：
累计有效制作产生数量
= 系统内仍存制品数量
+ 已消费制品数量
+ 已实际销毁制品数量
+ 已转线下库存制品数量
```

其中累计有效制作产生数量只由正常或超额制作任务的完成数量增加；包装、修复和售后退回重入只移动原制品。“已消费制品数量”是当前仍在系统外的净余额，不是历史消费事实累计值：有效退回重入会从该余额扣减，再次交付或原样退还产生的新消费会重新增加，但历史消费事实均保留。来源投影必须满足：

```text
来源当前工序总量
= 进入当前工序有效数量
  + 有效返工/修补回流数量
  - 本来源未制取消数量（仅尚未制作的制作入口）

来源当前工序可用总量
= 来源当前工序总量
  - 合格流转数量
  - 返工/修补转出数量
  - 实际销毁数量
  - 转线下库存数量
  - 已消费数量

来源当前可安排数量
= 来源当前工序可用总量 - 活动任务预留数量

来源当前工序可用总量
= 来源当前可安排数量 + 活动任务预留数量
```

需求义务账按全部有效需求减量更新；来源阶段账不能把相同减量再扣一遍。已制移交数量只通过“转线下库存数量”退出物理来源，包装、修复、退回制品池及已达目标的来源不扣未制取消量。补产缺口取消只减少缺口及相应尚未制作入口，不扣已经报废的历史物理数量；尚无补产入口的缺口不能虚构入口扣减。

数量示例：已制作且未占用的 10 件减量 2 件并同步转线下库存，剩余物理可用量为 `10 - 2 = 8`，不是 `10 - 2 - 2 = 6`；尚未制作的 10 件减量 2 件，待制义务为 8 件，不生成移交事实也不改变累计制作数量；混合减量 5 件可以分为未制取消 3 件、已制移交 2 件，每一部分仅影响对应的义务及阶段账。

质量核验例：制作完成 10 件，8 件合格、2 件线上报废并转线下。完成量与劳动/材料来源量均为 10，线上报废为 2，物理账为系统内 8 + 线下 2 + 实际销毁 0；需求账为待交付/处理中 8 + 缺口 2。不得把报废 2 与线下 2 相加，造成完成量 12、来源余额 6 或缺口 4。另一例：报废 2 件中销毁 1 件、转线下 1 件，物理账为 8 + 1 + 1，责任仍只按报废 2 件。

其中“可用总量”按当前来源阶段定义，不能把不同阶段或不同物理根重复相加。来源占用满足“可用总量 = 可安排数量 + 活动任务预留数量”，不得重复计入需求义务账和物理制品账。占用、核验、处置和消费均不得使任一数量为负。已被发货或售后消费的来源不能直接回退阶段，必须由订单退回接收事务登记重入，或先更正下游消费业务。履约缺口是生产需求当前投影，不是新生产需求；它只能由终态损失和上游有效需求变化重建，不能手动关闭。`NEW_PRODUCT` 的履约缺口可由原需求补产消除；`RETURNED_PRODUCT_REPAIR` 的履约缺口只能通过售后义务变更减少原修复需求，并视决定另建补发需求，生产模块不得把修复缺口自动转成制作任务。

### 7.8 更正

原生产事实不得覆盖。更正命令必须引用原事实，检查后续工序、质量、处置和消费影响，追加失效及替代事实，并重建受影响数量投影。

线下移交一旦提交即表示制品已脱离系统监管，按不可逆终态处理：

- 移交数量、来源、物理根、工序、上游业务关联、移交人、接收人、说明和业务日期全部属于不可变移交事实；一期不提供修改、冲销、取回、再次安排、再次交付或重新纳入系统的命令。
- 订单减量、取消或售后义务变更不得回写或反转已经完成的线下移交；订单只能基于移交发生前仍受系统监管的数量处理变更，已移交数量不再作为可用履约来源。
- 不定义 `prepareCorrection / commitCorrection` 或 `correctMetadata` 线下移交更正接口。若录入前发现数量、来源或资料错误，必须取消本次尚未提交的操作并重新核对；提交后只能通过线下管理流程处理，超出一期系统边界。
- 通用核验、更正和处置命令如果会修改、撤销已提交移交或恢复其数量，同样必须拒绝；不能凭 `production.correct` 绕过终态。独立责任事实更正只改变责任链，不得回写移交事实或恢复制品。

责任更正遵循独立的追加式事实链：

- 更正人必须具有 `production.correct` 权限并填写更正原因；
- 同一事务将原责任事实置为失效，并追加关联原事实的新责任事实，不允许直接更新或删除原记录；
- 新责任事实必须引用有效的报废处置明细，数量等于该报废明细数量，并重新校验员工、小组、工作室、客户或免除责任的主体规则；
- 责任更正不改变已经确定的缺陷原因、返工、转线下库存或报废处置；其他事实错误必须通过各自的更正命令处理；
- 生产模块不查询财务结算表，也不因工资已经核定或支付而拒绝保存真实责任更正；
- 每次更正都增加责任来源版本，并通过公开查询暴露原版本失效和新版本生效；财务结算模块自行决定冲销原结果、重新计算或在后续结算期调整；
- 生产模块只负责责任事实及其版本，不计算任何工资、扣款、赔偿或调整金额。

核验/处置更正使原报废不再有效时，必须在同一事务撤销其责任来源并发布原版本 `REVERSE`；替代处置为返工或合格时不发布新的责任 `APPLY`。报废数量或责任变化时，发布旧版本 `REVERSE` 和新版本 `APPLY`，新数量取替代报废明细数量；返工更正为报废时才首次产生报废责任来源。财务据有效报废集合重新计算参考和当月胶水减免，不能把重跑当作再次消耗额度；已核定实际工资仍不自动更改。

上述更正不得绕过线下移交终态：报废已关联有效线下移交时，线上报废结果、数量、去向和对应退出均不得改为合格或返工，不允许恢复系统内数量；仅独立责任主体/免除结论可按责任更正链处理，不能改动移交及已固定报废数量。未移交的错误报废记录也只能更正真实录入错误，已实际销毁制品不得因更正恢复可用。

### 7.9 期初事实与上线后事实衔接

期初初始化将生产来源的接管数量分布到 `NOT_STARTED`、方案内有效工序阶段、`REWORK_REQUIRED`、`SCRAPPED` 或已达到目标工序的状态。它不代表上线前完整生产历史，也不得伪装成普通任务核验事实。

期初初始化和更正均须锁定生产需求、生产来源及其数量投影后一次提交。初始化完成后：

- `NOT_STARTED` 和尚未达到目标工序的可用数量可以进入正常任务安排；
- 待返工数量只能进入对应修补或重做任务；
- 报废制品无论销毁或转线下均不可再次占用或消费；线上报废按需求类型只形成一次缺口：`NEW_PRODUCT` 形成可由后续正常制作解决的补产缺口，`RETURNED_PRODUCT_REPAIR` 形成必须由售后义务变更解决的修复终止缺口；上游需求减量事务产生的转线下库存不形成缺口；
- 已达到目标工序的合格数量可以被订单模块正常消费；
- 所有上线后事实必须引用该生产来源，并与期初事实共同满足数量守恒。

### 7.10 生产需求减量事务

```text
orders 锁定订单和约定组
→ production.prepareChange 只读发现影响任务，再依统一锁序锁任务、workforce 原预留守卫、日期模式、负载、产能及需求/来源
→ 持来源锁重查影响任务集合与版本；不匹配则整笔回滚重试，禁止在此补拿任务或人员锁
→ 分类计算未制取消、已制移交及不可减少数量，生成任务调整方案，校验分类之和等于需求减量
→ 对已生产未消费的多余数量要求 orders 同时提交转线下库存明细；缺少去向时整体拒绝
→ orders 写新约定版本、订单变更事实和移交业务关联
→ production.commitChange 写带分类数量的需求减量事实及已制部分对应的转线下库存事实
→ 缩减未核验任务明细，重建任务评估、负载、产能和数量投影
→ 剩余数量为零的任务追加取消事实
→ 一次提交
```

预检结果只在当前事务和锁定依据下有效，不能保存后跨事务直接提交。重复命令通过订单变更业务标识和生产变更守卫复用原结果。缩减既有任务必须在同一 orders 事务中调用 workforce 活动预留调整/释放参与接口，仅减少原占用，不创建任务或更换主体。任何失败都必须同时回滚订单变更、任务调整、负载、产能、人员预留和转线下库存。

### 7.11 售后义务变更与退回制品处置

售后只调整由售后案例派生的义务、退回制品来源、修复需求和补发需求，不修改原订单、原发货或原生产事实。

客户退回不是“重新生产”，而是原制品从客户侧重新进入系统。订单确认退回时必须调用生产参与接口，依据最近一次交付明细、交付来源类型、对应消费事实和物理根建立售后退回制品来源，并追加退回重入事实：物理制品投影将对应数量从“当前已消费”移动回“系统内待处置”，累计制作产生量不变，原交付和原消费事实仍永久保留。

- 客户尚未退回制品且尚未建立修复生产来源时，可以变更或取消返工义务；
- 工作室确认收到退回制品后，取消返工义务必须在同一事务处理全部相关数量：仍在退回制品池的可用数量直接确定为原样退还客户、线上报废并指定去向，或非报废义务释放转线下；已路由但尚无不可逆事实的数量先写反向路由事实释放回池，再完成处置；已形成修复终止缺口的数量按修复失败转路线处理；不允许留下无归属数量；
- 已安排但尚未核验的修复任务可以缩减或取消，并同步释放负载、活动引用和来源占用；修复任务不占用商品新制产能，取消任务也不等于处置退回制品；
- 已核验的修补、重做、质量、责任和处置事实永久保留；仍在系统内且未消费的制品可按需求减量规则解除占用并同事务非报废移交，不反向路由回池。无法合法处理的数量阻止取消，分支核对见订单模块 13.2.1；
- “修复失败转路线”只允许转换 `RETURNED_PRODUCT_REPAIR` 当前投影中的 `fulfillment_gap_quantity`；已修复完成、处理中、已达目标待交付和已交付数量均不得被该操作减少或迁移；
- 转路线数量可以小于当前修复终止缺口。每次转换后只减少等量修复义务、修复需求和缺口；未转换缺口继续保留并阻止原返工义务完成，直到后续再次明确路线；
- 补发义务的减量和取消使用订单生产需求减量规则；已生产未交付的补发制品必须保留义务、完成交付，或者同步转线下库存；
- 已经售后交付的数量必须先更正售后交付并冲销生产消费事实，才能重新变更对应义务。

其中原样退还客户由 orders 的售后交付命令调用生产退回制品处置参与接口，在同一事务把退回制品池数量标记为 `RETURN_TO_CUSTOMER` 并写入以退回制品池为来源的消费事实；线上报废写退回制品处置及唯一终态退出，去向为实际销毁或转线下；转线下时追加关联同一退出的移交事实。非报废义务释放使用 `RELEASE_FROM_OBLIGATION + TRANSFERRED_OFFLINE_INVENTORY`，保留原质量；任一组合只增加一次池内 `disposed_quantity`。以后再次退回时必须引用这次最新售后交付及其消费事实。售后义务事实、交付事实、退回重入、生产处置/消费/移交事实必须在对应事务中完整提交，任一步失败全部回滚。

## 8. 状态设计

### 8.1 生产需求

- `ACTIVE`：仍有未完成数量；
- `SATISFIED`：目标工序合格数量已满足，履约缺口为零；生产模块不能手工设置该状态；
- `CANCELLED`：业务来源已有效取消，且不存在禁止取消的下游事实。

状态由有效事实推导，可保存为当前投影。

### 8.2 作业任务

- `ARRANGED`：已安排且有效核验数量为零，存在活动引用和计划占用；
- `PARTIALLY_VERIFIED`：至少一条任务明细已经提交唯一一次最终核验，仍有其他任务明细尚未核验；明细中的未完成数量不代表该明细还能再次核验；
- `VERIFIED`：安排数量已经全部核验，活动引用和计划占用结束；
- `CANCELLED`：未核验的剩余安排已经取消，活动引用和剩余计划占用结束；已有核验事实仍然有效。

一期不提供“开始任务”命令，不保存缺乏设备、考勤或计时依据的 `IN_PROGRESS` 状态。允许：`ARRANGED→PARTIALLY_VERIFIED→VERIFIED`、`ARRANGED→VERIFIED`、`ARRANGED/PARTIALLY_VERIFIED→CANCELLED`。禁止从 `VERIFIED` 直接退回；生产事实错误必须通过更正链处理。

### 8.3 质量和处置

质量、线上处理结果、实物去向和活动占用分别管理，不压缩成单一巨大状态枚举：

```text
质量：PENDING / QUALIFIED / DEFECTIVE
线上处理：QUALIFIED / REWORK_REQUIRED / SCRAPPED
实物去向：IN_SYSTEM / DESTROYED / TRANSFERRED_OFFLINE_INVENTORY / CONSUMED
活动占用：AVAILABLE / RESERVED
责任：EMPLOYEE / TEAM / STUDIO / CUSTOMER / WAIVED
```

`ArrangeTaskCommand` 和 `RescheduleTaskCommand` 必须携带有序任务明细；正常/超额明细指定生产来源，返工明细指定返工来源。服务端只按来源已冻结的商品/方案快照解析工序标准，不读取商品当前工时。`VerifyTaskCommand` 按任务明细提交唯一一次最终结果，并在同一命令中携带全部缺陷原因、返工或线上报废处置，以及报废处置明细的实物去向和责任/免除结论；返工不要求责任输入，线上报废无论去向均提交责任/免除结论，非报废业务移交不得伪造扣款责任。初次核验不允许先保存质量、再调用独立接口补报废责任或处置。服务端校验数量方程并从任务明细取得全部来源。质量、责任和处置的独立应用服务只用于已核验事实更正。

`prepareReduction / commitReduction` 处理售后义务缩减中的可逆路由释放及已制非报废移交，返回分支数量、路由/需求变更/退出引用和阻塞原因；锁序沿用“售后义务缩减既有任务”。只减少已有安排，不新增任务或人员占用。修复缺口释放必须调用独立的 `prepareRouteChange / commitRouteChange`，其准备结果必须按原终态明细给出本次分配量并校验剩余可转换量。orders 按订单模块 13.2.1 合并各参与结果，任一分支失败整体回滚。

`ProductionAfterSalesReturnParticipant` 在退回接收事务中依据最近交付明细、交付来源类型和消费事实登记售后退回制品来源及重入事实，不改写原消费事实；在原样退还、线上报废并指定去向，或非报废义务释放转线下事务中，通过 `prepareDisposition / commitDisposition` 原子减少池内可用数量并写生产侧处置、消费或移交事实。`ProductionAfterSalesDemandParticipant` 只在后续售后命令事务中基于该退回制品来源建立 `RETURNED_PRODUCT_REPAIR` 需求/返工来源，或建立 `NEW_PRODUCT` 补发需求，不创建作业任务，也不选择执行人员。修复失败改为补发、退款、赔偿或结束时，orders 必须调用 `prepareRouteChange / commitRouteChange`：生产参与端校验修复终止缺口和不可逆事实，减少或取消原修复需求，并且仅在补发路线下原子建立独立 `NEW_PRODUCT` 需求；不得把修复需求改型，也不得在生产模块自行决定售后路线。售后提交后由生产排班人员通过普通任务安排能力选择日期和执行主体，不得在售后参与事务中新增 workforce 占用；缩减既有任务时仅按跨模块规则调用原预留调整/释放能力。退回制品完成修复并再次交付时，修复需求的已完成交付量增加，但原物理来源的累计制作量不增加。修复过程中发生线上报废（实际销毁或转线下）时只形成一次修复终止缺口，必须等待订单售后模块变更义务，不得自动排新制作任务。`ProductionOfflineInventoryTransferParticipant` 只记录单向移交，不提供仓库余额、取回或再次消费能力。

`ProductionLaborSourceFeed` 是追加式劳动来源数据流。正常、超额、修复和关联商品的其他任务核验首次发布 `APPLY`；事实更正同事务发布原版本 `REVERSE` 和新版本 `APPLY`。劳动来源数量固定为实际完成数量，即“合格 + 返工/修补 + 线上报废”，未完成数量不进入工资；责任扣减通过独立责任来源处理，不能从劳动来源中先行扣除。每项保存任务类型、主体及快照、商品/方案快照、工序、完成数量、业务日期和输入指纹，不返回工资金额。

`ProductionResponsibilitySourceFeed` 以追加式数据流独立公开责任认定、免除和更正，避免把“完成劳动”和“责任扣减”混成同一来源模型。首次责任认定发布 `APPLY(version=1)`；责任或报废数量更正时在同一生产事务发布 `REVERSE(affectedVersion=n)` 和 `APPLY(version=n+1)`；报废撤销为非报废时仅发布原版本 `REVERSE`。游标只由单调递增的 `feedSequence` 推进，消费者必须在整页持久化成功后提交游标；`feedItemBusinessId` 是财务幂等消费键，重复拉取不得形成重复结果。

责任数据流只发布报废处置关联的员工、小组、工作室、客户和免除责任事实，包含报废处置标识、`disposition_type = SCRAPPED` 和对应报废数量，不返回扣款金额；不发布返工或非报废业务移交扣款责任，线上报废后转线下的责任仍发布。报废被更正撤销时只发布原版本 `REVERSE`，不得为替代的非报废处置伪造责任。小组责任返回人工归责证据对应的历史小组快照引用，任务报废用本任务安排，池内报废用所选历史作业安排；财务需要到人处理时，通过 workforce 的公开快照接口读取成员，不得要求生产模块拆分金额。生产模块不查询工资核定或付款状态，财务模块使用责任链、来源版本和幂等守卫刷新待核定参考；已核定金额保持不变，需要补差时另行人工确认。

`ProductionMaterialCostSourceFeed` 输出 `NORMAL_PRODUCTION`、`EXTRA_PRODUCTION` 和 `REPAIR` 的已核定工序来源。首次核验输出 `ACCRUE`；更正原事实时输出 `REVERSE`，替代事实再输出 `ACCRUE`。来源数量固定为该明细完成数量：`合格 + 返工/修补 + 线上报废`，未完成数量不进入材料成本。所有来源均提供所属需求冻结的 `ResolvedProductionBasis` 及指纹，修复另明确返工工序与完成数量；财务按商品模块公开接口从该生效依据解析“当前工序、工作室承担、非人工”的历史单件成本，再调用 `calculation` 计算金额；产品级胶水/色浆在每条实际 `MAKING` 生产或修复来源中按该工序历史成本计算一次，包装工序不得重复取用，不能把“一笔预算内只归入制作明细”误解为整个产品生命周期只计一次。生产模块不得计算金额。

生产任务创建时先调用 `WorkforceActivityReservationParticipant.prepareReserve`，在主体、成员及标准活动守卫下重新取得一致的资格与版本依据，之后按固定锁序锁日期模式、负载、产能和来源，最后固化快照并 `commitReserve`。不得先取当前快照再预留。调整时锁新旧预留守卫并集后原子替换；任务终态时在已持原守卫的事务中释放活动引用。生产模块内部的员工日历史模式和唯一槽位按“从未核验可释放、已经核验则保留”处理，两者不得混为同一守卫。

## 11. 事务、锁序和并发

固定锁序：

```text
orders 根/义务（仅 orders 发起时）
→ 全部受影响任务/命令守卫（稳定业务标识排序）
→ workforce 活动引用守卫（主体、成员、标准按类型和稳定业务标识排序）
→ 员工日期工作模式守卫（员工稳定标识升序）
→ 员工日期负载（员工稳定标识升序）
→ 适用的商品日期新制产能（仅 `NEW_PRODUCT + MAKING`，产品稳定标识升序）
→ 需求、生产/返工来源及物理根守卫（按类型及稳定标识升序）
→ 上游快照唯一键
→ 任务、事实和投影
```

- 员工作为个人或任意小组成员时都写入相同员工日期负载；
- 仅 `NEW_PRODUCT + MAKING` 使用商品日期新制产能原子守卫；新制产能守卫满足 `committed_new_making_quantity + reserved_new_making_quantity ≤ capacity_limit`；全部生产/返工来源数量均使用原子守卫，防止并发超占；
- 事实写入与对应数量投影、负载投影、生产材料成本数据源项更新在同一事务；
- 创建、调整、取消、核验、减量及影响占用的事实更正共用上述锁序，先锁新旧受影响键的并集，再变更占用；不允许来源 → 人员/负载的逆序释放；
- 只读发现影响任务、主体、成员和标准集合后，持锁重新读取并核对集合与版本。变化时回滚整个幂等命令并重新发现，禁止边持来源锁边追加较早层级的任务、人员或负载锁；
- 更正命令锁定原事实及全部受影响后续事实；
- 与订单、workforce 活动预留等跨模块命令失败时全部回滚；
- 订单减量或售后处置涉及转线下库存时，业务决定、生产来源退出和数量投影必须同事务提交；
- 页面预览不构成授权，正式命令必须重新取得依据并评估；
- 死锁只能重试整个幂等命令，不能局部重试 SQL。

### 12.1 生产作业交互原型基线

本轮已确认的正式交互修订：核验先录合格、返工、线上报废数量，报废明细再录实物去向（实际销毁或转线下）及责任/免除结论。报废转线下仍保留责任，不作为第四类核验数量。返工及非报废业务移交不要求报废责任。本轮仅同步方案；以下现有 HTML 的旧四分类演示尚未改造，不可作为正式计算口径。

> 整理日期：2026-10-09。
> 页面入口：[生产作业原型](../../production-element-plus.html)。
> 本节记录用于页面与操作流程确认的 HTML 原型，不代表正式后端、跨模块事务或一期业务已交付。前文的正式业务设计与本节的原型演示范围应分别阅读。

#### 12.1.1 原型文件与使用方式

| 文件 | 用途 |
|---|---|
| `production-element-plus.html` | 生产工作台、周视图、任务列表、新建任务、只读详情，以及核验、追溯和需求缺口的示例页面 |
| `production-task-store.js` | 在当前浏览器保存新增任务、保留任务来源信息并计算示例来源余额 |
| `assets/vendor/` | 本地 Vue、Element Plus 和图标依赖，页面启动不依赖在线 CDN |

打开原型后，默认展示当前任务记录中最近计划日期所在的一周；没有新增任务时展示示例任务所在周，不因实际日期变化而一进入页面就只看到空排班。“今天”按钮仍切换到实际当前日期所在周。新建任务的计划日期默认今天，可以修改；保存后切换到该任务计划日期所在周。

原型主要用于确认页面是否清楚、字段是否合理、操作能否走通。示例日期、编号、进度和来源不作为真实订单或生产事实，不因原型能保存数据就认定正式业务已完成。

#### 12.1.2 工作台信息分区

| 分区 | 内容与交互 | 当前数据性质 |
|---|---|---|
| 顶部导航 | 显示生产作业、原型演示标识、管理员与新建任务入口 | 演示身份，不是登录和权限系统 |
| 整体进度 | 展示订单需求、排班、生产事实、已完成履约与待完成数量；查看需求缺口 | 示例订单进度，不随本地新建任务联动 |
| 各工序进度 | 制作、捏毛装袋、缝边剪袋分别展示需求、排班、完成与待完成 | 示例数据，不是实时生产投影 |
| 所选周排班任务 | 所选周全部任务数 | 根据本地任务记录计算，不受搜索关键词影响 |
| 所选周执行主体 | 所选周参与任务的不同员工或小组数 | 一个小组计为一个主体，不冒充小组成员人数 |
| 待核验任务 | 对应生产核验列表的示例任务数 | 独立核验示例，不与本地新增任务自动联动 |
| 所选周制作超额 | 所选周的制作超额任务数 | 根据本地任务记录计算 |
| 业务页签 | 任务安排、生产核验、生产事实追溯 | 用于切换不同业务视角 |

原型说明使用默认收起的简短说明区，不在主操作区展开大段技术限制。当前页面不保留没有行为的任务筛选按钮和来源筛选按钮；搜索框直接过滤数据。

#### 12.1.3 任务安排：周视图与全部列表

1. 周视图按“执行主体 × 计划日期”展示任务；执行主体可以是员工或小组。
2. 任务卡片显示产品或任务内容、类型、工序、计划数量、状态及工时展示信息；其他任务显示“不计产量”，新增任务工时显示“待评估”，不伪造计算结果。
3. 上周、下周、今天按钮切换实际日期范围；点击任务卡片进入该任务只读详情。
4. 全部列表展示任务编号、产品、订单、类型、工序、执行主体、计划日期、来源、数量、工时与状态；不限制为当前所选周。
5. 搜索用于查找产品、订单、任务等信息；周视图按所选周展示搜索结果，全部列表在全部任务中搜索。
6. 从周视图或列表新建、查看任务后，返回相应的任务视图，不把来自列表的操作错误描述为“返回周视图”。

#### 12.1.4 新建任务页面与字段

新建使用独立页面，不把多来源安排塞进列表行。正常生产与制作超额采用“左侧可安排来源、右侧已选来源”的结构；工序由来源带出，不另填一个与来源矛盾的工序。

| 字段或分区 | 展示与填写规则 |
|---|---|
| 任务类型 | 正常生产、制作超额、修补 / 重做、其他任务 |
| 执行主体 | 从示例员工、小组中选择，不在生产页面创建员工或小组 |
| 计划日期 | 默认今天，可以选择业务计划日期 |
| 生产来源 | 展示产品、订单、工序、商品快照引用与当前可安排数量，支持搜索 |
| 已选来源 | 展示所选来源及本次安排数量，允许移除明细；同一来源不能重复加入 |
| 关联正常生产任务 | 仅制作超额显示，选择同一执行主体、同日、有效的制作正常任务 |
| 不合格生产来源 | 仅修补 / 重做显示，当前原型一次选择一条示例不合格来源 |
| 返工目标工序 | 仅修补 / 重做显示，只能选择该制品已经历的工序 |
| 本次安排数量 | 生产任务填写正整数，不能超过来源当前可安排数量；其他任务不填写产量 |
| 任务内容 | 仅其他任务填写，不为空，最多 500 字 |
| 页面底部操作 | 取消、保存并查看任务；取消不新增任务、不占用来源数量 |

| 类型 | 本地原型当前执行的保存校验 |
|---|---|
| 正常生产 | 选择 1 至 20 条同工序来源；同一执行主体同日最多一个正常生产任务 |
| 制作超额 | 仅制作工序，选择同工序来源；关联同主体、同日、未完成且未取消的制作正常任务；同主体同日最多一个制作超额任务 |
| 修补 / 重做 | 选择一条不合格来源、合法的返工目标与数量；同主体同日必须有未完成且未取消的正常生产任务 |
| 其他任务 | 必须填写任务内容，不产生生产来源明细或产量；同主体同日最多一个，并与该主体当日生产任务互斥 |

以上校验针对当前原型中的执行主体与示例来源，不代表已完成员工资格、小组成员跨任务冲突、工作时长、人员日负载或商品日产能的正式校验。示例任务用于展示不同类型与状态，不能作为正式接口规则已经验证的证据。

#### 12.1.5 保存、只读详情与返回流程

```text
任务周视图 / 全部列表
  → 新建任务
  → 选择类型、执行主体与计划日期
  → 选择来源并填写本次数量，或填写其他任务内容
  → 保存并查看任务
  → 生成任务编号并进入只读详情
  → 返回原来的任务视图
  → 搜索或重新打开已保存任务
```

- 新增编号采用 `T-YYYYMMDD-序号`，其中日期取计划日期；初始状态为“待开始”。历史示例可以保留原有编号。
- 保存时保留来源编号、订单、产品、工序、商品快照引用及本次安排数量；打开详情时使用已保存信息，不按产品名称重新猜测来源。
- 正常生产与制作超额详情展示任务基础信息、关联正常任务（适用时）、全部来源明细及数量合计。
- 修补 / 重做详情展示不合格来源、返工目标工序、来源信息与本次安排数量。
- 其他任务详情展示执行主体、计划日期及任务内容，不显示虚假生产数量。
- 详情只读，不提供保存按钮；本轮没有任务调整、取消剩余安排或更正事实的持久化操作。
- 同一次保存不重复生成任务；保存失败保留填写内容，显示错误，不显示成功提示，也不占用来源余额。

#### 12.1.6 核验、需求缺口与追溯的演示范围

| 页面 | 可用于确认的内容 | 尚未实现的业务结果 |
|---|---|---|
| 生产核验 | 查看示例任务，展示计划、未完成、合格、返工 / 修补、转线下库存、报废数量，以及原因、责任、处置字段 | 核验提交当前只有演示反馈，没有持久化生产事实、质量事实或责任事实 |
| 需求缺口 | 按订单、产品、工序查看示例需求、排班缺口、完成数量和状态，搜索示例数据 | 不根据新增任务、核验结果或订单变更实时重建缺口 |
| 生产事实追溯 | 按订单聚合，展开产品、来源、任务和示例生产链路；支持搜索 | 不代表已经建立不可覆盖事实链、正式更正链或跨模块追溯接口 |

不能把点击核验后的提示理解为“已经产生合格产量”，也不能把示例工序进度理解为订单当前可发数量。生产原型不直接生成工资金额、材料成本、订单发货余额或收退款记录。

#### 12.1.7 本地数据与页面加载边界

- 新增任务保存在当前浏览器的 `localStorage`，键为 `yumi-v2-production-tasks-v1`；在同一浏览器与访问环境下刷新可以恢复。
- 示例来源池表示期初剩余可安排量；新增任务按来源明细占用余额，不再从期初余额中重复扣除历史示例任务。
- 来源池不是来自订单模块或核验模块的真实接口，也不会随其他原型页面的订单、售后、生产核验自动更新。
- 本地数据不等于正式业务草稿、后端数据库、可靠备份或多用户共享；不同浏览器、不同访问环境之间不承诺共享或恢复。
- 保存前重新读取本地记录并校验余额；这只是本地演示保护，不提供服务端锁、事务或可靠的跨窗口并发保证。
- 存储不可用或数据异常时显示提示，不覆盖原数据；当前原型最多保存 500 个新增任务。
- 初始化完成前隐藏未解析模板；依赖加载或初始化失败时展示失败提示和重新加载入口，不把 `{{…}}`、未解析组件或所有隐藏页面直接暴露出来。
- 页面内的组件标签使用完整的开始与结束标签，避免浏览器解析自闭合组件时错误嵌套任务区域和表单。

#### 12.1.8 原型确认清单与验证状态

- 打开页面能看到示例任务周，整体进度和核验任务明确标注示例性质。
- 切换周次时任务数、执行主体数和制作超额数与所选周一致；搜索不改变周总体统计。
- 周视图和列表都能打开对应任务详情，返回后保留原来的视图类型。
- 新建任务的来源、数量和日期可以填写，正常保存后进入只读详情；取消不新增记录。
- 刷新可恢复本地新增任务，重新打开详情时来源与计划量不变。
- 数量、来源或依赖不合法时不保存；存储失败不误报成功。
- 其他任务不显示生产产量；未评估工时不显示虚构值。
- 加载失败有明确提示，页面不泄漏模板变量。

截至本次整理，已执行 DOM 挂载、周视图与列表切换、新建表单、保存后详情、失败提示及本地任务逻辑检查；实际浏览器刷新后的视觉效果尚未完成截图验收。本节清单是原型确认项，不替代第 13 节的正式业务验收标准。

## 13. 验收标准

- 一个订单项只建立一个有效生产需求，重复命令复用原结果；
- 已有订单只接管当前生产状态，不补造历史任务、执行人员、劳动、材料成本或责任来源；
- 同一生产来源只能完成一次期初初始化，期初状态数量合计严格等于接管数量，录错时只能追加冲销与替代事实；
- 期初数量与上线后的任务、核验、返工、转线下库存、报废和消费事实共同满足数量守恒，且期初事实不会进入工资或成本核算；
- 订单减量或取消不会删除任何已制作、包装、修复或已合格事实；已生产未消费的多余制品只有在同一事务完整转线下库存后才允许从订单义务中移出；
- 混合来源任务减量时只调整目标来源并重新评估任务；任务无剩余数量时取消，其他来源和已有核验事实保持不变；
- 已发货数量必须先更正订单发货并冲销生产消费，整单取消不能绕过逐项生产校验；
- 转线下库存保留产品、来源、阶段、质量和业务原因追溯，移交后不能安排任务、再次交付或在一期内直接取回；
- 售后取消按池内可用、已路由未终态、已路由终态和已交付分别核对；仅池内可用及成功反向路由回池数量新增池处置，已修复报废/移交引用原终态并变更缺口义务，不重复处置，详见订单模块 13.2.1；
- 售后退回、修复、再次包装和再次交付始终沿用原物理根来源；履约来源可以切换，但累计新制数量不得增加，同一物理数量同一时刻只能处于一个活动履约来源或退回制品池；
- 需求、来源和执行事实都能直接定位产品编号及当时商品/方案快照；
- 个人和小组任务通过公开接口取得上游依据并调用计算中心评估；
- 同一员工同一工作日期最多一个有效正常生产任务和一个有效超额任务，二者使用独立槽位；由于一个任务只能对应一个工序，员工当天正常生产只能负责正常任务确定的一个工序，不能再创建其他工序的第二个正常任务；
- 员工当天没有工序为制作的有效正常生产任务时，不能创建或保留超额任务；正常制作任务取消、改期或改成其他工序时，必须同步处理依赖它的超额任务；
- 创建超额任务要求同员工同工作日期存在未取消且工序同为制作的正常生产任务；不要求正常任务已经核验，也不要求正常任务与超额任务属于同一产品、商品快照、方案或生产来源；
- 正常任务与超额任务产品不同时，两个任务分别按各自产品、快照、工序标准和来源可安排数量完成校验、核验与追溯；
- 同一员工同一工作日期最多一个有效其他任务；其他任务不能与正常生产任务共存，并且由于超额任务和返工任务依赖正常任务，其他任务也不能与超额任务或返工任务共存；
- 个人任务及小组任务中的成员都执行相同的员工日工作模式互斥校验，并发创建不能绕过该限制；
- 返工任务不能成为员工当天唯一的作业安排；创建或保留返工任务必须依赖同一员工同一工作日期的有效正常生产任务；
- 同一员工同一工作日期允许存在多个返工任务，但每个返工任务只能关联一个原不合格来源，并分别参与工作量评估与事实追溯；
- 在有效正常生产任务存在的前提下，超额任务可以与一个或多个返工任务同时存在，系统不设置额外的组合限制，由管理员根据现场情况决定是否安排；
- 正常生产任务取消或改期时，必须同步取消或调整依赖它的超额任务和返工任务，不能留下只有返工任务的工作日期；存在超额任务时，也不能把其所依赖的正常制作任务单独改成其他工序；
- 制作任务允许在倒胶后的第二天或更晚脱模核验，生产事实分别保留任务明细、工作日期和核验时间，延后核验不改变劳动归属日期；
- `OVER_STANDARD` 只表示工作量评估结果，不等同于超额任务；正常生产、返工和其他任务默认因该结果被拒绝，超额任务允许保留该评估结果并继续创建；
- 超额任务即使评估为 `OVER_STANDARD`，仍不得超过真实需求、补产缺口、来源可安排数量或商品单日产能；
- 超额任务只允许制作工序，用于记录正常制作任务之外的额外制作产量；捏毛装袋和缝边剪袋不设置超额任务，只能按上游合格可用数量安排正常任务；
- 生产模块不计算超额激励金额；超额任务仅保留数量、工序和劳动事实用于追溯，不生成自动激励来源金额。若实际工资需要覆盖该工作，由财务逐人手工核定，不拆出系统激励项；
- 小组效率缩短整体标准时间，但不产生成员个人产量；
- 小组任务占用任务小组快照中每名成员对应的员工日任务槽位；任意成员槽位冲突都会拒绝整个小组任务，且小组共同产量不会因此拆分为成员个人产量；
- 同一员工参与个人或不同小组任务时不会绕过任务槽位限制，也不会漏算同日负载；
- 模具数量和每日批次参与商品侧单日产能，生产模块只守卫返回的上限；该上限只约束 `NEW_PRODUCT + MAKING`，不约束修补、包装或其他任务；
- 一个生产任务必须且只能对应一个执行工序；正常生产任务可以通过多条任务明细同时安排该工序下的不同订单、不同产品和不同商品/方案快照；超额任务也可以包含多个订单和产品，但任务工序固定为制作；任务产生有效核验事实后不能再修改工序；
- 同一任务的全部明细必须继承任务头的同一执行工序；每条任务明细直接对应一个生产需求和一个生产来源，同一产品来自不同订单或来源时必须在新建任务时拆成不同明细；
- 任务计划作业数量等于全部任务明细计划数量之和，每条任务明细计划数量就是其对应生产来源的本次安排数量；返工任务只能包含一条任务明细并关联一个原不合格来源；
- 多产品任务必须按任务明细分别提交唯一一次最终核验，不允许只核验任务合计，也不允许同一明细分多次核验；每条明细满足“计划=未完成+完成”“完成=合格+返工/修补+线上报废”；
- 核验结果和生产事实能够逐项追溯到具体任务明细和生产来源；
- 正常制作和补产任务均不能超过当前可安排数量，不允许为了备用、囤货或转线下库存主动超产；
- 任务明细允许存在未完成数量；未完成数量不属于不合格，核验后释放回原生产来源或返工来源并只能通过新的任务明细再次安排；线上报废按需求类型形成一次补产缺口或修复终止缺口，转线下只记录去向；额外需求必须先由正式上游业务增加；
- 并发任务创建不会超过员工日负载、适用的商品新制日产能或生产/返工来源可用数量；
- 调整、取消和核验正确处理计划负载、产能和活动引用；已有核验事实时取消剩余安排不会释放当日唯一任务槽位；
- 生产数量全流程守恒，不出现负数；
- 每个实际产品只能归属一个缺陷原因；同次核验可以按不同原因形成多条缺陷事实，但任何产品数量不得重复归属；
- 每条缺陷事实数量大于 0，只保存一个原因及其编号、名称快照；有效缺陷事实数量合计严格等于对应不合格数量，“其他”必须填写说明；
- 已停用的缺陷原因不能用于新核验，历史质量事实仍能按核验时名称完整追溯；
- 缺陷原因不触发缺陷等级、工资扣款、赔偿或成本计算；
- 只有报废处置明细必须同步生成唯一的责任或免除结论，数量等于对应报废明细数量，不存在报废待认定状态；返工无需责任输入，不产生扣款来源；线上报废后转线下仍须认定报废责任，非报废业务移交不自动扣款；
- 责任主体只能是员工、小组、工作室或客户，不存在含义不明的外部责任类型；
- 个人任务的员工责任只能落到执行员工；小组任务可以落到执行小组或任务所用小组快照中的具体成员，不能选择无关主体；
- 小组共同责任不在生产模块内自动分摊到成员，生产模块也不计算责任扣款；
- 责任更正保留原事实并追加新来源版本；即使财务已经核定或支付，生产模块仍可纠正责任事实，已核定工资不得自动覆盖，人工补差由财务模块处理；
- 责任来源数据流首次报废认定发布 `APPLY`，责任或报废数量更正发布原版本 `REVERSE` 和新版本 `APPLY`；报废撤销为非报废时只发布 `REVERSE`；重复消费同一 `feedItemBusinessId` 不得形成重复财务结果；
- 不合格数量在核验事务中全部确定返工或线上报废，报废同步确定实物去向，不存在待处置余额；
- 只有 `NEW_PRODUCT` 需求下正常生产或超额生产的制作任务能够产生新制品数量；修复需求中的制作属于修补，捏毛装袋和缝边剪袋只移动既有制品的阶段；
- 任意阶段发现问题后返回制作工序都表示修补原制品；返回其他工序表示重做对应包装工序；
- `NEW_PRODUCT` 核验中的线上报废（含转线下去向）自动形成补产缺口，但不自动创建任务；补产沿用原生产需求、来源和快照，并重新经过排班及产能校验；
- `RETURNED_PRODUCT_REPAIR` 核验中的线上报废（含转线下去向）形成修复终止缺口，不能在修复需求下重新制作，必须由订单售后变更义务并在需要时另建补发需求；
- 订单减量、取消或售后义务取消产生的转线下库存不形成履约缺口；
- 生产模块不能手动忽略、关闭或核销履约缺口；新制补产缺口只能通过正常补产或上游需求减少消除，修复终止缺口只能通过售后义务变更消除；
- 重新制作只作为线上报废缺口的正常补产，不因同一报废的线下移交重复补产；
- 不合格、返工、转线下库存、报废、重新合格和责任更正链可追溯；
- 已消费来源不能非法回退；
- 其他任务不产生虚假生产工序事实或生产材料成本来源；
- 正常、制作超额和修复核验能生成不含金额的材料成本来源项，更正能生成对应冲销来源项；
- 工序核验的不合格制品必须选择返工或线上报废；报废再选实际销毁或转线下，移交后不能继续安排、消费或直接取回，线上结果与实际去向均可追溯；
- 生产模块不计算工资或成本，不读取其他模块业务表；
- 原 `scheduling`、`workforce-coordination` 和 `fulfillment-coordination` 顶层模块不再存在。

## 14. 开发准备结论

生产作业的数量分类、锁序、活动释放和线下移交终态契约已补齐。转线下后制品脱离系统监管，移交事实不可在一期内更正、取回或重新纳入；商品内置标准方案已固定覆盖三道工序，使用该方案的新需求可以按已确认范围设计。生产只提供责任及历史来源事实；财务据此逐项展示成本和胶水减免参考，负责人填写处理金额并独立核定工资，不生成自动扣款合计。
