# 跨模块接口与事务规则

## 1. 基本原则

- 模块之间只能调用能力提供方公开的 Application Service、Query、Participant 或 Source/Reporting Feed。
- 禁止访问其他模块表、Repository、内部领域对象和内部实现包。
- 接口及其命令、结果、引用类型由能力提供方定义。
- 同一顶层模块内部的子域也不得直接写对方表，应通过明确的应用/领域能力协作。
- 强一致业务采用同一数据库事务；可从不可变来源重建的派生数据采用提交后归集。

## 2. 公开接口类型

| 类型 | 用途 | 是否写入提供方 |
|---|---|---:|
| `ApplicationService` | 模块拥有的完整业务命令 | 是 |
| `Participant` | 加入调用方事务，参与跨模块强一致命令 | 是 |
| `Query` | 实时查询和资格读取 | 否 |
| `SnapshotQuery` | 按内容版本取得或复用不可变快照 | 仅必要时生成快照 |
| `SourceFeed` | 下游按游标读取不可变来源并幂等归集 | 否 |
| `ReportingFeed` | 报表按提供方游标读取变化 | 否 |

不得用 `moduleName + type + JSON` 的通用接口替代编译期明确的类型化契约。

## 3. 接口模型规则

- 跨模块只传稳定业务标识、值对象、版本号、快照引用和明确 DTO。
- 不传数据库自增主键、JPA/JDBC 实体、Repository 或调用方内部类型。
- 金额必须包含币种；数量、重量、工时必须包含或由契约固定单位。
- Feed 游标由提供方定义并解释，消费方不得推测数据库主键顺序。
- 快照接口必须保证：相同内容版本返回同一有效快照引用，不同内容版本不得复用旧快照。

## 4. 命令所有者与依赖方向

| 业务动作 | 命令所有者 | 参与/提供能力 |
|---|---|---|
| 创建或变更订单 | `orders` | customer/product 快照，production 需求参与接口 |
| 安排生产任务 | `production` | workforce 活动预留，product/workforce 快照，calculation 评估 |
| 员工离职、资格撤销、小组变更 | `workforce` | 本模块活动引用守卫 |
| 发货 | `orders` | production 可交付来源参与接口 |
| 售后退回、返工、修复失败转路线或补发 | `orders` | production 退回制品重入/池内处置、修复需求减少、返工/补发需求与来源参与接口；不创建任务或选择人员 |
| 生产材料成本归集 | `finance.costledger` | production 成本来源 Feed、product 快照查询、calculation |
| 售后成本归集 | `finance.costledger` | orders 售后成本来源 Feed |
| 工资核算和封账 | `finance.payroll` | production 劳动/责任来源，product/workforce 快照，calculation |
| 订单及售后收退款 | `finance.cash` | orders 支付资格参与接口 |
| 工资支付 | `finance.cash` | finance.payroll 内部应付参与能力 |
| 经营费用支付 | `finance.cash` | finance.costledger 内部成本登记能力 |

`orders`、`production` 不得反向调用 `finance`。成本台账通过下游 Feed 归集生产和售后成本。

## 5. 两阶段参与模式

跨顶层模块强一致写入采用同一事务内的 prepare/commit：

```text
命令所有者锁定自己的业务根
→ participant.prepare 校验并锁定提供方业务依据
→ 命令所有者写自身事实
→ participant.commit 写提供方参与事实
→ 幂等与审计成功
→ 一次提交
```

准备令牌仅在当前事务有效，不允许持久化后跨请求复用。

一期使用该模式的主要接口：

- `production` 调用 `WorkforceActivityReservationParticipant` 预留、调整和释放活动引用；
- `orders` 调用 production 参与接口建立/调整需求、消费交付来源、登记售后退回制品重入、池内原样退还/报废/转线下库存处置，并建立返工或补发需求/来源；返工使用 `RETURNED_PRODUCT_REPAIR`，补发使用 `NEW_PRODUCT`；修复失败转路线必须调用 production 的 `prepareRouteChange / commitRouteChange`，在同一 orders 事务中减少原修复需求，并且仅在补发路线下建立继任 `NEW_PRODUCT` 需求；售后参与事务到此为止，作业任务由 production 后续独立安排；
- `finance` 调用 `OrderPaymentParticipant` 和 `AfterSalesPaymentParticipant` 校验义务并写支付关联。

工资支付和经营费用支付在 `finance` 模块内部完成，不再使用跨顶层模块 Participant，但 payroll、costledger、cash 仍通过内部类型化能力协作。

## 6. 下游归集模式

不要求与上游同事务、且可以从不可变来源安全重建的派生事实，由下游读取 Source Feed：

```text
上游提交权威事实
→ 平台提交后任务触发或管理员补跑
→ 下游按提供方游标读取来源
→ 以来源标识和版本幂等处理
→ 成功后推进游标
```

一期包括：

- `finance.payroll` 分别读取 `ProductionLaborSourceFeed` 和 `ProductionResponsibilitySourceFeed`，使用独立游标维护劳动与责任当前投影；
- `finance.costledger` 读取 `ProductionMaterialCostSourceFeed`；
- `finance.costledger` 读取 `OrderAfterSalesCostSourceFeed`；
- `reporting` 读取各模块 ReportingFeed；`orders` 分别提供订单与售后 Feed，`finance` 分别提供工资、成本与现金 Feed。

要求：来源不可变或有明确更正项、游标稳定、失败可观察、处理幂等、游标不得越过失败项。劳动和责任首次发布 `APPLY`，更正时发布旧版本 `REVERSE` 与新版本 `APPLY`；生产材料和售后成本首次发布 `ACCRUE`，更正时发布旧版本 `REVERSE` 与替代版本 `ACCRUE`。不同 Feed 使用独立游标。生产或订单权威事实不得因下游归集失败而回滚。

## 7. 固定锁序

| 业务动作 | 锁序 |
|---|---|
| 订单确认 | orders 根/编号 → product/customer 快照唯一键 → production 需求守卫 |
| 作业任务创建 | production 任务守卫 → workforce 活动守卫（类型、稳定标识升序）→ 员工日期负载 → 适用的商品日期新制产能（仅 `NEW_PRODUCT + MAKING`）→ 生产/返工来源 → 快照唯一键 |
| 人员可用性变更 | workforce 活动守卫 → 员工根 → 小组根 → 成员/资格投影 |
| 任务调整 | production 任务 → 新旧 workforce 活动守卫并集（稳定顺序）→ 负载/适用的新制产能 → 生产/返工来源 |
| 生产核验 | production 任务 → 来源/阶段 → 核验、阶段和负载投影 |
| 发货 | orders 订单/约定组 → production 可交付来源 → 订单履约投影 |
| 售后退回接收 | orders 售后案例/义务 → 最近交付明细 → production 对应消费事实、物理根与退回来源守卫 |
| 售后退回制品处置/原样退还 | orders 售后案例/义务 → 退回接收明细 → production 退回制品池来源与物理根 → 处置、消费或线下移交事实 |
| 售后返工/补发 | orders 售后案例/义务 → 退回接收明细与退回制品来源（返工）→ production 返工来源/补发需求守卫；不进入任务和 workforce 锁序 |
| 修复失败转路线 | orders 售后案例 → 原返工义务 → production 修复需求/返工来源/终态事实与当前修复终止缺口 → 继任补发义务及 `NEW_PRODUCT` 需求守卫（仅补发路线）；只转换本次确认的缺口数量，不直接创建任务 |
| 订单/售后收付 | orders 业务义务 → finance 账户 → finance 来源现金投影 → 现金事实 → orders 支付关联 |
| 工资封账 | finance 工资期间 → 工资来源守卫 → 工资结果 → 成本来源守卫 |
| 工资支付 | finance 工资应付 → finance 账户 → 来源现金投影 → 现金事实/分配 |
| 经营费用支付 | finance 账户 → 成本来源守卫 → 现金事实 → 经营成本事实 |
| 成本归集 | finance 来源游标/租约 → 成本来源守卫（稳定标识升序）→ 原成本事实 → 新成本事实和游标 |
| 现金冲销 | 原现金事实 → 来源义务/应付 → 账户与投影 → 冲销事实 |

真实 MySQL 测试必须验证锁序、超时和死锁重试策略。

## 8. 活动引用守卫

`workforce` 拥有执行主体活动引用守卫和预留记录。生产安排个人任务时预留员工；安排小组任务时必须预留小组及快照中的全部成员。活动任务取消或完成后释放。

员工离职、资格撤销、小组成员变更、停用小组、效率标准变更等操作，必须先锁定本模块守卫；存在活动引用时拒绝修改。任务与预留必须同事务提交或回滚。

## 9. 幂等和失败语义

- 所有正式写请求携带幂等键；相同键和输入返回原结果，不同输入返回冲突。
- 幂等成功记录与业务事务一起提交；失败事务不留下成功结果。
- 写命令内用于决策的数据必须重新读取并锁定，不能信任页面预检查。
- 跨模块任一参与步骤失败，整个事务回滚。
- Source Feed 归集失败不回滚上游事实，但必须记录失败并允许幂等重试。
- 稳定错误类型：`VALIDATION`、`BUSINESS_REJECTION`、`NOT_FOUND`、`FORBIDDEN`、`CONCURRENT_CONFLICT`、`IDEMPOTENCY_CONFLICT`、`SYSTEM_FAILURE`。

## 10. 查询一致性和禁止事项

- 历史解释必须使用当时事实或快照引用，不能用当前定义覆盖历史。
- 列表和报表允许最终一致，操作资格必须由权威模块实时校验。
- 禁止跨模块表查询、共享 Repository、跨模块数据库外键和数据库触发器业务。
- 禁止复制其他模块公式或资格规则。
- 禁止参与模块在 prepare/commit 中继续调用第三个顶层模块；因此售后返工参与接口只能建立 production 需求/来源，不能继续安排任务或调用 workforce。
- 禁止 Query 隐式修改业务状态。

## 11. 前端接口消费规则

- 页面只能通过本模块 `services` 调用后端公开 HTTP 接口，不得直接使用通用 HTTP 客户端、数据库访问层或其他模块内部 service。
- `services` 负责请求参数组装、响应解包、DTO 到页面模型的归一化和错误类型映射；页面不依赖后端持久化实体字段名。
- 前端一次用户操作只能调用命令所有者的正式命令接口。跨模块事务、Participant、锁序、回滚和幂等由后端处理，前端不得用多个请求模拟事务。
- 跨模块只读页面可以组合公开 Query；需要跨模块聚合时，优先由命令所有者或查询责任模块提供聚合 Query，避免每个页面重复拼接和解释业务事实。
- 页面预检查只用于交互提示，正式命令必须由后端重新读取并锁定权威数据；前端不能根据预检查结果直接放行。
- 命令请求必须携带幂等键。超时后不得盲目重复提交，必须通过幂等结果查询或重新读取确认最终状态。
- Source Feed、快照版本、生产事实和财务结果只作为后端返回的只读数据展示；前端不修改游标、不生成快照、不复制公式。
- 前端可以做单位和格式转换，例如秒转时分秒、金额格式化和分页展示；不能做工资、成本、产能、来源余额、应收或利润的权威计算。
- 接口错误必须保留稳定错误类型和请求编号，页面按 `VALIDATION`、`BUSINESS_REJECTION`、`FORBIDDEN`、`CONCURRENT_CONFLICT`、`IDEMPOTENCY_CONFLICT`、`SYSTEM_FAILURE` 分别处理。
- 异步归集或报表延迟必须返回状态和更新时间；页面不得把“尚未归集”展示为零，也不得将报表投影作为业务操作资格。
