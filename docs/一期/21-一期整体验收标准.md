# 一期整体验收标准

## 1. 验收目的

本标准用于判断一期是否真正形成可运行、可追溯、边界清晰的完整系统。单个页面可用或单元测试通过不能代替整体验收。

## 2. 业务闭环验收

### 2.1 标准订单闭环

- 创建商品并自动形成内置标准方案；
- 创建并确认订单，取得最新商品/方案/客户快照；
- 建立生产需求；
- 为个人排班并核验生产；
- 合格来源发货；
- 记录客户收款；
- 双向履约后完成订单；
- 工资自动采集、复核、封账、支付；
- 成本、现金和利润报表一致。

### 2.2 自定义方案和客户供料

- 自定义方案能改变目标工序、材料来源和允许的工序费用；
- 内置方案与自定义方案使用同一套完整方案结构；
- 人工标准、标准分钟和额外单件费用由商品同步且保持只读；
- 客户供料保留全资源价值但不计工作室承担成本；
- 订单冻结本次约定，后续商品修改不回溯。

### 2.3 小组共同产出

- 建立不同人数小组及效率标准；
- 小组排班使用效率因子减少整体标准时间；
- 小组任务标准分钟计入每名成员的当日负载，小组可用分钟取成员剩余分钟最小值；
- 生产只记录小组共同产出；
- 活动任务期间不能修改小组；
- 任务结束后可以修改且历史快照不变；
- 工资按历史成员等额分配，效率因子不参与工资。

### 2.4 其他任务和工资来源

- 其他任务直接录入整个执行主体的标准分钟，不套用商品工序分钟和小组效率；
- 其他任务标准分钟计入个人或小组全体成员的当日负载；
- 未关联商品的其他任务核验后不自动产生计件工资；
- 关联商品的其他任务在安排时冻结商品快照和其他任务单件人工费，核验后按完成数量生成工资来源；
- 商品后续修改不改变既有其他任务工资来源。

### 2.5 订单变更和取消

- 变更保留旧约定并形成新版本；
- 生产需求和活动排班原子调整；
- 已完成或已发货数量受到保护；
- 任一模块失败时无部分提交。

### 2.6 售后闭环

- 已完成订单可受理售后；
- 客户和工作室义务可跟踪；
- 退回、返工、补发、退款和赔付链完整；
- 原订单、生产和现金事实不被覆盖；
- 全部义务满足后才可结案。

## 3. 架构边界验收

- Spring Modulith 验证所有模块依赖无环；
- ArchUnit 验证跨模块只能访问公开 `api`；
- Repository、行模型和 `infrastructure` 不跨模块；
- SQL 静态检查确认每个模块只访问自有表；
- `calculation` 无数据库和业务模块依赖；
- `workforce-coordination` 和 `fulfillment-coordination` 都无业务 Repository 和业务表；
- `reporting` 不被业务模块依赖；
- 没有通用 `save/executeSql/getRepository` 跨模块接口。

## 4. 数据模型验收

- 所有业务表有明确所有者；
- 稳定业务标识和内部主键分离；
- 金额、比例、数量和时间类型符合公共规则；
- 关键唯一约束、检查约束和查询索引存在；
- 当前记录、事实、快照和投影没有概念混用；
- 事实只能通过更正/冲销，不允许覆盖；
- 快照使用完整类型化引用，不保存裸版本；
- 跨模块无数据库外键；
- 服务端不存在业务草稿表和 `DRAFT` 状态。

## 5. 快照和追溯验收

- 商品、小组、客户、员工和有效工作时间标准的快照由各自模块管理；
- 同一 `content_version` 重复取得复用同一快照；
- 内容变化后取得新快照；
- 消费模块只保存快照引用；
- 历史订单、任务和工资可以解析当时数据；
- 生产、成本、现金和审计被正确实现为事实/追溯记录，而非快照；
- 公式版本保存为代码规则版本，不建立公式快照。

## 6. 事务和回滚验收

真实 MySQL 环境至少覆盖：

- 商品创建中预算失败，全商品事务回滚；
- 订单确认中生产需求失败，订单和应收回滚；
- 排班创建中生产占用失败，任务、员工日负载和商品日产能占用回滚；
- 核验中任一模块失败，生产和排班均回滚；
- 发货中生产消费失败，发货回滚；
- 小组修改与排班并发，必须竞争同一小组活动引用守卫，不能漏过活动引用；
- 工资封账中成本提交失败，封账回滚；
- 财务支付中业务关联失败，现金事实回滚；
- 售后返工需求与任务不能部分成功。

## 7. 并发和死锁验收

- 同员工日期的个人/小组并发排班不超每日有效分钟，授权超排除外；
- 同商品日期并发排班不超最大产能；
- 同生产来源并发占用、核验、消费不产生负数；
- 同订单并发变更和发货保持数量守恒；
- 同账户并发付款余额正确；
- 同期间并发工资计算/封账只有一个成功；
- 同内容版本并发取得快照只产生一个版本；
- 所有多行锁按稳定标识排序；
- 对可重试死锁只重试整个幂等命令，不重试局部 SQL；
- 达到重试上限返回稳定错误，不吞掉异常。

## 8. 幂等验收

每个正式写接口验证：

1. 同幂等键和同输入重复调用只产生一份事实；
2. 返回同一业务结果引用；
3. 同幂等键不同输入返回冲突；
4. 首次事务失败后可以安全重试；
5. 幂等成功记录与业务事实同时提交。

## 9. 计算和金额验收

- 商品预算明细合计等于汇总；
- 胶水标准用量等于“标准克重 ×（1 + 损耗率）”，胶水和色浆成本均使用该用量，色浆不重复乘损耗率；
- 目标工序正确控制成本范围；
- 商品单日最大产能使用模具数量和每日批次；
- 个人/小组任务标准分钟、剩余有效分钟和比较结果由计算中心完成；
- 其他任务直接录入的标准分钟不再应用小组效率，且只有冻结商品其他任务正式引用后才能自动计件；
- 小组可用分钟不乘人数，按成员剩余分钟最小值确定；
- 小组效率因子大于 1 且不参与工资；
- 2/3/4 人工资均分无分币差；
- 现金分配、成本分摊、订单应收和工资支付合计一致；
- 所有历史计算可显示规则版本和输入依据。

## 10. 权限和审计验收

- 未登录和无权限请求被后端拒绝；
- 工资、成本、现金等敏感数据按资源范围限制；
- 所有正式写入记录操作者、请求编号、命令执行标识和结果；
- 审计日志不泄露密码、令牌和敏感明文；
- 文件引用可追溯且被引用文件不能删除；
- 管理员操作与员工生产身份分离。

## 11. 页面和可用性验收

- 页面按业务结构分区，不直接暴露数据库概念；
- 只读继承字段明确标识；
- 禁止操作有明确原因，而不是只隐藏按钮；
- 列表、详情和时间线显示一致状态；
- 关键金额和数量展示来源与单位；
- 报表显示数据更新时间和延迟；
- 页面未提交数据刷新后可丢失，系统不承诺服务端草稿恢复。

## 12. 报表和重建验收

- 所有投影可从公开数据源重建；
- 增量水位失败不越过；
- 重建前后核心合计一致；
- 对账差异可定位到业务标识；
- 报表损坏或延迟不影响业务写入；
- 报表无跨模块 SQL。

## 13. 文档一致性验收

- 每个模块文档章节完整；
- 表名、字段名、状态和接口名称在全目录中无冲突；
- 所有跨模块调用在架构和事务文档中有记录；
- 开发顺序先完成 `team` 和 `scheduling` 核心，再实现 `workforce-coordination`；
- 不存在旧的通用材料目录、装箱工序、方案默认选择、服务端草稿等已否决设计；
- 所有待确认问题都有明确影响范围，且阻塞开发的问题已清零。

## 14. 一期通过条件

只有同时满足以下条件才可判定一期通过：

1. 核心业务闭环全部通过；
2. 架构边界自动测试通过；
3. 真实 MySQL 事务、并发、死锁和回滚测试通过；
4. 数据迁移在备份副本完成演练和对账；
5. 权限、审计和敏感数据测试通过；
6. 关键报表与来源数据对账无未解释差异；
7. 文档与最终实现同步，不存在已知关键偏差。
