# 系统总体架构与模块依赖

## 1. 架构选择

一期采用模块化单体：

- Java 21；
- Spring Boot 3.5.x；
- Spring Modulith；
- 单一应用和单一 MySQL 数据库；
- Flyway 管理表结构；
- Spring JDBC / `JdbcClient` / 显式 SQL；
- 同进程公开 Java 接口完成模块协作；
- 强一致跨模块动作使用同一个本地数据库事务。

一期不采用微服务、消息队列、事件溯源框架、JPA 作为核心持久化方案或通用工作流引擎。

## 2. 模块清单和能力

| 模块 | 业务所有权 | 主要对外能力 |
|---|---|---|
| `platform` | 身份、权限、文件、审计、幂等、请求上下文、提交后任务 | 鉴权、权限判断、正式文件、命令幂等、审计 |
| `calculation` | 公式代码、精度、舍入和规则版本 | 商品预算、产能、个人/小组工作量、金额分配等纯计算 |
| `base-data` | 客户、员工、工种资格、有效工作时间标准、静态选项、商品录入默认值 | 当前资料查询、资格校验、标准和必要快照 |
| `product` | 商品、工序配置、额外费用、标准/自定义方案、商品快照 | 商品维护、预算试算、取得当前快照 |
| `cost-ledger` | 经营成本事实、分摊和更正 | 登记成本、冲销、更正、成本查询 |
| `finance` | 账户、现金收支事实、支付分配和对账 | 收款、付款、退款、工资支付、现金查询 |
| `production` | 生产需求、制品阶段、质量、责任、处置、来源消费 | 创建需求、占用、执行、核验、交付消费 |
| `orders` | 订单、交付约定、变更、发货、应收、完成、已有订单接管 | 确认订单、变更、发货、履约和完成 |
| `team` | 小组、成员关系、按人数效率标准、小组快照 | 小组维护参与端口、主体解析、取得当前快照 |
| `scheduling` | 排班计划、任务、执行主体、活动引用、评估结果 | 创建/调整/取消/核验任务、活动引用守卫、排班查询 |
| `workforce-coordination` | 无业务数据，只拥有小组变更用例编排 | 原子协调 team 与 scheduling |
| `fulfillment-coordination` | 无业务数据，只拥有履约用例编排 | 原子协调 production 与 scheduling |
| `after-sales` | 售后案例、义务、退回、补发/返工、售后金额决定 | 售后受理、处理、重新交付、结案 |
| `payroll` | 工资期间、来源、到人结果、扣款、补差、封账 | 自动计算、复核、封账、工资单查询 |
| `reporting` | 可重建报表投影、水位和对账结果 | 报表查询、重建、差异检查 |

## 3. 依赖方向

```text
platform         ← 所有有入口或写入的模块
calculation      ← product / scheduling / payroll
base-data        ← product / orders / team / scheduling / payroll
product          ← orders / scheduling / payroll(只读快照解析)
cost-ledger      ← production / payroll / after-sales / finance
finance          ← orders / payroll / after-sales
production       ← orders / scheduling / fulfillment-coordination / payroll(只读)
team             ← scheduling / payroll / workforce-coordination
orders           ← after-sales / reporting
scheduling       ← workforce-coordination / fulfillment-coordination / payroll(只读来源) / reporting
reporting        ← 各模块的公开只读数据源
```

`calculation` 不依赖任何业务模块。`reporting` 不被任何业务写入模块反向依赖。

## 4. 模块内部结构

```text
com.yumi.<module>
├─ api
│  ├─ application     完整业务命令
│  ├─ participant     加入既有事务的受限写端口
│  ├─ query           只读能力
│  ├─ model           命令、结果、值对象和引用
│  └─ http            HTTP 适配
├─ application
│  ├─ command
│  ├─ query
│  └─ port
├─ domain
│  ├─ model
│  ├─ policy
│  └─ service
└─ infrastructure
   ├─ persistence
   └─ integration
```

只有 `api` 中明确导出的 named interface 可以被其他模块依赖。

## 5. 数据所有权红线

- 每张业务表只能有一个所有者模块。
- 模块 SQL 只能出现本模块拥有的业务表。
- 禁止跨模块外键；跨模块保存稳定业务标识或类型化快照引用。
- 禁止跨模块联表查询；需要组合数据时调用公开查询或在 `reporting` 建立投影。
- 协调模块无业务表、无 Repository，不复制参与模块的数据。
- 查询接口不能在读取时产生隐式业务写入；唯一例外是名称明确为 `acquire...Snapshot` 的正式取得快照命令接口。

## 6. 开发依赖顺序

1. 平台公共能力和架构门禁；
2. 计算中心；
3. 基础资料；
4. 商品；
5. 成本台账、财务；
6. 生产；
7. 订单；
8. 小组核心；
9. 排班核心；
10. 小组变更协调；
11. 履约协调；
12. 售后；
13. 工资；
14. 报表。

这里描述依赖顺序，不是工期计划。后续模块不得通过临时直连数据库绕过尚未实现的前置接口。

## 7. 架构验证

必须用 Spring Modulith 和 ArchUnit 验证：

- 非 `api` 包不能被跨模块访问；
- Repository、数据库行模型和 `infrastructure` 不得跨模块依赖；
- `calculation` 不依赖业务模块和持久化；
- `reporting` 不被业务模块依赖；
- 协调模块不拥有 Repository；
- SQL 静态扫描不出现其他模块表名；
- 禁止依赖环。
