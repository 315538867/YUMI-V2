# 系统总体架构与模块依赖

## 1. 架构选择

一期采用模块化单体：Java 21、Spring Boot 3.5、Spring Modulith、JDBC/JdbcClient、MySQL、Flyway。所有模块运行在同一进程和同一数据库中，但必须保持代码依赖、数据所有权和公开接口边界。

选择模块化单体是为了在一期保留本地事务、降低部署复杂度，同时通过模块测试防止系统退化成无边界单体。

## 2. 顶层模块划分原则

只有同时具备相对稳定的事实所有权、业务生命周期和外部能力边界，才建立顶层模块。以下情况优先作为模块内部子域：

- 只能依附已有业务根存在；
- 与已有模块存在高频同事务变化；
- 独立后只会增加参与接口、锁序和回滚协调；
- 独立权限可以通过模块内部应用服务和包边界实现。

模块合并不代表聚合合并。订单与售后、工资与成本、成本与现金仍然使用独立聚合、状态、表和权限。

## 3. 顶层模块清单和能力

| 顺序 | 模块 | 代码 | 核心能力 |
|---:|---|---|---|
| 1 | 平台公共能力 | `platform` | 身份、权限、文件、审计、幂等、编号、提交后任务 |
| 2 | 计算中心 | `calculation` | 商品预算、产能、任务标准、个人/小组效率、工资和成本金额纯计算 |
| 3 | 客户 | `customer` | 客户资料、地址、状态、内容版本和快照 |
| 4 | 商品 | `product` | 商品、工序输入、标准/自定义方案、预算输入、内容版本和快照 |
| 5 | 人员与小组 | `workforce` | 员工、资格、小组、效率、有效时间、执行主体快照和活动引用守卫 |
| 6 | 生产作业 | `production` | 生产需求、任务安排、负载、执行核验、质量、返工、报废、数量和来源消费 |
| 7 | 订单 | `orders` | 交易约定、应收退款、发货、履约、完成、售后案例及售后义务 |
| 8 | 财务结算 | `finance` | 逐人工资核定、成本台账、真实收付、支付分配、冲销和月度汇总 |
| 9 | 报表 | `reporting` | 消费公开 Feed，构建可重建只读投影 |

## 4. 已确认的合并与拆分

| 对象 | 结论 | 原因 |
|---|---|---|
| 员工 + 小组 | 合并为 `workforce` | 同属执行主体，资格、成员、标准、快照和活动占用必须统一 |
| 人员变更协调 | 取消顶层模块 | 活动引用守卫应由执行主体所有者 `workforce` 管理；生产只通过接口预留和释放 |
| 排班 + 生产 | 合并为 `production` | 任务、负载、产能、核验和数量守恒需要同事务维护 |
| 商品 + 定制方案 | 合并为 `product` | 方案只能依附商品，标准与自定义方案使用同一结构和版本机制 |
| 商品 + 计算 | 保持独立 | 商品拥有数据和快照，计算中心只拥有公式代码 |
| 客户 + 订单 | 保持独立 | 客户可独立维护和复用，订单只冻结客户快照 |
| 订单 + 售后 | 顶层合并、内部拆分 | 一期售后只能从已完成订单派生，不支持无订单或跨订单售后；仍保留售后独立聚合和表 |
| 生产 + 成本 | 保持顶层独立 | 生产属于 `production`，成本属于 `finance`；生产提交不能被成本归集失败回滚 |
| 工资 + 成本台账 + 现金财务 | 合并为 `finance` | 三者组成应付、成本、支付闭环；顶层拆分只会增加跨模块事务，内部仍严格区分事实 |
| 订单应收 + 财务现金 | 保持独立 | 订单决定资格，财务执行真实收付，避免复制交易规则 |
| 人员与小组 + 工资 | 保持独立 | 执行主体定义属于 `workforce`，工资期间和应付属于 `finance` |
| 业务模块 + 报表 | 保持独立 | 报表可重建，不能成为业务操作资格来源 |
| 通用基础资料 | 不建立 | 客户、商品、人员的生命周期不同，不能抽成无业务所有权的通用模块 |
| 材料管理 | 一期不建立 | 一期只使用商品/方案录入价格，没有库存、采购、批次和设备闭环 |

## 5. 子域边界

### 5.1 订单模块内部

```text
orders
├─ trade          订单、订单项、交付约定和变更
├─ fulfillment    发货、履约、完成和取消
├─ receivable     应收、退款义务和支付关联
└─ aftersales     售后案例、义务、退回、返工、补发、金额决定和结案
```

售后不能覆盖原订单、原发货或原生产事实。

### 5.2 财务结算模块内部

```text
finance
├─ payroll        工资期间、参考计算、逐人核定、人工调整、员工应付和支付状态
├─ costledger     材料、人工、售后、经营费用成本及分摊、更正、来源归集
└─ cash           现金事实、支付分配、来源收付汇总和冲销；一期无资金账户
```

必须始终保持：工资应付不等于人工成本，成本发生不等于现金支付，业务义务不等于真实现金。

## 6. 依赖方向

```text
platform
calculation               → platform
customer                  → platform
product                   → platform, calculation
workforce                 → platform
production                → platform, product, workforce, calculation
orders                    → platform, customer, product, production
finance                   → platform, calculation, product, workforce, production, orders
reporting                 → platform, customer, product, workforce, production, orders, finance
```

关键说明：

- `workforce` 不依赖 `production`。生产通过 `WorkforceActivityReservationParticipant` 预留或释放执行主体活动引用。
- `orders` 不依赖 `finance`。订单保存应收、退款和售后金额义务；财务调用订单支付参与接口。
- 售后退回由 `orders` 调用 production 参与接口，按最近一次交付来源、对应消费事实和原始新制物理根登记原制品重入；未修复原样退还直接消费退回制品池来源，返工建立 `RETURNED_PRODUCT_REPAIR` 需求/返工来源，补发建立独立 `NEW_PRODUCT` 需求。修复失败转路线由 `orders` 作为事务所有者，仅转换当前修复终止缺口并原子减少原修复义务/需求；只有补发路线建立等量继任补发义务/需求。上述参与事务不得创建任务或新增人员占用；仅在缩减既有任务时允许 production 加入 workforce 的调整/释放参与接口，沿用 orders 事务。新任务由 production 后续排班。
- 售后成本由 `orders` 提供不可变成本来源 Feed，`finance` 下游归集，避免 `orders ↔ finance` 双向依赖。
- `production` 不依赖 `finance`。生产仅发布正常、超额、修复和关联商品其他任务的劳动来源，独立发布责任来源，并发布正常、超额、修复的材料成本来源；finance 通过各自独立 Feed 下游接收和归集。
- 工资、成本和现金处于同一顶层模块，内部调用不得通过数据库表耦合，仍应通过应用服务或领域服务保持子域边界。
- `reporting` 只能读取公开 ReportingFeed，不得被业务写流程反向依赖。

## 7. 前端总体架构

### 7.1 前端形态和职责

一期前端采用单一 Web 应用，按业务模块组织功能，不拆分微前端，不为每个后端模块建立独立运行时。

#### 技术选型状态

历史前端方案推荐 Vue 3、TypeScript、Vite、Vue Router 和 Pinia；但该方案标记为待签字冻结，当前仓库也没有前端工程，因此这组框架/工具目前只能作为推荐选型，不能当作已经批准的技术事实。开始搭建前端工程前，应将最终选型补充到本节并更新文档状态。

本节其余内容定义的是与框架无关的一期前端架构边界，可先用于接口和模块设计。选定框架后，目录和状态管理实现可以按工具惯例调整，但不得改变模块所有权、接口调用和业务计算边界。

前端负责：

- 页面展示、路由、表单交互、查询条件和本地界面状态；
- 调用后端公开 Query 和命令所有者的 Application Service 对应 HTTP 接口；Participant 仅供后端同事务编排，不直接暴露给前端；
- 将接口错误、权限拒绝、并发冲突、处理中和最终一致延迟明确反馈给用户；
- 展示后端返回的金额、数量、工时、来源和快照引用，并标明单位与时间点。

前端不负责：

- 访问任何数据库、Repository、内部领域对象或其他模块的内部接口；
- 复制计算中心、生产、订单或财务的业务公式和资格判断；
- 通过页面预检查结果代替后端正式命令校验；
- 把当前定义覆盖历史快照或生产事实；
- 在浏览器中拼接多个模块的内部写操作来模拟一个跨模块事务。

### 7.2 前端分层

每个业务模块的前端功能都按以下层次组织。层次是依赖边界，不要求每一层都拆成独立 npm 包。

| 层 | 主要职责 | 禁止事项 |
|---|---|---|
| `app` | 应用启动、全局布局、路由注册、全局错误边界、登录态恢复 | 放置具体业务规则 |
| `pages` | 页面绑定、布局和页面级组合 | 直接发 HTTP 请求、直接计算业务结果 |
| `composables` / `use-cases` | 页面状态、查询/命令编排、加载和提交状态、缓存失效 | 访问数据库或依赖后端内部类名 |
| `services` | HTTP 调用、请求参数组装、响应解包、错误归一化 | 被页面绕过；复制其他模块公式 |
| `contracts` | 请求 DTO、响应 DTO、枚举、错误码、分页和游标契约 | 直接暴露后端持久化实体 |
| `components` | 模块内可复用的表单、表格、时间线、状态展示和操作控件 | 持有跨页面业务流程 |
| `shared` | 无业务所有权的视觉组件、格式化器、通用表格和输入控件 | 持有客户、商品、生产等业务状态 |
| `platform` | 登录、权限、文件、审计展示、幂等请求头、通知和 API 客户端适配 | 放置具体业务命令 |

统一数据流如下：

```text
页面路由
  → 页面/组件
  → composable 或 use-case
  → 模块 service
  → 模块公开 HTTP API
  → contract 归一化
  → 页面状态和展示
```

正式写入采用以下流程：

```text
表单/操作
  → use-case 组装完整命令和幂等键
  → 模块 command service
  → 后端重新校验并提交事务
  → 返回权威结果或明确错误
  → 失效相关查询并重新读取
```

提交成功后，页面不得仅凭本地修改推断最终事实；必须使用后端结果或重新查询更新状态。

### 7.3 模块前端目录约定

推荐采用单仓库单应用目录，模块代码与后端模块代码一一对应：

```text
src/
├─ app/                         # 启动、全局布局、全局错误处理
├─ router/                      # 路由注册和路由元数据
├─ platform/                    # 登录、权限、文件、API 客户端、通知
├─ shared/                      # 无业务所有权的通用组件和工具
└─ modules/
   ├─ customer/
   │  ├─ pages/
   │  ├─ components/
   │  ├─ composables/
   │  ├─ services/
   │  └─ contracts/
   ├─ product/
   ├─ workforce/
   ├─ production/
   ├─ orders/
   ├─ finance/
   ├─ reporting/
   └─ platform-admin/
```

`calculation` 是后端能力模块，一期不要求独立业务菜单；商品、生产和财务通过各自页面调用计算接口。`orders/aftersales`、`finance/payroll`、`finance/costledger` 和 `finance/cash` 是对应顶层模块内部的前端子域，不升级为独立顶层前端应用。

页面可以按用户任务组织，但写操作必须由拥有该事实的模块 service 发起。例如订单详情页可以展示商品、客户和生产信息，但创建任务必须调用 `production` 的命令接口，不能在订单页面直接拼接 workforce 或 production 的内部操作。

### 7.4 路由和模块入口

路由是前端导航边界，不是后端权限边界。后端仍必须在每个正式命令上重新校验权限和业务条件。

| 路由前缀 | 前端归属 | 主要页面范围 |
|---|---|---|
| `/customers` | `customer` | 客户列表、详情、地址、内容版本引用 |
| `/products` | `product` | 商品、工序字段、标准方案、自定义方案和方案版本 |
| `/workforce` | `workforce` | 员工、资格、小组、效率、有效时间和活动引用状态 |
| `/production` | `production` | 生产需求、排班任务、任务明细、生产核验、返工/修补、终态处置 |
| `/orders` | `orders` | 订单、履约、发货、收退款义务和售后子域 |
| `/finance` | `finance` | 工资、成本台账、收付、支付分配和月度汇总 |
| `/reports` | `reporting` | 只读报表、投影状态、延迟和重建状态 |
| `/platform` | `platform-admin` | 用户、权限、文件、审计和系统参数 |

路由元数据只用于导航、页面准入和按钮状态提示；隐藏菜单或按钮不能代替后端拒绝无权限请求。未授权、过期登录态和资源范围不足必须分别展示，不得统一伪装成“数据为空”。

### 7.5 状态、缓存和表单规则

- URL 状态只保存可分享的查询条件、分页、排序、选中标识和当前子页签；不把完整业务对象塞入 URL。
- 服务端查询状态由模块 service 管理；页面不得复制同一事实作为第二个可写来源。
- 表单状态只表示尚未提交的本地输入。一期没有服务端业务草稿，刷新或离开页面后可以丢失未提交内容。
- 正式命令提交期间必须锁定提交控件，携带幂等键；成功后按返回结果或查询失效策略刷新，失败后保留用户输入和后端错误原因。
- 查询缓存只能优化读取，不能作为操作资格判断或业务事实来源；需要资格时调用权威 Query 或提交正式命令。
- 涉及快照、版本、生产事实和财务结果的页面必须展示引用编号、状态和时间点；不能用当前商品或当前人员配置替换历史显示。

### 7.6 前端计算和展示精度

前端只做展示级转换，不承担业务计算：

- 工时以整数秒作为接口事实，页面可以格式化为小时、分钟和秒；录入分钟时必须明确转换结果；
- 金额按接口币种和精度展示，禁止用 JavaScript 浮点运算生成工资、成本、应收或利润结果；
- 小组效率、产能、工资分配、来源余额、应收和成本必须显示后端返回结果；
- 页面上的合计、预览或提示只能标明“预览”，不能写入业务事实，也不能在提交时替代后端计算；
- 后端返回的舍入结果、规则版本和输入依据需要在需要追溯的详情页可查看。

### 7.7 跨模块页面协作

跨模块页面只组合公开查询结果，不打破模块边界：

1. 详情页需要其他模块信息时，调用对方公开 Query 或由页面所属模块提供聚合查询接口；不得直接引入对方内部 store、service 或持久化类型。
2. 一个用户动作涉及多个模块的强一致变更时，前端只调用命令所有者的一个接口；Participant、事务和回滚由后端完成。
3. 需要最终一致的数据必须显示“归集中/延迟/失败重试”等状态和更新时间，不能把暂未归集显示成零。
4. 快照由定义模块生成和管理，前端只提交业务引用并展示快照版本号；前端不能拼装快照内容或自行决定复用版本。
5. 生产事实、售后事实和财务事实使用各自公开查询模型展示；页面不把它们合并成一个可编辑对象。

### 7.8 前端错误和并发处理

统一按接口错误类型处理：

| 错误类型 | 页面行为 |
|---|---|
| `VALIDATION` | 定位到具体字段或明细，保留其他输入 |
| `BUSINESS_REJECTION` | 展示业务原因，并刷新受影响的权威数据 |
| `FORBIDDEN` | 展示无权限或资源范围不足，不伪装成空数据 |
| `CONCURRENT_CONFLICT` | 提示数据已变化，重新读取后要求用户确认 |
| `IDEMPOTENCY_CONFLICT` | 展示原命令结果或输入冲突，不重复提交 |
| `SYSTEM_FAILURE` | 保留输入，展示请求编号和重试入口；不声称写入成功 |

网络超时不能推断命令失败或成功；页面应通过幂等查询、结果查询或重新加载确认最终状态。

### 7.9 前端测试边界

至少覆盖以下层次：

- `contracts/services`：响应解包、字段映射、错误归一化、幂等键和分页/游标参数；
- `composables/use-cases`：加载、提交、成功刷新、失败保留输入、并发冲突和权限状态；
- `pages/components`：字段只读/可编辑状态、单位、状态流转和关键按钮条件；
- 路由：未登录、无权限、资源范围不足和模块入口；
- 端到端关键流程：商品方案引用、生产排班与核验、订单发货/售后、工资/成本/现金查询。

前端测试不得通过直接写数据库准备数据来绕过公开接口；跨模块流程应验证命令所有者和最终页面状态。

## 9. 数据所有权红线

1. 每张业务表只能由一个顶层模块写入。
2. 模块不得直接查询或更新其他模块表，不得共享 Repository。
3. 跨模块稳定标识不建立数据库外键，由应用接口校验。
4. 业务定义模块管理快照内容和版本，引用方只保存快照引用。
5. 事实记录不可覆盖；错误使用失效、冲销或差额更正。
6. 投影可以删除重建，不能成为唯一业务依据。
7. `orders` 的售后子域可以访问订单模块内部公开领域能力，但不能绕过订单聚合不变量直接更新订单表。
8. `finance` 内部 payroll、costledger、cash 各自拥有表和 Repository；任何子域不得直接写另一个子域的表。

## 10. 开发依赖顺序

1. 建立模块骨架、Flyway、Spring Modulith 和 ArchUnit 边界测试；
2. 实现 `platform`；
3. 实现 `calculation`；
4. 并行实现 `customer`、`product`、`workforce`；
5. 实现 `production`，包括活动引用预留和释放；
6. 实现 `orders` 的交易、履约和售后子域；
7. 实现 `finance`：先成本来源与工资核算，再现金收付和对账；
8. 实现 `reporting`；
9. 执行真实 MySQL 的并发、死锁、幂等和全事务回滚验证。

后续步骤不得直接绕过尚未稳定的前置公开接口。

## 11. 架构验证

必须使用 Spring Modulith 和 ArchUnit 自动验证：

- 只存在上述九个顶层业务模块；
- 模块依赖图无环；
- 不存在跨模块 Repository 引用和内部包访问；
- `workforce` 不依赖 `production`；
- `orders` 不依赖 `finance`；
- `orders` 的售后生产参与调用不创建 production 作业任务，不新增 workforce 占用；缩减既有任务时仅允许 production 同事务减少或释放原预留；
- `production` 不依赖 `finance`；
- `reporting` 不被任何业务写模块依赖；
- 禁止出现已取消的顶层包；
- payroll、costledger、cash 子包不能直接访问彼此 Repository；
- aftersales 子包不能直接覆盖 trade/fulfillment 聚合状态。
