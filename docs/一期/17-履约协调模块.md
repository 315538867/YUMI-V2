# 履约协调模块

> 模块代码：`fulfillment-coordination`

## 1. 模块说明

履约协调模块只编排需要同时改变生产和排班的强一致动作，解决 `production` 与 `scheduling` 之间的双向业务协作，避免两个模块互相依赖。它不拥有业务数据。

## 2. 一期需求、范围与模块功能

- 订单变更导致生产需求与活动任务同时调整；
- 生产处置导致修复需求和修复任务同时建立；
- 某些生产来源失效导致任务取消和占用释放；
- 需要同时撤销生产事实影响和排班事实影响的更正用例。

普通排班创建、取消和核验仍由 `scheduling` 作为命令所有者直接调用生产参与端口，不必都经过协调器。

## 3. 模块边界

- 无业务表、无 Repository、无独立事实、无快照；
- 不提供通用编排或工作流；
- 只依赖 `production.api.participant` 和 `scheduling.api.participant`；
- 参与模块不能回调协调器；
- 业务结果由参与模块各自保存，协调器只返回组合引用。
- 数据模型与表设计：本模块无业务表、无 Repository、无 Flyway、无快照和事实表；幂等和审计使用 `platform` 公共能力。

## 4. 模块功能与公开接口

```java
interface FulfillmentCoordinationService {
    FulfillmentChangeResult applyOrderChange(ApplyOrderFulfillmentChange command);
    RepairArrangementResult createRepairAndTask(CreateRepairAndTask command);
    FulfillmentCancellationResult cancelSourceAndTasks(CancelSourceAndTasks command);
    FulfillmentCorrectionResult correct(CorrectFulfillment command);
}
```

每个命令都必须是明确业务用例，不提供 `execute(type, payload)`。

## 5. 事务和锁序

协调器开启事务并按固定顺序调用：

```text
业务来源根（由发起模块先锁定）
→ scheduling.prepare... 锁定任务和活动引用
→ production.prepare... 锁定需求和来源
→ scheduling.commit...
→ production.commit...
→ 返回组合结果
```

具体命令可规定 production 先于 scheduling，但同一命令的顺序必须固定并有真实 MySQL 并发测试。任何参与端口失败，全部回滚。

## 6. 错误语义

协调器不吞掉模块错误，只增加用例级错误：`FULFILLMENT_COORDINATION_CONFLICT`、`FULFILLMENT_PARTICIPANT_CHANGED`、`FULFILLMENT_TRANSACTION_FAILED`。错误响应保留原始稳定原因码。

## 7. 验收标准

- 模块没有业务表和 Repository；
- 参与模块不能形成依赖环；
- 任一参与者失败时两侧均无部分提交；
- 重复命令通过发起模块幂等返回同一结果；
- 并发订单变更、任务取消和核验不存在死锁或有明确重试；
- ArchUnit 禁止本模块依赖参与模块内部包。

## 8. 待确认问题

本模块当前无业务待确认项；每个新增跨模块用例必须单独写入本章后才能实现。
