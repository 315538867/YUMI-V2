> 文档状态：一期开发基线

> 权威目录：`docs/一期/`

## 1. 这套文档解决什么问题

本目录是一套按开发依赖顺序组织的完整设计文档。阅读者不需要先理解历史讨论，也能明确一期范围、模块所有权、表结构、接口、事务、权限和验收标准。

本目录不提供工期、人员安排或阶段排期。

## 2. 文档权威规则

- 一期开发、评审和验收以本目录为准；`docs/历史文档/` 仅保留讨论历史。
- 冲突优先级：模块文档中的已确认业务规则 > 公共规则 > 总体架构 > 历史文档。
- 新决定必须同步更新受影响模块、跨模块规则和整体验收标准。
- “待确认问题”不得由开发人员自行猜测；确认后应改写为正式规则。

## 4. 顶层模块关系

下图统一使用“调用方 → 能力提供方”：

```text
platform
calculation ───→ platform
customer ──────→ platform
product ───────→ platform + calculation
workforce ─────→ platform
production ────→ platform + product + workforce + calculation
orders ────────→ platform + customer + product + production
finance ───────→ platform + calculation + product + workforce + production + orders
reporting ─────→ platform + 各业务模块公开 ReportingFeed
```

所有连线都表示调用公开接口，不表示可以访问对方数据库表。

## 5. 一期统一结论

- 后端采用 Java 21、Spring Boot 3.5、Spring Modulith、JDBC/JdbcClient、MySQL 和 Flyway。
- 系统采用模块化单体、单进程、单数据库；模块之间禁止共享 Repository、跨模块表查询和数据库外键。
- 顶层业务模块收敛为九个：`platform`、`calculation`、`customer`、`product`、`workforce`、`production`、`orders`、`finance`、`reporting`。
- 员工和小组归入 `workforce`；排班计划和生产事实归入 `production`。
- 人员变更协调不再是顶层模块；活动引用守卫由 `workforce` 自己拥有，`production` 通过公开参与接口预留和释放。
- 售后不是独立顶层模块；它是 `orders` 内部独立子域，保留自己的聚合、状态、表和服务。
- 工资结算、成本台账和现金财务不是三个顶层模块；它们是 `finance` 内部三个独立子域。
- 订单应收、退款及售后赔付义务仍由 `orders` 决定；`finance` 只执行真实收付。
- 工资应付、成本发生和真实现金必须分别建模，不能因处于同一模块而相互替代。
- 生产只记录数量、工序、质量、劳动和责任事实，不计算工资或成本金额；订单售后退回通过生产参与接口登记原制品重入，不能把退回误算成重新生产。
- 系统不提供服务端业务草稿；错误通过失效、冲销或差额更正保留追溯链。
- 商品等可编辑定义只在跨模块正式引用时按内容版本取得不可变快照；生产事实是追溯记录，不称为快照。
- 一期不做材料目录、库存、采购、领料、批次价格、会计总账、税务和设备联动。
- 当前只剩财务金额规则待确认：超额制作激励公式，以及生产责任是否扣款、扣款公式、小组责任分配和余额结转；这些问题不改变已确认的生产事实和来源契约。

## 6. 文档维护要求

- 模块职责变化时，至少检查本文档、总体架构、跨模块规则、相关模块文档和整体验收标准。
- 表、接口和状态必须明确所有者；同一事实只能有一个权威写入模块。
- 模块合并只改变顶层边界，不得把不同业务事实强行合并为一套表或一个聚合。
- 文件编号必须连续，文件名使用中文并能直接表达内容。

### 7.1 已确认的原型口径

- 商品录入去掉目标工序选择，保留标准售价；自定义方案和订单约定仍保留目标工序。
- 人员页面一期没有绑定账号功能；小组只维护成员，效率与每日有效时间在全局标准中维护。
- 工资逐人核定，系统金额仅作参考；核定、人工成本和实际付款分别展示。
- 一期原型没有资金账户；订单收款、退款在订单内操作，财务共享查询，不重复录入。
- 日常经营收支在财务记录，用户选择日期决定月份；凭证跟随本条收付记录。
- 月度汇总在财务，分别统计现金与成本，资金净额不当成利润；[报表模块 8.1](14-报表模块.md#81-现有原型中的汇总入口)说明与正式报表设计的区别。

### 7.2 当前数据与联动边界

| 原型 | 当前数据保存 | 已有跨页关系与限制 |
|---|---|---|
| 客户 | `yumi-v2-customers-v1`，浏览器本地存储 | 订单选择启用客户并冻结本次资料；客户更新不回写旧订单 |
| 商品 | 页面内数据，刷新恢复示例 | 订单另有商品示例池，商品编辑不自动同步到订单 |
| 人员与小组 | 页面内数据，刷新恢复示例 | 活动引用、员工、小组及标准未与生产 / 工资原型形成真实共享 |
| 生产作业 | 新增任务存入 `yumi-v2-production-tasks-v1` | 来源余额可本地校验；进度、核验、缺口和追溯仍有独立示例，不自动形成可发量或工资 |
| 订单 | `yumi-v2-order-finance-v1`，部分写入路径仍有失败保护限制 | 发货与收退款共享演示状态；合格来源不来自生产原型实时核验 |
| 财务结算 | `yumi-v2-finance-prototype-v1`；订单流水使用订单共享存储 | 逐人工资、日常收支及关联成本可本地保存；材料 / 售后等来源仍含示例 |

商品与人员原型仍依赖外部 CDN；客户、生产、订单和财务使用本地前端资源。不能统一宣称所有原型均离线可用或所有修改均能刷新恢复。

### 7.3 记录与验证范围

本次对六个原型逐一核对源码并补充文档，不新增原型功能、不创建 OpenSpec 或实施计划。生产页已有 DOM 与本地逻辑检查记录；其他页面的源码核对不等于本轮实际运行或视觉验收。各模块的原型确认项与正式业务验收分开记录。

原型中的示例数据、提示反馈、浏览器本地保存与正式生产事实、数据库持久化、跨模块事务应明确区分。更新原型时同步对应页面说明；仅整理展示方式和演示边界，不自行改变正式业务规则、接口或数据库设计。
