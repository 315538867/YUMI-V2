# YUMI V2 一期文档总览

> 文档状态：一期开发基线
> 基线日期：2026-09-29
> 适用范围：YUMI V2 一期业务、架构、数据和验收
> 权威目录：`docs/一期/`

## 1. 这套文档解决什么问题

本目录是一套按开发依赖顺序组织的完整设计文档。阅读者不需要先理解旧文档，也能回答以下问题：

1. 一期为什么建设、做哪些业务、不做哪些业务；
2. 系统由哪些模块组成，每个模块拥有什么数据和能力；
3. 模块之间通过什么公开接口协作，哪些调用被禁止；
4. 每个模块需要建立哪些表、状态、规则、页面和接口；
5. 事实、追溯记录、快照和报表投影分别如何保存；
6. 开发完成后按什么标准验收。

本目录不提供工期、阶段、人员安排或 G0/G1 等实施计划。

## 2. 文档权威规则

- 一期开发、评审和验收以本目录为准。
- 旧目录仍保留作为讨论历史，不再作为一期实现依据。
- 同一事项发生冲突时，优先级为：模块文档中的已确认业务规则 > 公共规则 > 总体架构 > 旧文档。
- 任何新增决定必须同时更新受影响模块、跨模块接口和验收标准，不能只修改一处。
- 文档中的“待确认问题”不得由开发人员自行猜测；确认后应改为正式规则并删除待确认项。

## 4. 模块关系总览

```text
platform ───────────────────────────────────────────────┐
calculation ────────────────────────────────────────────┤
base-data ──┬── product ──┬── orders ────────────────┐ │
             │              └── scheduling             │ │
             └── team ───────── scheduling             │ │
workforce-coordination ── team + scheduling             │ │
cost-ledger <──── production / payroll / after-sales   │ │
finance <──────── orders / payroll / after-sales       │ │
production <──── orders / scheduling / fulfillment     │ │
fulfillment-coordination ── production + scheduling    │ │
after-sales <──── completed orders                     │ │
payroll <──────── production / scheduling / product / team / base-data │ │
reporting <─────── 各模块公开只读数据源 ────────────────┘ │
所有模块 ───────── platform；含公式模块 ── calculation ───┘
```

箭头表示“调用公开能力”，不表示可以访问对方数据库表。

## 5. 一期统一结论索引

- 后端采用模块化单体、单进程、单 MySQL。
- 模块之间只能调用公开接口，禁止访问其他模块的 Repository、行模型和表。
- 排班只拥有计划和任务，不自行计算商品标准工时、个人有效工作时间或小组效率。
- 每日有效工作分钟是基础资料模块管理的全局标准；排班正式引用时取得并保存其快照引用。
- 商品是独立模块；不建设通用材料目录。
- 内置标准方案和自定义方案使用同一套完整结构；内置方案由商品自动维护，不是交互默认项。
- 小组没有组长和可承接范围，小组任务是共同产出。
- 小组标准按人数配置统一效率因子，且与个人标准分开。
- 服务端不提供业务草稿；所有正式命令一次提交完整数据。
- 生产事实、财务流水、成本台账、审计记录属于追溯记录，不叫快照。
- 快照由业务定义所有者管理；消费者只保存类型化快照引用。
- 需要冻结当前定义时，由所有者的“取得当前快照”接口按 `content_version` 创建或复用快照。
- 计算公式属于计算中心代码能力，不把公式本身保存为业务快照。

## 6. 文档维护要求

1. 表字段发生变化，必须同步修改业务规则、接口输入输出和验收用例。
2. 增加跨模块调用，必须同步修改 `03` 和 `05`。
3. 增加状态，必须说明进入条件、退出条件、撤销/更正方式和并发保护。
4. 增加历史要求，必须先判断是事实、追溯记录、快照还是投影。
5. 所有模块文档必须明确“拥有”和“不拥有”，避免职责继续漂移。
