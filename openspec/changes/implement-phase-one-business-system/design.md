## Context

仓库当前没有正式后端、前端工程或测试构建链，只有六个 HTML 原型、共享浏览器 store、图片资源和 16 份一期文档。原型是交互参考，不是领域实现；生产四分类等旧演示已经被基线中的“三类线上结果＋实物去向”替代。业务口径以固定提交中的文档及本提案规范为准，不能复制原型中的旧规则。

基线已确认后端模块化单体和业务边界。基线 03 第 7.1 节将 Vue 技术栈保留为推荐而非历史批准结论；本提案明确提出下面的工程选择，用户批准本提案后再在实施首步回写该技术状态，不把该选择追溯成此前已确认事实。

## Goals / Non-Goals

**Goals**
- 一份全量一期提案，按独立能力规范和依赖明确的任务分阶段实施，每阶段都有可验证交付。
- 保持九模块、公开接口、历史依据、幂等、本地强事务与下游异步归集边界。
- 业务页面对接真实接口；任何金额、资格和数量裁决由事实所有者或计算中心执行。
- 验证用户已确认的非自动扣款、可选凭证、报废与去向分离以及售后数量闭环。

**Non-Goals**
- 本次不实施、不部署、不导入示例数据、不删除原型、不推送 Git；计划文件存在不表示功能完成。
- 不拆微服务、不引入跨服务事务、消息中间件或材料库存系统，不扩展为通用 ERP/CRM。
- 不设置自动责任债务、跨期扣款余额、统一自动扣款公式或超额制作自动激励。

## Decisions

### D1. 工程结构与技术选择

计划使用以下目录，不把根目录原型改成正式应用入口：

```text
backend/
  pom.xml
  mvnw
  src/main/java/com/yumi/YumiApplication.java
  src/main/java/com/yumi/{platform,calculation,customer,product,workforce,production,orders,finance,reporting}/
  src/main/resources/db/migration/
  src/test/java/com/yumi/
frontend/
  package.json
  src/{app,router,platform,shared}/
  src/modules/{customer,product,workforce,production,orders,finance,reporting,platform-admin}/
  e2e/
```

- 后端采用已确认技术栈，建议 Maven Wrapper 管理构建；依赖精确补丁版本在工程基线任务中解析、兼容验证并固定，不在本计划编造已验证的版本。
- 前端选择 Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus；pnpm 管理依赖。原因是匹配现有 Element Plus 原型与文档模块结构，避免重新设计交互。替代方案为原生 HTML store 或全栈框架；前者缺乏正式边界和测试能力，后者引入当前没有需求的服务端渲染。
- 后端单一构建模块、按业务包使用 Spring Modulith/ArchUnit 校验依赖；不为九个业务模块建立九个服务。测试使用 JUnit、真实 MySQL 的 Testcontainers；页面使用 Vitest 和 Playwright。容器环境缺失应明确失败，不以内存数据库伪装通过。
- 每模块内部使用 `api / application / domain / infrastructure`；前端采用 `pages / components / composables / services / contracts`。页面只绑定状态和交互，service 只处理所属命令与类型化结果，不在 UI 再算工资或生产守恒。
- 面向用户的命令和查询经过各 owner 的 HTTP 适配层，统一认证、请求校验、十进制字符串和稳定错误码；正式命令额外要求持久幂等。内部 Participant、Feed、快照服务和编排专用 API 不开放 HTTP。适配器只调用本模块公开命令或 Query，不能通过 platform 汇集业务内部依赖。具体文件和边界以 [交付清单](delivery-contracts.md) 为准。
- 首次管理员通过显式启用的一次性运维 CLI 初始化，不是匿名网页注册。空系统守卫在事务内检查并创建账号/角色，并发仅一个成功；非空系统拒绝重置，不提供默认密码、不输出秘密。日常账号角色维护仍经过授权 HTTP；初始化仅是部署前置，不增加员工绑定账号。

### D2. 权威写入与事务

遵循基线 03、05 的依赖图。orders 拥有交易、应收、售后义务，production 拥有生产及实物事实，workforce 拥有主体活动守卫，finance 内分别拥有工资、成本、现金。只有公开 API 暴露必要 DTO；Repository、内部实体和跨模块表名不得出现在调用方。

正式命令先鉴权及幂等，再按固定锁序准备和提交；已有数据不存在时也要创建/取得稳定守卫，不能只锁查询到的投影行。参与接口采用调用方本地事务，不能用新事务提前提交；锁后重新核对受影响任务和依据版本，变化时整体重试。订单缩减仅允许 production 释放既有 workforce 预留，不允许在售后事务新增任务。

对外由命令所有者返回稳定错误码、行版本冲突或已完成的幂等结果。死锁只重试整个幂等命令，不局部重跑 SQL。具体锁序不复制成另一套标准，以基线 05 的动作表和本提案事务测试为准。

### D3. 事实、快照、迁移及精度

主数据编辑维护内容版本，正式引用时取得内容版本快照；业务事实保存来源、发生时间和更正链，不称为快照。快照由原模块拥有，消费者保存引用；明确要求冻结的 `ResolvedProductionBasis` 及责任来源上下文按基线保存依据与指纹，不回读当前商品解释历史。

Flyway 迁移按基线每张表和唯一约束实施，数据类型遵循基线 04。金额 HTTP 传十进制字符串；成本 4 位、结算 2 位，重量 4 位；秒与分钟显式转换。禁止二进制浮点、负数量截断和把工资参考当实际成本。生产、订单及现金各有自己的守恒条件；更正不能删除已发生事实。

### D4. 来源 Feed 和重建

劳动、责任、生产材料、售后成本及各报表 Feed 独立游标与失败队列。原业务和来源项同事务写入，消费端整批成功后推进水位；责任的更正按 REVERSE/APPLY，报废撤销成非报废时仅 REVERSE。消费者不得越过失败项，也不得用下游失败回滚上游已提交事实。

读取到更正的一部分时不得发布自称完整的参考；实现时为同一源命令的更正项提供批次边界，消费者按完整命令批次更新有效投影和来源版本。分页限额不能截断原子更正集合；回放/重试保持同一来源键。该完整批次约束是对基线更正原子语义的技术落实，不新增业务事实。

报表影子版本全量重建、核对后切换；刷新任务使用租约和可恢复失败状态。报表只做聚合，不参与业务资格判断。

### D5. 生产及售后数量链

以下制品数量规则适用于生产/返工任务；OTHER_TASK 不关联生产需求或生产/返工来源，安排时只维护人员活动、日槽位及负载。可选商品引用仅用于冻结其他任务单件人工依据；核验不改变制品数量或阶段，不产生生产材料成本来源。关联商品时按完成数量发布劳动来源，未关联商品时不自动产生计件工资来源。

任务明细只提交一次最终核验，允许未完成。已完成＝合格＋无责任返工＋线上报废；线上报废＝实际销毁＋报废转线下。三者与物理账“系统内＋已消费＋已销毁＋已移交”分别维护。唯一 `terminal_exit_business_id` 驱动一次物理退出；移交只是同一退出的去向，不第二次扣减。

正常新制报废可形成原需求补产缺口，售后原物修复报废只能由 orders 变更义务路线。退回池按最近交付/消费记录重入，不新增制作量；池内直接报废使用独立来源类型和人工归责证据，不伪造任务。义务取消按池可用、可逆路由、已路由终态、仍在加工和已交付分支核对，禁止要求已经移交的实物再处置一次。

退回池初次处置的命令所有者是 orders，不是 production。售后 HTTP 经 `AfterSalesApplicationService.disposeReturnedProduct` 编排：锁定案例/有效义务/接收明细，调用 `ProductionAfterSalesReturnParticipant.prepareDisposition`，保存订单侧处置记录，再由 `commitDisposition` 写生产侧处置、责任和唯一退出及相应消费/移交；全部加入同一事务，任一步失败整体回滚。production 的内部事实写入服务不直接发布为售后池处置路由；网页不能串行调用两个模块补记事实。已有责任的独立更正仍归 production，不借此重做初次处置或恢复移交数量。

任务负载分为已核验标准秒数与未核验预留；生产、修复等适用效率的小组任务先汇总再除一次历史效率并取整，其他任务的小组标准分钟已代表整体经过时间，不再除效率。任务取消不能释放已经完成的负载。日期槽位、商品新制产能和人员活动预留使用各自守卫。

### D6. 工资参考、负责人填写和现金

`PENDING_REFERENCE` 刷新待核定结果；`CONFIRMED_REVIEW` 生成独立只读复核，不替换原核定引用。逐项成本显示来源、历史标准、承担方、已发生/未发生状态及预计分摊属性。非胶水参考按 4 位金额到人，胶水先按重量到人再逐行计价；不生成自动扣款总额。

人工处理金额默认空，可填 0，与最终工资独立保存。确认事务以明确填写的实际工资形成应付和人工成本；处理明细不自动相减、不形成额外成本或债权。核定和调整分别保存所引用参考及人工决定，过期指纹拒绝静默替换。

胶水免扣属于 finance.payroll 的版本化设置；自然月不等于工资期间。按全月有效责任、历史成员及稳定来源顺序纯重算，使用配置和员工月守卫防止并发混合依据，不维护“实际扣款额度账户”。

cash 处理真实收付；订单 UI 调用 finance 命令，finance 向 orders 校验资格并关联支付。日常支出只有显式计费用才同事务产生经营成本。工资真实部分退回关联原员工支付分配；错误现金冲销和实际退回使用不同命令。可选凭证与本条现金事实同事务正式化和引用。

工资页面还必须提供已核定员工的逐人或多人付款分配，以及有原因的人工差额调整。付款和退回统一调用 cash 的正式命令及 HTTP 入口；payroll 内部参与能力只校验员工应付并维护支付关联，加入 cash 的同一事务，不暴露可单独改已付金额的页面接口。人工调整调用 payroll 命令，只改变应付与人工成本；真实退回新增一次现金流入但不自动改变成本。

任务顺序先完成工资核定/调整和内部支付参与能力，再实现 cash 的实际付款、分配与原子回滚，最后接工资页面。内部参与测试使用调用方事务验证资格、关联及回滚，不在 cash 尚未实现时伪称完成实际付款验收。

### D7. 页面和兼容性

六个原型作为视觉/交互参考保留。正式页面通过模块 service 调用后端，不把 localStorage 当权威事实。管理端统一空态、加载、权限不足、来源不完整、版本冲突和重试提示；工资与现金敏感数据必须后端鉴权，不能仅隐藏按钮。

商品保留标准售价且无商品目标工序输入；人员无绑定账号；生产新建、核验及追溯采用新数量模型；订单提供收退款和售后入口；财务包括逐人核算、日常收支及按月汇总。筛选条件采用紧凑布局，不强制一行一个条件。菜单隐藏与路由守卫不能代替后端权限。

### D8. 测试、验收与执行顺序

按 `tasks.md` 先红后绿；模块完成不意味着一期完成。建议验证命令由工程任务建立后执行：

- 后端单元测试：`cd backend && ./mvnw -Dtest=<具体测试类> test`。
- 真实 MySQL：`cd backend && ./mvnw -Dit.test=<具体集成测试类> verify`，Failsafe 使用独立测试库/容器，禁止连生产库。
- 全量后端：`cd backend && ./mvnw verify`，包括模块边界、迁移和并发。
- 前端：`pnpm --dir frontend test:unit`、`pnpm --dir frontend typecheck`、`pnpm --dir frontend build`。
- 页面闭环：`pnpm --dir frontend exec playwright test`，测试服务由配置启动并在结束时清理，不复用未知生产服务。
- 计划校验：`openspec validate implement-phase-one-business-system --strict`。该命令只验证计划，不代替上述业务测试。

阶段门禁只覆盖该阶段已经交付的能力：1.10 只验证纯值和 HTTP 映射契约，不依赖尚未实现的认证或持久幂等；2.12 才验证真实平台 HTTP；各业务完成节点同时交付命令、Query、适配器和来源 Feed；13.8 用真实业务接口完成全清单复核后才接页面。测试替身只用于明确标记的孤立契约，不能作为真实集成通过证据。

执行顺序同时满足 tasks 的显式依赖和 delivery-contracts 的来源提供者门禁；前序红测试须包含该完成节点承担的清单行为。新增任务后必须重新校验全图，不只检查新增的两行。实现提交仍需用户授权，没有实际执行证据不得勾选任务、归档或宣称已上线。

### D9. 完整交付与管理恢复

[交付清单](delivery-contracts.md) 是用户操作到后端 owner、页面和测试的统一映射。除了六个原型主体，还包括录入配置、人员标准、生产更正和缺陷原因、已有订单接管、售后费用/结案、工资期间/月参考、成本分摊/更正、审计、后台任务恢复和报表管理。管理页面只组合合法 Query 与授权命令，不能直改业务表。

三种失败队列分别由 platform 的提交后任务、finance.costledger 的归集恢复、reporting 的投影管理负责；不能用一个延迟提示代替恢复，也不能用重建报表修补业务事实。文件组件在各业务页复用，预览和下载仍受业务资源权限约束，现金凭证保持可选且归本条。

计划校验脚本检查编号、显式依赖/来源门禁、要求覆盖、页面测试映射、链接及元数据；这些检查只防结构性遗漏。业务语义须对照固定基线人工复核，运行时权限、事务和界面结果仍以实施后的真实测试为准。

## Risks / Trade-offs

- [一期覆盖较大] → 保留一个全量总提案、按 14 项能力和任务依赖分段交付，不允许绕过前置测试同时实现未知接口。
- [原型规则滞后] → 基线提交与场景测试优先，根目录原型不做数据迁移，正式页面逐流程核对。
- [前端选型此前未冻结] → 明确为本提案技术决策，批准实施时回写架构 7.1；不伪称历史已批准，也不先搭工程。
- [跨模块锁死及更正半批次] → 固定锁序、命令批次完整性、真实 MySQL 并发/失败注入覆盖。
- [预计分摊被误作实际扣款或利润] → 分列标准/预计/实际，实际工资只取人工核定，报表标识缺失成本和数据延迟。
- [版本、部署参数尚未安装验证] → 首阶段固定兼容依赖和锁文件，后续在测试环境验证；部署密码、文件上限和会话时长从环境配置，不写入仓库。

## Migration Plan

1. 获得实施授权，确认本提案及源提交仍一致；变化则先修改工件和版本，再执行。
2. 新建独立工程及空测试数据库，逐模块应用可校验 Flyway 迁移；不推测现有正式数据，也不导入浏览器示例数据。
3. 如需接管已有订单，仅通过已明确的正式接管命令录入，并确保不重复生成历史工资、材料成本或责任参考；不能直接改表。
4. 在备份副本演练数据库迁移、恢复和对账；迁移不可随意 down，已经发生业务事实后通过兼容前滚或备份恢复方案处理，不删除记录“回滚”。
5. 完成基线 15 的权限、事务、并发、页面、成本/现金及报表重建验收后，再由用户决定试运行和部署。
6. 获授权并有实施证据后归档 OpenSpec，回写 `docs/一期/00-文档总览.md`；在此之前状态一直是计划或实施中。
